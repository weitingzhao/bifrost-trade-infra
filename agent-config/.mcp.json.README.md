# .mcp.json — MCP server 注册说明

平台类 server 指向 PROD platform-api：`http://192.168.10.100:30876`（kube-vip VIP + NodePort）。
单节点故障时 VIP 会漂，不把客户端钉在 `.70` 或 `.73` 上。
`bifrost-local` 是唯一指向 `127.0.0.1:8780` 的 server（笔记本上的 bdev 与 git-bridge）。

Claude 侧（本文件对应的 `.mcp.json`）比 Cursor 多一个 `bifrost-approve`。
Cursor 模板只有 `cursor/mcp.servers.json` 一份，没有 `bifrost-approve`。platform 的 `config/cursor-mcp-bridges.json` 已在 2026-10-10 删除（Owner 卡 8，platform `3dad199`）。

路径（W-36，2026-10-10）：两边都不写死工作区。

- Claude：`${BIFROST_WORKSPACE:-.}/bifrost-platform/...`。会话在工作区根启动，`.` 就是根；`CLAUDE_PROJECT_DIR` 在 `.mcp.json` 里不展开，所以不用它。
- Cursor：模板写 `${workspaceFolder}/...`。用户级 `~/.cursor/mcp.json` 没有自己的工作区，由 `python3 bifrost-trade-infra/agent-config/cursor/install-mcp.py` 渲染成绝对路径后合并进去（同名 server 覆盖、其余保留、先备份、权限 600），装完在 Cursor 里重载 MCP。工作区根取 `BIFROST_WORKSPACE`，否则取 `bifrost-trade-infra` 的上一级。
- Cursor 模板不带令牌插值：每个 server 用 `PLATFORM_TOKEN_ENV_KEY` 钉住自己的角色（operator 或 viewer），进程环境里没有这个键就读下面的 0600 令牌文件里的同名键。

| server | focus | 工具 | 令牌角色 | 用途 |
|--------|-------|------|---------|------|
| `bifrost-platform` | — | **75** | operator | PROD 读 + 写。`MCP_WRITES=on` |
| `bifrost-kubernetes` | `kubernetes` | **18** | operator | 集群读 + 写。`MCP_WRITES=on` |
| `bifrost-redis` | `redis` | **6** | **viewer** | 只读 |
| `bifrost-postgres` | `postgres` | **8** | **viewer** | 只读 |
| `bifrost-prometheus` | `prometheus` | **4** | **viewer** | 只读 PromQL |
| `bifrost-trade-api` | — | **12** | —（Trade 网关） | 只读。目录 URL 也改到 VIP:30876 |
| `bifrost-local` | `local` | **5** | operator | 只连笔记本：dev-sessions 与 git-bridge 状态 |
| `bifrost-approve` | `approve` | **3** | **admin** | 只在 Claude。`approve_request` / `reject_request` / `list_pending`，`channel` 固定 `"chat"` |

75 = 全量 `reg()`（原先 stdio 名单里的 dev-session 三件挪到 `bifrost-local`，加上 `request_action`、`get_request`、`list_requests`、`wait_for_request`）。
`bifrost-local` 的五件：`platform_mcp_health`、`list_dev_sessions`、`get_dev_session_logs`、`restart_dev_session`、`get_local_git_bridge`。
git-bridge 没有单独的 platform 写代理；重启与日志走名为 `git-bridge` 的 dev-session，状态走本机 `/api/v1/agent/bridge` 的 `git_bridge`。

## 写开关（合并时就是 on）

读已经指向 PROD：viewer server（redis / postgres / prometheus）和所有 GET。

`bifrost-platform` 与 `bifrost-kubernetes` 的 `"MCP_WRITES"` 在这份配置里就是 `"on"`。这个分支要等 B1R 在 PROD 上线之后才合并。如果先以 `off` 合并，写工具会在中间断掉（起流水线等都不发请求）。未设置时代码仍当作 off，返回：

```json
{"error":"writes not cut over","action":"…","tier":"B|C|D","hint":"…"}
```

合并后的状态（`check_mcp_cutover.py` 锁这个）：

- `.mcp.json` 里 `bifrost-platform.env.MCP_WRITES` = `on`
- `.mcp.json` 里 `bifrost-kubernetes.env.MCP_WRITES` = `on`
- Cursor 模板 `cursor/mcp.servers.json` 里同名的两处 = `on`

`on` 之后：

- B 级（重启无状态工作负载、删 Pod、cordon / uncordon、wake、按需备份、修 WAL、克隆到非生产、补采、清掉终态 PipelineRun、清单信号、跑发布门禁等）直接调用原路由。
- C / D 级（Argo sync / rollback、起 PipelineRun、扩缩容、装/升级 addon、join、Tier B 签收、drain、poweroff、kubeconfig Secret）改为 `POST /api/v1/approvals`，把返回体里的 `id` 交回去，不再打原来的写路由。动作 id 就是工具名。`reason` 为 `mcp:<action>`，`rollback` 为该动作写死的一句。要自己写理由和回滚，用 `request_action`。
- 目录里没有的写路由也走申请（`action` 为 `unlisted_write`），不会直接执行。

`bifrost-approve` 不看 `MCP_WRITES`。它用 admin 令牌直接 `POST /api/v1/approvals/{id}/approve`，body 只有 `{"channel":"chat"}`。批准或驳回只走这个 MCP 工具（`permissions.ask` 弹窗）。不要自己 curl 这个路径，也不要用浏览器打开 `#approvals` 去点——`preflight.js` 会拦。见 ADR §5「已知的接受风险」。

请求头 `X-Bifrost-Session`：`CLAUDE_CODE_HOST_SESSION_ID`，否则 `CURSOR_CONVERSATION_ID`（或 `CURSOR_SESSION_ID`），否则主机名。

## 令牌来源

配置不再要求进程环境里有令牌。三个键在 `.mcp.json` 里仍只写 `${PLATFORM_*_TOKEN:-}`，仓库里没有值。

MCP 进程从 `~/.config/bifrost/mcp-tokens.env` 读（B1R 在 `mcp/platform` 实现，本仓库只记录约定）：

- 进程环境里已经有的键优先。
- 环境里没有时，读这个文件。权限必须是 `0600`（`chmod 600`）；不是 600 就拒绝读。
- 每个 server 只读它被钉的那一个键（TD-225）。日志和错误里不打印令牌。

文件里的三个键：

| 键 | 谁用 |
|----|------|
| `PLATFORM_VIEWER_TOKEN` | redis / postgres / prometheus |
| `PLATFORM_OPERATOR_TOKEN` | `bifrost-platform`、`bifrost-kubernetes`、`bifrost-local` |
| `PLATFORM_ADMIN_TOKEN` | 只给 `bifrost-approve`。进程环境里的 operator 令牌不能顶上 admin |

非回环地址不读 `bifrost-platform/.env`。`bifrost-local` 仍是回环，可以回落到那份 `.env` 里的 operator 令牌。

从 `bifrost-trade-infra/.env` 里的 **PROD** 令牌生成（`PLATFORM_PROD_*_TOKEN` 改名写进文件，终端不打印值）。**不要**用 `bifrost-platform/.env`：那里的三个令牌是本机 platform-api 用的，和 PROD 不同（2026-10-07 实测指纹不一致），连 PROD 会 401。不要 `cat` 结果：

```bash
mkdir -p ~/.config/bifrost
umask 077
awk '
  /^PLATFORM_PROD_(VIEWER|OPERATOR|ADMIN)_TOKEN=/ { sub(/^PLATFORM_PROD_/, "PLATFORM_"); print }
' bifrost-trade-infra/.env > ~/.config/bifrost/mcp-tokens.env
chmod 600 ~/.config/bifrost/mcp-tokens.env
stat -f '%Lp' ~/.config/bifrost/mcp-tokens.env
awk -F= 'NF && $1 !~ /^#/ { print $1 }' ~/.config/bifrost/mcp-tokens.env
```

`stat` 应打印 `600`。最后一条只打印三个键名。本道不创建这个文件。

Mac mini 上的线程以后同样需要这份文件：同样三个键，权限 600。笔记本上的这一份不会跟着会话走。

## 令牌分级

`platformClient.ts` 默认读 `PLATFORM_OPERATOR_TOKEN`。三个只读桥用 `PLATFORM_TOKEN_ENV_KEY=PLATFORM_VIEWER_TOKEN` 钉住 viewer（TD-225）。
`bifrost-approve` 用同样的钉法钉 `PLATFORM_ADMIN_TOKEN`。

## 防线

```bash
python3 bifrost-trade-infra/agent-config/scripts/check_mcp_cutover.py --self-test
python3 bifrost-trade-infra/agent-config/scripts/check_mcp_cutover.py
```

预期：`--self-test` 打印 `self-test ok`，默认检查打印 `mcp cutover check ok`，退出码都是 0。默认检查读 `.mcp.json` 与 `cursor/mcp.servers.json`。除 `bifrost-local` 外没有 server 指向 `127.0.0.1`；`bifrost-approve` 只出现在 Claude 的 `.mcp.json`；`bifrost-platform` 与 `bifrost-kubernetes` 的 `MCP_WRITES` 是 `on`（别的 server 只要写了 `MCP_WRITES` 也必须是 `on`）。

`--cursor <file>` 用同样的规则再查另一份 Cursor 配置（例如渲染后的 `~/.cursor/mcp.json`）。

MCP 行为（在 `bifrost-platform/mcp/platform`）：

```bash
npx tsc -b && npm test
```

`writeGate.test.ts`：C/D 写返回申请号且不打原路由；`approve_request` 只在 approve server，body 的 `channel` 为 `chat`。
