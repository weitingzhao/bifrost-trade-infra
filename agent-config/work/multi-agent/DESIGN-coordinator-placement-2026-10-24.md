## 3. 和 10-12 被否的方案（W-67）比

10-12 的设计（`DESIGN-host-minimal-2026-10-12.md`）把 mini 当 Agent 执行主机：守护进程账户 + 槽位账户、sudoers 委派、`kill -TERM -1` 按 uid 清理、禁槽位的定时任务；量测要在 mini 上建测试账户、跑 1,003 行管理员脚本。复核 122 点出 34 条危险命令和 10 处清不掉的残留，并反对把没测过的权限、可写面、云端会话撤销和资源控制说成已成立，要求改系统的试验先在可丢弃的环境做（`reviews/codex-2026-10-12-review122-w67-measurement-material.md`；`LESSONS-from-practice.md` 第 110 条）。

| | W-67（否） | A1-mix |
|---|---|---|
| 跑什么 | 一池用完即弃的执行任务 | 一个长驻统筹会话；执行者在 06；本机只有 §4.6 三类 |
| 改系统 | 两个账户、sudoers、开机守护进程、禁定时任务、按账户发信号 | 一个标准账户；`vision` 家目录 700 并核对 ACL；一个限额卷；`autorestart 1`；卸 OrbStack。无 sudoers、无跨账户信号 |

**剩下的风险和控制**：

1. **碰带外**：家目录 700、无 sudo、无 `vision@` 钥匙；S0a 列出带外依赖的全部路径并核对有效权限（V3）；preflight 在 `BIFROST_HOST_ROLE=coordinator` 时拒绝 `ssh vision@`、写 `/Users/vision`（文本拦截，防误用不防绕过）。
2. **资源**：见 §4.5；A1-mix 的意义就是不把重活放在没有内存上限的机器上。
3. **同 uid 的执行碰到协调凭证**：例外只放三类我们自己仓库里的活；是否把它们当可信、接受它们读得到令牌，是 D3-8。
4. **令牌外泄面**：比今天小——今天 MacBook 同一用户还有 admin 令牌（ADR §5 已接受的风险），`bifrost-coord` 不配置 admin、不启用 `bifrost-approve`，并须通过 V3 验证取不到 Owner/带外凭证；审批只在 Console 和手机。受信设备防别人用 Owner 的 claude.ai 账号操纵会话，但不替代主机内的凭证隔离。
5. **网络**：统筹在运维区（ADR §10），和今天的 MacBook 相同；按用户的出站规则以后再说。

### 4.4 显式值守、持续推进与通知

**状态先于无人值守建立**：拟新增 `disabled → arming → armed → degraded/paused` 值守记录，绑定主机、会话、当班写身份、任务清单、开始/截止时间、最近一次实际检查的序号和时间。平台保存期望、`.52` 独立 watcher 保存只读副本；实现与公开接口须经 D3-9 选择和后续复核。本稿没有把它说成已有功能。

- 在派出跨回合任务、进入夜班或 Owner 离开前，先登记 `arming`，建立循环，完成两次相隔约 2 分钟的实际任务检查；平台及独立观察者确认序号递增、通知链和副本健康后才报 `armed`。Owner 最后发消息才两分钟也执行这一步，不再等“无消息 20 分钟”。未 armed 不允许宣称夜间有人推进。
- 首选 Stop 保持回合 + `wait_for_messages(timeout_seconds=120)` → 查任务/审批/结果 → 对账并推进。Stop 拒绝结束只是一种调度方式；用户中断、崩溃、额度/API 故障都不能清掉平台上的值守期望。正常结束也保留期望，漏检查由独立检测报警。只有 Owner 明确暂停或已完成交接才能改为 paused/disabled，并记原因、未决项和到期提醒。
- 每次检查生成进度回执（会话、检查序号、所查任务及结果版本、下一次检查时间）；固定定时器只能检查回执，不能替模型生成“任务已查”的回执。期望 armed 而回执超过 5 分钟未更新即 degraded，停止声称持续推进。平台与 `.52` watcher 每分钟检查；故障判定到提交通知提供方目标 ≤3 分钟，故从最后有效回执起目标 ≤9 分钟。长工具交后台轮询，不得把无进度的进程存活当回执。
- 项目已有 Stop `turn_end` 上报与新增钩子可能同时执行。S1 必须协调为同一最终判定：保留真实 `turn_end`，不得伪造仍在回合中；armed 期望独立于 idle。M13 查服务端最终事件、值守状态和下一次检查，注入并行钩子顺序/失败，不能仅凭 Stop 的返回值通过。
- M13 不支持时可试 `/loop 2m`，但仍须预先 armed、两次真实检查及相同独立超时检测，验证 idle 间隙退出应用能报警和恢复。`/loop 20m` 只作有人值守的降级模式，不能进入 S4。D3-9 未定或独立观察者未上线时保留 MacBook 有人在场协调。

**按状态区分告警（时限均须现场验，不保证提供方之外的手机送达）**：

| 情形 | 检测与负责人 | 时限与证据 |
|---|---|---|
| 正常结束/用户中断/idle 中应用退出，但当班仍 armed | 平台期望检测；`.52` 独立 watcher 补看平台及本机回执 | 上述 ≤9 分钟目标；无 `turn_end` 豁免。两者都须留检测、提交提供方、手机收到时间 |

### 8.2 验收用例

- **V1 跨夜因果链**：MacBook 22:00 前合盖至 07:00 后，留 pmset 证据；Owner 21:58 最后说话，统筹 22:00 前完成当前动作/尝试结束，无后续人工输入，值守已 armed。预登记 T1→T2（另一家复核）→T3（经原门禁合入及 STG）；T1 的可用结果刻意安排在 **02:00–04:00** 才产生，记录真实完成与结果可读时间。T2 必须在 T1 之后、07:00 前由 `.52` 建，T3 在 T2 accepted 后；记录 actor、任务/会话/run ID 和 SHA。22:05 已完成整链不算通过。
- **V1 负对照**：分别在回合中、正常结束后 idle 间隙（含 `/loop` 候选）、用户中断后退出应用；再测 API/额度失败和 `.52` 断网 15 分钟。按 §4.4 各状态时限核检测/提供方/手机三时间，随后按 §8.1 恢复。另由 H S2 证据覆盖 `.50` 断电、平台断开、relay 停机和摘要漏发；只报“主机健康”不能通过。
- **V2 手机交互**：蜂窝网说话，值守中 5 分钟内回复、忙工具时 15 分钟内回复；主及子会话权限请求分别允许/拒绝，核手机可达与拒绝后不执行。不为过测放宽审批规则。
- **V3 隔离与共载**：Owner/受信检查器查有效 sudo 策略（主 sudoers、所有 include、用户与组匹配），`id` 不含 admin 不是充分证据。机密范围含 Owner admin 目录、管理员 kubeconfig、登录钥匙串、带外/watcher 凭证及可调用的 credential helper/套接字；只测权限和合成标记，不输出或读取真实秘密。机密对象读/写/目录遍历都拒绝；公共执行依赖允许必要读/执行、必须不可改写。Claude 登录不导入 Owner Apple/iCloud、浏览器或钥匙串配置。确认 operator-plane PID 存在后 kill -0 得 EPERM，其他错误不算过。三次基线（S0a、S0b 完整负载、S4 后）及 watcher 送达达 §4.5；未知仍标待验。
- **V4a 可访问撤回与离机恢复**：S3 建一条记忆、已提交未推分支、已跟踪脏文件、新文件、在途/unknown 动作引用；成功远端确认，再禁止恢复端读取 `.52`，MacBook 只凭远端快照和平台账本 30 分钟内在新目录重建，逐项摘要一致。注入一次同步失败（含停 LaunchAgent/Gitea 不通/凭证失效探针），证明失约降级并恢复新的有效恢复点；完成 R1a。
- **V4b 不可访问故障接管**：S3 让 `.52` 对操作者不可访问但可能仍在跑。先走 R1b 撤旧写权、反验后才允许 MacBook 有副作用；随后旧 `.52` 重新联网，旧平台/Git 写身份仍拒绝，不能自行再 armed。重连后对账一次提交/派工/STG 请求不重复。做不到则新统筹始终只读，S4 不准入。R2 前再次核离机副本，不替代 S3 的提前验收。

### 8.3 回退与唯一写者

- **R1a 主动撤回（`.52` 可访问）**：停新派工、等正在写的操作得到结果或登记 unknown，写交接→远端确认→归档/退出会话→撤 `.52` 所有写授权并验证→MacBook 读回、对账、启用新统筹。取证文件可留，授权不留七天。不能先起新统筹再退出旧的。
- **R1b 故障接管（`.52` 不可访问）**：Owner 从独立管理入口（MacBook/已验远程管理，不能依赖 `.52`）撤销专用 PROD/STG operator、release.env 同源令牌，以及 Gitea 全部写 token/SSH key/main 白名单和 state 仓库写身份；更新并核验所有鉴权副本。旧令牌的鉴权读探针必须 401，旧 Git 身份在私有 canary 的可控写必须拒绝，MacBook 独立身份仍有效；用不泄露令牌的 Owner 受控测试。仅撤 main 白名单、RC 设备或本机文件均不充分。若无法取得撤权生效证据，MacBook 只能只读恢复上下文；D3-12 也可选独立确认旧机断电隔离后再接管，不能把网络失联当停机证据。
- 撤权不能撤回此前已受理的任务/审批/run；Owner/新统筹按旧 actor、时间、request/execution ID 拉全在途，等完成、明确取消或按原动作流程处理 unknown 后再派替代任务。release window 只管一次发布，不证明唯一统筹。此人工撤权流程不复用 H 的 executor 身份或自动跨机接管。
- 旧 `.52` 恢复后先保持停用，验证旧权被拒，导出缺失的证据并与平台/远端快照对账；不自动续期、换 token、重新 armed。再次启用是新的明确交接。
- **R2 最终销毁（Owner）**：R1 后至少 7 天，核对恢复证据；Owner 独立保管加密取证归档 30 天，再按 S2 创建清单（账户/UID/GeneratedUID/卷 UUID/Gitea ID/令牌主体）逐项删除。对不上不删；再次核撤权，无需为了排查留下有效写凭证。vision 权限收紧与 autorestart 保留。

## 9. 推荐与理由

**A1-mix 作为待 Owner 选择的推荐；S4 门槛通过后才切换；B 作为终点，按 §5 的退出条件并入；M2 / M3 不过时 A2 另出设计；C 可以当天开（只为手机能说话）。**

1. 只有 A 能在第 4 轮第一波里满足 4.4 的两条验收；统筹不搬，第 4 轮其余各项（包括 4.1）夜里照样停。
2. A1-mix 比 A1 少放：重测试本来就能交给分支 CI 和 06（本会话的提交全在运行时已接的两仓），macOS 上又没有按用户的内存上限，把重活留在 06 比在 `.52` 上设计资源控制更可靠；例外三类各有撤掉条件和到期日。
3. 工作方式和今天一样（桌面应用、子会话、夜班、子代理），换的是机器；agentd 留在 06，mini 上的本机测试和复核只按 §4.6 列明的临时例外执行；按 H 的独立通知与清退前置协同，修掉 `vision` 账户中的 Agent 及共享组可读问题；不向 coordinator 账户配置 admin，并验证其取不到 Owner/带外凭证。`.52` 仍有管理员账户和带外服务，不能说整机没有管理凭证。
4. 状态放我们的（ADR §12.2 第 7 条）：RC 只是窗口；状态在仓库、运行时和 `bifrost-coord-state`。B 接手时仍要把会话里的待办和决定迁成记录（§5）。
