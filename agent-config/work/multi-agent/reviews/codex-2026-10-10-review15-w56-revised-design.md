**2. A 动作的最小契约。**

- 调用者是有独立身份的授权 operator／发布服务；流水线最多提交发布记录 ID、幂等请求 ID和预期当前发布 ID。拒绝任意 Git URL、分支、路径、补丁、命令、摘要或闸门代码参数。
- 写入位置固定为 [PROD kustomization 的两项 images](<workspace>/bifrost-trade-infra/k8s/overlays/platform-prod/kustomization.yaml:75)：按固定镜像名匹配，使用 `digest`；首次移除 `newTag` 属一次人工批准的迁移。之后只替换两项摘要，仓库名、资源、patch、策略和其他键完全不能改变。
- 服务端重新读取并校验受保护发布记录及闸门证据；检查摘要格式、仓库归属、可拉取性、架构与构建身份。API 和 workers 必须映射同一 API 摘要。保留当前及上一份成功发布的完整组合，并防止 registry GC 删除恢复产物。
- 新动作必须作为**实际修改 PROD 的动作**进入签名策略；仅授权启动 Pipeline 不够。[现有策略](<workspace>/bifrost-trade-infra/agent-config/release-policy/template.json:7)尚未授权它，也未包含新晋升流水线。规则绑定动作、环境、来源、最低观察时间和验证要求；检查当前实际 PROD → 候选的完整差异，含 ui 与构建依赖，不能只比较相邻 STG 记录。
- 签名无效、过期、证据缺失、路径触及信任根／D10／不允许的 DDL，自动入口一律拒绝并记录原因。人工例外另建有界授权，不提供请求参数式 bypass。
- 发布窗口要由服务端验证持有者、范围及代次并续租；明确调用者窗口向持久发布操作的移交，避免“调用者持锁、动作等待同一把锁”死锁。冻结在最终写入边界复查；读取失败按冻结处理。
- 普通发布受冻结约束；恢复仅允许预先签定的“回到该次发布前已验证组合”，不能借恢复发任意旧版。冻结后的待同步提交如何阻止 Argo 生效必须明确，单纯停 API 请求阻止不了已推送的提交。
- 审计在写入前持久化意图，记录请求身份、规则 ID、证据 ID、前后摘要、Git 基准／提交、租约代次及每步结果；进程死亡后仍可查询和接续。重试不得生成第二次晋升。
- **只写 GitHub 权威源；Gitea 继续单向镜像。** 向 Gitea 推送不能交付 Argo，且可能被镜像覆盖。使用受保护分支检查、非强制推送和基准 SHA 校验；冲突后重新评估，不强推。
- GitHub 仓库写权限本身不能限制到两个 YAML 键。若平台持有完整仓库写凭据，“窄动作”只约束正常调用；要抵抗平台失陷，凭据必须留在独立受限写入器，由其验证授权和最终 diff，平台只拿调用能力。写入器无需承担完整发布编排。

**4. 建议上线顺序，每步独立验收，期间继续逐次人工批准。**

1. **先堵旁路与冻结缺口。** 演练新旧入口、直接起 run、直接改清单；冻结或无授权均拒绝，平台／STG 身份不能自行解除冻结。
2. **建立可信发布记录。** 演练伪造记录、错 SHA、缺一个摘要、记录覆盖和 GC；全部拒绝，真实构建能留存可恢复组合。
3. **闸门先影子运行，再强制执行。** 演练最新 CI 红／运行中、STG 错版、workers 未收敛、观察期重启及换版；明确拒绝原因，人工批准也不省略产物校验。
4. **部署窄动作与写入器，先人工授权。** 演练越权路径／键、任意摘要、并发请求、重复请求、Git 冲突和 push 后断线；只产生一次允许的成套提交，并能恢复状态。
5. **人工批准的摘要晋升及受限恢复。** 演练第二个工作负载失败、API 中途死亡、Argo 延迟、旧执行者恢复运行；最终收敛到候选或前一成功组合，无重建、无覆盖后来发布。
6. **部署带外监督器，执行 G6。** 发起后关闭 API 和 workers，新版本持续起不来；监督器无需平台领单即可恢复并独立通知。
7. **最后签自动规则。** 重跑完整通过与拒绝矩阵，含过期、冻结、信任根修改、证据重放；符合条件自动交付，不符合由程序拒绝，随后移除旧自动旁路。
