# Response to review 526, the coordinator · 2026-10-23

All four taken, plus one more A of the same kind the report names in passing.

- **A1 — agentd's synchronous prune (up to 2 min work + 30 s report budget, every 10 min) leaves a host silent for longer than 30 s.** Fix on the platform side only (no agentd change: replacing agentd on 06 needs the Owner): a host that asked for its prune list (`GET /agentrt/prunes`) is not lost until it reports the prune or agentd's own prune budget runs out (take the budget from the code, `api/internal/agentd/prune.go`, plus a small margin, as one named constant with a comment pointing there); any authenticated agentd call from that host (prune list, prune report, attempt heartbeat or renew) refreshes its liveness. No schema change: record what is needed as notes on the `host:<id>` stream (the way disk and offered are) or derive it from existing rows. `TaskStatus`'s `host_lost` uses the same rule, so a running attempt on a pruning host is not shown lost. Regression test: a host that asked for its prune list and stays silent 2 min is neither offline nor its executors unavailable nor its attempts host_lost; past the budget without a report it is offline.
- **A1b (the report's section 2: a Recreate rollout of the platform) — every platform release stops api and workers for tens of seconds; when they come back every host's last poll is older than 30 s.** The controller must not announce offline for a gap the platform itself caused: measure a host's silence from the later of its last poll and the moment this controller (workers) started, so the first announcement can come only 30 s after the platform is back and the host still has not polled. Test with the fake clock: hosts silent through a simulated 60 s platform restart are not announced if they poll within 30 s of the restart.
- **A2 — "Every job has an executor that can take it again" while another job's candidates are still unknown (null).** Say all jobs are covered only when every job has at least one confirmed available candidate; otherwise name only the executors confirmed back and say which jobs are still unknown. Test: one executor recovers while another job's candidate is null.
- **B1 — recovery is announced for drained / stopped / retired hosts.** One host scope for both directions; a host put into drain/stop/retired after its offline was told closes its open offline record quietly (a note, no message to the chief) and nothing is told when it polls again during maintenance; when maintenance ends and it is online, nothing stale is sent. Tests for drain, stop and retired after an announced offline.
- **B2 — the latest-state queries scan history with no fixed bound.** Without a migration (an index is DDL on PROD): read the latest state per host / executor in a bounded way (for example keep the newest presence state in one note per stream that the loop reads by a bounded query, or restrict the scan to the presence event types with an existing index); show with EXPLAIN on a test database seeded with many unrelated events and with "never matched" streams that the pass stays bounded. If a bounded read is impossible without an index, say so and record it as a TECH_DEBT item instead of adding a migration.

The infra `SPEC-agentrt-progress` lines (3 min → 30 s) and the `whyNoHostTakes` wording are updated with the merge, not in this round.
