# Response to review 522 (round 1), the coordinator · 2026-10-23

## Taken as A, fixed before STG

- **A1 — the card TakeIssue opens for an out-of-envelope mission carries no BI identity.** Slice 1 opens no card at all: TakeIssue passes no ask to proposeMissionTx (the mission waits for the Owner with no card, and still counts against the product's quota, which the existing test keeps). Cards for BI missions come in slice 2 with the BI identity (Card.WorkID, workIDPattern, agentRuntimeAsk), the neutral template of §5.3 and no AI assessment. A test: an out-of-envelope take leaves no card in the question store and the mission awaits the Owner. The store must refuse any other path that would ask a card for a `BI-` mission (proposeMissionTx with an ask and a BI work id).
- **A2 — an agent's own proposal could use fault_small.** The exception needs a served person; a proposal (served_person NULL) always needs the Owner's priority on the current B. Tests both ways.
- **A3 — the decision points are outside D's hash.** D becomes the hash of the canonical design (text and decision table together), so the same text with a different table is a different D: reviews and Owner evidence bound to the old D no longer count. Tests: same text with points removed, with Proceed changed, and a decision table that disagrees with the text's header if the text carries one.
- **A7 — the two-round stop is not enforced.** A review's round is the previous round plus one (the first is 1); a third round counts only after the Owner's review_dispute evidence on the current D chose another round; take accepts a pass only from round 1 or 2, or from an Owner-authorized round 3. The database holds the round sequence too. Tests: a third pass without the Owner refused; a repeated or skipped round refused; an authorized third round accepted.
- **A8 — superseding an ask could rewrite who answered.** A supersede changes superseded_at and nothing else (the whole row otherwise equal). Tests on an answered and an unanswered ask.
- **B1 — a guard test matrix.** For each guard branch added in 0009 (guard_issue, guard_issue_text, guard_issue_ask, guard_issue_work, guard_issue_check, guard_person, guard_intake_client, the legacy_imported exclusion per table), one minimal counterexample under the runtime role with the right event type, violating only the target condition, expecting refusal. Table-driven, no new framework.

## Reclassified to B (not blocking STG): A4, A5, A6

The design decides where the take and close predicates live: §4.3 「接单谓词（`take_issue` 在一个事务里算）」; the state table at line 331: `active` is written only by `take_issue` 「守卫按事件类型挡」. The database layer is there against the old binaries (§4.6, the deferred BI- check, the terminal trigger, the token key old binaries do not read) and against `legacy_imported`; it is not specified to re-derive every predicate against the new binary itself writing correctly typed events by direct DML with the runtime role. Only platform-api and platform-workers hold the runtime role; agents hold agent_reader (read only). The coordinator's brief asked for more than the design promises; that was the brief's mistake, not the code's. So:
- A4 (a crafted issue_taken with a link row bypasses evidence and quota), A5 (a crafted close event closes without her answer), A6 (agent scope on UPDATE, product scope on text, daily limits only in Go) are recorded as defense in depth to consider, not as defects of slice 1.
- The cheap part that matches the design's own words is taken: §5.2 「Agent 只能在它看得到的问题上写字」 is a database rule in choice 19, so the text guard also checks the issue's product is in the client's products and the client is not revoked, on INSERT and on the UPDATE branch for agent writers (A6's first two bullets). The daily limit stays in the store.
