- **P1 — 证据丢失可能洗掉已登记的否决。** §3 L88、§4 L93 从历史 review manifest 提取否决集合，`step_recorded` 本身只保存摘要（§2 L43）。一份首行 `fix first` 的 review 已记账，随后 manifest 丢失；用 `evidence-lost` 关闭，再开下一轮，规格没有要求保留该集合的否决，也没有要求历史证据缺失时阻止重审。同一集合可能拿到第二个意见并通过，不需要改写原判词。应把消费集合及否决事实随记账原子写入事件；补充“完整/截断否决 → manifest 丢失 → resolve → 同集合”测试。

- **P1 — 人工关闭仍有未定义的裁决崩溃窗口。** §5 L122 把有 intent、无 recorded 定义为开着的步骤，L124 却要求 `verdict_pending` 没有开着的步骤。B4–B7 经 `resolve failed/cancelled` 落下人工补记后、追加 verdict 前崩溃，没有对应边界或明确状态；再次 resolve 是否被拒绝、是否能换 kind/reason，实施者仍须猜。应规定人工补记立即逻辑关闭 attempt，并统一进入补落判词；补记不可重复或替换。正常 B8 在证据稳定时，持锁加“已有判词不再落”已防住重复 verdict。

- **P2 — 残尾修复不是所声称的幂等事务。** §2 L29 使用随机备份名：备份写完但未截断时崩溃，重跑会生成第二份备份及第二条修复事件；备份写到一半也可能被第③步当成正式备份。备份文件 fsync 后没有规定目录 fsync，再截断可能失去备份。应使用稳定修复身份、临时文件发布、目录 fsync，并覆盖修复每次写入内部的崩溃。按现有截断位置不会删除摘要正确且换行完整的事件；另需明确完整换行但摘要错误属于损坏，不得自动当残尾删除。

- **P2 — 无锁读取能显示从未成立的状态。** §2 L30：读者先读到 `step_started`，驱动随后记账、落判词、释放锁，读者探测锁空便显示 `unknown`；实际过程只有进行中和已关闭。另一个 `resolve` 持锁又可能被误认成驱动仍在。需要事件头与锁观测的一致性校验、有限重读，以及无法取得稳定快照时的明确显示；`overdue` 必须使用同一快照。

- **P2 — 来源配置影响可用性，不能宣称完全无配置影响。** §3 L73–75 足以解决硬链接、目标 alternates、模板 hooks、继承环境及替换对象问题；来源配置仍能影响 upload-pack 行为，例如隐藏引用。对象校验和树号比对使其通常表现为失败，尚未证明能替换内容通过。官方文档也说明 upload-pack 会限制危险配置和 hooks，不能直接把来源 `packObjectsHook` 当成任意执行漏洞。[Git 配置](https://git-scm.com/docs/git-config)、[upload-pack 安全说明](https://git-scm.com/docs/git-upload-pack)。应明确来源配置允许范围并拒绝其他项，或通过配置受控的导出仓库取对象；不要修改旧执行目录来清理配置。
