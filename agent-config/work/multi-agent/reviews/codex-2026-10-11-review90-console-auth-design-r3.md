P1 · §4、7、9、10：文件级裸 `fetch` 豁免仍是绕过封闭结果的入口。普通贡献可以在豁免的 `api/network.ts` 增加读取 helper，将错误 JSON 的 `error` 返回给 `useQuery`；服务端自由文字随即进入查询缓存。现有 `network.ts:22–32`、`marketDataPlugin.ts:23–60` 已采用这类模式，包括异常 message 透传。无需读令牌、修改 session、关闭检查或玩字符串技巧；AST 禁项不命中，逐路由 fixture 和模块矩阵也不覆盖表外 helper，所有所述检查可保持绿色。这直接违反目标 (2)，不属于成功 `text` 残余，也不只是服务端拒绝更多。最小修改：取消 API 网络调用的文件级豁免，公共读取也经现有 `request` 的封闭结果出口；加入“旧豁免文件新增错误正文透传 helper”必须失败的阳性对照。[document]
同一豁免还能容纳普通 `fetch(..., {method:'POST'})`，在未确认身份时发出请求，违反目标 (1) 的“离开浏览器”标准；服务端随后拒绝不能补回客户端发送闸门。此为同一个 P1 的另一表现。

P2 · §5、7、10：`chi.Walk` 对实现 `chi.Routes` 的子路由递归累积中间件，识别 `ChainHandler` 的 With/Group；当前审批、问题及 operator-plane `register` 可覆盖。但 `Mount` 一个普通包装后的 `http.Handler` 会隐藏内部子路由，Walk 只能看到外层通配入口，不能声称交出全部内部中间件。最小修改：限定保证范围，并增加包装 Mount 的拒收/登记对照；这不会绕过身份确认，隐藏的角色限制通常只让服务端更严，故为 P2。[slice 1 acceptance]

P2 · §5、10：假令牌探测只能证明给定请求条件下能到达哨兵。依赖路径、参数、正文、请求头或外部状态的中间件，不能用同一个空请求推导稳定角色集合。任务 brief 须回答探测请求如何构造、不可确定时如何拒收；加参数相关中间件对照。保守漏收只导致拒发，过宽集合仍不能让未确认身份发送，故非 P1。[document]
