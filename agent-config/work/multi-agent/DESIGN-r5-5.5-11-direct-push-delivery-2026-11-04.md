## 1. 要做成什么

1. main 上明确认领了「某步的某一片」的提交，被运行时记成一条**认领观察**，作为不可变的事实。
2. 认领经过核实、确认合格后，这一步可以离开 planned。解释里能看到：哪一片、哪个仓库、哪个提交、什么时候、是否有效。
3. 认领不替完成规则做决定。只有规则里**明确写出**新原子 `step_delivered` 时，它才参与判定。已有原子含义不变。
4. 按片计。同一片有多份证据，只算一片。
5. 被 revert 或被明确撤销的认领会失效，失效会显示出来。

## 2. 信任边界（Owner 选的 C）

- **它证明的**：某个提交已经在 main 上，并且它的提交消息里有显式的认领尾注。
- **它不证明的**：
  - 谁推的（本机的 Gitea 推送凭据各会话共用，见 `agent-config/work/multi-agent/CUT-gitea-primary-2026-10-17.md:298`）；
  - 是否经过了 push-main；
  - 内容是否真的完成了那一片。
- **兜底**：
  1. 能写 main 的只有分支保护允许的身份；
  2. 含 `step_delivered` 的完成规则一律由 Owner 在卡上批（D6）；
  3. 完成规则里带 `owner_signoff`，最后一关是签收。

  认领最多让一步从 planned 变 active，并为 Owner 批过的规则提供证据，替代不了签收。
- **认领内容只从 Git 对象里读**：平台按 SHA 取提交消息、解析尾注，不接受任何客户端报上来的认领清单。

## 4. 契约（实施前冻结，各附测试）

### 4.1 读 main：固定 SHA，完整闭合
- 每一轮先钉住 main 的 head SHA，复用 `PlanHistoryReader` 的读法，验证从水位 SHA 到这个 head 的祖先闭合。算出 `reachable(head) − reachable(水位)` 的完整提交集合，合并带进来的提交也包括在内。
- 只有闭合完整时，水位才前进到这个 head。
- 分页截断、中途失败、仓库读不到：保留可重试的状态，水位不动。
- 水位不是 head 的祖先（main 被强推）：这是确定的错误，记一条 `main_scan_broken`，不反复重试，等统筹或 Owner 处理。
- 首次扫描从一个配置好的起点 SHA 开始，起点写进第一条扫描事件。

### 4.2 记录与状态（M2）
- **扫描事件** `direct_scan`：（仓库，起点 SHA，钉住的 head，是否完整，读的时间）。
- **认领观察** `direct_claim_observed`：每个（仓库，SHA，认领原文）一条，不可变。
  - 内容包括：尾注解析状态（§4.4）、步骤号原文、片号原文、提交时间、首次观察时间。
  - 存在仓库自己的流里（`main:<仓库>`），不挂计划节点的外键，所以指向不存在的步骤也能先存下来。
  - 同一个（仓库，SHA，认领原文）再出现，返回同一条观察，不新建。
- **资格** `direct_claim_eligibility`：引用一条观察，记 `eligible`、`rejected`（带原因）或 `pending`（带原因）。
  - 观察本身不变，资格可以重算：步骤后来建立了、规则后来声明了这一片、对应的落地后来找到了，都会重算。
  - 每次重算写一条新事件，引用上一条，旧的不改。
  - 资格变成 `eligible` 时，在计划流里写关联和激活事件，锁序和现有激活一致：先锁步骤，再解析 root，再锁计划流（`store/planactivate.go:65-98`）。
- **有效性** `direct_claim_validity`：每一轮对已合格的认领重新核对，记 `valid`、`reverted`、`unknown`，并带上 `checked_head` 和 `checked_at`。
- **撤销** `direct_claim_revoked`：统筹或 Owner 明确撤销某条认领，引用原观察，写明原因。撤销的授权和 D8 回填同级：要 Owner 的卡。
- **回填**（D8）：Owner 批过的清单，按清单写入 `direct_claim_observed`，来源记为 `backfill`，并引用审批编号。这是「只从尾注读」唯一的例外。

### 4.3 可信度回放（M1）
- 正文只提到步骤，不产生观察。
- 尾注写错格式，记 invalid，不计入。
- 同一提交认领两片，产生两条观察。
- 区间外的提交不会被收进来。
- 合并提交带进来的认领，照样收进来。
- 强推后水位不是 head 的祖先，记 `main_scan_broken`，资格不变。
- 回填清单里的 SHA 不在 main 上，被拒。

### 4.4 尾注解析与落地去重（S2）
- 在 `landinggit/provenance.go` 的尾注区域规则之上，加一个返回 4 种状态的解析：missing、valid、invalid、ambiguous。处理大小写、空值、重复、续行和冲突。
- `Plan-Step` 是 invalid 或 ambiguous：资格记 `pending`，原子取 Unknown，不取 False。
- 去重：
  - 提交带有效的 `Agentrt-Task`，并且对上一个已落地的操作：这个提交按落地任务计，认领记 `rejected: landed_task`，按任务原本的步骤和片计，不按认领计；
  - 带有效的 `Agentrt-Task`、但还没找到对应的操作：记 `pending`；
  - 已知的落地 SHA 去掉尾注后又出现：仍按落地任务计。

### 4.5 `step_delivered` 的真值表（S1）
- 每一片的证据来源有两种：
  - 一件已验收、已落地、经 5.5-15 绑定到这一片的任务；
  - 一条 `eligible` 且 `valid` 的认领。
- 一片的取值：
  - 任一证据为 True，这一片就是 True；
  - 否则只要有一份是 Unknown，这一片就是 Unknown；
  - 否则是 False。
- 绑定到这一片的任务失败了、但有一条有效的认领：这一片为 True，解释里写明「由直接交付替代」。
- 证据后来全部失效：这一片回到 False。整条规则是否重开，按现有语义：`step_delivered` 本身是历史原子，和常驻原子组合时，跟整条规则走（§0 #6）。
- 整步：`parts` 里的每一片都要成立（三值的 AND）。
- 只有 infra 的认领能取得资格（D7 A）。其他仓库的认领记 `rejected: repo_not_supported`。

### 4.6 revert 与持续核对（S3）
- 每一轮扫描，都对已合格认领按钉住的 head 重新核对有效性。读不到，或者 `checked_at` 超过 6 小时，有效性就记 `unknown`。原子和解释用的是同一个有效性结果。
- revert 的识别：复用 `EvaluateHistory` 的撤销算法，但改成按精确 SHA 判定，因为这里的提交不一定带任务或 Change-Id（§0 #11）。只认标准的 `This reverts commit <sha>`；部分回退、手工改写的情况，用 §4.2 的显式撤销。
- 已经签收的：不改签收，只在解释里标出「已签收的证据后来失效」。

### 4.7 Console（S4）
- 按 D9 A，新加只读接口 `GET /agentrt/plan/steps/{id}/delivery`，返回每一片的证据：来源（落地 / 认领 / 回填）、仓库、短 SHA、时间、资格、有效性、拒绝或待核实的原因。
- 接口不截断求值。界面每片最多列 20 条，多出的给个数。
- 部署顺序：先部署 API（只多了一个接口，旧 Console 不读它），再部署读它的 Console。新、旧两种组合都要测。
