## 1. 范围与不做的事

- 回答一个问题：此刻哪些身份、经哪些路径，能改变 PROD 的平台和它的控制面。每一行要么有证据证明被拒，要么有具名例外，要么明说不知道。
- 不做：不解释 RBAC 规则；不求值 CEL；不判断一条准入策略「适用不适用」；不在离线状态下说任何一行被拒；不读 Secret 的内容；不分析流水线（那是 B 片的检查，这里只用它的输出）；不修任何权限（C–F 片修）。
- **测量是一次快照，不是不变式。** 它证明不了的事分别写在各节里。

| 输入 | 第 3、4 节的清单、探针、例外、B 片的输出 | 仓库清单、基线文件、B 片的输出 |

## 3. 身份

身份不是一个名字，是一份上下文：`user`、`groups`、`uid`、`extra`，加来源。`uid` 和 `extra` 各有两种状态：已知（带值，值可以为空）或未知。未知的不填进请求，也不由程序编一个，行里照实记「未知」。每一种身份的上下文如下，照表原样，不增不减：

| 种类 | `user` | `groups` | `uid` / `extra` |
|---|---|---|---|
| ServiceAccount 对象 | `system:serviceaccount:<ns>:<name>` | `system:serviceaccounts`、`system:serviceaccounts:<ns>`、`system:authenticated` | `uid` 已知（对象的 UID）；`extra` 未知（随令牌而变） |
| 绑定里点名而对象不存在的 ServiceAccount | 同上 | 同上 | 都未知。单列：令牌现在不可用，建出来就可用 |
| 绑定里的 User | 绑定里的名字 | `system:authenticated`（别的组成员关系集群不知道） | 都未知 |
| 节点 | `system:node:<名字>` | `system:nodes`、`system:authenticated` | 都未知 |
| 「组 `<g>` 的任意成员」，每个被绑定的组一行 | 固定的占位名 `prod-matrix:member-of:<g>` | `<g>`、`system:authenticated`（`<g>` 是 `system:unauthenticated` 时只有它自己） | 都未知 |
| 匿名 | `system:anonymous` | `system:unauthenticated` | 都已知，为空 |

- **未知的 `uid` / `extra` 影响哪些行**：RBAC 和 Node 授权不看这两样，所以授权链已确认只有这两个环节时，授权的回答照常有效；没确认时，这个身份的全部授权行是 `unknown-surface`。第二轮里，一个探针只证明发出去的那份上下文：匹配到的策略原文提到 `userInfo.uid` 或 `userInfo.extra`，或者匹配到 webhook，这个探针就算无法取证。
- **「这个组的任意成员」**：成员是谁，集群不知道，所以这一行只能是具名例外（写明成员怎么发放、谁管）或未分类，不会因为「没看到成员」而消失。RBAC 是相加的，逐组问就盖住了多组的并集；授权链里若有 RBAC 和 Node 之外的环节，组合不可枚举，归下一条的固定行。
- **固定风险行**（`prod_fixed_identities.json`；缺一行程序就拒绝运行）：`system:masters` 的任意成员；k3s 的管理凭证和能登上 server 节点的人；节点上的 root（kubelet 的凭证、本节点 Pod 的令牌）；匿名（`system:anonymous`、`system:unauthenticated`，同时照常提问）；外部认证渠道和授权链的构成（OIDC、令牌 webhook、客户端证书的签发、授权 webhook——由 Owner 对照 k3s 的启动参数确认有还是没有，没确认就是 `unknown-surface`）。这些行只能是具名例外，理由必填，永远在表里。不读任何凭证的内容。
- **SubjectAccessReview 的四种回答都留着**：`allowed`；`denied`；没有意见（两者都为假）；出错（`evaluationError` 非空，或没有 `status`）。出错是 `unknown-surface`；畸形的和自相矛盾的回答也是（第 16 节）。没有意见只有在授权链已确认只有 Node 和 RBAC 时才等同于不允许，否则也是 `unknown-surface`。现有脚本把回答压成一个布尔值（`check_platform_rbac.py` 第 193 行），新程序不这样做。
- 它问的是 apiserver 的授权链；不验证某份凭证认证得过，也不回答准入。

## 4. 目标与完整性清单

- 目标也是一份上下文：API 组、版本、资源、子资源、命名空间或集群范围、名字（可空）、要问的动词、对应的探针。`prod_targets.json` 沿用停掉的分支里那份的内容（含 review 33 补的控制面），并包含方案里「矩阵至少要有的行」。
- **完整性清单**每次测量重新生成，三样：发现接口给出的全部资源和子资源；全部命名空间；第 3 节的全部身份。每一种可写的资源、每一个命名空间，必须要么在目标里，要么在「不算 PROD 目标，因为……」的清单里；两边都不在就是 `unknown-surface`。新装的 CRD 因此不会无声地落在表外。
- 每个身份另问一次全通配（动词、组、资源都是 `*`）；放行就是一行「全部资源，含以后新增的」。它不代替下面任何一个具体的提问。
- **按名字问全**：空名字的提问不反映「只对点名的对象」的授权——回答对，不等于问全。所以每个（身份，目标资源，命名空间，动词）除了问一次空名字，还对每个候选名字各问一次。候选名字三处来：集群里现存的对象（只读的一半按目标资源逐个命名空间列名字）；集群里每个 Role / ClusterRole 的 `resourceNames`（只读身份读得到角色对象；只取名字当问题，不解释规则）；仓库清单里声明的，和被引用而还不存在的（卷、`envFrom`、绑定、`paramRef` 里提到的）。只对某个名字放行的回答成一行，带 `only: <名字>`。`create` 和 `deletecollection` 只问空名字，授权时没有名字。
- **展开**：动词取发现接口给这个资源列的全部写动词，加目标文件里点名的特殊动词（`impersonate`、`bind`、`escalate`、`approve`、`use` 等）；发现接口列出的每个子资源各自是一组问题；版本用发现接口的首选版本去问，并记下全部在供的版本（探针按版本另试，第 5 节）。穷尽不了的各是一行明确的 `unknown-surface`，写明缺的是什么：角色对象读不到；Secret 的现存名字在只读的一半里列不了；授权链未确认时别的环节可能按名字放行。
- `kubectl auth can-i --list --as`（Owner 那一半）只用来提示「这里可能还有没列的目标」，不是完整性的证明：它可能不完整，也不反映准入。

## 5. 探针：一次拒绝证明的是一个请求

- **一个探针**是一个完整的请求：身份上下文；操作（CREATE、UPDATE、PATCH 及其类型、DELETE、CONNECT）；API 组和版本；资源、子资源、命名空间、名字；旧对象（当时集群里那一个，记 `resourceVersion` 和哈希）；新对象全文；**恰好一条**被改的字段路径和改法（新增、删除、替换），其余字段与旧对象相同且合法；`dryRun=All`。探针直接发 API 请求并解析返回的 `Status`，不靠匹配命令行的报错文字（`check_admission_guards.py` 第 275 行是匹配文字，九个固定用例）。
- **结果五种**：放行（保存服务端返回的对象）；被准入拒绝（记下策略、绑定、原话）；被授权拒绝（这是被模拟账号的 RBAC，不是准入，单独记，不算准入的证据）；被改写（放行了，但返回对象里那个字段不是发出去的值）；无法取证（其他错误，或 webhook 不支持 dry-run）。
- **`refused` 的含义**：一行是（身份，目标，字段路径）的一个请求族。标成 `refused` 要同时满足三条。这条路径的新增、删除、替换（有意义的每一种）都有探针，都被准入拒绝。拒绝它的策略每一个相关的条件分支至少有一个探针走到，探针文件里逐个写明走的是哪一支。探针文件里列了想得到的放行反例并且都试过、都被拒：同一父字段下的其他子字段、别的 PATCH 类型、别的 API 版本、子资源路径（`/scale`、`/status`）、先删后建。任何一个反例放行，这一行就不是 `refused`。
- **父字段不从子字段推**：行只按确切的路径立。想对父路径下结论，要么它的每条子路径各有一行，要么不下结论。
- **「其余请求」一行永远在**：一个身份对一个目标只要授权放行，除了探针覆盖的请求族，还有一行「其余没试过的请求」，它是 `unclassified`。它只能靠收回授权消失，或由具名例外承担——例外里写明靠哪条策略、试过哪些探针、谁接受剩下的不确定。
- **有限个样本证明不了一条 CEL 策略挡住了所有请求，本文不作这种声明。** `refused` 只是说：这些具体的请求在那个时刻被拒了，想得到的反例也都被拒了。

## 6. 证据与失效

- **每个探针存什么**：时间、谁跑的、集群的标识和版本；探针输入全文；状态码、`Status` 和服务端返回的对象；匹配到的每条 ValidatingAdmissionPolicy（名字、内容哈希），它的绑定（名字、`validationActions`、参数引用、匹配范围）和参数对象的哈希；目标命名空间的标签、新旧对象的标签；相关的 `matchConditions` 原文；匹配这个资源的 validating 和 mutating webhook 配置（名字、哈希、`sideEffects`、`failurePolicy`、条件）；目标资源的 API 版本和（CRD 的）定义哈希。
- **只有 Deny 算拒绝**：绑定的动作是 Warn 或 Audit 时请求照样成功，永远不产生 `refused`。
- **dry-run 证明不了的**：之后由控制器发起的请求（Job、Deployment、Tekton 的控制器用自己的身份建 Pod，另过一遍准入）；对 dry-run 和真实请求表现不同的 webhook 或策略（条件里出现 `dryRun` 的一律算无法取证）；策略依赖的外部状态以后的样子（参数对象、标签、webhook 背后的服务）；没被探针走到的条件分支和请求路径；准入之后别处的约束。
- **什么让证据作废**：上面记下的任何一项输入变了——策略、绑定、参数、命名空间或对象的标签、webhook 配置、资源定义，或者目标对象不在了；或者证据超过 **14 天**（第 10 节）。作废的证据不删，那一行回到 `unclassified`，原因写明是哪一项。
- 只读的一半每次运行都重算这些指纹，所以大多数失效不用等 Owner 就能发现；补证据要等他。

## 7. 借用边与闭包

一条边是「A 能以 B 的上下文做事」，或「A 能改一个别人会执行或信任的对象」。边自己也是量出来的，带确定性：`measured`（问到了、试到了）或 `unknown`（问不了，当作存在）。经过 `unknown` 边得到的行不能是 `refused`。

| 边 | 怎么量 | 得到什么 |
|---|---|---|
| impersonate | 对 `users`、`groups`、`serviceaccounts`、`uids`、`userextras/*` 逐个名字问 | 一份上下文：能模拟哪个用户、哪些组、UID 和 extra 的哪种组合。能模拟一个组，不等于能当某个用户 |
| bind / escalate，加写角色和绑定 | 问这几个动词 | 范围内全部目标的保守行（只能是例外或未分类）；它还等于能在范围内建工作负载，所以接着走下面各条边，不是终点 |
| 建**和改**带 Pod 模板的对象：Pod、Deployment、StatefulSet、DaemonSet、ReplicaSet、Job、CronJob | 问 create / update / patch；ServiceAccount 字段能填谁，用 dry-run 试 | 改模板里的镜像、命令、挂载：到这个对象现在的 ServiceAccount。改 ServiceAccount 字段或新建：到命名空间里填得上的 ServiceAccount。除了直接建 Pod，都要经过控制器，Pod 的 dry-run 证明不了控制器建的 Pod 会不会放行，这种边是 `unknown`。一次 dry-run 被拒只说明那一个请求被拒（第 5 节）：别的模板改动、别的操作和路径仍是 `unknown` 的边；边不因探针被拒而消失，只能由具名例外承担 |
| 建 PipelineRun / TaskRun；改 Pipeline、Task、触发器的定义 | 问动词；run 的 ServiceAccount 选择用 dry-run 试 | 到 run 用得上的 ServiceAccount；改定义：到以后跑这条流水线的 ServiceAccount（来自 B 片的输出） |
| `pods/exec`、`pods/attach`、临时容器、`nodes/proxy` | 问 create 和 get（GET 也能执行命令） | 到命名空间里或节点上每个 Pod 的 ServiceAccount |
| `serviceaccounts/token` | 问 create，逐个名字 | 到那个 ServiceAccount |
| 读 Secret | 问 get / list / watch；Secret 的名字和类型由 Owner 那一半列出，内容不读 | 「可能持有……的凭证」：`prod_credential_holders.json` 登记每个 Secret 装的是谁的凭证；没登记的是 `unknown-surface` |
| 改准入对象、它的参数、它匹配的命名空间标签 | 问动词 | 靠这条策略得到的 `refused`，对这个身份不成立 |
| 改 Application / AppProject、CRD、别人挂载并执行的 ConfigMap；批准客户端证书的签发 | 问动词 | 到执行或信任它的那个身份：Argo 的控制器、挂载它的工作负载、任意身份 |

- **闭包是全集群的**，不只在 PROD 的命名空间里走：在范围外取得一个身份，或在范围外改一个控制面对象，再影响到范围内的目标，都是路径。每一行留着：最初的主体、实际执行的上下文、每一跳的边和确定性、实际的作用范围、需要的操作、之后能做什么。
- **算法**（review 39 给的）：状态是（最初的主体，执行的上下文）；哈希集合加工作队列增量传播；每个状态只存一个前驱，不枚举所有路径；一个状态有一条全是 `measured` 的路径就记 `measured`，否则 `unknown`。准入按执行的上下文判，不按最初的主体。
- **截断**：超出预算就输出一行 `unclassified: derivation truncated` 并以 2 退出，不给出部分结果。

## 8. 仓库棘轮

- 基线文件是规范化、排好序的文本，检查要求**逐行相同**。多一行是面变大，要有一次经过复核的基线改动；少一行是面变小，在同一个改动里重新生成基线。
- 基线记六样：每条绑定（类型、名字、作用域、角色、每个主体）；每个角色的标签、`aggregationRule` 和全部规则原文（含 `resourceNames` 和通配）；通配会展开到的资源和子资源清单——仓库里的 CRD，加上测量提交回来的发现清单；每个有副作用的 task（来自 B 片）的内容摘要，和它的 ServiceAccount 是怎么选的；分类所依赖的准入对象（策略、绑定及其动作、参数、webhook 配置）和它们匹配的命名空间标签；固定身份清单和凭证登记表。
- 所以下面每一样都是一处差异：新的 CRD；给一个角色加上聚合标签；改 `resourceNames`；同名的 task 换了脚本，或换了选 ServiceAccount 的办法；绑定的动作从 Deny 改成 Warn。
- **只有现场复测才发现得了的**：组里多了人、在集群外发的凭证；手工应用的、Helm 或 operator 带来的对象；仓库和集群不一致；聚合在集群里的实际结果；准入的实际行为。棘轮是绿的，只说明仓库声明的面没变。
- B 片的输出没有提供时，棘轮和测量都把它记成缺的输入（`unknown-surface: side-effecting tasks not provided`），不跳过，也不自己去读流水线。

## 9. 分类、例外、退出码

- 一行的类别：`refused`（第 5、6 节）；`named-exception`；`unclassified`，附原因（没试、无法取证、证据作废、经过未知的边、其余请求、推导截断）；`unknown-surface`（读取或提问失败，或有一块面没清点）。固定风险行只能是例外或未分类。
- **读不到不等于没有**：每条命令记自己成功没有；空的返回只有在命令成功时才算空。
- **例外分两类**，格式和汇总里都分开：`trust-root`（信任根：系统组件、固定身份）和 `field`（普通的字段或请求族）。必填：类别、身份、目标、字段或请求族、授权验证点、期限、由哪一步收回、理由。精确匹配，不许通配；过期的不生效。例外永远不能吸收 `unknown-surface` 和截断：读取失败、清单缺失、预算截断不是可以接受的风险，是没做完。
- **吸收「其余请求」的例外**另外必填：精确的身份上下文和目标范围；它吸收的那一行余集的行键；所靠的策略和绑定的指纹；跑过的探针和已知放行的路径；没覆盖什么、它让持有者能借到什么；谁装的、为什么需要、收窄的计划；具名的风险接受者和批准记录；到期日和复查间隔；失效触发条件；由哪一步收回。
- **零未分类的含义**：面已经完整清点，剩下的每一项风险都有人点名接受；不是「没有绕过闸门的路」。「其余请求」一行说的是「不知道能不能写」，不是「已知能写」。汇总把两类例外分开列：各有多少条、涉及多少身份和目标、多少条吸收了余集、多少个身份对全部目标可写。
- 退出码：0 完整，没有未分类和未知；1 有未分类或未知；2 不完整（命令失败、被禁止、超预算、固定行缺失）；3 只跑了只读的一半，这时不可能是 0。同时满足几条时，2 先于 3，3 先于 1。
- 明细留在本机，不进仓库。进仓库的是汇总：时间、行数和各类计数、输入指纹、谁跑的。

## 10. 谁跑、多久跑一次

- **只读的一半**：`bifrost-access/bifrost-agent`（绑定 `bifrost-agent-read` 和 `view`）。它能建 SubjectAccessReview，没有 impersonate。仓库里的声明缺四类读权限：`validatingwebhookconfigurations`、`mutatingwebhookconfigurations`、`priorityclasses`、`runtimeclasses` 的 get / list，由 Owner 改 `k8s/agent-access/clusterrole-read.yaml` 并应用（D 级）。仓库的声明不等于集群的现状，所以程序开头先问自己的每一项读权限，缺一项就以 2 退出。这一半可以每天跑。
- **要模拟身份的一半**：只由 Owner 用自己的 kubeconfig 经 `owner_run_command` 跑。不建带 impersonate 的常驻账号：这个动词限制不到「只许 dry-run」，准入也看不出一个请求是经谁模拟的；谁常驻拿着它，谁就是最强的一条借用边。
- **Owner 什么时候跑**：第一次完整测量；C、D、E、F 每一片应用之后；棘轮报出差异并合并之后；只读的一半报告有指纹变了；此外**最长 14 天**一次。选 14 天的理由：有些变化没有任何触发——组成员、webhook 背后的服务——只能靠期限兜住；14 天是 ADR §12.2 第 5 条里「等 Owner 的事变红」的同一条线；一次是一条命令、十来分钟不用守着；再短他又成了每周的瓶颈，再长一行 `refused` 可能有一个月是旧的。
- **第 1 步的退出认证的是一次快照**：记下时间、输入指纹、什么会让它作废（第 6 节）。证据作废或过期，那些行重新是未分类，退出条件不再成立，直到补测。

## 11. 预算（要量的，不是已证明的）

SubjectAccessReview 2 万次以内、10 分钟以内（成批提交；现有脚本是每问一次起一个进程）。探针 2000 个以内、15 分钟以内。闭包 60 秒、100 万次状态访问以内。第一轮量第一项，第二轮量后两项，实测值写回这里；超出就以 2 退出，再决定是调预算还是改做法。

## 16. 第一轮的契约（照此实现，不留给实现者猜）

- **格式**：本片自己的数据文件和录制包全部是 JSON：UTF-8，对象的键排序输出，顶层带整数 `schema_version`；读到不认识的版本或未知的键就以 2 退出。Python 标准库没有 YAML 解析器，本片不为自己的文件加依赖，也不手写解析器；停掉的分支里的 YAML 材料转成 JSON。仓库里的 Kubernetes 清单本来就是 YAML，棘轮读它们用仓库检查脚本已经在用的 PyYAML（`check_admission_guards.py` 等十多个脚本都 import 它），只用 `safe_load_all`。
- **上下文**（第 3 节）：`{"kind", "user", "groups": [排好序], "uid": {"state": "known", "value": …} 或 {"state": "unknown"}, "extra": 同样, "source"}`。授权链和认证渠道没确认，在固定身份清单里写作 `{"confirmed": false}`；程序读到它就产出 `unknown-surface`，不替 Owner 改成 `true`。
- **行键**：最初的主体、执行的上下文、API 组、资源、子资源、命名空间、名字、动词、请求族，这九项的规范化 JSON 的 SHA-256。同样的输入两次运行，键相同。
- **录制包**：一个 JSON 文件。头部：`schema_version`、起止时间、调用身份的上下文、工具版本。`commands`：每条读取一项——编号、请求（方法、路径、参数）、每一页的回答、`ok`、状态码、起止时间。`reviews`：每次提问一项——编号、请求全文、请求的哈希、回答原文。每个回答带着它所答请求的哈希，对不上就以 2 退出。
- **分页**：列表一律带 `limit` 读，逐页记 `continue`，最后一页的 `continue` 必须为空。中途缺页、`continue` 过期（410）、页数对不上，这条命令算失败。空列表只有在 `ok` 且分页完整时才算「没有」。
- **提问的回答**：第 3 节的四种状态之外，畸形的（不是合法 JSON、缺 `kind`、`allowed` 不是布尔值）和自相矛盾的（`allowed` 和 `denied` 同为真）都是 `unknown-surface`。
- **目标 / 非目标清单的维度**：（API 组，资源，子资源，命名空间或集群范围）。发现清单乘命名空间清单的每一格都要落在某一条里。非目标的条目必须带理由；命名空间可以写 `*`，资源不可以。名字规则见第 4 节。发现清单来自发现接口的原始回答（录在 `commands` 里），不来自仓库。
- **仓库扫描**：根是本仓库的 `k8s/` 整棵树，全部 `.yaml` 和 `.yml`，多文档；有一个文件解析失败，棘轮就以 2 退出，不跳过。别的仓库里的清单不在扫描范围，归现场复测。基线每行一个 JSON 对象：键排序，无序的列表排序，规则的原文保持原样；行按（类别，命名空间，类型，名字）排序。
- **B 片接口缺席时的固定记录**：`{"kind": "missing-input", "input": "side-effecting-tasks", "provider": "slice-B", "reason": "not provided"}`。它在棘轮的基线里占一行，在测量里产出一行 `unknown-surface`。
- **例外的匹配**：身份上下文、目标的四个维度、名字、动词、请求族逐项相等才算匹配，有一项不同就不匹配。`expires` 是 UTC 日期，当天仍有效，次日起失效。
- **超时、重试、并发、预算**：每个请求 30 秒超时；只对连接错误、429 和 5xx 重试，最多两次，重试也记进录制包；并发不超过 8；预算按实际发出的请求数算，含重试，到第 11 节的数就停，以 2 退出。
- **离线重放不联网**：分类和全部测试只读录制包。测试夹具把 `subprocess` 和 `socket` 换成一调用就失败的桩；重放的路径上开了子进程或套接字，测试就失败。

## 17. 第一轮缩小后的范围（统筹方 2026-10-11 决定，Owner 事后审计；与前文冲突时以本节为准）

三次纸面复核（40、44、47）每次都在「把授权问题问全」上找到新的必须改的问题，最后一次是带名字的 `create`（`serviceaccounts/<name>/token` 的授权属性里有名字，第 4 节却写「create 只问空名字」）。同一处连着三次不闭合，说明第一轮承诺得太多。不给规格打第四次补丁，照复核 47 给的最小缩减改范围：**第一轮交工具，不交「问全了」的结论。**

- **交什么**：① 完整性材料的原始清点——发现接口的全部资源和子资源、全部命名空间、第 3 节的全部身份，照录进录制包；② **显式问题**的 SubjectAccessReview 采集和离线重放；③ 逐行相同的基线棘轮；④ 例外文件的加载和匹配。
- **显式问题**只有 `prod_targets.json` 里逐条写出来的：（身份范围，API 组，资源，子资源，命名空间或集群范围，名字，动词）。程序不替它展开候选名字，不拿发现接口的动词去乘，不从角色对象里取 `resourceNames`。第 4 节「按名字问全」「展开」两条第一轮不实现，全通配那一问保留。
- **没问到的要明说，不许沉默**。发现清单乘命名空间清单的每一格，按下面的顺序各出至多一行 `unknown-surface`，写明原因：没有任何显式问题覆盖 → `not-asked`；有问题，但只问了空名字 → `names-not-enumerated`；发现接口列出的**具名子资源**（`serviceaccounts/token`、`*/scale`、`*/status`、`pods/exec`、`pods/ephemeralcontainers`、`*/finalizers` 等，判据是发现接口返回的名字里带 `/`）没有被逐个点名 → `named-subresource-not-asked`。落在「不算 PROD 目标，因为……」清单里的格不出行。这三种行和第 9 节别的 `unknown-surface` 一样，不能被例外吸收。
- **结论的写法固定**。汇总第一行：`authorization only; questions are the explicit list, not exhaustive`。第二行：三种原因各自的行数。输出里没有 `refused`；退出码不可能是 0；只跑只读的一半时照第 9 节是 3，有命令失败或超预算是 2。
- **第 1 步的出口不由第一轮满足**。方案里「测量由读得全的身份跑完、零未分类」要等第二轮（dry-run 证据）和把问题问全的做法定下来之后；第一轮之后能说的只有「面至少这么大，其中这些格没问」。

复核 47 列的五处「实现者要猜」的地方，这里定下来：

- **字段表只有一份**：`scripts/release/prod_matrix/schema.py` 里的声明（每个数据文件、录制包的每一段、每种输出行：字段名、类型、是否必填、允许的取值）。`schema_version` 一律是整数 `1`。校验函数从这份声明生成；目录下 README 里的字段表也由它生成，测试核对两者一致。缺必填字段、多出未知字段、类型不对，都以 2 退出，并指出文件和字段。固定身份和授权链确认记录是 `{"confirmed": bool, "by": 字符串, "at": UTC 时间, "evidence": 字符串}`，`confirmed` 为真时后三项必填。
- **请求族**第一轮只有一个值：`authz`（授权提问）。dry-run 的各族属于第二轮，第一轮读到别的值以 2 退出。
- **提问的哈希**：对 SubjectAccessReview 的 `spec` 一个对象做规范化 JSON（键排序，分隔符 `,` 和 `:`，UTF-8，不转义非 ASCII），取 SHA-256。规范化的内容：`user`；`groups` 排序去重；`uid` 和 `extra` 在状态为未知时整个键不出现，`extra` 的键排序、每个值列表排序；`resourceAttributes` 七个字段（`group`、`version`、`resource`、`subresource`、`namespace`、`name`、`verb`）全部出现，没有的写空字符串。`metadata` 不参与。提问的编号是 `q-` 加哈希的前 16 位十六进制。一次运行里编号重复、生成的问题在录制包里没有回答、或有两个回答，都以 2 退出。
- **集群范围的资源**：`namespace` 写空字符串，另有 `scope: "cluster"`；每个（组，资源，子资源）是一格。**子资源不继承父资源的名字**（第一轮不展开名字）。**Secret 的名字读不到**：每个目标命名空间出一行固定记录 `{"kind": "unknown-surface", "reason": "names-unreadable", "resource": "secrets", "namespace": …}`。
- **输入入口**：发现清单只来自录制包的 `commands`；仓库清单的根是本仓库 `k8s/`；目标、固定身份、例外、基线各有默认路径（第 2 节的文件名，都在 `scripts/release/prod_matrix/` 下）和一个同名的命令行参数可以改。**过期的例外**：加载时不报错，标成 `expired`，不参与匹配，在汇总里单列；它原来盖住的那一行回到未分类。日期写不对的例外以 2 退出。
- **预算**：提问数等于显式问题数乘各自身份范围里的身份数，开跑前先算出来并打印；超过 2 万就一个请求都不发，以 2 退出。只读请求（发现、列命名空间、列身份、列角色）不计入这 2 万，另设 500 条上限。10 分钟是墙钟，从第一个请求算起，到点就停，以 2 退出。重试记成独立的一项，带 `retry_of` 指回原编号。离线重放只验证数量和分类，吞吐等第一次现场运行，实测值写回第 11 节。

测试：第 13 节列给第一轮的各条照旧，其中 **T26** 改成断言上面三种原因行的产出（某身份只能 `patch` ConfigMap `platform-config`，而目标文件只问了空名字 → 不放行，同时有一行 `names-not-enumerated`；目标文件点了这个名字 → 一行带 `only: platform-config`）。新增：**T37** 发现清单里有 `serviceaccounts/token` 而目标文件没点名 → 一行 `named-subresource-not-asked`；点名并带名字提问 → 没有这一行。**T38** 算出的提问数超过 2 万 → 没有任何请求发出，退出码 2。**T39** 问题缺回答、有两个回答、编号重复 → 各自退出码 2。**T40** README 的字段表与 `schema.py` 的声明逐字段一致；每个数据文件各有一个缺字段、一个多字段、一个类型错的负例。**T41** 汇总前两行是固定写法，任何输入下输出都没有 `refused`，退出码都不是 0。
