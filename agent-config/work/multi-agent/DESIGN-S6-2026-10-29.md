## 0. 先说结论：S6 照原稿做，Owner 手推几乎不减

原稿把 `agent-config/**` 整个列为 infra 底线。实测近 30 天 infra main 的提交里 **61.8% 只改了文档**，几乎全在 `agent-config/work/**`、`TECH_DEBT.md`、`WORK.md`（§1.2）。照原稿，运行时在 infra 能落的东西每月只有个位数，而 Owner 手推的大头不受影响。

还有第二个更根本的问题：**落地只搬运「运行时任务被接受的结果」**。infra 的文档提交几乎全是统筹会话自己写的，不是运行时任务，S6 根本碰不到它们。所以「你不再手推 main」对 infra 要两件事一起做：

1. 运行时任务的 infra 结果可以落地（本稿 §2–§4，原 S6 的本义）；
2. 统筹自己的文档提交有一条不经 Owner 的窄通道（§5，需要 Owner 决定，见 D2）。

## 3. 两仓抢额度：锁序与用例

现行最终闸锁序（`store/landing_live.go` `AuthorizeLandingPush`）：能力共享锁 → 规则共享锁（`landing:<tenant>`）→ 绑定（任务 / mission / 计划节点）→ **当天额度流 `landing-quota:<tenant>:<UTC 日>`** → 本仓库落地流。额度流按租户、不按仓库，两个仓库的最终闸都先拿额度流、再拿各自的仓库流，锁序一致，不会死锁；额度计数（`ReservedToday`）在额度流锁内读，第二个到的看到额度已满，按 `limit` 拒，不写意图、不预留。

需要改的只有一处：`OtherInFlight`（每仓在途上限）今天读的是 platform 流，改为读本仓库流；每日上限读额度流（跨仓库）。

**用例**（PostgreSQL、两个连接）：额度只剩 1；platform 与 infra 各有一个 `branch_pushed` 的操作；两个连接同时跑最终闸，第一个在拿到额度流后挂住（测试钩子），第二个等锁；放开后恰好一个写 `main_intent`，另一个 `limit` 拒、无预留。旧代码上红：infra 根本没有落地流，第二个连接报「未知操作」。

## 5. 统筹自己的文档提交（D2，需要 Owner 决定）

运行时落地解决不了统筹会话直接写的文档。三个选项：

- **A（推荐）**：Gitea 的 `unprotected_file_patterns`（受保护分支上「有写权限就能直接推、不受推送白名单限制」的文件模式）只填第一批的两条模式（`agent-config/work/**/*.md`、`docs/**/*.md`），另给统筹一个专用身份（`agentrt-coordinator`，只有 infra 的 Code Write）。效果：统筹推只改这些文件的提交可以直接进 main；碰到任何别的文件 Gitea 照旧拒。缺点：这条通道不经 CI 和评审（但只有文档）；Gitea 对这些模式是「任何有写权限的人」都放行，`landing-drill` 团队今天对 infra 有写权限，要先收回或接受。**需先实测 Gitea 1.21 对 `**` 与 `OWNER-STEPS-*` 排除的匹配行为**（不支持排除，就把 OWNER-STEPS 挪到 `agent-config/owner-steps/`）。
- **B**：统筹的文档改动也写成运行时任务（每次提 task → 执行者照抄 → 验收 → 评审 → 落地）。走同一条受控通道，但每次 10–20 分钟、耗执行与评审额度，统筹频繁的小改动不划算。
- **C**：维持 Owner 推。统筹把文档提交攒成批，一天推一两次。
