## 0. 先说会改变走向的核实结果

第 1–4 条是第 2 稿的，第 5–8 条是第 2 轮复核核出来的，第 9–11 条是第 3 轮复核核出来的。

1. **记忆的方向早已定了。** 还要按程序签的，是具体的表、接口、岗位规则和权限。依据：
   - 台账 WORK.md:547 记着记-1 至记-5 和 A1、B1 都按推荐；
   - 记忆导入计划写明「权限与 DDL 按既有规则签批」（`agent-config/work/crew/PLAN-memory-import-2026-10-24.md:104`）。
2. **两次「失忆」是工作记忆的失败，不是长期知识的失败。** 统筹 11-02 两次没想起自己几天前的判断（陈述）。本稿推断原因是：统筹的决定没有落成系统记录（推断）。
   - 运行时本来有放这类东西的事件 `decision_recorded`。它的迁移说明写着「下一次规划读这些记录，而不是对话的记忆」（`api/internal/agentrt/migrations/0006_decision_recorded.sql:1-5`）。
   - 但今天只有参谋长的规划任务会写它，作者固定为席位（`api/internal/agentrt/store/planresult.go:274`）。统筹线程没有任何工具能写。
3. **ADR 有一条与 10-26 决定冲突的原则，从没处理过。** ADR §12.2 第 10 条写着不汇总各主机的对话记录、不做 Agent 之间的聊天总线、不许 Agent 自建频道（`agent-config/ADR-ops-architecture.md:241`）。10-26 定的完整会话时间线，正是把各主机的会话汇总到平台，只有 Owner 能读（台账：WORK.md:551）。见 §13 N13。
4. **任务线程只能是类型化记录的投影，不能是聊天。** 理由同上一条 ADR。
5. **外部工作没有尝试行，复核独立性的排除对它静默失效。**
   - 路由排除同家复核时，只读运行时的尝试行（`api/internal/agentrt/store/route.go:220-221`、`:344-350`）。外部工作没有尝试行，这个循环一次也不跑，什么都不排除，也不报错。
   - 外部工作的厂商只写在登记者自己上传的说明里（`api/internal/agentrt/store/externalwork.go:23`），服务端只查它非空、不超长（`:157-161`）。
   - 复核任务必须有一个运行时的被审任务（`api/internal/agentrt/migrations/0001_core.sql:147`），复核结论必须挂在尝试上（`:270-271`）。控制器自动提复核的唯一入口也以运行时任务为输入（`api/internal/agentrt/store/accept.go:150-170`）。
   - 所以第 2 稿「外部工作提交后，控制器按同一路由规则提复核任务」在今天的数据模型上不成立。见 §6 和 N14。
6. **钩子手里的令牌写不进出门条。** Claude 线程钩子用 reporter 令牌（`agent-config/scripts/thread-heartbeat.js:52-55`）。非席位的 reporter 只能上传外部工作说明（`api/internal/agentrt/agentrtapi/api.go:641-644`、`:662-666`），发消息、提议一律被拒（`api/internal/agentrt/agentrtapi/reporter.go:13-21`、`api.go:146`）。见 §7.1 和 N15。
7. **压缩那一刻没有写点，新会话也拿不到上一次的东西。** Claude 侧只接了六个钩子事件：用户提问、工具调用前、工具调用后、通知、子代理结束、结束（`agent-config/claude/settings.json`；`agent-config/scripts/thread-heartbeat.js:101-109`）。没有压缩前（PreCompact），也没有会话开始（SessionStart）。ADR §12.2 第 13 条要求边界和条件由程序执行，不由模型记着（`agent-config/ADR-ops-architecture.md:244`）。但止失忆的主力不是压缩钩子：压缩钩子只能从系统记录拼，没记下的决定它和结束钩子一样发现不了。主力是「当场记下」（N9 写入口）和「开工时读回来」（第 9 条）。见 §5.2 和 N16。
8. **上下文包不能用 `brief` 种类。** `brief` 是不扫描本机路径的种类（`api/internal/agentrt/store/localpath.go:13`）。钩子的 reporter 令牌传不了它（`api.go:641-644`），但 MCP 用的 operator 令牌和席位令牌能上传任何种类（`api.go:122`、`:649`；`mcp/platform/src/index.ts:695-704`）。接手的人开工先读的东西，不能是一个谁都能传、又不扫描的种类。见 §4.2。
9. **决定记录只有写的路，没有读的路。** MCP 没有任何读事件的工具：`get_plan`、`get_mission`、`list_tasks`、`get_task` 只取行（`mcp/platform/src/runtimeTools.ts:72-91`）。REST 有跨流读事件、按类型过滤的接口 `GET /events?types=decision_recorded`（`api/internal/agentrt/agentrtapi/events.go:19-20`、`:73-82`），读权限包括 reporter（`api.go:119`、`:176`），但 MCP 没包它。今天读决定事件的只有参谋长快照（`store/snapshot.go:168`）和 Console 的进度时间线（代码：`console/src/pages/shell/progress/timelineModel.ts`）。所以只加写入口止不住失忆：出门条里的决定编号，模型没有工具解析成四样字段。见 N9。
10. **钩子和 MCP 不能用同一个线程身份写。** 一个 `thread:<session>` 归第一次以它写入的那把令牌，别的令牌再以它写或读信，一律被拒（TD-370；`api/internal/agentrt/store/propose.go:42-47`、`:62-88`）。MCP 的会话头取侧栏会话编号（`mcp/platform/src/sessionId.ts:14`），登记工具也强制用侧栏编号（`scripts/agent-host/register-claude-work.py:69`），钩子环境里也拿得到它（`thread-heartbeat.js:221`）。如果钩子（reporter 令牌）先以 `thread:local_X` 登记，统筹线程自己的 MCP（operator 令牌）再以同名提议、发消息、写决定，就全部被拒，而这正是要止失忆的那条线程。见 §7.1 和 N15。
11. **钉住任务的复核只给固定的一家。** 被审任务带 pin 时，复核候选先被筛成固定复核者 codex、openai（`api/internal/agentrt/store/route.go:258-267`；`store/pinresult.go:205-209`），之后再排除被审尝试用过的执行器和厂商（`route.go:344-350`）。如果把 Codex 做的外部工作变成受信 openai 的钉住尝试，唯一的候选也被排除，没有人能复核。pin 今天只许「实现 + 分支」，也不能检查别的任务（`api/internal/agentrt/migrations/0010_executor_pin.sql:54-55`；`api/internal/agentrt/store/pin.go:168-171`）。所以外部尝试不只是加一个 pin 字符串，还要改路由。见 N14。

## 1. 目标与非目标

目标：
1. **协作**：Agent 之间经平台持有的类型化记录协作，不互相读会话，不靠统筹中转。
2. **沉淀**：多 Agent 产生的内容按可信程度和生命周期分层；值得记住的经复核进入大脑，其余按约定遗忘。
3. **看得见**：Owner 在 PROD Console 上看得到进度和细节，按注意力分档，原始信号不推给他。
4. **不失忆**：任何一个会话被压缩、换模型或结束，下一个接手的人从系统记录里接得上。当场记下的入口、开工时读回的路径、压缩时的快照，以及「已声明但未落盘」的计数，都由程序保证，不靠自觉（ADR §12.2 第 13 条）。

非目标：
- 通用多 Agent 平台；
- 读或解码厂商不给的内部推理；
- Agent 读别人的会话正文；
- 改动任何硬边界（D10、preflight、审批分级）；
- 与实盘交易执行相关的任何能力。

## 2. 架构：以「一件活的身份」为脊柱，按可信程度分层

两条轴：
- **可信程度**：事实、观测、自述、提炼；
- **生命周期**：多久、谁能删。

把一切串起来的，是一件活的稳定身份：运行时的任务和尝试、外部工作、观测会话。没有身份绑定，上面哪一层都提炼不出来。

层是逻辑组织，不是迁库指令。每层的权威记录留在原处：
- 审批和发布状态留在 statefile；
- CI 和发布事实留在 Gitea、Tekton 和发布窗口；
- 运行时自己的事实留在 PostgreSQL。

**层号不是可信等级。** L7 是意图，不比 L3 更可信。L3 里的复核记录只证明「某个身份对某个版本给过这个结论」，不保证结论正确。

| L0 身份与绑定 | 主体、主机、会话、外部工作、尝试之间的绑定 | 事实；外部工作的厂商除外，它今天是自报（§0 第 5 条） | 运行时的 actor、host、task、attempt 表；外部工作在 `external-work:<id>` 流（D-PV2 A）；观测会话按 10-26 §3（未建） | 控制器、agentd、登记包装器、钩子 | 所有人（只是元数据） | 任务永久；会话元数据 90 天（D-SS2 A） |

## 4. 流向

### 4.1 上行提炼：由事件触发，不由模型判断「值不值得记」

两步：
1. **事件触发候选**：控制器或收集员按事件写候选，模型不参与；
2. **写入门**：候选要变成经验，必须过三组门（结构、证据、语义）。

**候选触发器**（只写候选，不写经验）：

| # | 触发 | 来源事件 | 候选里放什么 | 何时启用 |
|---|---|---|---|---|
| T1 | 验证或复核不通过 | `verification_recorded`，结论 fail | 只放编号和枚举：对象、类别、复核意见产物编号 | S6 |
| T2 | 同一模块同一类第二次不通过 | T1 + 5.6-4 的类别账本（运行时） | 只放编号和枚举；转设计步（5.6-4 已排，运行时），并要求带防线编号或设计步 | S6 |
| T3 | Owner 没按推荐选 | 计划改动的决定、答卡、签收被拒 | 推荐是什么、他选了什么。可能带个人的决定背景，所以首次落盘就进受限存储 | **等 A1**（S7 之后） |
| T4 | 等待超限 | `wait_limit_passed` | 只放编号和枚举：哪类等待、多久 | S6 |
| T5 | 闸门拦截 | `policy_alert`、preflight 拦截计数 | 只计数，进周报 | S6 |
| T6 | 会话留下的教训 | 受限存储里的教训记录（出门条 v1 不带自由文本，§5.2） | 自述，受限 | **等 A1**（S7 之后） |
| T7 | 一次通过的交付 | 任务接受且只有一轮 | 只留统计（复核几轮、用时、额度），不生成条目 | S6 |

候选的规矩：
- **幂等键**：触发器 + 源事件编号 + 工作编号 + 轮次。夜里重跑不重复写候选、卡片或统计；迟到的事件和重复的事件不算「第二次不通过」。
- **去重**：同一出处只留一条候选。
- **过期**：14 天没入库的候选标「过期」，计数，不再处理。
- **升级条件**：T6 的教训被另一个会话引用过，才进整理。
- **度量**：候选积压数、最老一条的年龄、候选到有效条目的转化率（§12）。

**写入门**。在档案员专用写工具的服务端执行，不通过就拒。分三组，前两组是程序判，第三组要人或另一家判：

结构门（确定性）：

| # | 规则 |
|---|---|
| R2 | 形状：一句话，不超过 200 字；适用范围非空；种类在封闭词表里；有条目键（§5.5） |
| R3 | 内容过滤：本机路径检查、工作区引用检查；人名与账户的否定词表（词表本身只放受限存储）。命中就只能存受限。**没命中不等于公开**（导入计划已写明，`PLAN-memory-import-2026-10-24.md:29-30`）。数据类别由写入方声明，过滤只能把它降为受限，不能升级 |
| R5 | 失败类第二次：T2 来的条目必须带防线编号或设计步，二者至少一个，否则拒（§5.5 用同一条规则） |
| R8 | 正文过「自称已批准」检查（`api/internal/agentrt/store/claims.go:61-76` 的 `ApprovalClaim`），命中就拒 |

证据门（确定性）：

| # | 规则 |
|---|---|
| R1 | 出处可解析，并绑定版本：事件存在、产物存在、提交存在。提交可以在 main 上，也可以是运行时保全过的未合入提交（例如尝试推过的提交）；未合入的标「未合入」，不能写成已落地的事实 |
| R4 | 冲突（确定性部分）：按**条目键**查，不按适用范围查。同一个键已有有效条目、新条目又没声明替代它，记「冲突」并出卡。声明替代时，被替代的版本号必须等于当前版本，而且照样要复核。`decision_rationale` 引用的决定已被推翻，也记冲突 |
| R6 | 复核独立：确认它的复核，身份和厂商必须来自运行时尝试或受信的外部尝试（N14），不取自报；复核绑定条目的不可变版本、被审的提交和作者集合。同一家、身份缺失、厂商是自报、复核后换了稿，都判不通过。用的排除函数是 `route.go:318-353` 的 `exclusion`；`api/internal/agentrt/store/planobservations.go:441-442` 里还有一份 SQL 写的同一规则，R6 上线前要么合并，要么加一个契约测试证明两份结论一致 |
| R7 | 涉及人：按**数据类别**判，不按读者范围判。数据类别是「涉及人」的条目，要有 Owner 对这个条目版本的记录（他在卡上的回答或签收事件）才生效。不接受客户端传来的「Owner 已看过」布尔值；沉默不算看过。只限 crew 读的工程条目不送 Owner |

语义门（另一家审读，记成检查记录）：
- 是陈述，不是指令；
- 出处是否真的支持结论；
- 与已有条目在意思上冲突（结构门只查键）；
- 是否夹带对 Agent 的指令或伪装成规则。

这些格式检查判不了，只能由另一家审读给结论。

提示注入的测试用例（S7 验收用，§11.2）：
- 持久记忆被污染：一条坏条目进了包，之后每个任务都受影响；
- 出处合法但不支持结论；
- 写成陈述句的恶意文本；
- 伪造身份或伪造 Owner 确认；
- 跨人检索：按 A 的读者身份取到 B 的受限条目；
- 复核后换稿。

固定前言和「只能是陈述句」只是辅助，不是权限边界。工具授权始终在模型上下文之外由服务端执行。另一家审读有助于发现错误，但不证明判断正确，也挡不住所有注入；语义用例通过不能替代读写权限。

**Owner 的记录在它自己的作用域里最高。** 决定记录证明意图，签收证明验收，签名规则证明授权。它们不覆盖代码和运行事实。聊天里的原话只进受限存储，标为自述。依据：
- 问题的回答不是批准（W-65）；
- 记忆不是规则签名，也不是批准记录（`PLAN-memory-import-2026-10-24.md:46`）。

**Owner 的选择怎么变成 L3 事实**：§13 各项（以及以后同类的选择），Owner 的选择只有经计划改动卡或 `request_owner` 的答卡，才成为 L3 事件（`plan_change_decided` 带 `by` 和 `question_id`，`vocab.go:72`；`issue_owner_decided`，`vocab.go:54`）。统筹的决定记录引用那个事件编号。没有卡的，只能记成「统筹在约束内自定」。决定记录里写「Owner 已批准」一类的话，R8 和写入口的「自称已批准」检查会拒（`claims.go:61-76`）。

### 4.2 下行注入：服务端生成、可重放、守住私密边界

- **谁生成**：只有控制器在服务端生成上下文包。上传路由拒绝任何令牌外部上传这个种类。注意：`validateViewArtifact` 同时挂在内部写入（`PutArtifact`）和外部上传（`UploadArtifact`）两条路上（`store/write.go:45-48`、`:76-79`），所以「只许控制器写」要在校验里分开内外两条路，不能只靠种类名。
- **用什么种类**：不用 `brief`。用 `other` 加封闭种类 `agentrt.crew.context_pack/v1`（§5 的新命名空间）。`other` 会过本机路径扫描（`localpath.go:13` 的免扫描名单里没有它）。
- **`brief` 的口子另说**：今天 MCP 的 operator 令牌和席位令牌都能上传免扫描的 `brief`（§0 第 8 条）。这是现存的口子，建议统筹另登记技术债；上下文包不依赖它被修好。
- **包里放什么**：
  - 目标血统：北极星 → 轮 → 项 → 步，各自的标题和完成条件；
  - 最近的决定记录（事件编号和四样字段）；
  - 按适用范围命中的有效经验，只放公开条目和工程条目的正文；
  - 上一轮复核的「必须改」清单；
  - 同一步上的出门条编号；
  - 受限条目只放引用，引用里不带私人标题，也不带能反查的摘要。
- **指纹**：包的指纹绑定这些输入，做法同路由决定的指纹（`api/internal/agentrt/store/vocab.go:80` 的 `route_decided.fingerprint`）：
  - 生成器版本；
  - 源快照的截止点（读到的最大事件编号和读取时间）；
  - 每个条目的编号和版本；
  - 策略版本（读者规则、数据类别规则）；
  - 排序和截断规则的版本；
  - 接收者（主体和岗位）；
  - 省略清单：哪些条目因为权限、大小或状态没放进来，各自的原因用枚举写。
- **怎么交付**：任务说明里只放包的产物编号和指纹。执行者自己去取，取到后核对指纹。S8 之后，会话开始和压缩之后的钩子注入里也带这个指针（N16）。S8 之前，钩子注入的是决定正文和最近的出门条（§5.2），不等上下文包。
- **重放和再交付是两件事**：
  - 重放：把存着的旧包原样拿出来，给审计用；
  - 再交付：按当前的授权重新生成一份新包。
  - 撤销读权以后，之后的交付都不再包含相关条目；旧包里本来就没有受限正文，受限引用由专用读工具（B1）按当前权限拒读。旧包不能用来恢复读权。
- **大小**：按岗位设上限，数字等 S0 实测。
- 扩展参谋长现有的快照（`store/snapshot.go`），不另写一份生成器。
- **私密边界**（10-24 已定，这里只是落实）：
  - 私密条目由 B1 按接收者的身份取，不进通用的消息、简报、任务说明和卡片（`PLAN-memory-import-2026-10-24.md:86`）；
  - 厂商自己的记忆文件到第二阶段只留指针和公开索引，不再灌回私密正文（导入计划 §4，`:115-117`）。

### 4.7 夜间巩固与遗忘

夜间批次在平台的 workers 上跑，不在 MacBook 上跑。每一步失败只影响自己。

1. 核对收录水位：列出「未收录」的会话。
2. 按 T1、T2、T4、T5、T7 从当天的事件里抽候选；A1 建成后加 T3、T6。按 §4.1 的幂等键写。
3. 候选过期：14 天没入库的标「过期」。
4. 档案员的整理任务：本地 GPU 模型可以先出草稿，这一步可选。
5. 另一家的检查任务，加 R1 到 R8 的确定性检查。
6. 过期扫描：到了复核日期又没有新出处的，标「待确认」；待确认满 90 天的，标「退役」，只标记不删除。被注入后任务仍然失败的条目，也标「待确认」（§5.5 的退役信号）。
7. **撤销传播**：条目退役、冲突、被替代，或某个读者的读权被撤销以后，同步：
   - 公开索引和受限索引；
   - 之后生成的上下文包（旧包不改，见 §4.2）；
   - 公开文件的状态，经 N8 的落地路径改；
   - 审计记录保留。
8. 计数：已声明但未落盘的决定（§5.2）、压缩写点与压缩后回注的对账缺口、候选积压、提炼积压。
9. 合成早报：12 行以内，每行带读取时间。

**GPU 离线时只跳过第 4 步里可选的本地草稿。** 档案员改用订阅模型出草稿，或者不出草稿直接整理。第 5 步的另一家检查不依赖 GPU。没跑成的提炼记为积压：条数和最老一条的年龄，写进早报。早报照常出，但「早报没停」不等于「沉淀没有积压」。GPU 主机平时关机（陈述）。

## 5. 数据模型草图

原则：
- **先走 D-PV1 A 的路子，不加 DDL**：用 `other` 产物加 JSON 里的 `kind`；挂 `note.*` 事件到命名流上。
- **封闭种类只在新命名空间里**：今天 `validateViewArtifact` 只校验计划视图和外部工作说明两种 `kind`，别的 `kind` 或非 JSON 正文一律放行。这是有意保留的兼容（`api/internal/agentrt/store/planview.go:280-282`），现有规则提议就把 YAML 存成 `other`（`store/rules.go:450`）。所以本稿不全局收紧。新规则只管一个新命名空间：`kind` 以 `agentrt.crew.` 开头的 `other` 产物，必须是封闭清单里的一种，并通过它的格式校验；别的 `other` 照旧。命名空间的名字由统筹定（N6）。
- **不加 DDL 不等于不改契约**：事件正文是封闭词表（`vocab.go:95` 的 `verification_recorded`、`:162-168` 的 `note`），加字段是 Go 改动，要加契约测试。新增产物种类、消息种类、事件类型会撞数据库的 CHECK 约束，要迁移，所以尽量不加。
- 只有受限记忆（A1）、会话表（D-SS1 A，10-26 已定）、外部尝试（N14）和必须靠数据库强约束的东西才建表或改约束。

### 5.0 分类先于首次落盘

规则：
- 候选、草稿、检查答卷、出门条、报告，**在第一次存下来之前**就定好数据类别。
- **没分类就算受限**。
- 过滤只能把类别降为受限，不能升级。

### 5.1 线程信封（投影的输出，不是存储格式）

```json
{
  "seq": 34190,
  "at": "2026-11-03T01:54:00Z",
  "author": {"actor": "exec:codex", "kind": "executor", "provider": "openai",
             "provider_source": "runtime_attempt | attested_external | declared | unknown",
             "model": "…", "job": "reviewer"},
  "trust": "fact | observation | statement | derived",
  "kind": "task_spec | report | review | verify | exit_note | message.ask | message.handover | state | owner_signoff | decision",
  "ref": {"event_id": 34190, "artifact_id": "sha256:…"},
  "work": {"task_id": "t_…", "attempt_id": "a_…", "round": 2, "plan_node_id": "R5:…"},
  "data_class": "public | engineering | person | account",
  "summary": "≤ 200 字，从记录字段生成，不摘正文"
}
```

`author` **由认证的主体和绑定推出来**，不取正文里的自报。身份要分开三样，不能混成一样：
- **认证凭据**：请求用的令牌，说明是哪把令牌交的；
- **会话归因**：`X-Bifrost-Session` 会话头。它只决定「记在哪个线程名下」，不授予任何权限（`agentrtapi/propose.go:24-27`）。同一把令牌之下，换个会话头就能记到另一个会话名下，所以「自己的会话」靠它判定，只是卫生规则，不是权限边界；
- **受信的执行证明**：受管启动器经它自己的通道证明「启动了哪个执行器」，并绑定这件工作和产物版本（N14）。执行的 Agent 不能自己代报。

厂商也分三种来源：声明的（外部工作说明里写的，`declared`）、受信的（运行时尝试记录的，或受管启动器证明过的外部尝试）、未知（`unknown`）。只有受信的算数。`declared` 和 `unknown` 在独立性判断和中转度量里一律当作「证明不了」。

产物按内容寻址，同样的正文第二次上传什么都不存（`api/internal/agentrt/store/write.go:54-55`、`:92-96`），产物上只留第一个作者。所以**每次交付的作者取自点名这个产物的事件**（谁的事件引用了它），不取产物的创建者。

信封里的 `data_class` 只是显示用，保护靠 §5.0 的存放位置，不靠这个字段。

压缩钩子能拿到会话记录的位置和触发方式，会话开始的钩子能把输出注入上下文（厂商文档）。这两个钩子今天都没装（§0 第 7 条）。装钩子改的是 `agent-config/claude/**`，是治理文件，由 Owner 推，还要按 parity 改 Cursor、Codex 两侧（N16）。Codex、handin、agentd 没有压缩钩子，它们只有结束和收尾写点，列进 N16 的缺口清单。

**压缩钩子的失败语义**：
- 当前的厂商文档写着，压缩钩子可以用退出码 2 或 `decision: block` 阻止压缩（厂商文档，复核方引用）。SS0-S 要在固定的版本上核实。
- 本稿的设计是**默认不阻止压缩**：平台不通时阻止压缩，会把会话卡住。
- 写失败或超时：在本机留一个缺口标记，下一个钩子用同一个幂等键补写；补不上的算缺口，进早报。
- ACK 丢失：用同一个幂等键重试，平台按幂等返回原结果，不重复写。
- 对账：压缩写点的条数和压缩后回注的条数，按会话对一遍，不相等就记缺口。
- 所以「装了钩子」不等于「每次都写成了出门条」。

**止失忆靠什么**：
- 主力是两样：决定当场写进 L3（N9 的 `record_decision`），开工时读回来（N9 的 `get_decisions` 和会话开始的注入）。
- 压缩钩子只补两样：压缩那一轮的快照（提交、产物、开着的事），以及压缩后马上回注。它和结束钩子一样，发现不了没记下的决定。

**程序能保证的和不能保证的**：
- 能保证：有写入口和读回路径；写过的决定在新开、压缩、续接后都被注入正文；在受管决定入口上发生、却没有对应决定记录的，每条都变成一个计数事件，进早报（§12「已声明但未落盘决定数」）。受管入口：计划改动提议里统筹自定的、复核轮次的追加，以及**统筹把设计稿或改动交出去复核的那一刻**（handin、派活包装器、上传报告）：这时如果本会话在该计划节点下一条决定或核实结论都没记，计一条。最后这个入口专门对着 11-02 那两次：忘掉的是调查中得出的核实结论。
- 不能保证：不在受管入口上、也从没写下的决定，系统发现不了。「已声明但未落盘」为 0，不等于所有决定都记全了。这一块靠接手演练抽查（§11.4）。

计数事件用 `note` 事件加一个封闭字段写（Go 词表改动，`vocab.go:162-168`），不加 DDL。

### 5.4 收录回执（「先提后清」的机械依据）

回执绑定这些内容：

- **来源世代**：同名文件被截断重写、替换、轮换或恢复，就是新的世代；
- 内容摘要和分块摘要，以及覆盖的区间；
- 最终的封口水位；
- 每一段的处置：已接纳、扣下（withheld）、缺口（gap）；
- 收集器版本；
- 产出了什么：出门条、摘要、候选的产物编号，以及它们的版本关系。

规则：
- **平台只在目标产物和版本关系都写下之后才确认**。确认是平台事件，本机单方面写的不算。
- 回执上的三个状态分开：「已收集」「已提炼」「可清理」。只有「可清理」能授权删除。
- **清理时再核一次**：来源世代没变、末尾没长、会话已结束不再打开。任何一条不符就不删，保留原文件。重试是幂等的。
- 契约沿用 10-26 的 SS0-P（绑定事务）、SS1-H（EOF 转交、回执和缺口）、SS2-D（预留、提交、ACK、封口）（`CUT-session-stream-2026-10-26.md:421`、`:425`、`:426`）。S10 只为交接件实现这份回执；正文分段的回执仍在 S11，用同一份契约，不另起一套。
- 没收录的积压要有容量告警；满了就暂停新的采集，不承诺无限磁盘。

S10 的负测（§11.2）：错世代、文件被替换、漏了尾部、平台写入后 ACK 丢失、目标产物缺失、清理中途来源变了。还要一个阳性对照：全部条件满足时，文件确实被删。否则「什么都不删」也能通过全部负测。

### 5.5 经验条目（L6）

```yaml
id: K-123                  # 平台发号，与 TD 编号同一套发号器（R5:5.8 可复用，运行时）
key: lesson/route.go/independence   # 条目键：种类 + 主题键，冲突按它查（R4）
version: 3
kind: lesson | decision_rationale | preference | fact | procedure
statement: 一句陈述，不超过 200 字
scope: {repos: [...], paths: [...], task_class: [...], jobs: [...]}   # 检索范围，不是唯一命题
provenance: [{event_id: …}, {artifact: sha256:…}, {commit: …, repo: …, merged: true}, {decision: event_id}]
trust_of_source: fact | observation | statement
data_class: public | engineering | person | account   # 数据类别，R3、R7 按它判
readers: public | crew | owner_only | person:<编号>     # 读者范围，和数据类别分开
confirmed_at: …
confirmed_by: {check_event_id: …, checker_attempt_id: …, owner_record_event_id: …}   # 都是记录编号，不收布尔值
status: candidate | active | stale | retired | conflict
recheck_at: confirmed_at + 30 天
supersedes: {id: K-45, version: 2}
ratchet: RATCHETS#…        # T2 来的条目：ratchet 与 design_step 至少一个
design_step: R5:…
hits: {packed: 12, cited: 3, failed_after_inject: 0}
```

- `decision_rationale` 必须在 `provenance` 里带 `{decision: event_id}`，`statement` 只写「为什么」。
- `failed_after_inject`：条目被放进包、那个任务之后仍然失败的次数。过阈值就标「待确认」，这是退役信号之一。
- 公开条目存 infra `agent-config/knowledge/`，frontmatter 就是上表，git 历史就是修订记录。数据类别不是 `public` 的条目只存运行时受限结构（A1）或 crew 可读的运行时存储（工程类）。

### 5.6 知识候选

`agentrt.crew.knowledge_candidate/v1`，内容：
- 触发器编号、幂等键；
- 来源引用（事件、产物、提交）；
- 猜测的适用范围，用结构化字段（仓库、路径前缀、任务类别、岗位）；
- 类别枚举；
- 由谁生成。

T1、T2、T4、T5、T7 的候选只有引用和枚举，没有文字。T3、T6 的候选在 A1 建成后才有，只存受限结构。候选的过期、去重、升级规则见 §4.1。
