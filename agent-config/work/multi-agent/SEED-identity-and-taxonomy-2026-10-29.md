# 编号与归类（种子稿，2026-10-29，统筹与 Owner 讨论记录）

状态：**只讨论、不动手**。Owner 定：过渡期结束之后作为一个正式设计工作项打磨（盘点 → 本体讨论 → 设计稿 → 两轮复核 → Owner 签 → 迁移），不在过渡期内实现。

## 1. 起因

2026-10-29 Owner 问：「698、699、700 是按什么编的？ops.bifrost.lan 里要批的单也有编号，对不上；进度页里还有 B5-a、S6-3……」。盘点出约 30 种编号，分三类：

- **A 系统发号**（数据库生成，Console 有页或可查）：审批单 `#n`/`appr_…`、问题卡 `#n`/`q_…`、目标 `M-n`、任务 `t_…`、尝试 `a_…`、验收 `v_…`、落地操作 `land:t_…:k`、落地卡 `card:<seq>:<n>:<kind>`、计划步骤 `R4:4.1`、业务问题 `BI-n`、主机与座位、规则版本（`landing:dev v1`、`standing-envelope:dev v4`）。
- **B 工具产生**（不是给人看的）：提交 SHA、`Change-Id`、CI / 发布运行名、会话 id（`local_…`、CLI uuid）、Codex 工作目录号 `codex-work-n` / `RUN_KEY`。
- **C 文档里手工起的**：`W-n`、`TD-n`、防线条目、`LANE-…`、Gate A `Tn`、阶段 `S0–S7`、「第 n 轮」、里程碑（无号）、设计分块（`C-0…7`、`B5-a…h`、`S6-1…8`、`B1–B6`）、设计待决项（`F1–F4`、`O-1…`、`E1–E4`）、复核号与复核条目（`B-01`/`R-02`/`N-01`，不同报告重名）、测试编号 `T1…T81`、决策号（`D10`、`D-Journal-Stores`、「Work 609」）、文档章节 `CUT §11.15`、前端设计版本 `Rev .154` / `Package .26`。

三个症状：Owner 追踪的单位大多落在 C 类；A 与 C 之间没有对照；C 类手工发号，没有唯一性保证（10-29 `TD-452` 撞号；`B-01` 每份报告各一个；摘入集成分支后提交 SHA 全变，`fd5d7205` 与 `f2891105` 是同一件事）。

## 2. 已定的五条（Owner 2026-10-29「按照你的推荐来」）

1. **里程碑成为对象**（如 `MS-n`，挂在 `W-n` 下）；现在的进度页就是它的页面。
2. **设计分块强制成为计划步骤**；没有计划步骤的活不能派。
3. **每次 Agent 的活长期走运行时任务**；过渡期内外部工作先加「所属计划步骤」字段。
4. **技术债与决策分两步**：先能从 Plan 页链接过去，迁进平台以后再说。
5. **汇报方式立即改**：凡提到 C 类的号，先写 Owner 在 Console 能查到的号（目标、单号、问题卡、计划步骤），C 类号只作括注。

## 3. 初稿原则（待打磨，不是定论）

- 你追踪的东西必须是运行时对象：系统发号、一页、一个状态；手工号只是别名。
- 一条主干：`W → 里程碑 → 计划步骤 → 目标 M → 任务 t → 尝试 / 落地操作`；审批、问题、复核、债务都挂在某个节点上。
- 给人看的号只用「前缀 + 递增数字」；内部 id、SHA 只在详情页。
- 每种号只有一个发号人。

## 4. 打磨时要回答的深一层问题（Owner：「哲学思辨非常深，值得好好打磨」）

1. **身份、名字、地址、引用要分开**：不可变的身份（`appr_…`）、给人记的号（`#185`）、在树上的位置（`R4:4.1.C5`）、文档里的引用（`§11.15`）。现在常把四者混成一个，这是混乱的主要来源。
2. **本体（这个系统里有哪几种「东西」）**：目标、计划、任务、尝试、证据、决定、规则、事故、债务、发布……哪些是一等对象，哪些只是另一个对象的属性或附件。归类决定了人要记几种东西。
3. **按 Owner 的问题组织，而不是按实现组织**：Owner 问的是「要不要我出手、谁的事、做到哪、有没有风险、为什么」。每个问题应能从一个号出发一步答到。
4. **生命周期与号的关系**：一件事从提出、计划、执行、复核、落地、发布到观察，号要不要变？（落地操作 `land:t:k` 把父任务编进了号里；提交 SHA 在重放后会变而 `Change-Id` 不变——哪些号该随生命周期变、哪些必须不变。）
5. **作用域**：全局唯一，还是在父节点内唯一（复核条目 `B-01` 若写成「复核任务号 / B-01」就自然唯一）。
6. **跨域与平台通用性**：编号体系属于平台通用能力，不得知道 Trade / Research 的业务（双飞轮验证：平台换一个应用也能用）；三个域各自的业务号（例如 Trade 的订单）怎样挂进来。
7. **记忆与编号**：编号是记忆的键（包工队记忆是核心资产）；号乱，记忆就会烂。
8. **人的因素**：长度、能否口头说出、中文语境下怎么读、手机上怎么显示。
9. **演进**：号如何退役、合并、重定向；历史引用不能断。

## 5. 建议的打磨过程（过渡期结束后）

1. 自动盘点：扫代码（ID 生成处、前缀、正则）、扫文档与记忆（手工号），给出每种号的数量、发号人、出现位置。
2. 本体讨论：用几个真实场景与 Owner 走一遍（「昨晚发生了什么」「这张单为什么要我批」「C-5 做到哪了」），确定一等对象。
3. 设计稿 v1 → 两轮 Codex 设计复核 → Owner 签。
4. 迁移：先加别名与重定向，再改页面，最后退役旧号；历史引用不断。

与之相关：Design v3.6（Ops 界面）、TD-454（看不见的卡住）、包工队记忆核心资产、制度北极星。

## 6. Owner 补充：借鉴 Home 的多维度视角（2026-10-29）

Owner：「这个编号同时还可以部分借鉴 UI 里 Home 页面的多维度视角来考量……好的编号体系就是可以让人通过不同的维度了解到目前项目的状态。」任务先记下，过渡期结束后安排落地。

Home（Design v3.6，`design/ops/DATA-MAP-v3.6.md`）的看法：一句结论 → Only you → Since you last looked → 六个维度：**Projects、Team、Tokens、System、Data、Audit**。

对编号设计的含义（待打磨）：

- **号负责「是哪一个」，维度负责「从哪个角度看」**。不要把维度编进号里（`land:t_…:k` 把父任务编进号，一旦要按「谁在做」「哪个系统」「花了多少」去看，就得拆号）；每个对象带一组稳定的维度属性，页面按维度切片。
- **每种一等对象都应能回答六个维度中相关的那几个**：属于哪个项目 / 计划步骤（Projects）、谁在做（Team：哪位执行者、哪台主机、哪个模型）、花了多少（Tokens / 额度）、碰了哪个系统（System）、读写了哪些数据（Data）、谁批的、留下什么证据（Audit）。
- **Only you 与 Since you last looked 本身就是两个横切维度**：「是否等 Owner」「Owner 上次看之后是否变化」——它们应是对象的状态与时间戳，而不是另起一套号。
- 由此，盘点（§5 第 1 步）要同时记下每种号「能回答哪几个维度、缺哪几个」，作为归类的依据之一。
