# 调度脚本并排跑一周：办法

日期：2026-10-12。依据：Owner 当天 09:10「主线选 ②」——调度脚本第一片当作不可信的代码进主线，跟手工看板并排跑一周，
对不上的地方变成测试。这是 `TECH_DEBT.md` TD-319 第三个验收条件的做法。属于 W-66。

## 1. 要回答的问题

同一批真实的活，手工看板说什么，调度脚本说什么。每一处对不上，归到三类之一：

| 类 | 是什么 | 怎么办 |
|---|---|---|
| 脚本错 | 事件是对的，折叠出来的状态、起算时间、截断标记不对 | 先写一条会失败的测试，再修；记进 TD-319 |
| 看板错 | 手工看板说错了（第一个样本：2026-10-12 上午几轮共用完成标记，旧的几轮被显示成「进程不在了」） | 记为换掉手工看板的依据；看板的错只修到不误导人为止 |
| 两边的模型不同 | 两边都对，说法不一样（例如看板的「比往常慢」脚本里没有） | 写进对照表，以后不再算差异 |

三类都归不进去的叫**没解释的差异**。验收数的是它。

## 2. 事件从哪来——不包住真实的活

脚本的 `run` 不拿来包真实的任务：它出错会带倒任务，那就等于接了线。改用**影子进程**：

- 每派出一件真实的活，旁边用 `rec.py run` 起一个只做一件事的小进程：看着那件活的进程，活着它就活着，
  活结束了它用同一个退出码退出（退出码取自那件活的完成标记）。
- 这样脚本「记录一侧」的全部机制——运行目录、存活锁、开始和结束事件、观测——都在真实的时间线上跑，
  而且不经过手工看板的任何判断；脚本崩了，死的只是影子。
- 不是进程的步骤（等复核结论、等 Owner、手工关掉的步骤）由统筹方在改看板的同时调一次对应的记账命令。
  这一半两边的来源相同，能查出的只有折叠的错，查不出漏记。
- 事件放在本机的 `~/agent-work/shadow-recorder/`，不进仓库。

## 3. 怎么比

- 一张对照表把看板的步骤对到脚本的步骤，比四样：状态属于哪一类（没开始 / 在跑 / 结束且成功 / 结束且失败 / 等 Owner）；
  开始和结束时间（容差 60 秒，影子有至多几秒的滞后）；现在开着的 Owner 事项是哪几条；各自从几点起。
- 每 5 分钟比一次，另外每次记账之后比一次。差异写进一份只追加的日志，每条带两边的值和当时的原始事实
  （完成标记的内容、进程在不在）。
- 统筹方每天分一次类，报四个数：比了多少次、差异多少处、各类多少、没解释的多少。

## 4. 不许做的

- 页面、看板、流水线、任何 Agent 都不读脚本的输出来做决定（`agent-config/scripts/recorder/STATUS.md`）。
  比较工具是唯一获准的读者，它的输出只进差异日志和每天那四个数。
- 影子进程和比较不跑重活：不跑种错测试，不并行。

## 5. 做完的标准

连续 7 天，没解释的差异为 0。中间出现一处没解释的，修掉或解释清楚之后重新数 7 天。
最早的结束日期是工具做好那天加 7 天；工具（影子进程、对照表、比较、它们的测试）交实现者做，独立复核后才开始计日。

TD-319 另外两个条件不变：复核 113 的 3 处错修掉并过独立复核；没被拦住的种错清零。三样都成立，脚本才算可信，
`STATUS.md` 才改，页面才可以读它。
