## 2. 判定顺序（infra）

一次 infra 变更（运行时任务的 A，或待推的 R）依次经过下列层，**第一个失败的层给出拒绝原因**；后层不运行。每层的测试在 §13 构造「只有该层会拒」的样本。

| 层 | 在哪执行 | 内容 | 拒绝原因（`landing_refusal.reason` / CI 结果） |
|---|---|---|---|
| L0 入口 | platform | repo 在 `LandingRepos` 表内、该仓库 live、规则有效且含该 repo | `repo` / `live` / `rule` |
| L1 结构 | platform | 路径可解析（§3.1）、模式 `100644`、非符号链接/子模块、非二进制、无类型变更 | `floor{structural}` |
| L2 硬底线 | platform | 每个存在的端点不命中 §3.4 | `floor{hard}` |
| L3 变更类型 | platform | 只允许 A、M（§3.6） | `floor{change_kind}` |
| L4 规则路径 | platform | 每个端点匹配规则 `allow`（§3.5） | `floor{soft:[rule_paths], grant_supported:false}` |
| L5 单件上限 | platform | 文件数 ≤ 5、增删合计 ≤ 1500 行（§7.1） | `floor{soft:[size], grant_supported:false}` |
| L6 CI | ci-infra → platform 读回 | §5 全部阶段：范围复核、消费者、文档内容、Owner 决定证据、快测、静态、kustomize、code-health 差值、parity 静态 | 第二道闸 `ci_red` / `ci_unknown` |
| L7 全局 | platform 第二道闸 | 全租户日总额、该仓在途、发布窗口、main 仍为 `M0` | `limit` / `window` / `stale` 等现有原因 |

L1–L5 已在 platform 现有资格判定框架里（`landing/eligibility.go`、`rules/landing.go`），本稿只扩展其 infra 分支；`floor{...}` 细节字段区分 hard、structural、change_kind 与 soft，B3/B4 按现有 `failed{floor}` 处理。

## 3. 路径政策

### 3.1 端点语义（N-02）

- infra 的变更集合一律以 `git diff --no-renames -z --name-status <base> <commit>` 与 `--numstat -z` 读取，**不做改名检测**。于是每条记录只有一个路径：A（新增）的端点是新路径；M、T 的端点是同一路径；D 的端点是旧路径。改名表现为 D + A，复制表现为 A。
- 「空端点」不再是一个概念：每条记录恰有一个路径。**路径解析失败**才拒绝，归 L1 `structural{path_invalid}`：记录缺路径、含 NUL、以 `/` 开头、任一段为 `.` 或 `..`、不是 UTF-8。Git 不会产出含 `..` 的路径，这一条只能由路径解析器的**内层单测**覆盖（§13 T16），不拿它冒充 rename 的 hard 测试。
- 硬底线、规则路径、消费者读集都对**每条记录的端点**判定；D 的旧路径与 A 的新路径各自成为一条记录，所以「改名到硬底线路径」由 A 记录在 L2 拒，「从开放文件改名」由 D 记录在 L3 拒。
- platform 侧（核心）若对 platform 仓库保留改名检测，对硬底线的效果相同（两端都查）；本稿只约束 infra 分支与 ci-infra。

### 3.2 结构（L1）

非 `100644` 模式（可执行位、`120000` 符号链接、`160000` 子模块）、Git 判为二进制（numstat 为 `-`）、T 类型变更、路径解析失败，一律 `floor{structural}`。

### 3.3 文档内容（L6 中执行）

UTF-8 可解码、单文件 ≤ 256 KB、无 NUL。platform 只有 diff 元数据，内容检查只在 ci-infra 的 `doc-policy` 阶段做（§5.5）。

### 3.4 硬底线与 infra 信任闭包（L2；B-02 影响 S6 部分）

硬底线常量由核心统一维护（`api/internal/agentrt/rules/landing.go`，按仓库分表）；本节是 infra 表的权威内容。全部为**仓库相对全路径**，`**` 跨目录，`*` 不跨 `/`；「任意深度」表示按基名匹配。

| 类 | infra 模式 |
|---|---|
| 运行时清单 | `k8s/**`（全部：D10 两个补丁、Secret 示例、RBAC、NetworkPolicy、准入、Argo、Tekton） |
| 治理层 | `agent-config/**` 中除 `agent-config/work/**` 外的一切 |
| 脚本与构建 | `scripts/**`、`docker/**`、`config/**`、`Makefile`、`docker-compose*.yml`、`mkdocs.yml`、`requirements*.txt`、`.github/**`、`.gitea/**` |
| Git 行为文件（任意深度） | `.gitattributes`、`.gitmodules`、`.gitignore` |
| 编辑器自启动（任意深度） | `.vscode/**`、`.idea/**`、`*.code-workspace` |
| 指令入口（任意深度） | `AGENTS.md`、`CLAUDE.md`、`SKILL.md`、`*.mdc`、`.claude/**`、`.cursor/**`、`.codex/**`、`OWNER-STEPS-*`、`*RUNBOOK*`、`TICKET-*`、`REQUEST-*`、`RULE-*` |

### 3.5 第一批开放（L4，正向清单）

规则 infra 段 `allow` 只写下列六条，`deny` 为空（硬底线已在 L2 判过）：

```
agent-config/work/multi-agent/CUT-*.md
agent-config/work/multi-agent/DESIGN-*.md
agent-config/work/multi-agent/REPORT-*.md
agent-config/work/multi-agent/REVIEW-*.md
```

`*` 不跨 `/`，`reviews/*.md` 只含一层。名字同时命中 allow 与硬底线的（如 `reviews/SKILL.md`、`DESIGN-RUNBOOK-x.md`）由 L2 拒——这正好给硬底线提供不被 L4 遮蔽的测试样本（§13 T4）。

**不在第一批**：`agent-config/work/crew/**`（`PROFILE-*.md` 有读者）、`work/ops-arch/**`、`work/cursor-tasks/**`、`work/release-approval/**`、`work/multi-agent` 下其他名字（`PLAN-*`、`BRIEF-*`、`OWNER-*`、`P0-*`、`INVENTORY-*`、`CONTRACT-*`、`HANDOVER-*` 等）与全部非 `.md`（`PLAN-VIEW-R4-v1.json`、`benchmark/`、`d-l5-*/` 有读者）、`docs/**`。这些在以后逐个登记消费者后另议。

### 3.6 变更类型（L3）

首版只开 **A（新增）与 M（修改）**。D（删除；含改名产生的 D）在 L3 拒 `floor{change_kind}`。30 天样本里只有 1 个提交因此不过（§11）。理由：删除与改名会使其他文档、`PLAN-VIEW` 数据中的路径引用悬空，而首版不做引用完整性检查；需要删除或改名时由 Owner 手推。

### 3.7 单件上限（L5）

infra 每仓 limits：`max_files: 5`、`max_changed_lines: 1500`（增删合计，按 numstat，二进制不计入但已在 L1 拒）。另受 256 KB（§3.3）、CI 全部阶段（含 code-health 差值）约束；见 §5.6 与 §16 F2 的说明：**单件上限之内的大报告也可能因 CI 不过**。

### 3.8 infra 不支持 grant（R-05）

- `LandingRepo` 表（§8.1）每项带 `GrantSupported bool`；infra 为 `false`。该表在 `api/internal/agentrt/landing/**`，属核心 hard。
- 资格判定对 `GrantSupported=false` 的仓库：L4、L5 的软失败**直接终态** `failed{floor}`，`detail = {soft:[...], grant_supported:false}`，不写 `awaiting_approval`、不准备 R、不建单（要求核心的 awaiting 状态机按 `GrantSupported` 分支，§14.2）。
- 授权动作（核心的 `approve_guardrail_landing`）的服务端建单校验：任务所属仓库 `GrantSupported=false` 时拒绝建单，原因 `grant_unsupported`，零审批记录。消费侧（第二道闸）对该仓库不读 grant。
- 超出 §3.5–§3.7 的 infra 修改：**合法拆分**（例如把 7 个文件拆成两件、每件 ≤ 5），或由 Owner 照现行流程手推（`push-main.sh`，带 Codex 复核）。v2 中「Owner 推或走 D 级单」「超限走 D 单」「与核心 D override 联测」全部删除。
- 以后若要 infra 尺寸豁免，另写仅限六类文档、仅豁免 `size` 的能力矩阵，并单独复核；不在本块。

## 4. 机器消费者：封闭登记（B-06）

### 4.1 原则

v2 想用字符串字面量的词法扫描「证明没有动态消费者」，679 证明它既会误拒（`scan.sh` 的 `'*.md'`）也证不了（相对路径、拼接、变量、遍历）。v3 不再声称证明，改为：

1. **登记**：把 infra（及 CI 能检出的 platform）中所有「可能读 `agent-config/work/**`」的程序列成封闭登记表，每项由人核实类别；
2. **棘轮**：CI 用保守的发现信号扫描整棵候选树，凡命中而未登记、或已登记但命中行内容变了，**整条 infra 落地通道变红**，直到 Owner 推登记更新（登记文件是硬底线）；
3. **具体校验**：登记中「行为型读者」的读集用候选树上的**具体文件**与开放集合求交，交集非空即红；不做 glob 代数；
4. **如实承认剩余信任**（§4.5）。

### 4.2 登记文件

`agent-config/landing/doc-consumers.yaml`（新，硬底线）。每项：

```yaml
- file: scripts/release/test_dl5_approval_consistency.py   # 仓库相对路径；跨仓写 repo: bifrost-platform
  class: reader            # reader | constraint | skip | data | mention | token
  reads:                   # 仅 reader：读集，仓库相对路径或 glob（* 不跨 /）
    - agent-config/work/multi-agent/d-l5-2026-10-25/*
    - agent-config/work/multi-agent/TICKET-D-L5-landing-s0-2026-10-24.md
  effect: test             # runtime | tool | test | ci-check（仅说明，供复核）
  hits: sha256:…           # 该文件全部命中行（去首尾空白、排序后以 \n 连接）的哈希
  why: "D-L5 审批正文与 SQL 一致性测试"
  checked_by: "Codex 复核 #<n>"   # 登记或更新时的复核记录
```

类别含义与对开放集合的影响：

| 类别 | 含义 | 对开放集合 O |
|---|---|---|
| `reader` | 读取 `work/**` 下具体文件并据此改变行为（运行时、工具或测试的判定） | 读集必须与 O 不相交（§4.4 不变式） |
| `constraint` | 全树内容检查，只能让 CI 失败、不能授权或改变运行时（例：`test_no_exam_keys.py`、`code-health/scan.sh`） | 允许读 O；其结果并入 L6 |
| `skip` | 只为排除该目录而写出路径（例：`check_hardcoded_paths.py` 的 `SKIP`） | 允许 |
| `data` | 数据文件里以字符串记录路径，读它的程序另行登记（例：`PLAN-VIEW-R4-v1.json`、platform `planview/testdata`） | 允许；若其读者解析这些路径，读者按 `reader` 登记 |
| `mention` | 注释、文档字符串、报错文本中提及 | 允许 |
| `token` | 命中的是单词 `work` 而非该目录（JSON 键、夹具临时目录名） | 允许 |

### 4.3 发现信号与棘轮（`scripts/landing/doc_consumers.py`）

扫描范围：候选树 R 上**所有被跟踪文件**，排除 `agent-config/work/**/*.md` 文档本身；`.md` 中只扫指令入口名（`CLAUDE.md`、`AGENTS.md`、`SKILL.md`）与 `*.mdc`。另扫 CI 工作区里固定提交的 platform 检出（只用 S1）。

- **S1 目录引用**：行内出现 `multi-agent`、`agent-config/work`、`work/multi`，或作为独立路径段的 `"work"` / `'work'` / `/work/`（覆盖 `ROOT / "agent-config" / "work" / "crew"` 这类拼接）。
- **S2 全树遍历**：行内出现 `ls-files`、`git grep`、`rglob(`、`os.walk(`、`.glob(`、`readdirSync`、`filepath.Walk`、`WalkDir`、`find .` / `find "` / `find '` / `find $`。

判定：

1. 命中而未登记 → 红 `unregistered_consumer <file>:<line>`。
2. 已登记但 `hits` 哈希与当前命中行不符（新增、删除或改写了命中行；行号移动不算）→ 红 `consumer_changed <file>`，要求重新核实并更新登记。
3. 登记项文件已不存在或已无命中 → 只告警 `registry_stale`（不影响安全，由下次登记更新清理）。

**为什么这是棘轮**：新增消费者只能出现在硬底线路径里，由 Owner 推。即使 Owner 推入时没有更新登记（`push-main.sh` 不等 infra CI），下一件 infra 落地的 CI 在 R 的整棵树上运行发现，立即变红，**整条通道失败关闭**，直到登记更新。不会出现「未登记的读者与开放文档同时进 main」。

2026-10-28 在 `85f578e` 实测：S1 命中 43 个文件、S2 命中 64 个、去重 **100 个**；platform `cb47820d` 的 S1 命中 5 处。首版登记全部 100+5 项（§12 给出分类）。其余 9 个工作区仓库（core、worker、api、frontend、research、ui、三个插件）的本机检出用同一 S1 模式只读扫描为 0 命中；这些仓库不在 CI 检出里，属剩余信任（§4.5）。

### 4.4 具体校验（`doc_policy.py consumers` 子阶段）

在 R 上：

- 记 T = R 上全部被跟踪文件 ∪ 本次变更 C 的全部端点。
- **不变式**：对每个 `reader` 的每条读集模式 r、T 中每个匹配 r 的路径 p：p 不得匹配 §3.5 任一 allow。违反 → 红 `registry_overlap <reader> <p>`。这条保证「开放集合与读集不相交」在每一次落地时用真实文件重验，不依赖一次性的人工判断。
- **变更检查**：C 中任一端点匹配任一 `reader` 读集 → 红 `consumed_path`（与不变式重复，作纵深防御；在当前登记下不可达，只做内层测试）。
- allow 模式从 **M0** 的 `agent-config/agentrt-rules/prod/landing-dev.yaml` 读取；与 PROD 签名生效的规则不一致时两者都要过（platform L4 用签名规则）。

### 4.5 剩余人工信任（如实）

封闭登记**不是**机械证明。仍依赖：

1. **发现信号的覆盖**：字符串拼接（`"multi" + "-agent"`）、环境变量或命令行传入的路径、从网络读取路径等，S1/S2 都看不到。缓解：infra 全部可执行内容都在硬底线路径，只能由 Owner 推、带 Codex 复核；复核清单加一项「本变更是否读取 `agent-config/work/**`？是则同提交更新 `doc-consumers.yaml`」。
2. **登记类别的判断**由人（复核者）给出；`hits` 哈希只保证「判断之后命中行没变」。
3. **不在 CI 检出里的仓库**：其他 9 个仓库与仓库外工具（`~/agent-work` 下脚本、记忆）只做了一次性扫描。缓解：开放文档不进任何镜像、ConfigMap 或 Argo 同步对象（`85f578e` 的 `k8s/**` 无对 `agent-config/work` 的引用；`docker/**` 无 COPY），运行时读 infra 的只有 platform 的三条 Gitea 读取路径（§12 platform 段），都指向硬底线文件。
4. **LLM 读者**：Agent 会把这些文档当参考材料读入上下文。这是 F1 的范围（§4.6）：文档不产生授权，Owner 决定须带证据，复核者核对。

### 4.6 Owner 决定的证据（F1 A 的机械下限，`doc_policy.py owner-claims` 子阶段）

范围：C 中所有开放文档的 `M0..R` diff。

- **决定标记行**：新增或删除的行，匹配 `Owner\s*(的)?\s*(决定|已定|采纳|批准|签收|拍板|点选|定了|同意)`，或位于标题含「Owner 决定」的小节内。
- **新增标记行**须在同一段落（相邻非空行）内带至少一个证据标记，否则红 `owner_claim_unlinked <file>:<line>`：

| 证据形式 | 机械核验 |
|---|---|
| 审批 / 请求单号：`(审批|单|request|approval)\s*#\d+` | 只核格式（CI 无审批库权限）；真实性由复核者核对 |
| 线程原话时刻：`线程` 与 `\d{4}-\d{2}-\d{2} \d{2}:\d{2}`（CDT） | 只核格式；复核者核对 |
| 已有决定记录：`<文件名>.md §<编号>` | 该文件在 **M0** 存在，且 M0 中有以该编号开头的标题；指向本次新增小节的不算 |
| 提交：7–40 位十六进制 | 在 infra 的 M0 祖先或 platform 固定提交的祖先中存在 |

- **删除标记行**（改写或移除已有决定）：同一 hunk 内必须有带证据的新增行，否则红 `owner_claim_removed`。
- CI 日志输出全部标记行与证据，标准评审 spec（核心 §2.4 的服务端生成 spec）对 infra 文档任务加固定一项：「逐条核对 owner-claims 列表中证据的真实性与是否支持该文字」，复核结论缺此项视为未完成。
- 这是**下限**：措辞不含标记词的决定（如「他点了 A」）抓不到，依赖复核者；误报（引用别人的决定作背景）补一个证据即可。

### 5.6 code-health：以 M0 为基线的差值（N-03）

2026-10-28 在 `85f578e` 实测 `scan.sh --repo bifrost-trade-infra`：infra 三项指标已超 `baselines.env` 的绝对基线——`files over 500 lines` 52 / 3、`duplicated function names (infra-py)` 34 / 1、`duplicated shell function names` 10 / 3。infra 今天不在 `push-main.sh` 的 `GATED` 表里，所以这些从未被门禁过。若 ci-infra 照 v2 直接跑 `scan.sh`，每次运行都红，通道永远开不了。

### 7.1 规则 schema

- 规范序列化：签名覆盖原文字节；解析后按仓库展开有效值用于比较。
- `landingTightens`：逐仓比较展开后的有效值——总额只降、每仓单件与在途只降、仓库只减、allow 只减；**已有 deny 不得删除**；`stg_release` 只能保持或向 `none` 收紧；`repo` 只能是 `LandingRepos` 的键。任何一项升高或新增仓库都是放宽，需要签名。
- 每仓**日**额度本版不加；以后若加，只是附加上限，总额照旧在额度流里串行预留。

### 7.2 计数维度

- 总额：`ReservedToday` 读当天额度流 `landing-quota:<tenant>:<UTC 日>`（跨仓库），现状不变。
- 在途：`OtherInFlight` 读 `landing:<repo>`（`store/landingfacts.go:104` 已按仓库）；须核对所有调用者传对 repo：`landingFactsDB`、`AuthorizeLandingPush`、`ClaimLanding`/`ClaimLandingDrill`、`SettleUnclaimed`、`ReconcileMain`/`ReconcileDenied`、卡片结算（`HandleLandingAnswer`）。

### 7.3 锁资源表（全部落地操作）

全局顺序：**能力（共享）→ 租户落地规则（共享）→ 计划节点 → 任务 → mission → 当天额度流 → 仓库落地流（多仓按仓库名字节序升序）**。任何操作不得在持有仓库流后再取前面任何一级；不需要额度的操作不取额度流。

| 操作 | 取锁（按序） | 备注 |
|---|---|---|
| 领取（`ClaimLanding`/`ClaimLandingDrill`） | 能力 → 规则 → 节点 → 任务 → mission → 本仓流 | 不预留额度 |
| 候选准备代（核心 v3） | 任务 → mission → 本仓流 | 只写准备记录 |
| 第二道闸（`AuthorizeLandingPush`，含 grant 消费） | 能力 → 规则 → 节点 → 任务 → mission → 额度流 → 本仓流 | 唯一预留额度的操作；跨 UTC 日整体回滚重判（`ErrLandingDayChanged`）保留 |
| grant 建立 / 撤销（核心；infra 不适用） | 任务 → mission → 本仓流 | infra 在取锁前即以 `grant_unsupported` 拒 |
| 卡片答复（`HandleLandingAnswer`） | 任务 → mission → 本仓流 | — |
| 首次领取窗口结算（`SettleUnclaimed`） | 任务 → mission → 本仓流 | 每仓独立一轮 |
| 对账（`ReconcileMain*`、`ReconcileDenied`） | 本仓流 | 不取绑定锁；只读 main |
| 模式写入（`EnsureLandingMode`） | 本仓流 | 每仓独立 |
| B4 收尾（`CloseMissions` → `landingCloseB4`） | mission（`FOR NO KEY UPDATE`）→ 它承载的各仓流按字节序 | 见 §7.4 |

### 7.4 多仓 B4

- mission 承载的仓库集合 S = 其 `implement` 根的 `task.repo` 中属于 `LandingRepos` 的那些；不在表内的仓库沿用旧的 `landingHolds` 逻辑。

- S 部分 live：live 的仓库走 B4 判定，非 live 的走旧 `landingHolds`；任一方说「持有」，mission 保持 active（保守合并）。
- 迭代顺序由排序后的切片决定，不用 Go map 迭代。

## 17. 仍有的风险

1. **消费者发现是启发式**：动态构造路径、仓库外工具、CI 未检出的 9 个仓库不在机械覆盖内；缓解是硬底线 + Owner 推 + Codex 复核清单项 + 「未登记即全通道红」的失败关闭，但不是证明（§4.5）。
2. **日总额是真正瓶颈**：总额 5 与 platform 共用，30 天里单日最多 38 个文档提交；开门后 Owner 手推减少的幅度受它限制，提高总额需另行决定。
3. **owner-claims 的正则**会漏掉措辞不同的决定、也会误报背景引用；真实性完全依赖复核者。
4. **infra code-health 绝对基线已失真**（52/3、34/1、10/3）：本块只加差值门禁、不动基线；该偏差须在实施时登记为技术债，否则以后有人把 infra 加入 `push-main.sh` 的 `GATED` 会立刻全红。
5. **核心 v3 同时修订**：§14.2 列出的契约若在核心 v3 中改名或改语义，S6-1/S6-2/S6-6 需要跟随；语义冲突回统筹裁定。
6. **工具镜像与 Tekton 变更都要 Owner**（硬底线），镜像摘要更新、kubectl/Go 升级都是一次 Owner 推 + 构建 + `apply`。
7. **agentd 与 CI 的 Python 包安装来源不同**（PyPI 与镜像内 wheelhouse），版本与哈希相同；若以后有人只改其一，金样测试不会发现——`requirements.lock` 与 `infracheck` 的包清单由 `test_ci_infra_pins.py` 交叉比对（实施时加入）。
8. **30 天粗算**是在没有落地通道时的提交习惯上算的；开门后统筹会改写批次方式，实际数字以开门后 14 天实测为准。
