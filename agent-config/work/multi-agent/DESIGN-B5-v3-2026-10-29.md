## 0. 一段话

B5 是 PROD workers 里的一个循环，与落地共用仓库流 `landing:bifrost-platform`。它把已落地、在 main 上有效、还没发到 STG 的成果攒成批：
1. 持发布窗口，为 main 头 P 选出恰以 P 为 revision 的 CI（得到 U），冻结完整的创建输入（P、U、infra SHA）。
2. 证明 P 相对**可信部署基线**的每个提交都有落地授权、每个未交付成果都在本批预算里、部署方向只前进不回退。
3. 用带 finalizer 的确定名字起 `bifrost-deliver-platform`。
4. 从该 run 自己的子任务结果、严格的工作负载摘要判定（现有 `PodDigests`）和 STG 健康检查核验，逐个成员结算。

失败重试按成员记账，最多 3 次，换批不清零；不可重试或用完就进阻断区间并发卡。任何人手动发的 STG，只要证据完整，也结算为这些成员的交付。

签名规则对该仓库是 `stg_release: none` 时，B5 **不创建任何发布**；只读对账（观察已有 run、外部发布取证）照常记录事实（676 N-02）。

| `diag`（batch） | `try`、`what ∈ {lease_lost, running_long, verify_unknown, ci_waiting}`、`gen` | 任意非 CLOSED | `(what, try, gen)` 一次 | 诊断，不改阶段 | 状态展示 |

转移要点（全部由 `checkStgReleaseAppend` 校验）：
- 批次阶段：OPEN → SNAP(try) → STARTED → [bound] → 终态（`run_evidence`）→ `verify` → 成员去向 → `settled`。
- `retry` → 新的 `snapshot(try+1)`，inputs 必须与 try=1 相同。
- `unsent` 结束 try 但不退款。
- `quarantined` 只能由 `run_evidence`（对象重新出现且有终态）或 `quarantine_closed` 解除。
- `settled` 只收口：每个成员的去向都要先由 `member` 写下（676 B-02 第 4 点）。

### 2.4 折叠

`store/stg_release.go`：`StgFold(events) → {batches, members(按 (root,op,R)), budget(按 (R,gen)), grants, withheld, blocks(open/closed), evidence(按身份), covers}`。确定性、无进程内状态；每个断点重启回放的结果都相同（676 B-02 最低验收）。

## 3. 待发布、开批、首次启用

### 3.1 待发布集合

`(root, op, R)` 同时满足以下条件：
- 最新落地操作 `landed`，最新有效性证据 `effective`；
- 落地时间晚于 STG 栅栏（§3.3）；
- 没有 `delivered`、`covered`、`disposed` 或 `withheld` 去向，不在未关闭批次里；
- 当前代际有余额，不在开着的阻断区间涉及的集合里。

### 3.2 开批条件

`env=prod && live && 规则对该仓库 stg_release≠none && 无未关闭批次 && 待发布非空 && (没有活动落地 || 最老成员等待 ≥ 20 分钟)`；成员 = 当前全部待发布。`first_pending_at` 从成员首次进入待发布起算，换批不重置。

### 3.3 首次启用（none → 非 none）

- 规则第一次对该仓库给出非 none 时，B5 在流锁下写一条 `blocked` 以外的普通落地记录 `stg_enabled{rule_version}`（新增到 `note.landing`，与 `enabled` / `mode` 同类，只写一次）。它的时间就是 STG 栅栏。
- 栅栏之前落地的成果：
  - 所在 mission 仍开着 → 也进入待发布（B4 按当前规则判，它们需要 STG 才算交付）；
  - mission 已关闭 → 不进入，历史分类不变，不重开（676 N-02）。
- 首次启用时没有可信基线（没有 `evidence`）→ 读 `releases.Current`；`ErrUnsettled` 时写 `blocked{baseline_unknown}`，等一次外部发布建立基线。

## 4. P 与 U（676 R-02）

1. 持窗口（§11），读 main 头 → P；本批第一次选 P 时写 `p_selected`。
2. 列 `cicd` 中 `pipelineRef.name=bifrost-ci-platform`、参数 `revision==P`、`repo-url` 参数为 platform 仓库的全部 PipelineRun，分页读全。
3. 按 `creationTimestamp` 取**最新**一次；同一时刻有多次时，结果全相同取名字字典序第一，不同则为 unknown。
   - **最新一次是 Running / Failed / Unknown**：即使更早的一次绿，也等待（Failed 写 `blocked{ci_red}`）。
   - **最新一次 Succeeded**：`platform-commit==P`，`ui-commit`、`infra-commit` 为 40 位小写 SHA，每个结果名恰好出现一次；任何缺失、重复或非法都不采用，写 `blocked{ci_results}`。通过则写 `ci_accepted`，U = `ui-commit`。
   - **没有任何 CI**：等推送触发的 CI；从 `p_selected.at` 起 30 分钟仍没有 → `blocked{ci_missing}`。
4. **快照之后出现同 P 的新 CI**：
   - 同 U 且成功 → 追加 `ci_accepted`，核验时接受任一已接受的 CI；
   - 同 U 但 Running / Failed → 当前 try 不受影响（创建输入已冻结），下一 try 的最终闸等它有结论；
   - 换了 U → 不改快照：SNAP 未 started 时立即交接（成员 `released`，批次 `settled`，新批重新选 P、U）；已 started 的跑完后再交接。
5. `infraRevision` 取 `ci_accepted.infra_commit`（被测输入与交付输入一致）。

## 5. 发布授权：针对整个 P（666 B-03、676 R-07、C 块）

### 5.1 逐提交授权

可信基线 `base.P`（§5.3）到 P 的每个提交 c（`git rev-list --first-parent base.P..P`）：
- **出现合并提交就整体阻断**：`blocked{non_linear}`，main 只接受快进。
- c 带 `Landed-By: agentrt-prod/<op>` 尾注，且落地流里 `<op>` 有 `landed{R=c}` → c 是**落地提交**，它的授权按落地时记下的依据判：
  - 规则授权：该 op 的 `landing_gate` 记了规则版本，且**当前**规则（`stg_release≠none`）对 c 的改动 `CheckChanges` 仍通过；
  - override 授权（C 块）：该 op 有一致的 `landing_override{task, attempt, commit, approval_id, paths_digest}`，且其审批参数含 `stg: true`（见 §16 决定 O-1）；
  - 所属 mission 当前不是 `no_merge`，计划步骤未撤。
- 否则 c 是**非落地提交**（Owner 手推，例如硬底线改动、紧急修复）。

### 5.2 阻断与停发的区别

| 情况 | 处理 |
|---|---|
| 有非落地提交 | `blocked{diff_unlanded}`；人工发布（外部证据）把基线推过它后解除 |
| 落地提交的当前规则不再允许（规则收紧、过期、缺失、读不到） | `blocked{rule}`；规则变化后解除。**不停发**，不让 B4 关成 stopped |
| 落地提交触到硬底线（`LandingFloorHard`，C 块 §2.5） | 成员 `withheld{hard_floor}`，整个快照阻断，直到人工发布 |
| 成员 mission 在落地后被标 `no_merge` | `blocked{no_merge_after_landing}`；人工发布或受检撤销后解除 |
| 被**落地提交**撤销的成员 | 两个提交都有授权，可以一起发出；被撤销的成员记 `member{disposed}` |
| 被**非落地提交**撤销 | 走「有非落地提交」那一行（676 R-07 的保守规则） |

### 5.3 可信部署基线

- 基线 = 最近一条 `evidence`（自动或外部均可，`deployed.pin_sync_ok` 且工作负载判定通过）的 `(P, api_digest, console_digest)`。首次启用见 §3.3。
- 不使用 `Deployed("stg")`（`server/agentrt_sources.go:88`）：它把 unsettled 压成 false，失败之后的下一次就永远起不来。

### 5.4 部署方向（676 B-04）

最终闸要求同时满足：
- `base.P` 是 P 的祖先或等于 P（`git merge-base --is-ancestor`）；
- 当前工作负载的 `PodDigests` 判定结果等于基线的 `api_digest` 与 `console_digest`（STG 没被别人改过）。

不满足 → 不创建：
- 工作负载等于某条更新的 `evidence` 的摘要 → 先结算那条证据，基线前移，重选 P；
- 工作负载哪条证据都对不上 → `blocked{baseline_moved}`。

**永远不自动发布 P 的祖先或分叉。**

## 6. 预算（666 B-02、676 B-03）

1. **集合 S**：最终闸内求 P 中「已落地、未交付」的成果，即 `base.P..P` 中落地提交对应的 `(root, op, R)`，排除已有 `delivered` 或 `covered` 的。**已在可信基线内交付的历史代码不在 S 里，不重复扣款**。
2. **S 必须 ⊆ 本批成员**。S 有不在本批的成果（后到的 R3）→ 不创建，本批交接（成员 `released`），下一轮重开，把 S 全部纳入。
3. **S 的每个成员都要有余额**：已用次数 = 该 `(R, gen)` 在所有批次里不同 `(batch, try)` 的 `started` 数。任何成员已用满 3 次，或处于 `withheld`，就整体阻断：`blocked{budget_exhausted}`，发 `stg_failed` 卡。不承诺「其余成员一定继续自动发」（676 决定 4 的条件）。
4. **扣款**：`started` 写入时，存储层重算 S 中每个成员的已用次数，写入 `spend`；超额拒绝。`resend` 不扣；`unsent` 不退。
5. **退避**：同一成员两次 `started` 之间至少 10 分钟（第 1→2 次）、30 分钟（第 2→3 次），跨批、跨代际都算，起算点是上一次 run 的终态时刻（长时间运行的 run 结束后才开始计）。
6. **授权**：`granted{gen+1}` 绑定问题的 `trigger_seq` 与精确成员。重复处理、Ack 失败后重读，都不再加额度。已有去向的成员不复活（答复时现读）。

## 7. 创建、发送许可与恢复（676 B-01、B-06）

### 7.1 最终闸（首次发送与每次恢复都走）

1. **无锁慢读**（全部有界）：main 头、CI 列表、P 的提交与差异、工作负载判定、窗口记录（含 resourceVersion）。
2. **事务**：
   1. 从库里发现绑定：S 与本批成员对应的 task、mission、计划步骤；
   2. 按全局锁序加锁：capability → 规则（`landing:<tenant>`）→ 步骤（按 id 排序）→ 任务（排序）→ mission（排序）→ 仓库流（沿用 `store/landing_live.go:45–124` 的顺序）；
   3. 锁后重读绑定：集合与第 1 步不同 → 回滚、重来（不在持着流锁时补加前置锁）；
   4. 取一次 `at := DecisionAt()`，按 `at` 重选现行规则，重算 §5、§6 与 `not_before`；
   5. 核对窗口：第 1 步读到的租约在 `at` 未过期，who / what / env 精确匹配本 try，租约代际等于本进程持有者的当前代际；
   6. 全过 → 写 `started`（或恢复时写 `resend`），`deadline = min(租约到期, at + 2 分钟)`。
3. **发送**：提交后检查 `now < deadline`，且租约持有者的当前代际仍等于记录的 gen；否则不发，交给恢复。回包不明 → 先 GET 同名，不在事务重试回调里创建。

锁序与其他写者：
- B4 Close：mission → 仓库流；
- B3 答复：任务 → mission → 仓库流；
- 外部取证：只锁仓库流；
- B5 的授权写入（`granted` / `withheld`）在 B3 答复事务里。

四者与上面的顺序一致，不会反序等待。

### 7.2 名字、标签、注解、指纹（676 R-01）

- run 名：`stgrel-<n>-<try>-<P 前 8 位>`，n 为批次序号，只含 `[a-z0-9-]`，≤ 40 字符。
- 标签：`bifrost.io/stg-release=true`、`bifrost.io/stg-release-n=<n>`、`bifrost.io/stg-release-try=<try>`。
- 注解：`bifrost.io/stg-release-batch=stg:bifrost-platform:<n>`、`bifrost.io/stg-release-intent=<intent_seq>`。
- finalizer：`bifrost.io/stg-release-hold`。
- 指纹：`sha256(规范 JSON{namespace, pipeline, params_canonical, labels, annotations})`。
- 首次 Create 的返回对象与之后 GET 的对象，名字、指纹、注解都相符才写 `bound`。
- 外部字符串用真实的 Kubernetes 校验函数做单测（676 R-01：假 client 不校验标签）。

### 7.3 恢复判定表

| 观察 | 处理 |
|---|---|
| 未绑定，GET 404，最近许可的 deadline 未过 | 等（原调用者可能在途） |
| 未绑定，GET 404，deadline 已过 | 有 finalizer 保证（§7.4）：对象从未被创建。重走 §7.1：通过 → `resend` 后发送；最终闸不通过（规则撤回、关 live、窗口失效）→ `unsent{gate_failed_before_send}`，try 结束、扣款不退，成员按 §9 交接 |
| 找到对象，名字 / 指纹 / 注解相符 | `bound`（对象处于 Terminating 也照样绑定、取证，然后摘 finalizer） |
| 同名但不符 | `quarantined{collision}`；不修改、不接管；发 `stg_blocked` 卡 |
| 已绑定，GET 404 | 只有 finalizer 被强行摘掉才会发生：`quarantined{object_lost}` |
| 403、超时、其他读错误 | 未知：等待重读，不写任何结论 |
| Create 返回 409 | 走 GET，按本表处理 |

隔离的出口：
- 对象重新可见并有终态 → `run_evidence` 正常继续；
- Owner 在卡上选「接受未对账风险」→ `quarantine_closed`。卡面明说「旧执行未对账；关闭只解除占位，不代表已核实」。
- 普通的 ack 或另一次发布成功，**都不能**关闭隔离（676 B-01 第 3 条）。

### 7.4 finalizer 的取证与摘除

- `run_evidence` 写入（终态 + 原始结果）后，B5 用 JSON Patch（带 resourceVersion）摘掉 finalizer。
- 摘除失败不影响结论，下一轮重试。
- 绑定后超过 30 天仍摘不掉 → `diag` 并告警。
- 开门前探针：platform SA 能否带 finalizer 创建 PipelineRun（准入策略 `k8s/platform-rbac/40-admission.yaml`）、能否 patch 摘除。

### 7.5 finalizer 不可用时的后备（O-2 选 B）

未绑定的 404 一律不当作「未创建」：直接 `quarantined{unknown_execution}` 并发卡，由 Owner 人工发布并接受风险。不自动补建。

## 8. 观察、证据、核验（676 B-05、B-07）

### 8.1 观察

- 按 UID 读 PipelineRun 的 `Succeeded` 条件。
- 终态时同事务写 `run_evidence`：带 `status.results`、`status.childReferences`，以及每个子 TaskRun 的 `status.results`、`spec.taskRef`、`params`、`ownerReferences`。之后才可能摘 finalizer。
- 读不到 → 不写，重读。

### 8.2 证据判定（自动与外部共用）

1. **子 TaskRun 归属**：
   - 从 PipelineRun 的 `childReferences` 取 `{name, pipelineTaskName}`；
   - TaskRun 的 owner UID 等于 run 的 UID，`taskRef` 等于流水线定义；
   - `clone-platform` / `clone-ui` / `clone-infra` 的仓库 URL 参数分别是对应仓库；
   - 每个 `pipelineTaskName` 恰好一个 TaskRun，结果名唯一。任何缺失、重复或冲突，都**不采用**这份证据。
2. **实际输入**：`clone-platform.commit==P`、`clone-ui.commit==U`、`clone-infra.commit==infraRevision`；`build-platform-api.digest`、`build-platform-console.digest` 为 `sha256:` 加 64 位 hex。
3. **部署效果**：`pin-sync` 任务（`pipeline-deliver-platform.yaml:182–213`）Succeeded，Argo 应用当前钉的两个摘要等于构建摘要 → `deployed.pin_sync_ok`。
4. **工作负载**：`releases.PodDigests`（`pods.go:19–143`）全部条件，对 api、workers、console 三个 Deployment：
   - 副本数为正（**workers=0 不通过**）；
   - `observedGeneration == generation`；
   - updated / ready / available 与副本数全等；
   - Pod → ReplicaSet → Deployment 的 UID 与当前 revision 归属一致；
   - 容器实际状态正常。

   另加：Deployment 模板里该容器的镜像摘要等于对应构建摘要（api、workers 都等于 api_digest，console 等于 console_digest）；imageID 只取 `@sha256:` 之后的部分比较。读取开始前和结束后各读一次三个 Deployment 的 UID 与 generation，有变化就丢弃本次证据重读。
5. **健康**：STG `platform-api.bifrost-platform-stg.svc:8780/health`：
   - 返回 JSON、`status=="ok"` → 通过；
   - HTML 200、非 JSON、`status≠ok`、错误服务名 → 确定失败；
   - 超时 → 未知。

### 8.3 结论（写 `verify`）

| 情况 | verify |
|---|---|
| run Failed | `failed{run_failed}` |
| Succeeded，第 1–5 项都过 | `verified`，同时写 `evidence{automatic}` |
| Succeeded，实际输入与快照不符（U2≠U、infra 不符） | `failed{wrong_input}`（不可重试，§9.3） |
| Succeeded，第 3–4 项不过 | 从 run 终态起观察最多 15 分钟（起点是 `run_evidence.at`，跨重启不归零）；仍不过 → `failed{rollout}`；如果工作负载等于另一条**有部署效果证据**的发布 → `superseded` |
| Succeeded，健康确定失败 | 观察 15 分钟后 `failed{health}` |
| 任何读取失败 | 不写（未知），记 `diag{verify_unknown}`；超过 30 分钟发卡（只发一张） |

### 8.4 失败后的部署状态（676 B-05）

`verify{failed}` 后读三个工作负载，写 `effect`：

| class | 判定 | 后续 |
|---|---|---|
| `unchanged` | 全部等于可信基线的摘要 | 可重试（同输入、同授权差异，`base` 不变） |
| `this_try` | 每个工作负载等于基线摘要或本 try 的构建摘要（至少一个是后者），且本 run 已终态、不再有副作用 | 可重试：下一 snapshot 的 `base` 仍是可信基线（不缩短授权差异），核验时期望值仍是本 try 的构建摘要 |
| `other` | 有工作负载的摘要既不是基线也不是本 try 的 | 先跑外部取证；结算到那条证据 → `superseded` 路径；结算不到 → `blocked{baseline_moved}` |
| `unknown` | 读取失败 | 等，不重试 |

## 9. 失败、重试、终结、阻断

### 9.1 可重试

`verify{failed}`，why ∈ {`run_failed`, `rollout`, `health`}，`effect ∈ {unchanged, this_try}`，S 的每个成员有余额 → 写 `retry`，到 `not_before` 后写 `snapshot(try+1)`。

### 9.2 superseded（676 B-04）

1. 先消费所有已有交付事实：对本批每个成员，如果某条 `evidence` 覆盖了它，就写 `covers` 和 `member{covered}`。
2. 其余成员 `member{released}`，然后 `settled`。
3. 下一轮按当前 main 头重新开批、选 P。

**不重试旧 P。**

### 9.3 不可重试与阻断区间（676 R-05）

| why | 区间 | 解除条件 |
|---|---|---|
| `wrong_input` | `blocked{wrong_input}`，身份含 (P, U, infra) | main 头变成新的 P，或接受了不同的 CI |
| `ci_red` / `ci_results` / `ci_missing` | `blocked{ci_*}` | 同 P 出现被接受的成功 CI，自动解除 |
| `diff_unlanded` / `non_linear` / `no_merge_after_landing` / `baseline_moved` / `baseline_unknown` | 对应 why | 有外部证据让基线前移，或 main 头变化导致身份变化 |
| `rule` | `blocked{rule}` | 规则版本变化 |
| `budget_exhausted` | 对应 why | `granted` 或 `withheld` |

- 区间开着时，不为涉及的成员开新批。
- 同一身份重复扫描不新建区间，`first_at` 保留首次时刻。
- 本批遇到阻断时，成员 `member{released}`、`settled`；它们因为区间开着而不会立刻再入批。

### 9.4 settled 的前提

每个成员都已有 `member` 去向，且本批没有「STARTED 未终态」：要么有 `run_evidence`，要么 `unsent`，要么 `quarantine_closed`。

## 10. 外部发布结算（676 R-03）

1. 只读循环，不持窗口，不看 live 和 none：列出 `bifrost-deliver-platform` 的 Succeeded run，凡是还没有 `evidence` 身份的就按 §8.2 取证。
   - run 带 `stg-release-intent` 注解，且匹配某个 `started` → `source:automatic`，由自动观察循环写，外部循环遇到时跳过；
   - 其余 → `source:external`。

   两个循环共用同一个身份幂等键，先后顺序不影响结果。
2. **内容覆盖**：证据完整 → 对每个仍未交付、未处置、R 在该 P 的历史里且在该 P 有效的成员，写 `covers`。后来才落地的成员，只要满足条件也可以对同一证据补写。
3. **部署效果**：只有 `deployed.pin_sync_ok` 为真，且工作负载判定等于该证据的摘要时，这条证据才能成为可信基线，或用于 superseded 判定。相同摘要的另一个 run 不算（676 R-03）。
4. **未关闭批次**：
   - 无执行占位 → 被覆盖的成员 `member{covered}`，其余 `released`，`settled`，释放批次槽；
   - 有执行占位 → 只写 `covers`，等原 run 终态，再走 §9。
5. 外部证据不计入运行时自动发布（★ 与占比统计）。

## 11. 窗口与租约（676 R-01、R-08，S3 用例 ⑦⑧）

- **持窗口的时段**：只在「选 P 到最终闸」和「`started` 到 run 终态」两段。等待、阻断、核验未知、退避都**不持**。
- **who** = `stgrel-bifrost-platform-<n>-<try>`，what = `bifrost-platform`，env = `stg`。
- **租约持有者**：每个 try 一个持有者对象，带代际 gen（单调递增，写进窗口记录的 reason 字段）。
  - 续租由它的 goroutine 做：每分钟一次，ttl 5 分钟。窗口 I/O 有界（10 秒），不碰数据库锁。
  - 诊断（`diag{lease_lost}`）经 channel 异步入库。
- **释放**：先停止续租 goroutine 并等它退出，再用读到的 resourceVersion 做带版本删除（`delivery/window_store.go:213`）。版本冲突就放弃，不覆盖别人的窗口。
- **续租失败**：`diag{lease_lost}`，继续观察 run；不以此 verify，也不以此判失败（用例 ⑧）。尚未 `started` 的 try 放弃本轮。
- **重启**：新进程读窗口：
  - who 等于自己某个 `started` 未终态的 try → 以新代际接管续租；旧进程的迟到续租因 resourceVersion 冲突失败，不会刷新新代际；
  - who 不是自己的 → 不动。
- **读到过期窗口**：只判断能否持有，**从不删除**（`aa30a556`，用例 ⑦）。
- **B5 适配器的创建入口**（`CreateNamedDeliverRun`）自己核对活窗口与 who / what / env，不依赖 `mustHoldWindow`（`delivery/release_window.go:93` 对 platform deliver 返回 false）。

## 12. 问题卡：新增「批次」卡族（接 B3，676 R-04、R-05）

- **身份**：`{family:"stg", kind, block | batch, trigger_seq}`。不复用 `repo_stopped` 的 `stop_generation` 分支。
- **要改的位置**：`CardRecord` 加 `Family` 与 `Block` 字段；`LandingCardTriggers` 增加 STG 触发源；`badCardRecord` 的 prepared 与 outcome 按族校验；`HandleLandingCardAnswer` 按族分派到 B5；`ReadLandingCard` 视图与 Console 文案（问题页标签 3 个）。
- **沿用 B3 的机制**：问题在 PROD 问题库；业务记录与答复记录同事务；Ack 在提交后；唯一绑定、过期补卡、held 24 小时、限频。

| kind | 触发（持久） | 选项 | 适用性（答复时现读） | 结算 |
|---|---|---|---|---|
| `stg_failed` | `blocked{budget_exhausted}` 的区间 | `retry_release`（再自动发三次）、`do_not_release`（不发） | 区间仍开、成员仍为 exhausted；已有去向的成员剔除；全部剔除 → moot | `granted` 或 `withheld{owner}`，并 `unblocked{granted}` |
| `stg_blocked` | 除 `budget_exhausted` 外的阻断区间，以及 `quarantined` | `ack`（我会人工发 STG）、`remind_later`；`quarantined` 时多一个 `accept_unreconciled`（接受未对账风险） | 区间仍开 / 仍在隔离 | ack 不解除阻断、不授权发布；`accept_unreconciled` 写 `quarantine_closed`；区间自动解除时卡 resolved |

## 13. 与 B4 收尾的接口（676 R-04）

### 13.1 优先级表（规则 `stg_release≠none` 时，已落地的根）

| 顺序 | 条件 | 类别 |
|---|---|---|
| 1 | 本轮关闭取证在 main 上有效，且成员有 `delivered` 或 `covered` | 已交付 |
| 2 | Owner 处置：旧的 `landing_disposed{owner}`，或新的 `withheld{owner}` | 已处置未交付 |
| 3 | `withheld{hard_floor}`，或 `member{disposed}`（被撤销） | 已处置未交付 |
| 4 | 规则缺失、过期、读不到 | 未了结（rule） |
| 5 | 待发布 / 在批中 / exhausted / released / 阻断中 | 未了结（`stg_pending` / `stg_running` / `stg_exhausted` / `stg_blocked`） |
| 6 | main 上的有效性证据未取到 | 待取证（现有逻辑） |

- `none` 时沿用现行表，只要求 main 上有效。
- 规则在 none 与非 none 之间切换：按决定时的规则判；已关闭的 mission 不重开。
- 外部事实后来出现，不改写已关闭 mission 的分类。

### 13.2 in_main 的根（规则非 none）

- **推荐**（O-3 选 A）：Owner 选「算已交付」之外，还要有一条可信发布证据，它的 P 含该根的 main 提交 H（取自 `failed{in_main}` 的历史证据）。只有前者 → 未了结（`stg_pending`）。
- 「算未交付」的人工出口保留。

### 13.3 快照键

`snapshotKey`（672 B-01 的轮次快照）只纳入：
- 成员去向（delivered / covered / disposed / withheld）；
- 对应证据或处置的身份；
- 阻断区间的身份。

不纳入 read_at、预算余额、诊断。某个根补了证据，不让同一轮里其他根失效。

### 13.4 状态接口

每个根加 `stg:{batch, try, phase, budget_used, budget_gen, blocked:{why, since}, quarantined}`；目标详情的 Landing 块显示一行。

## 15. 测试清单

实现完成后，**注入指定错误时断言失败**；不以「旧代码编译不过所以红」为准（676）。分四层：纯协议、PG 双连接、假 K8s / HTTP（外部字符串用真实校验函数）、真实 STG canary。

**S3 用例**
- ④ 首次 run 在 rollout 之前、一个工作负载更新之后、全部更新之后分别失败：前两种产生第二个 run（Create 请求 2 次、真正创建的 UID 2 个）；回包丢失后 GET 接管，UID 只有 1 个；409 时走 GET。
- ⑥ 当前部署前进到 P2 后不重试 P1；同 P 换 U；冻结后到达的 R3；耗尽的成员随批夹带；落地后被标 `no_merge`；被落地 revert 撤销（允许发出）与被人手 revert 撤销（阻断）；分叉基线。去掉方向检查、或只检查成员的变异必须红。
- ⑦ 真实 who 校验；无窗口、env 错、what 错时 Create 为 0；释放冲突不覆盖；旧代际续租不能复活。
- ⑧ 两个进程；旧续租者迟到；丢租后发生外部发布；关 live 或规则改为 none；原 run 终态与外部证据的先后交错。Running 或未知时不能 verify、settle 或开新 try。
- ⑨ Trade smoke 不是输入；health 超时 → 未知；HTTP 失败、错误 JSON、HTML 200、status 非 ok 分别为确定失败；15 分钟观察期跨重启不归零。

**676 最低验收**
- B-01：未绑定时 Create 已成功，1 小时内经 `delete_pipeline_run` 删除，对象停在 Terminating 被取证，不补建；Create 未发送时撤规则 → `unsent`；Create 在途时发生人工覆盖；绑定后 finalizer 被强摘 → `quarantined`。逐项断言真正创建的 UID 数、批次槽是否释放、预算不退。
- B-02：事件矩阵的每条合法边都经 Parse → Append 校验 → Fold；非法边拒写；6 个断点逐个重启回放；某个成员未知不阻塞其他成员的 `member{delivered}`。
- B-03：混余额的例子，R1 第 3 次之后、没有新授权时 Create=0；R1 已被可信人工发布覆盖时正常推进；OPEN 之后追加 R3；两个连接竞争最后一次额度；换批、换代际时 `not_before` 继承。
- B-04：P2 是 P1 的后继、只改允许的路径；同 P 不同 U；外部 covers 先于原 run 终态落库；全部覆盖与部分覆盖；外部循环早调度和晚调度两种顺序。均不得自动创建向后部署的 run。
- B-05：同 ④ 的三种失败时点，外加混入第三方更新时不重试。
- B-06：规则收紧、`no_merge`、撤步骤分别发生在闸前与闸后；读取跨过规则失效时刻；Close、卡答复、外部覆盖与 B5 并发；两批多根以不同顺序读绑定；gate 之后挂起直到丢租。无死锁、无过期 Create。
- B-07：workers=0；Pod 列表为空或不完整；observedGeneration 落后；错误的 ReplicaSet；滚动中旧 Pod 还在；模板已变而计数未变；clone / build 结果重复；同名异 UID；infra 实际不符。都不能 verified。

**应修项**
- R-02：最新的 run 在后面的分页；同一时刻不同 U；结果重复；新的失败压在旧的成功之上；同 U 接替后原 CI 被清理；U 改变且没有 started。
- R-03：自动 run 不被记成 external；同一 run 为后发现的成员补 covers；相同摘要的两个 run。
- R-04：in_main（按 O-3）；旧处置与新 withheld 并存；none、非 none、规则缺失三种情况；取证轮次快照变与不变；已关闭 mission 不重开。
- R-05：`wrong_input` 不换批重试；同 P 同原因扫描百次只有一个开着的区间；CI 变绿后自动解除；429 时 trigger 不丢；答复已落库而 Ack 失败，重读后不重复授权。
- R-06：旧链、新子协议与普通落地记录混排回放；存储入口拒绝新写入旧 kind，但仍能回放旧 kind。

**变异**（每项都要有计数、身份或分类断言）：去掉 S 的预算覆盖；允许 P 回退；忽略部分 rollout；新 snapshot 重置阻断时钟；`wrong_input` 直接 released；重复写 started；用旧规则或旧决定时间；取消 mission 锁；零副本通过；只按 run 名认 TaskRun；同一 run 不补 covers；未绑定的 404 不看 finalizer 就补建。

### 17.2 仍需 Owner 决定

**O-1** 统筹提交经 D 级单（override）落地后，能不能随 B5 自动发 STG：
- A：D 级单参数加 `stg: true`，批准时一并授权该提交随批发 STG（**推荐**：STG 是测试环境，你批的是这份改动进 main；在单上写明，审批一次）；

**O-2** 未绑定的 404 能否自动补建：
- A：创建时带 finalizer，摘除由 B5 负责；任何删除入口都只能让对象停在 Terminating，所以 404 可证明「未创建」（**推荐**：可验证的保留保证；先探准入策略和 patch 权限，不通则可能要你应用 RBAC）；
- B：不自动补建，未绑定的 404 一律隔离并发卡，由人工发布、你接受风险后关闭。

**O-3** 规则非 none 时，in_main 的根：
- A：你「算已交付」之外，还要有一次可信的 STG 发布覆盖它的 main 提交（**推荐**）；
- B：一律算未交付，只保留人工出口。

**O-4** B5 与 C 块的先后：
- A：先做 C 块，B5 紧随（**推荐**：C 让 main 上的非落地提交大幅减少，B5 才不常态阻断；B5-a 协议等不依赖 C 的部分可以并行写）；
- B：先做 B5，C 随后。

### 17.3 「整个 P 含非落地提交」的风险重估（Owner 决定 A 之后）

- **以前**：近 30 天 platform main 830 个提交里 819 个由 Owner 手推（CUT §11.14）。按 1A，B5 几乎每批都会因非落地提交阻断。
- **C 块上线后**，手推只剩三类：
  - `LandingFloorHard` 范围的改动（D10 overlay、Secret、RBAC、NetworkPolicy、`.env*`、`go.mod` / `go.sum`）；
  - 紧急修复；
  - 统筹没走落地的例外。

  其中 `go.mod` / `go.sum` 是 platform 上最常见的一类，依赖升级时会出现。
- **预计**：从「几乎每批都挡」降到「每月数次」，每次由一次人工 STG 发布解除（外部结算接手）。
- **O-1 的影响**：选 A，override 提交随批发出；选 C，每个 override 提交都会挡一次。按 S5 初稿统计，platform 73.3% 的提交碰治理底线包，它们会走 override，所以 O-1 选 C 会把阻断又带回常态。这就是 O-1 推荐 A 的原因。
- **残余风险**：硬底线类提交的节奏决定 STG 人工发布的频率；建议 B5 上线后第一个月统计「被非落地提交阻断的批次 / 全部批次」，作为后续是否需要 O-1 之外放宽的依据。
