## 6. 协作协议

已有、只需用起来的：
- **独立性**：复核任务的路由会排除与被审尝试同一执行器或同一厂商的候选，厂商没记录的也排除（`route.go:315-317`、`:344-350`）。但这只对有尝试行的工作有效；外部工作没有尝试行，排除静默失效（§0 第 5 条）。
- **handin 的厂商是自报**：统筹用 handin 交的件，提议的是钉给 `external:coordinator` 的实现任务，提供方写 anthropic（`handin.sh:216-218`），起尝试时厂商也由脚本写死（`:421`）。这让路由排除了 anthropic，但证明不了实际用的是哪家。被审任务带 pin 时，复核候选先被筛成固定复核者 codex、openai（`route.go:258-267`；`api/internal/agentrt/store/pinresult.go:205-209`）；pin 只许「实现 + 分支」（`0010_executor_pin.sql:54-55`；`store/pin.go:168-171`）。
- **复核结论是事实**：`verification_recorded`（代码）。
- **席位协议**：参谋长不能说「已派活」「已批准」（代码：`seatproto`）。
- **消息是数据**：写入方不能发「叫醒」，`sendKinds` 里没有它（`messages.go:17-18`）。消息正文过「自称已批准」检查，命中记为 `policy_alert`（`claims.go:78` 起的 `alertClaim`，由 `store/signals.go` 调用）。

**在外部尝试（N14）批下来之前，必须说清两件事**：
- 外部工作的独立性排除什么都不排除；
- R6 和中转度量都不能依赖自报的厂商。外部工作的复核只能记成复核意见和类别事件（N14 的 B），不写 `verification_recorded`。

**重复提交就是新一轮**：同一件外部工作「已提交」之后，除了 `linked` 不再接受任何事件（`externalwork.go:389-391`）；同一序号重发是幂等的（`:370-384`）。所以返工后的再提交，是一次新的登记（N14 A 下是一条新的外部尝试），算新一轮。复核意见钉住被审的提交（`0001_core.sql:278` 的 `subject_commit`）。提交重放不重复派复核；取消和撤销要有回执；任意多的「已提交」不能把调度队列冲垮（每件工作每轮最多一个复核任务）。

**复核方额度用完时**：钉住任务的复核固定给 codex（`pinresult.go:209`）。Codex 的额度池冷却时，复核任务一直挂在 ready，只有 `wait_limit_passed` 能看见它（代码）。规矩：
- 等待超限后，统筹可以手工安排复核，但只能记成复核意见加 `fallback: quota` 枚举，不写 `verification_recorded`，也不算独立复核通过；
- 额度恢复后照常派运行时复核，手工复核不顶替它；
- 每次退回手工都计数，进早报。

这条只管额度冷却。「没有独立候选」是规则组合出来的静态结果，额度恢复也不会好，按 N14 A 的「阻塞」处理，不套用这条。

**「提到不等于派活」落成代码**：
- 今天唯一一条「消息变成工作」的路径，是参谋长收信：控制器按规则把发给席位的信变成一个简报任务（`store/brief.go:21-25`）。
- 要加一个测试：往任务线程发「请某某复核」之类的消息，断言之后没有提议任务、没有领活。
- 线程投影不解析 @。
- 席位协议加一行：「被提到或提到别人，都不会启动工作」，考试加一题。

**统筹中转次数的可测定义**：
- **分母**：受管的交接义务清单。每条义务是 `(work_id, attempt 或 round, target_role, artifact_version)`，由控制器从工作清单生成：实现提交了，就有一条交给复核岗位的义务；复核不通过，就有一条交回实现岗位的义务。不数「收到了多少产物」。
- **每条义务记三样**：`origin_actor`（这个版本的作者，取自受信来源）、`relay_actor`（把它交到目标手里的身份）、因果事件。
- **只计代传**：`relay_actor` 是统筹的任一身份、又不是 `origin_actor` 时，算一次中转。统筹的身份包括 `thread:<统筹会话>`、`seat:coordinator`、handin 用的 `agentd:coordinator-…`（令牌见 `handin.sh:39-40`，上传报告见 `:418`；记成 `host:coordinator-…`，`agentrtapi/controls.go:18-24`）。统筹自己写的原创报告不算中转。
- **缺口单列**：没交付、没收到确认、链断了，都算缺口，不算「零中转」。
- 每次交付的作者按 §5.1 取自点名产物的事件，不取产物的首个作者。
- 平台外有没有中转，平台看不见，另做抽查。
- 原作者证明不了时，`origin_actor` 记 Unknown，算一个来源缺口。它不能贡献「零中转、零缺口」的验收；不能把提交者同时填进原作者和代传者，那样会把统筹转抄的报告算成原创，得出假的零中转。外部尝试（N14）批下来之前，外部工作就是这种情况：只能确认认证的提交者，厂商记 `declared`。

**复核独立**还要这几条：
- 新的身份和新的上下文；
- 必须是另一家，厂商来自受信来源；
- 钉住被审的提交和产物；
- 实现者不能给自己写接受结论；
- 消息里声称「已批准」不改变任何机器状态。

**TD-370：一个线程名只归一把令牌。** 一个 `thread:<session>` 归第一次以它写入的那把令牌；别的令牌再以它写或读信，一律被拒（`store/propose.go:42-47`、`:62-88`）。今天钩子（reporter 令牌）和统筹线程的 MCP（operator 令牌）都能拿到侧栏会话编号（`thread-heartbeat.js:221`；`sessionId.ts:14`；登记工具强制用它，`register-claude-work.py:69`）。如果两边都以 `thread:local_X` 写，谁先写谁持有，另一边全部被拒。出路有三条，由 Owner 在 N15 里选：
- (i) 钩子写成另一种主体：收集员 `collector:<host>`，会话编号作字段（推荐）；
- (ii) 一个会话两个线程主体：钩子用 CLI 编号写成 `thread:<cli_id>`，MCP 用侧栏编号写成 `thread:<local_id>`，L0 把它们记成一对，「自己的工作」检查接受这一对里的任一个；
- (iii) 把 TD-370 放宽成「每个会话一组令牌」：这是改已定的规则。

S1 加负测 `HookAndMcpWriteSameSession`：同一个会话里钩子和 MCP 各写一次，两次都成功，而且记到同一个会话上。

**三样身份分开**（§5.1）：认证凭据决定能做什么；会话头只决定记在谁名下，不授予权限；受信的执行证明走启动器自己的通道（N14）。新增的上传权（N15）以 SS0-P 的绑定通过为前提：身份从认证来源派生，不能自填别人的身份（`CUT-session-stream-2026-10-26.md:69`、`:421`）。

### 7.2 原则

1. **身份由认证的主体推出来**：事件、产物、消息的作者，取请求所用的令牌和绑定，不取正文自报。厂商分三种来源（§5.1）。
2. **每条记录带可信程度**：事实、观测、自述、提炼，不同级不能混写。
3. **最小读写范围**：

   | 岗位 | 可写 | 可读 |
   |---|---|---|
   | 收集员 | L0 绑定、L2 类型化摘要、出门条、收录回执 | 本主机的会话；决定和出门条（读回注入用） |
   | 档案员 | 候选、草稿（按 §5.0 定类别） | 公开和工程条目、候选、事件和产物引用 |
   | 检查员 | 检查记录 | 被检条目及其出处 |
   | 简报员（控制器） | 上下文包 | 规则允许的条目 |

   授权不能在委派之后扩大。
4. **D-SS6 A 的读面收口是 S5 的前提，S5 只传类型化摘要**：
   - 非 Owner 读动作时，只能拿到固定枚举、时间和退出状态，或者被拒（`CUT-session-stream-2026-10-26.md:318`）。
   - S5 从宿主送出的动作，**只有枚举、时间和退出状态**，不带命令、路径、正文和日志尾部。不复用今天 `scrub.go` 那种「过滤后的命令和路径」格式。
   - 做到这一点，S5 才能排在私有存储之前。
   - S5 之前还要：来源身份绑定；按身份投影、旧读面收口；负向权限测试。
   - 要显示命令和路径，就要先有 Owner 专属读面，10-26 §8 的全部要求照样适用（`:319-325`），正文启用还要满足 10-26 的启用门槛（`:439`）。
   - 10-26 的 SS5-R 依赖私有存储（SS2-D），整片提前做不了。S5 只提前其中「旧动作接口和 MCP 读面对非 Owner 收口」这一个子项；S11 只把验收过的这个子项记为完成（§11.3）。
5. **公开仓库**：
   - 只放公开工程知识；
   - 人和账户的内容只在运行时受限存储；
   - 本稿不逐字引用 Owner 的话，不描述私人对话经过，不写内部域名。
6. **受限存储先定信任边界，再比方案**（N7）：
   - `agent_reader` 是 `pg_read_all_data` 的成员，能连三个平台库（台账：`scripts/release/db-steps.d/sql/2026-10-09-w33-agent-reader-verify.sql`、`2026-10-14-w31-agentrt-2-connect.sql:28-31`）。它能读这些库里所有 schema 的所有表，**新 schema 挡不住它，收回授权也没用**。
   - 运行时角色能读 agentrt 的全部表（`api/internal/agentrt/migrations/0003_grants.sql:13-14`）。
   - PROD 上有一条默认权限：运行时 owner 角色以后建的新表，逻辑备份的登录角色都能读（`2026-10-14-w31-agentrt-2-connect.sql:36-43`）。
   - 逻辑备份用普通 `pg_dump` 整个 schema 导出（`k8s/data/logical-backup/backup.sh:88`），agentrt 在导出目标里，恢复演练要求行数一致（`k8s/data/logical-backup/README.md:70`、`:85`）。
   - 集群有两个实例、Barman 对象存储备份和 WAL 归档，每天一次物理备份（`k8s/data/cluster.yaml:12`、`:46-48`；`k8s/data/backup-scheduled.yaml:11`）。物理备份复制整个集群，库级的连接权限和表上的行级安全都管不到它。
   - 受限记忆**不是谁都不能读**：获授权的接收者要经专用读工具 B1 读自己读者范围内的最小记录（`PLAN-memory-import-2026-10-24.md:57`、`:94`）。要挡的是绕过 B1 的路。边界分三条，见 §13 N7。
   - 方案比较和推荐见 §13 N7；S7 的启用条件见 §11.2。
