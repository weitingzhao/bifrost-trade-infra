# S5 放开一部分 api：拆分与设计初稿（2026-10-29，统筹；待设计复核）

上一段：S3 已开门（CUT-landing §11.13），第 1 版规则 `landing:dev` 只允许 console 展示类路径。本稿回答 CUT §3 S5 行「按代码清单重审底线；第 2 版规则；X6」，用例「规则允许 `approvals/**`，仍被拒」。代码基线：platform main `1116f3e3`。

## 0. 结论先说

- **只放开 api 的叶子包，减少不了多少手推。** 近 30 天 platform main 830 个提交里，73% 碰到了治理底线包（`agentrt`、`agentd`、`server`、`approvals`、`actions`……），因为这段时间做的正是运行时本身；api 第一批叶子包只多覆盖 2.5%，第二批再多 2.2%。
- **第二大头是 console 数据层**（`console/src/{api,lib,hooks}`，12.8%）。它在第 1 版里是底线，但它不碰审批、令牌、集群，放开的风险可控。
- 所以 S5 拆成两条：
  - **S5a 规则可放开的范围**：console 数据层 + api 第一批叶子包，第 2 版规则，Owner 签名。累计覆盖约 17%（含已开的展示类）。
  - **S5b 底线代码的「Owner 一键批准落地」**（需要 Owner 先定原则，见 §6 D2）：底线包的改动仍不允许无人批准地落地，但不再要 Owner 在终端手推，而是运行时准备好、CI 和异家评审都过了以后，Owner 在 Console 批一张 D 级单，由落地身份推 main。这是让「过渡期结束」真正成立的那一块。
- 工时（单人有效工时）：S5a 约 22–34 小时；S5b 约 20–32 小时。

## 1. 代码清单（api/internal/*，59 个包）

判据：一个包进入 platform-api 进程，就拥有进程的全部权限（PROD 的 ServiceAccount 能重启 Deployment、起 PipelineRun、改集群）。所以路径底线保护的是「治理逻辑本身」，而不是「进程能做什么」；后者由 §3.3 的 Go 新增行检查兜住。

### 1.1 底线（规则永远放不开；代码里写死）

| 包 | 理由 |

| `server` | 路由注册与装配（`server/server.go`、`agentrt_*.go`）；新端点、鉴权链都在这里 |

| `releasepolicy`、`releasefreeze`、`delivery`、`gitops`、`promote`、`releases` | 发布策略、发布窗口、PipelineRun 与 Argo 同步、提升 |

## 2. S5a 底线的代码改法

`rules.LandingFloor`（`api/internal/agentrt/rules/landing.go:186`）现在对 `api/**`、`console/src/{api,lib,hooks,pwa}/**` 一律返回底线。改为：

1. **api**：`api/**` 仍是底线，除非路径是 `api/internal/<包>/` 且 `<包>` 在代码里的 `LandingEligibleAPIPackages` 名单（§1.2 的 12 个）里。名单写在 `rules` 包的代码里、带棘轮测试；扩名单要 Owner 推代码（它本身在 `agentrt/**` 底线里，运行时改不了）。
2. **console**：`console/src/{api,lib,hooks}/**` 移出底线，进入「数据层」类；`console/src/pwa/**`、`main.tsx`、`App.tsx`、构建配置仍是底线。
3. 不变的底线：任意深度的 `go.mod`、`go.sum`、`package*.json`、`.env*`；`mcp/**`、`agent/**`、`scripts/**`、`config/**`、`Makefile`、`.husky/**`。
4. **防线**：棘轮测试把 §1.1 每个包逐个列成「即使规则 allow 了也被底线拒」的用例（CUT S5 用例：规则允许 `api/internal/approvals/**`，仍被拒）。新加一个 `api/internal/` 包时，默认就是底线（名单是白名单），不需要记得去加。

## 3. 规则检查：按路径分三类判定

第 1 版的 `LandingPresentationOnly`（`landing.go:212`）只适合 TSX/CSS。改为按路径分类，每类一套判定，`CheckChanges` 逐个文件按类检查：

### 3.1 展示类（不变）
`console/src/components/**/*.{tsx,css}`、`console/src/pages/**/*.tsx`、`console/src/styles/**/*.css`：沿用三条纯展示判定。

### 3.2 console 数据层（新）
`console/src/{api,lib,hooks}/**/*.{ts,tsx}`：新增行里
- 不得出现写方法：`method: 'POST'|'PUT'|'PATCH'|'DELETE'`（及双引号、大小写变体）、`.post(`、`.put(`、`.patch(`、`.delete(`；
- 不得出现审批与控制相关路径片段：`/approvals`、`/answer`、`/controls`、`/agentrt/rules`、`/delivery/`、`token`；
- 不得新增 `localStorage`/`sessionStorage` 写入令牌的代码（`setItem(` 与 `token` 同行即拒）。

读请求、解析、展示逻辑都能落地。剩余风险（语义）交给异家评审。

### 3.3 api 叶子包（新）
`api/internal/<名单内的包>/**/*.go`：
- **新增 import 黑名单**：`os/exec`、`syscall`、`unsafe`、`plugin`、`net`（原始网络）、`k8s.io/**`、`sigs.k8s.io/**`、`github.com/jackc/pgx/**`、`github.com/redis/**`，以及 `github.com/weitingzhao/bifrost-platform/api/internal/<任何底线包>`。按新增行里的带引号 import 路径判定（Go 的 import 块每行一个路径，diff 的新增行能直接看到）。
- **新增行效果黑名单**：`os.WriteFile`、`os.Create(`、`os.Remove`、`os.Rename`、`os.Getenv(` 且名字含 `TOKEN|SECRET|PASSWORD|KEY`、`http.MethodPost|Put|Patch|Delete`、`"POST"|"PUT"|"PATCH"|"DELETE"`。
- **测试随代码**：改了非 `_test.go` 的 Go 文件，同一个包里必须有 `_test.go` 的新增或修改（D3）。
- 其余（编译、vet、全套测试）由 CI 保证：落地前 CI 必须是这个 R 的最新一次且 Succeeded（§2.10 已有）。

### 3.4 规则字段
不加新字段：分类由路径决定，写在代码里。规则只多几条 allow。这样 v2 仍走现有闭合解析器，签名格式不变。

            "api/internal/agentprogress/**/*.go", "api/internal/agentthreads/**/*.go",
            "api/internal/checklist/**/*.go", "api/internal/datahusbandry/**/*.go",

注意：allow 写了也挡不住底线。若有人把 `api/internal/approvals/**` 写进 allow，底线照样拒（§2 第 4 条的用例）。

## 5. X6：base 漂移后的集成复核

CUT §4 定的是「S5 起有交集的做集成复核」。第一片做法是文件级交集 → `failed{overlap}`。Go 的语义跨文件，同包不同文件也会互相影响，所以 S5a：

- **包级交集**：base..M0 改过的 Go 文件与 A 改的 Go 文件**同包** → 按交集处理（`failed{overlap}`，该根可「再试一次」在新 main 上重做实现）。
- console 数据层：同目录视为交集。
- 不做「自动集成复核任务」：第一片的 `failed{overlap}` + 再试一次已足够，复核任务留到 S5b 视需要再加。

## 6. 需要 Owner 决定的点

- **D1 S5 的范围**
  - A：只放开 api 叶子包（约 +2.5%）；
  - B：叶子包 + console 数据层（约 +15%，累计约 17%）；**推荐**；
  - C：B + S5b 底线代码的审批落地（目标覆盖到底线提交，过渡期才能真正结束）。
- **D2 底线代码能不能经你批准后由落地身份推（改 §2.3「决定卡放不开底线」的原则）**
  - A：不能，底线永远手推（过渡期不会结束，只会缩小）；
  - B：能，每件一张 D 级单，你在 Console 批；运行时先跑完 CI、异家评审、集成复核；单子里写清改了哪些底线包、为什么；**推荐**；
  - C：能，但只限部分底线包（例如 `agentrt` 的非落地子目录），其余仍手推。
- **D3 Go 改动是否必须带测试**：A 必须（**推荐**，防止无测试的逻辑改动）；B 不要求，只靠 CI 与评审。
- **D4 v2 的行数上限**：A 400（**推荐**）；B 保持 300；C 按类分（展示 300、Go 600），需要加规则字段。
- **D5 console 数据层的写请求**：A 一律不许新增（**推荐**）；B 允许，但审批与控制路径除外。

## 7. 测试清单（每条在旧代码上必须红）

1. 规则 allow 写了 `api/internal/approvals/**`，改 `api/internal/approvals/x.go` → `FloorViolation`（出生即 `failed{floor}`），不进入规则判定。
2. §1.1 每个底线包各一条同上用例（表驱动），外加 `api/cmd/main.go`、`api/go.mod`。
3. 名单内包 `api/internal/probe/x.go` + `x_test.go`、规则 v2 → 允许；只改 `x.go` 不改测试 → 拒（`tests`，暂停等规则或修正）。
4. 名单内包新增 `import "os/exec"` / `"k8s.io/client-go/kubernetes"` / `".../internal/cluster"` → 拒。
5. 名单内包新增 `os.Getenv("PLATFORM_ADMIN_TOKEN")`、`http.MethodPost` → 拒。
6. console 数据层新增只读 `fetch` 解析 → 允许；新增 `method: 'POST'` 或 `/approvals` → 拒。
7. `console/src/pwa/sw.ts`、`console/src/main.tsx` 仍是底线。
8. 不在名单内的新包 `api/internal/newpkg/x.go` → 底线（默认底线）。
9. 包级 overlap：base..M0 改了 `probe/a.go`，A 改 `probe/b.go` → `failed{overlap}`；改的是别的包 → 不算。
10. 规则从 v2 收紧回 v1（删 allow）→ 不要签名即生效；v1 → v2 要签名。
11. 第 1 版下 console 数据层仍是底线（保持 S3 行为，直到 v2 生效前不变）—— 注意这条与第 2 条底线代码同时改：数据层从「底线」变为「规则可放开」，v1 下表现为 `rule` 暂停而不是 `floor` 结束。是否接受这一行为变化，在复核时确认。
