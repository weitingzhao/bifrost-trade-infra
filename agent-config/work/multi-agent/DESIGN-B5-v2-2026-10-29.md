## 0. 一段话

B5 只在**签名规则对该仓库写了 `stg_release: <流水线>`**（不是 `none`）时才工作。开门的第 1 版规则写的是 `none`，所以本块上线后不改变任何行为，直到 Owner 签一版放开 STG 发布的规则。

B5 的循环跑在 PROD workers 里，与落地循环同一个仓库流锁。它把「已落地、在 main 上仍有效、还没发到 STG」的落地结果攒成批，持发布窗口，为 main 的某个头 P 选出**恰好以 P 为 revision** 的那次 CI（得到 U），对**整个 P 相对上次 STG 的差异**做资格检查，然后以确定的名字起 `bifrost-deliver-platform`。run 跑完后，用该 run 自己的子任务结果、STG 工作负载的镜像摘要和健康检查做四项核验，逐个成员结算。失败最多自动重试三次（按成员记账、换批不清零）；用完或遇到不能自动处理的情况就发问题卡，由 Owner 决定再给三次或不发。任何人手动发的 STG，只要证据完整，也会被结算为这些成员的交付证据。

## 2. 记录协议：`note.stg_release` v1

### 2.1 放在哪里、为什么不扩 `note.landing`

- 流：仍是 `landing:bifrost-platform`（与落地共用一把流锁，预算扣减、批次冻结和落地写入天然串行）。
- 键：`body_json.stg_release`（与 `landing`、`landing_card_*`、`landing_close` 并列），封闭解析器 `badStgRelease`，写入方只有 `controller`（`checkStgReleaseAppend`，仿 `store/landing_cards.go:203` 的做法）。
- 旧 kind 退役：`landing/protocol.go:47–48, 484–529` 的 `stg_pending … stg_failed` 七种从不写入（PROD、STG 库实测 0 条）。`Parse` 对它们返回「已退役，改用 stg_release」，`Terminal()`（`:544`）去掉 `stg_verified`、`stg_failed`。理由：v1 的 `Operation.Try ≤ 3`、单 Run 字段、`stg_result{ok|failed}` 的边无法表达 B-01/B-02/B-04 要的语义（666 R-05 反例），在原记录上加字段会破坏旧事件的精确解码。

### 2.2 记录种类与字段（全部带 `v:"1"`, `kind`, `batch`；`batch = stg:bifrost-platform:<n>`）

| kind | 字段 | 含义 |
|---|---|---|
| `opened` | `members:[{root, op, R}]`、`gen`（各成员的授权代际）、`first_pending_at`（各成员最早进入待发布的时间） | 冻结成员元组。非空、`R` 唯一、每个 `(root, op)` 不在任何未终结批次里 |
| `snapshot` | `try`、`P`、`U`、`ci:{name, uid, created_at, read_at}`、`base:{P, digests, source}`、`not_before` | 本次尝试的发布内容与基线；`base.source ∈ {verified, external, release_record}`（§5.3） |
| `gate` | `try`、`decided_at`、`rule_version`、`checked:{members, diff, ci, window}` | 最终闸的结论（只在放行时写，放行即写 `started`，两者同事务） |
| `started` | `try`、`run`、`fingerprint`、`marker`、`spend:[{R, gen, n}]` | 创建**意图**：先落库、后发 Create。`spend` 是本 try 对每个成员扣掉后的累计次数 |
| `bound` | `try`、`run`、`uid` | 首次观察到同名、指纹与来源标记都相符的对象；每个 try 一次；不改阶段 |
| `run_observed` | `try`、`uid`、`status ∈ {Running, Succeeded, Failed}`、`at` | 外部事实，只追加；同一状态不重复写 |
| `verify` | `try`、`outcome ∈ {verified, failed, superseded}`、`why`、`evidence`（§8.2） | 核验结论，每个 try 至多一次，写了就不改 |
| `diag` | `try`、`what ∈ {lease_lost, object_lost, collision, running_long}`、`gen` | 诊断附注，不改阶段；`(what, try, gen)` 去重 |
| `retry` | `try`（下一次）、`not_before` | 上一 try 已确认结束且失败、预算未尽时，开下一 try 的意图 |
| `settled` | `members:[{root, op, R, to}]`，`to ∈ {delivered, released, exhausted, disposed, superseded}`、`why` | 批次终结：每个成员恰好一个去向（原集合的完整、无重叠分区） |
| `ext_verified` | `ext`（`stg-ext:bifrost-platform:<m>`）、`evidence`、`covers:[{root, op, R}]` | 外部发布的结算（§10），不占批次槽 |
| `granted` | `members:[{root, op, R}]`、`gen`（新代际）、`question_id`、`trigger_seq` | Owner 在 `stg_failed` 卡上选「再发一次」：精确成员获得新的 3 次 |
| `withheld` | `members:[{root, op, R}]`、`question_id`、`trigger_seq`、`why ∈ {owner, ineligible}` | Owner 选「不发」或成员被判永久不可发：成员离开自动发布，B4 计为已处置未交付 |

### 2.3 合法转移（批次执行状态）

```
(无) ─opened→ OPEN ─snapshot(try=1)→ SNAP ─started→ STARTED ─bound→ STARTED（不改阶段）
STARTED ─run_observed(终态)→ ENDED ─verify→ VERIFIED | FAILED | SUPERSEDED
FAILED|SUPERSEDED ─retry→ SNAP'（同 P、U，try+1，not_before≥退避）
OPEN | SNAP（无 started）| FAILED | SUPERSEDED（run 已确认终态）─settled→ CLOSED
VERIFIED ─settled→ CLOSED
```

- `started` 只能接 `snapshot`（同 try）且 `at ≥ not_before`；同一 try 只能有一条 `started`。
- `verify` 只能在本 try 的 `run_observed` 为终态之后；`Succeeded` 才可能 `verified`；`Failed` 只能 `failed`。
- `retry` 要求上一 try 有 `verify{failed|superseded}`，且本批每个成员在当前代际仍有余额（§6）。
- `settled` 不能在「已 `started`、尚未确认终态」时写：执行占位只能由外部事实解除（B-01、B-05）。
- 同仓库同时只能有一个未 CLOSED 的批次；`ext_verified` 不受此限。
- 折叠：`store/stg_release.go` 的 `StgFold(events) → {batches, members, budget, grants, withheld, external}`，独立于 `landing.State`；每次落库前 `checkStgReleaseAppend` 在流锁下用当前折叠验证转移（仿 `checkCardAppend`）。

## 3. 待发布、开批与成员

1. **待发布集合**（派生，§11.4 已有定义，此处收紧）：最新落地操作为 `landed`、最新有效性证据为 `effective`、未被任何 `delivered`/`withheld` 结算、不在未终结批次中、当前代际仍有余额的 `(root, op, R)`。
2. **开批条件**：`env=prod && live && 规则对该仓库 stg_release≠none && 无未终结批次 && 待发布非空 && (没有活动落地 || 最老成员等待 ≥ 20 分钟)`。活动落地 = 落地操作处在 `claimed` 到 `main_result` 之间。规则读不到、关 live、或 `none`：不开批（已开的批次照常观察到终态，§11）。
3. **成员范围**：开批时把当前全部待发布成员冻结进 `opened`（不按余额拆批，原因见 §6.3）；`first_pending_at` 取成员首次进入待发布的时间，换批不重置（`pending_long` 的年龄不因重组归零，666 R-03）。

## 4. P 与 U（R-01、B-06）

1. 持到窗口（§11）后，读 main 头 → **P**。
2. 列 `cicd` 中 `pipeline=bifrost-ci-platform`、参数 `revision == P` 的全部 PipelineRun（分页读全，`delivery/landing_drill.go:21` 现有 `landingCI` 改为返回完整列表并带 UID 与结果，已有字段 `UID`、`PlatformCommit`、`UICommit`，`:68–69`）。
3. 按 `creationTimestamp` 取**最新**一次：
   - Succeeded，且结果 `platform-commit == P`、`ui-commit` 为 40 位小写 SHA → **U**；
   - Running / 未出结果：等待，**不开 snapshot**，释放窗口（§11）；从 P 首次被选中算起 30 分钟仍未出结果 → `stg_blocked` 卡；
   - Failed 或结果缺失 / 不合法：不回退到更早的提交，`stg_blocked{ci_red}`；
   - 不存在：等推送触发的 CI（落地分支上的 CI 若 revision 就是 P，也算），30 分钟仍没有 → `stg_blocked{ci_missing}`；
   - 同一创建时刻有多次且结果或状态不一致 → unknown，等待并发卡。
4. snapshot 记下所选 CI 的 name、UID、创建时间与读取时间。之后同 P 出现**新的**成功 CI：U 相同 → 追加 `diag` 之外不改快照，核验时接受；U 不同 → 不替换快照，当前 try 结束后批次以 `settled{released, why:ci_changed}` 交接，下一批重新选 P、U（不悄悄改旧快照）。

## 5. 发前检查：针对整个 P（B-03）

### 5.1 检查内容（每次可能发出 Create 前，在最终闸里现读，不用缓存）

1. **差异归属**：从部署基线 `base.P`（§5.3）到 P 的每个提交 c（`git rev-list base.P..P`，用完整历史，不用 clone 任务的浅克隆）：
   - c 带 `Landed-By: agentrt-prod/<op>` 尾注，且该 op 是某个落地结果（`landed`、R==c），且其 root 的 mission 不是 `no_merge`、计划步骤未撤、规则 `EligibleToDeploy`（`landing/eligibility.go:124–138`）通过 → 「可发布提交」；
   - 否则 → 「非落地提交」（例如 Owner 手推的 api 改动、人手迁移）。
2. **任何一个非落地提交，或归属到已处置 / 不可发布结果的提交，都挡住整个快照**：不起 run，`stg_blocked{diff_unlanded | diff_ineligible}`，批次以 `settled{released}` 交接（成员回到待发布、次数不变），直到人工发布（§10）把基线推过这些提交。
3. **整段差异按规则判权限**：`rules.(*Landing).CheckChanges`（`agentrt/rules/landing.go:259`）作用于 `base.P..P` 的全部改动；不过 → 同上挡住整个快照，不归罪于某个合法成员。
4. **成员自身**：每个成员在 P 中仍有效（R 在 P 的历史里、未被撤销）；已被撤销的成员（确定的 `reverted`）可以单独以 `settled{disposed}` 结算，不影响其他成员。读取未知 → 等待，不算无效。
5. **精确 CI 仍是快照里那一次**（或 §4.4 允许的同 U 接替）。

### 5.2 与「合法后到的 R 要继续」的关系

不区分「谁先谁后」：只要 main 头含禁止自动发布的内容，就整体等待人工发布。这是正确的阻断（666 B-03 改法第 4 条）。

### 5.3 部署基线（B-04 反例 3）

- 不再用 `Deployed("stg")`（`server/agentrt_sources.go:88`）：它把 unsettled 压成 false，失败后第二次永远起不来。
- 基线取 B5 自己的最新可信记录：最近一次 `verify{verified}` 或 `ext_verified` 的 `(P, digests)`；没有时（首次）读发布记录 `releases.Current`（`releases/current.go:13–75`），`ErrUnsettled` 则 `stg_blocked{baseline_unknown}`，等一次人工发布建立基线。
- 每个 try 开始前再读 STG 工作负载的镜像摘要：与基线一致才用；不一致（有人在 B5 之外发过 STG 而尚未结算）→ 先跑 §10 的外部结算；仍对不上 → `stg_blocked{baseline_moved}`。

## 6. 预算与授权代际（B-02）

1. **账**：成员 `(R, gen)` 已用次数 = 所有批次里含该成员的、不同 `(batch, try)` 的 `started` 记录数。同名接管（`bound`）不扣；意图已写、是否创建未知，按已扣计（不退款）。
2. **扣减**：写 `started` 的同一事务里，在流锁下重算每个成员的已用次数，任何成员已到 3 → 不写 `started`（存储层 `checkStgReleaseAppend` 拒绝超额，不只靠扫描器）。`started.spend` 记下扣后的累计数，供审计。
3. **混余额批次**：开批时不按余额拆批；某个 try 确认失败后，若有成员用满 3 次而其他成员仍有余额，以 `settled{exhausted 给用满的; released 给仍有余额的}` 结算，仍有余额的回到待发布，下一批继承它们的次数与**下次可执行时间**（`not_before` 不因换批提前，666 B-02 改法第 3 条）。
4. **退避**：同一成员两次 `started` 之间至少 10 分钟（第 1→2 次）、30 分钟（第 2→3 次），跨批次也算。
5. **Owner 授权**：`stg_failed` 卡答「再发一次」→ `granted{members, gen+1}`，成员获得新的 3 次，历史账不清除；授权绑定该卡的 `trigger_seq` 和精确成员集合，**一次性**：同一答复重复处理、Ack 失败后重读，都不再加额度；已被外部结算或已处置的成员不在授权里复活（666 R-03）。

## 7. run 身份、创建与恢复（B-01）

### 7.1 最终闸（每条可能发出 Create 的路径都走，包括恢复补建）

在仓库流锁下现读：`env=prod`、live、规则（版本、`stg_release`）、窗口（未过期，且 who / what / 环境就是本 try，§11）、§5 全部检查、§6 预算与 `not_before`、本批本 try 仍是当前状态。全过 → 同事务写 `gate` 与 `started`，提交后才发 Create。提交回包不明 → 先读库确认，不在事务重试回调里创建。

### 7.2 名字、指纹与来源标记

- run 名：`stgrel-<batch 序号>-<try>-<P 前 8 位>`（只含 `[a-z0-9-]`，长度固定 ≤ 40），确定、可重建。
- 标签：`bifrost.io/stg-release-batch=<batch>`、`bifrost.io/stg-release-try=<try>`、`bifrost.io/stg-release-intent=<started 事件的 seq>`。
- 指纹：`sha256(规范 JSON{namespace, pipeline, params 全部(revision=P, uiRevision=U, infraRevision=<钉死的 infra SHA>), labels})`。
- 首次 Create 返回的对象与之后 GET 到的对象，都按「名字 + 指纹 + 三个标签」核对后才写 `bound{uid}`。

### 7.3 404 与恢复（四种事实）

| 事实 | 判定 | 处理 |
|---|---|---|
| 未绑定，GET 404 | `started` 写下不到 **6 天** | 可当「未创建」：重新过 §7.1 最终闸后用同名创建（终态 PipelineRun 在 `cicd` 保留 7 天，`k8s/cicd/tekton/pipelinerun-ttl.yaml` 第 1 遍；运行中的不删。6 天留 1 天余量） |
| 未绑定，GET 404 | `started` 写下已满 6 天 | 不能证明未执行：`diag{object_lost}` + `stg_blocked{object_lost}` 卡，不创建 |
| 已绑定，GET 404 | 任何时候 | 不创建：`diag{object_lost}`；已有 `run_observed` 终态的照常核验（证据在 §8.2 已落库）；没有终态 → `stg_blocked{object_lost}` |
| 同名但 UID / 指纹 / 标签不符 | 碰撞 | 不接管、不修改对象：`diag{collision}` + `stg_blocked{collision}`；**不自动开新 try**（原执行可能仍在跑） |
| 403、超时、其他读错误 | 未知 | 等待，不当 404；按读取退避重试 |
| 409（Create 冲突） | 走 GET，按上表 | — |

### 7.4 关 live 时

已 `started` 的 try 照常观察、核验、结算；**任何需要 Create 的恢复都过 §7.1**，关 live 时不创建，发 `stg_blocked{live_off}`（只在状态里显示，不发卡）。

## 8. 观察与核验（B-04、B-06）

### 8.1 两层

- `run_observed`：外部事实，按 UID 读 PipelineRun 的 `Succeeded` 条件；只追加变化。
- `verify`：在 `run_observed` 为终态后计算一次确定结论。证据读不到、发布记录延迟、HTTP 超时 → **unknown，不写 verify**，按退避重读同一次证据，超过 30 分钟发 `stg_blocked{verify_unknown}`。

### 8.2 证据结构（自动与外部共用，存进 `verify.evidence` / `ext_verified.evidence`）

```
{cluster, namespace:"cicd", run, uid, pipeline:"bifrost-deliver-platform", target:"bifrost-platform-stg",
 params:{revision, uiRevision, infraRevision},                      // 请求
 results:{platform_commit, ui_commit, infra_commit,                  // 实际：子 TaskRun clone-* 的 commit 结果
          api_digest, console_digest},                               // 实际：build-* 的 digest 结果
 workloads:{platform-api, platform-workers, platform-console:{imageIDs:[…], ready, updated}},
 health:{status:"ok", read_at},
 read_at_start, read_at_end}
```

- 子 TaskRun 必须带 `tekton.dev/pipelineRun=<run>` 且其 `ownerReferences` 的 UID == run 的 UID；`clone-platform` 的 commit == P，`clone-ui` 的 commit == U；不读请求参数代替结果（交付流水线没有顶层结果，`k8s/cicd/tekton/pipeline-deliver-platform.yaml:56–96, 133–152`）。
- 三个工作负载：`platform-api` 与 `platform-workers` 的运行中 Pod `imageID` 都等于 `api_digest`，`platform-console` 等于 `console_digest`（workers 用 API 镜像，不是第三个构建，666 R-04）；rollout 完成（updated == replicas == ready）。
- 健康：STG `platform-api.bifrost-platform-stg.svc:8780/health` 返回 JSON 且 `status=="ok"`（不验版本，§11.7 补记）。
- 读工作负载前后各读一次 Deployment 的 pod template 摘要；两次不同 → 丢弃证据重读（不宣称跨系统原子快照）。

### 8.3 结论

| 情况 | verify |
|---|---|
| run Failed | `failed{run_failed}` |
| run Succeeded，四项都过 | `verified` |
| run Succeeded，results 与 P / U 不符 | `failed{wrong_input}`（不重试：发 `stg_blocked`，因为同样参数会再错） |
| run Succeeded，工作负载摘要等于**另一次**可信 run 的摘要，且那次 run 晚于本次 | `superseded`（需要那次 run 的完整证据，§10 结算它） |
| run Succeeded，rollout 未完成或健康失败 | 先等（最多 15 分钟），仍不过 → `failed{rollout|health}` |
| 任何读取失败 | 不写（unknown） |

`verified` 之后同事务逐个成员现读其 R 在 P 中的有效性：确定有效 → `delivered`；确定撤销 → `disposed`；未知 → 保持未结算，下一轮再读（不并入无效集合，666 B-06）。全部成员有去向后写 `settled`。

## 9. 失败、重试与终结（B-05）

1. `verify{failed|superseded}` 后：
   - 预算未尽、错误可重试（`run_failed`、`rollout`、`health`、`superseded`）→ `retry{try+1, not_before}`，同 P、U；
   - 不可重试（`wrong_input`）或预算用尽 → `settled`（用尽的 `exhausted`，其余 `released`），用尽的成员发 `stg_failed` 卡。
2. **放弃 / 交接**的合法来源：`OPEN`；`SNAP` 且该 try 没有 `started`；`FAILED|SUPERSEDED`（上一 try 已确认终态）。`STARTED` 且未确认终态时不得终结。
3. 去向词表：`delivered`（verified 且 R 有效）、`released`（回到待发布，次数与 not_before 不变）、`exhausted`（当前代际用尽，等授权）、`disposed`（确定撤销 / no_merge / Owner「不发」）、`superseded`（已被外部发布结算，§10）。
4. 候选集合（§3.1）排除 `delivered`、`disposed`、`superseded`、`exhausted`（直到 `granted`），只接回 `released`。

## 10. 外部发布的结算（661 B-07、666 B-05、B-06）

1. 只读循环（不持窗口，不受 live 开关限制）发现任何 Succeeded 的 `bifrost-deliver-platform` run X 未被结算：按 §8.2 取证。证据不全 → 不结算。
2. 证据完整 → 取 X 的实际 P2；对每个「仍未交付、未处置」的成员，若 R 在 P2 的历史里且在 P2 中有效 → `ext_verified{covers}`。
3. 未终结批次：
   - 没有执行占位（OPEN、SNAP 无 started、FAILED|SUPERSEDED）且成员全被覆盖 → 追加 `settled{superseded}`，释放批次槽；部分覆盖 → 覆盖的 `superseded`，其余 `released`；
   - 有执行占位（STARTED 未终态）→ 只写 `ext_verified`，不终结批次、不停止观察原 run；原 run 终态后其 verify 可能是 `superseded`。
4. 外部结算保留 `ext` 来源与 X 的身份，**不计入**运行时自动发布（★ 与占比统计用）。
5. 外部发布也成为新的部署基线（§5.3）：人工发布正是 §5.1 第 2 条「非落地提交挡住快照」的出口。

## 11. 窗口生命周期（R-02、S3 用例 ⑦）

| 阶段 | 持窗口？ | 说明 |
|---|---|---|
| 选 P、U、发前检查 | 持（who = `stg:<repo>:<n>/<try>`，what = 仓库名） | 拿不到 → 本轮不做，不开 snapshot |
| CI 未出结果 / 资格等待 / `stg_blocked` | **释放** | 等待不占窗口，人工发布可以拿到 |
| 最终闸 → `started` → Create | 持 | 最终闸核对窗口未过期、who/what/环境就是本 try |
| run 运行中 | 持并续租（每分钟、ttl 5 分钟） | 续租在独立的有界 goroutine 里，慢 Git/HTTP 不阻塞 |
| 续租失败 | — | `diag{lease_lost}`（按 try + 租约代际去重），**继续观察**，不终止 run（用例 ⑧：不因此算 verified，也不因此算失败；核验按 §8.3 用部署身份判断） |
| 核验完成（任何结论）/ `retry` 进入退避 / `settled` | **释放** | 释放用读到的 resourceVersion 做带版本更新（`delivery/window_store.go:213`，`aa30a556`）；冲突（别人的新窗口）不强删、不重试覆盖 |
| 关 live 且无执行 | 不持 | — |

读到过期窗口时只判断「是否可持」，**从不删除**（`aa30a556` 已实现，用例 ⑦）。

## 12. 问题卡（接 B3，R-03）

批次卡没有 root：仿 `repo_stopped`（`store/landing_cards.go:43, 57, 66, 182`），卡身份为 `{kind, batch, trigger_seq}`；`badCardRecord`、`HandleLandingCardAnswer` 加一个按 kind 分派到 B5 的分支，业务记录（`granted` / `withheld`）与答复记录在同一事务；继承唯一绑定、先落库后 Ack、过期补卡、held 24 小时、限频。

| kind | 是否发卡 | 触发（持久 seq） | 选项 | 适用性 / 结算 |
|---|---|---|---|---|
| `stg_failed` | 发 | `settled` 中出现 `exhausted` 的事件 | `retry_release`（再自动发三次）、`do_not_release`（不发） | 答复时现读成员：已被外部结算 / 已处置的剔除；全部剔除 → moot；写 `granted` 或 `withheld{owner}` |
| `stg_blocked` | 发（决定类：需要人工发 STG） | 首次阻断事件（`diff_unlanded`、`diff_ineligible`、`baseline_unknown`、`baseline_moved`、`ci_red`、`ci_missing`、`collision`、`object_lost`、`wrong_input`）| `ack`（我会人工发 STG）、`remind_later` | 外部发布结算后自动 resolved；计时从持久事件起算，不用每轮的 now |
| `stg_ineligible` | 发 | `withheld{ineligible}` 事件 | `ack`、`remind_later` | 只是告知：规则硬底线不能靠答复绕过 |
| `pending_long`、`running_long`、`lease_lost`、`verify_unknown`、`live_off` | **不发卡**，只在落地状态里显示 | 对应持久事件 | — | 与 S3 的 `ci_stuck`、`parked_long` 同一做法（问题库额度共享） |

`do_not_release` 是发布处置，写 `withheld`，**不**伪装成 `failed{declined}`。
