## 2. 口径（脚本里写死，改动即升版本、重跑基线）

| 项 | 口径 | 理由 |
|---|---|---|
| 窗口 | 夜班 23:00–09:00，交接 09:00–12:00，美国中部时间，按夜班开始的日期命名。时区换算按美国规则内置在脚本里（3 月第二个周日到 11 月第一个周日是 UTC-5，其余是 UTC-6），不依赖系统时区库 | CI 镜像不保证装了时区数据。窗口边界都不落在 01:00–02:00 的切换小时里 |
| 归段 | 一件事按开始时间归到某一段；时长截断到段内 | §7.3「跨窗口的时段按窗口截断」 |
| 运行种类 | 名字以 `landing-` 开头的是落地；否则 revision 在 main 首亲链上的是推 main；其余是推分支 | 沿用设计稿 §2.3 |
| 结果 | Succeeded 算绿，Failed 算红，Cancelled 算无结论、不参与，仍在跑算 Unknown | 取消的运行不代表代码的对错 |
| main 状态（代理钟） | 在时刻 t，取「到 t 为止有 main 运行的、首亲链上最新的 revision」，用它最近一次运行的结果，结论在运行创建时生效 | 设计稿基线用的口径，保留它以便对照 |
| main 状态（终态钟） | 同上，但只看到 t 为止已经结束的运行，结论在 completionTime 生效 | 这是当时真正能读到的状态 |
| 旧 revision 重跑 | 不改变 main 状态，因为 revision 按首亲链上的位置排序，不按运行时间排序 | 重跑旧提交说明不了 main 顶端的情况 |
| Owner 推送 | 某个 revision 的第一次 main 运行，且它的 `base..revision` 首亲链区间里没有带 `Landed-By` 的提交。同一 revision 的重跑不重复计数 | 落地的推送都带 `Landed-By` 尾注 |
| 交付 | 夜班段内由 `seat:coordinator` 创建的 hand-in 任务 | 运行时里能查到的交付 |
| 上 main | 该任务任一落地 op 第一次出现 `landed` 事件 | 落地流的对账结果 |
| 等待 | 交接结束前上了 main 的，取「上 main − 交付」；其余（包括被拒的）取交接结束时的年龄，并标为未完成 | §7.3「没完成的按窗口结束时的年龄计」 |
| 分位数 | 最近秩法（nearest-rank），不插值 | n 很小时也有定义，也不会编出两件之间的值 |
| 复核第一轮 | 该交付在交接结束前的第一条 `method=review` 记录的结论 | 运行时的复核记录 |
| 落地失败归因 | 把候选首条失败行和基点 M0 的 main 运行首条失败行比较，得到 `same_first_line_as_base`、`differs_from_base`、`base_green`、`base_unknown` 之一 | 只是机械标签。按 S5 规则，首错截断时一律算 `unattributable` |

## 5. 判定口径（按推荐冻结为 `night-metrics/1`）

每项列出了选项和推荐；判定按推荐执行，要改就升口径版本、重跑基线。两边的数脚本都会出。

- **O1 基线样本不足**：11-03 夜只交付了 2 件。
  - (a) 仍然用 11-03 作基线，标上「样本不足」；
  - (b) 交付相关的几项（完成率、等待、复核、积压），改用同一份快照里达到样本数的几晚合并；事故相关的几项（红时长、卡片、补漏）仍然用 11-03；
  - (c) 在 S1 开工前再量一个合格的夜班。
  - 推荐 (b)：查询和保留期都相同，不拖慢实施。只用 2 件算分位数，说服力太弱。同快照里各晚的数见 §6。
- **O2 补漏推送的口径**：
  - A：一次 Owner 推送，推的时候 main 是红的（按终态钟），它自己的 CI 是绿的，也就是把 main 修回绿的那一推；
  - B：凡是推在红 main 上的 Owner 推送都算；
  - C：每次推送由人标注是不是补漏，并写原因。
  - 推荐 A：可以机械地判定，含义也就是「把 main 修好」。B 会把正好赶上红 main 的普通推送也算进去，比如 `xn7w9`。设计稿的 1 次最接近 `4xkk4`（`1a6ae34`，补 `0c841a4` 带进来的重名函数），但这只是从提交说明读出来的，系统里没有标记。
- **O3 交付到上 main 等待的判定**：分位数一律用最近秩法。
  - (a) 只看 P50；
  - (b) P50 和最大值都不比基线差；
  - (c) 同 (b)，但允许 10% 的余量。
  - 推荐 (b)：未完成件按年龄计入以后，最大值正好能挡住「留一件不管」的做法。n 在 3 到 9 之间时，P90 就等于最大值，所以不单列 P90。
- **O4 挂起时长的基线**：`base_only` 现在还不存在。
  - (a) 基线记为 0 次、0 小时；
  - (b) 用等价量：基点红导致的落地失败，从失败到卡片答复的时长，这一晚是 #102，00:36 → 09:21，8.75 小时；
  - (c) 用现有的 parked（window/limit）。
  - 推荐 (b)：S5 要替换的正是这一段。选 (a) 的话，以后只要有一次挂起就判为变差。
- **O5 「交付」的范围**：
  - (a) 只算统筹的 hand-in（现行口径）；
  - (b) 把夜里备好、等 Owner 推送的提交也算进去，这一晚是 19 个、2.2–9.4 小时。
  - 推荐 (a)，(b) 照常列为参考项。A1 不改变硬底线推送要等 Owner 这一点。
- **O6 红时长按哪个钟判定**：两个钟都报。推荐判定用终态钟，因为那才是当时能读到的状态。
- **O7 被拒的交付怎么算等待**：现行做法是按窗口结束时的年龄计入，依据 §7.3 的原文。另一个做法是只计入完成率、不计入等待。推荐保持现行做法。
