## 修订一：§4.3 选哪一次 CI

原文：「按 creationTimestamp 取**最新**一次……最新一次是 Running / Failed / Unknown：即使更早的一次绿，也等待（Failed 写 `blocked{ci_red}`）。」

改为：

3. 列出 P 的全部平台 CI（条件同第 2 条），先把**范围不全的绿**放到一边：Succeeded 且 pipeline 结果 `api-scope` 为 `console`
   的那次只测了 console 能碰到的 Go 包，既不能放行 P，也不能盖住任何一次红。没有 `api-scope` 结果的 run 早于这个结果，视为 `full`；
   `api-scope` 不是 `full` / `console`、或出现不止一次，算结果不可用（`ci_results`）。
4. 在剩下的里面按 creationTimestamp 从新到旧，**越过「还没有结论」的运行**，取第一次有结论的：
   - 「还没有结论」：身份合格（同第 2 条与结果检查前的身份检查），没有 `completionTime`，并且 Succeeded 条件恰好一个且 `status=Unknown`
     （Tekton 的 Running、Started、PipelineRunPending、CancelledRunningFinally、StoppedRunningFinally 等都属此类），或还没有任何
     Succeeded 条件（刚建、还没有 status）。有 `completionTime`、或 Succeeded 条件不止一个，都不算「还没有结论」。
   - 只越过**严格更新**的运行：与所选那次同一时刻的，仍按并列规则（结果全同取名字字典序第一，否则 unknown）。
   - 身份不合格的运行不被越过，照旧以 unknown 挡住。
   - 全部都还没有结论：照旧报告最新那次（Running），等待。
5. 选中的那次：Failed → `blocked{ci_red}`；Unknown 且有原因 → `blocked{ci_results}`；Succeeded → 照原第 3 条检查结果并写 `ci_accepted`。

与原文的差别在三类运行：**更新但还没有结论的**（原来让 B5 等它，现在越过它）、**范围不全的绿**（原来没有这一类），
以及 **`api-scope` 畸形的绿**（原来算绿，现在 `ci_results`）。
更新的红、更新的不可用结果、身份坏的运行、同一时刻并列，处理不变。

## 修订二：§4.4 快照之后出现同 P 的新 CI

原文：「同 U 但 Running / Failed → 当前 try 不受影响（创建输入已冻结），下一 try 的最终闸等它有结论」。

改为：「同 U 但还没有结论 → 当前 try 不受影响；下一 try 的最终闸**同样越过它**（按修订一）。它之后的结论由修订三的发送后检查接住。
同 U 且已是红 → 下一 try 的最终闸 `ci_red`，与原来相同。」

## 修订三（新增 §4.6）：发送后的检查

每一次发送（try 的最新许可：它的 `started`，或替换它的 `resend`；`retry` 开出的新 try 是另一次发送）在 24 小时内，B5 读
P 的全部平台 CI（规则同修订一，**不按创建时间截断**：main 那一轮的 webhook 晚多久都算）。如果其中最新有结论的那次比本批接受过的所有 CI 都新：

- 为 Failed → 写 `blocked{ci_red}`；结果不可用（含身份不合格 `ci_identity`、同一时刻并列 `ci_tie`，与最终闸相同）→ `blocked{ci_results}`。记录与最终闸写的同形，`detail.sent` 另记
  `{batch, try, permit_seq, run, ci_run}`，标明这是发送之后才发现的。
- 后果全用现有机制：Owner 收到「STG release blocked」卡（发送后的阻断另有说明：P 已在 STG、哪次 CI 变红、STG 不回滚、怎样解除）；
  阻断开着时不开新批、最终闸拒发；正在跑或在核验的 try 照常观察、核验、结算。
- 解除与原 ci_red 相同：同一 P 出现更新的、范围为 full 的绿（例如重跑 P 的平台 CI）。较晚提交的绿、手工发布 STG 都不解除。
  重跑要走带 `repo-url` 参数的途径：platform 的 `start_pipeline_run`，或保留原 spec 的 Tekton 重跑。手工新建、缺 `repo-url` 的 run 身份不合格：
  它会成为最新有结论的那次，另开一个 `ci_results` 区间，什么也解除不了。
- 一次被拒的运行只开一个区间：已有区间（开着或已解除）点名过它，就不再开——否则解除它的那次绿已记在旧区间里、不能再用，B5 会停住。
- **只在 main 仍停在 P 时开**（统筹 11-01 定为选项 A）：开之前用 B5 读 main 的同一途径读一次 main 头。头已不是 P → 不开、不写台账，
  记一条日志「P 的发送后 CI 红未开阻断，因为 main 已前进到 X，交给 X 的检查」（含 P、X、原因、CI run、批次 / try / 许可），这次发送记为了结。
  这次运行已被某个区间点名过的，不记日志，直接了结。
  理由：B5 只发线性快进的 main，X 的树包含 P；**B5 只凭 full 范围的绿发 X**（修订一第 3 条：console 范围的绿被放到一边，`Record()`
  也拒收非 full 的证据）。所以 X 发 STG 前，必有一次 X 的 full 绿：X 的落地 CI 跑的是 full 时就是它，X 只改 console 时
  （落地 CI 是 console 范围）就必须等 X 在 main 上的 full 一轮。两种情况都是在含 P 的树上跑整套 Go 测试；X 的最终闸与 X 发送后的检查也照本节执行。
  这与 §4 原有的「main 变了就交接」一致。读 main 失败 → 不开、不算前进，按读的间隔再读（发送后头一小时 2 分钟，之后 10 分钟）。
  - **兄弟仓库漂移**：STG 上此刻是 P 加上被复用那次 CI 测过的 U / I——这个组合本身是绿的；main 那一轮变红若是因为它取到了更新的 ui / infra main，
    而漂移到 X 的 full 一轮时仍在，X 也会红，X 的最终闸（发送前）或 X 的发送后检查（发送后、main 仍在 X 时）会开阻断。
  - **偶发 / 不确定的缺陷**：可能在 X 的 full 一轮里不复现，于是没人拦——这是残余风险 6。

了结（不再读这一次发送）：没读到可拒的运行，**main 已离开 P**，且 P 没有比最新有结论那次更新、还未出结论的运行
（更旧的在跑运行不等：按修订一，它的红永远不会被选中）。main 还停在 P 时，**任何绿都不了结**——
P 的新运行随时可能建出来再变红（webhook 晚多久都算），而且分不出哪一轮是 main 推送的：每次落地先把 P 推到 `land/prod/…` 分支，
这次推送跑的是同一条 ci-platform、带同样的标签（实测 cicd 里 41 次落地每次都有，比落地 CI 早 5–30 秒建出）。所以 main 停在 P 期间一直读到 24 小时。
**开了阻断也不了结**：阻断可能被 P 的重跑之绿解除，之后 main 那一轮晚建出来再变红，仍要挡（另一次运行，等前一个区间解除后另开一个；同一次运行永不开第二个区间；区间开着时又来同一原因的拒绝（同一 P、同一原因、同一基线），按最终闸的规则复用开着的那个，不出第二张卡；
原因不同——例如开着 `ci_red` 时又来一次不可用的 `ci_results`——仍另开一个区间、另出一张卡）。
读 main 失败、或读到的不是完整提交（ls-remote 什么也没打印）→ 不了结、不开阻断，按读的间隔再读。
main 离开 P 时 P 还有比最新有结论那次更新的在跑运行 → 读到它出结论（红则按上一条记日志交给 X）；了结之后建出的不再读。

读的间隔：发送后一小时内每 2 分钟一次，之后每 10 分钟一次。
（R5:5.7-2 平台复核第 1 轮指出：最初按「许可时刻 + 10 分钟」截断，webhook 晚过 10 分钟的 main CI 先绿后红都看不到；
第 2 轮本地预审又指出：按名字分辨「落地 CI / main 那一轮」不成立，落地分支推送那一轮的绿会让检查提前了结。已改为上面的规则。）

## 残余风险（必须写进设计）

1. **STG 会在 main 上那一轮 CI 出结论之前拿到 P。** 依据是同一个完整 SHA、同一棵树、范围为 full 的另一次绿（通常是落地 CI）。
   两次的差别只在兄弟仓库 ui / infra 的取值：STG 用的是被复用那次的 U / I（§4.5「被测输入与交付输入一致」不变），
   main 那一轮可能取到更新的 ui / infra main。main 那一轮若因此或因偶发失败变红，STG 上已经是 P；兜底是修订三：阻断后续自动发布并告知 Owner，不回滚。
2. main 停在 P 超过 24 小时后才变红的 P 的运行不在发送后检查范围内；main 那一轮一直没建出来（例如 webhook 丢了）也看不出来——
   分不出哪一轮是 main 的，检查只认「有没有更新的红」。
3. platform-api 停机超过 24 小时，期间变红的不会被发现。
4. 范围规则依赖 infra 的 `api-scope` 结果名与取值，**三处**读它：infra 的 `scripts/release/ci_gate.py`（R5:5.7-1 起）、platform 的
   `delivery.PolicyFacts.CIIndex`、platform B5 自己的 `agentrt/landingci/release.go`（`APIScopeResult`、`fullScope`、把 console 范围的绿放到一边、
   `Record()` 的全量检查）。结果名或取值一旦变了，三处必须一起改，否则新 run 会被当作旧 run（full），范围不全的绿会被放过，B5 会凭部分测试发 P。
   三处共用结果名与取值，但用法不同：畸形 `api-scope` 的绿，CIIndex 跳过、B5 判 `ci_results` 挡住；`ci_gate.py` 推 main 时（没有全量 run 结束）
   把 console 范围的成功算成功，发布时（`--require-full`）不算。
5. 发送后检查每次读是一次 cicd 的 PipelineRun 全量列表（实测 435 个、约 12 MB），之后再读一次 main 头（只有「没有可拒的、但 P 还有比最新有结论那次更新、未出结论的运行」时不读）；
   每次发送在头一小时最多每 2 分钟读一次、之后每 10 分钟一次，每轮最多读一次发送。长期在读的只有 main 当前那个提交的发送：
   main 停在 P 读满 24 小时，**每次发送**约 168 次；同一 P 的每次 retry / resend 各算一次发送，k 次发送约 k×168 次列表加 k×168 次 ls-remote。
   旧提交的发送在 main 离开后的第一次读就了结（P 没有比最新有结论那次更新的在跑运行时）。

6. **（选项 A 的代价）main 已前进之后才出结论的 P 的红不进台账**：main 离开 P 时已在跑、且比最新有结论那次更新的运行，红了只在
   platform-api 日志里留一行（已被区间点名过的不记）；比它旧的在跑运行、以及了结之后才建出来的运行，不再读，连日志也没有。Owner 不会因它们收到卡片。
   兜住它的是 X 的 full 绿（见修订三最后一条）：确定性缺陷与仍在的兄弟仓库漂移会让 X 也红；**偶发 / 不确定的缺陷可能在 X 上不复现**，
   这时 P 的那次红就无人跟进。若 X 把 P 的那个失败测试删掉或绕过，同样无人跟进——那属于人为改动，由 X 的评审负责。

## 已定（统筹 11-01，按推荐）

main 已前进到 X 之后 P 的 main CI 才变红：选项 A，不开阻断、交给 X 的检查（见修订三最后一条与残余风险 6）。
