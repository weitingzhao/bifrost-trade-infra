## 0. 结论

- 11-03 夜的 A 类问题有 4 件，背后是同一个缺口：**「进 main 前要过什么」有三份定义，而且结果怎么读也有两套规则**。三份定义是集群 CI 的 quick 段、push-main 的本机测试、统筹手动跑的检查。
- 逐件补，只会让清单和读法越来越多。push-main 已经因此多了一条特例（TD-515），TD-513 的原修法还会再加两条。
- 推荐方案 A1：
  - **一个裁判**：集群流水线 `bifrost-ci-infra`；
  - **一份清单**：放在 infra 自己的仓库里，按实际执行结果证明覆盖；
  - **一套证据读法**：候选、基点、兄弟仓库、工具和用途，全部对上的结果才算数。
  - push-main 和落地读的是同一种证据。
- 第 1 轮复核补上了 4 个原稿没有想到的地方：
  - 已登记的消费者跨仓变化时，没有可行的先后顺序（§5 S6）；
  - main 已经红了的时候，补登记那一推本身过不了门禁（同上）；
  - CI 镜像里没有 Node，quick 段的隔离约束要保留，agentd 也在用同一个清单生成器（S1b）；
  - 「基点的错」不能只看同一段都红来判定（S5）。
- 其余三类实测后的结论（§8）：
  - B 类（先存后发）：机制是共性，语义不是。先定一份契约测试清单，不急着做公共件；
  - C 类（控制器每轮从全历史重建）：共性。同族 8 条债合成一份设计，但要分别给出修法和验收；
  - D 类（两种时钟混比）：同一条规则被抄了 7 份。只换成另一个进程的事件时间还不够，必须统一到一个时钟或一种顺序语义。
- 有没有效，看三样东西：
  - 每行回放写明预期结果类型（§7.1）；
  - 覆盖按实际执行来量（§7.2）；
  - 用统一窗口和反作弊的指标，连量 3 个夜班（§7.3，即 R5:5.7-7）。

| 写入 infra main 的入口 | 谁走 | 进 main 之前过什么 |

## 3. 目标（可量化，验收用）

1. 落地和 push-main 两条写入入口，进 main 之前都取得同一条流水线、同一份清单的结果。结果按 §5 S4 的证据键读取。
2. platform 引入的消费者命中变化，在 platform 进 main 之前就被检查（S6）。
3. 清单的发现全集里，每个测试文件要么被实际执行，要么带原因和期限豁免。执行证据包括收集数、执行数、跳过数及跳过原因（S1）。
4. push-main 里不再有 infra 专用的挑测试逻辑，也不再有纯文档跳过 CI 的分支。
5. 落地失败按归因分成 4 种状态（S5）。只有「纯基点的错」不推卡，其余照常推。
6. 推 infra 的端到端等待先实测再定目标（S3），不拿本机并行的成绩外推。

## 4. 选项

| 选项 | 做法 | 好处 | 代价 |
|---|---|---|---|
| **A1（推荐）** | 集群流水线是唯一的执行者；清单只有一份；push-main 和落地读同一种证据 | 一个执行环境，一套读法；push-main 的特例可以删掉 | 要改 trigger、resolve、infracheck 和工具镜像；推送要等集群（S3 实测） |
| A2 | push-main 在本机跑同一份清单和同一份检查代码 | 不依赖集群 | 要长期维护本机和集群在工具、输入、证据上的等价；本机跑不了 quick 和 parity-static |
| A3 | Owner 的硬底线推送也改走落地，由他在 Console 上批 | 只剩一条入口 | 授权模型要改；5.5-11 失去意义；Owner 每推一次多点一张单 |
| A1 + 分支保护 | 在 A1 之上，Gitea 给 main 设必需的状态检查 | 连第三条入口也收口 | 这是授权改动，只能由 Owner 来改；紧急修复要有放行办法 |

推荐 A1，「加分支保护」列为 Owner 可选的下一步。共用清单和判定规则，其实可以由多个执行者分别使用；选 A1 不是因为「两个执行者」本身是问题，而是因为在本机复现集群的工具和输入，成本比让 push-main 等集群高。

## 5. A1 的切片

顺序：S0（已做）→ S0b → S1 → S1b → S6 → S2 → S3 → S4 → S5。S4 落地之前，push-main 的本机测试保留作兜底。

- **S0b 冻结基线查询**：把 §7.3 的查询写成脚本，在任何实施之前提交。脚本输出原始的运行、卡片和交付标识，基线跑一次、存档。
- **S1 一份清单**（`scripts/landing/test-inventory.yaml`）：
  - **发现全集**：按文件名和目录规则列出所有测试，包括 4 种命名之外的 `*_test.sh`、agent-guard 的 JS、`*.test.yaml`。新增的命名形式要先进规则。
  - **每条记录**：路径、执行器（pytest、node、bash、promtool）、依赖、环境标签。环境标签分 `agent-fast`（单仓、无网络、无回环）、`main-gate`、`needs-host`（要真 NAS 或真集群）。
  - **豁免**：每条写原因和到期日，不设无期限的豁免。
  - **执行证据**：每次运行记下每个文件的收集数、执行数、跳过数及跳过原因。清单里的文件收集数为 0 就算失败（不再沿用 pytest 退出码 5 当成功的规则）；整个文件全部跳过也算失败，除非这一跳过写在豁免里。
  - **防线**：发现全集里有文件既不在清单、也不在豁免里，报 `inventory_uncovered`。
  - **跨仓依赖矩阵**：要读别的仓库的测试和检查（flex-query 的发布测试、11 个仓库的路径检查、parity），每一项写清：由哪个执行入口跑、用哪个提交、依赖缺失时怎么判。缺失一律报「未核实」，不能因为执行了一部分用例，就掩盖必要的断言被跳过。
- **S1b 执行环境**：
  - ci-infra 的工具镜像加上固定版本的 Node，同时更新 `docker/ci-infra/TOOLS.expected` 和镜像 pin（`docker/ci-infra/Dockerfile:8-14`）。
  - 并行执行器保留 quick 现有的隔离：Python `-I`、`-c /dev/null`、`--noconftest`、关闭插件自动加载、拒绝测试路径上的 `__init__.py`（`api/internal/agentrt/infracheck/check.go:20-50`）。用「候选自带的配置想藏住一个失败」做回放。
  - agentd 的 Verify 也用 `infracheck.Check()`，它的 checkout 是单仓（`api/internal/agentrt/store/repos.go:97-109`）。Verify 只取 `agent-fast` 的子集；放进 main 只认 `main-gate` 的结果。
  - 旧的 golden 留作渲染回归，写明退出条件：S1b 上线、agentd 的版本都读清单以后删掉。
- **S6 跨仓的消费者登记**：
  - 台账里已有两条和这一片直接相关，修法都等 Owner 定：
    - TD-490：platform 的落地不查 infra 的登记表。它的修法 A 就是下面的 (a)。
    - TD-466：platform 一侧把单词 `work` 也当成信号。修法 A 是只认目录信号（`agent-config/work`、`multi-agent` 这类）。
    - §2.4 里出自 platform 的 4 起，以及 11-04 的 3 处（P-a 到 P-c2 带进的，已在 infra `8ff29ec` 登记），全都只是单词 `work`。
    - **推荐 TD-466 A 加 TD-490 A 一起做**：platform 一侧大部分登记负担会随之消失，下面 (b)(c)(d) 只剩真正读文档的程序。
  - (a) platform 的落地 CI 和推送 CI，都以「platform 候选 + infra main」跑一次 infra 的 consumers 段。新命中没登记，就在 platform 一侧被拒。
    - platform 的 CI 证据要带上这次用的 infra 提交；infra 的登记表变了，旧的 platform 结果作废，不能沿用（现在 `ci_gate.py` 不看 infra 输入，S4 的共用读者同样用于 platform）。
    - 纯文档跳过 CI 对 platform 的 `CLAUDE.md`、`AGENTS.md`、`SKILL.md` 也适用，而这些文件会被消费者扫描（`scripts/landing/doc_consumers.py:16-17`）。S6 的接线验收包括：这些文件进 main 之前也跑 consumers。
  - (b) **已登记的消费者命中变化**：登记行加一个迁移状态，在有限的窗口里同时接受旧、新两个指纹。顺序是：infra 先加新指纹 → platform 落地改动 → infra 删掉旧指纹。转移规则在 S6 的设计里列成矩阵，至少写清：
    - 新指纹什么时候生效：迁移行上了 infra main 才生效；
    - 删旧指纹之前，怎么确认固定的 platform 输入已经是新版本；
    - 窗口过期还没收尾时，怎么报错、回滚；
    - 真实的读者如果 `class` 或 `reads` 变了，迁移期间要保护的读集合怎么保留。
  - (c) **main 已经红了时补登记**：候选只补登记、补的都是基点 main 上已经存在的命中、并且指纹和基点内容一致，就作为「登记修复」放行，并留审计记录。候选自己新加的命中，照旧只认基点的登记表。
    - **登记表自己也是被扫描的文件**（`agent-config/landing/doc-consumers.yaml:11`）：补一条登记行，会让登记表自身的指纹变化。处理原则是：
      - 先用冻结基点的检查器，核对这次登记改动在语义上合法：只补基点已有的命中，指纹和基点内容一致；
      - 核对通过后，接受这次合法改动机械带来的登记表自身指纹变化；
      - 其他所有外部消费者，仍按冻结的输入和已经生效的迁移允许集合检查。
    - 候选整张登记表，不因为处在「修复」或「迁移」状态就成为这次放行的依据。
  - (d) 把「保守扫描的登记负担」和「真正读文档的程序」分开计数，作为以后要不要收窄发现规则的依据。是否收窄不在本方案里定。
- **S2 推分支以 main 为基点**：
  - trigger 加上 ref 参数，区分推 main 和推候选分支。推 main 保持现在固定 before 和 after 的语义。
  - 推候选分支时，resolve 以当时的 main 为基点，并核对候选是 main 的后代。候选 clone 的深度要足够证明祖先关系，否则报 `ancestry_unproven`，不能默认通过。
  - `agent/` 和 `land/` 照旧排除，落地照旧用固定的 M0，不改成后来的 main。
  - webhook 晚到时，按证据键（S4）判断这次结果还算不算数。

  - **判定的前提是证据完整、可比**。现在 consumers 和 code-health 遇到第一个错就退出，前面一段失败后，后面几段也不会执行（`scripts/landing/doc_consumers.py:46-52`、`scripts/landing/coverage_infra.py:82-89,239-246`）。所以：
    - 各段要能在诊断模式下列出全部失败，而不是只给第一个；
    - 每个失败都要有可以比较的指纹；
    - 对照组的比较基准要写明：候选检查的是「基点 → 候选」；对照组要用同样的比较语义、同一检查器和执行身份，具体怎么构造在 S5 里定。不能简单地重跑「基点 → 基点」，那样 code-health 会恒等通过。
    - 首错截断、某段没有执行、比较语义不同，一律判 `unattributable`，直到补齐证据。
  - **判定表**（B 是基点的失败集合，C 是候选的失败集合，两者都完整、可比）：

    | 条件 | 状态 | 处理 |
    |---|---|---|
    | C 为空 | 成功 | 照常落地 |
    | C 非空，C ⊆ B（包括相同，以及候选修掉了一部分旧错） | `base_only` | 挂起，不推卡 |
    | C 非空，且 C 与 B 不相交 | `candidate_new` | 照常推卡 |
    | C 与 B 相交，且 C 不包含于 B | `mixed` | 照常推卡 |
    | 证据不完整或不可比 | `unattributable` | 按同样的输入补跑对照组，再判 |

  - 这些状态互斥，并且覆盖所有情况。只有 `base_only` 挂起、不推卡。
  - 状态转移：
    - 基点用原来的 SHA 重跑转绿 → 重放；
    - main 前进 → 控制器重新准备候选（现在的行为，`api/internal/agentrt/controller/landing_drill.go:108-132`），然后重新归因；
    - 基点 CI 缺失 → 去跑；
    - 进程重启 → 按事件流恢复；
    - 挂起时间计入 RootBudget（`landing/drill.go:146-190`），超过上限就推卡，写明「基点一直没恢复」。这类卡单独计数，和「归因判错导致的推卡」分开统计（§7.3）。
  - 现在 scope、consumers 和 doc-policy 三段的结果合写在 `doc-policy` 一个字段里（`scripts/landing/coverage_infra.py:235-245`）。S5 要先把每一段的失败行分开存。
  - 这一片在 platform 的落地模块。
