## 1. 要做成什么

1. **只读界面的判定改准**（原 5.2-10）：
   - 只引类型的 import 不算 I/O；
   - 测试文件不进产物，不做 I/O 检查；
   - 页面调用登记为只读的数据钩子不算 I/O。
2. **放行跟着改动走**（E1）：等放行期间 main 动了，重放出来的改动内容和已放行的那次一样、CI 也绿，就沿用原放行，不作废、不再出卡。
3. **落地额度按仓库设**（原 5.2-10）：landing:dev 每个仓库可以有自己的 `max_landings_per_day`。

## 2. 契约

### 2.1 只读界面的判定
- import 检查只看会产生值的 import：
  - `import type {…}` 整句跳过；
  - `import { type A, type B }` 所有名字都带 `type` 时跳过；
  - 只要有一个不带 `type`，照旧判。
- 测试文件（`**/__tests__/**`、`*.test.ts(x)`）只检查路径在不在 allow 里，不做 import 和副作用检查。
- 只读数据钩子登记表：放在 platform 仓库 `console/src/hooks/readOnlyHooks.ts`，导出一个名字列表。页面从 `hooks/` 引的名字全部在表里，不算 I/O。
  - 一条 Console 测试保证表里每个钩子只发 GET：mock `fetch`，断言 method 为 GET 或缺省。
  - 表本身的改动不在 landing:dev 的 allow 里，所以改表要卡。
- `fetch(`、`useMutation`、`window.location` 的判定不变。

### 2.2 放行跟着改动走
- 沿用条件（全部满足才沿用）：
  1. 同一任务、同一尝试、同一候选提交 A；
  2. 新操作的 `PatchSHA256` 与已放行操作相同（R 对 M0 的差异内容一样）；
  3. 文件清单、核心路径、决策链、可信复核四项相同；
  4. 新操作的软门集合是原放行豁免集合的子集；
  5. 规则身份和检查版本没变；
  6. 新操作的落地 CI 绿；
  7. 原放行没被撤销、没过期。
- 沿用写一条新的放行事件，引用原放行编号，标明「沿用」。审批单不变，不再出卡。
- 任一条不满足：照旧作废、照旧出卡，卡上写明是哪一条不满足。
- 硬核心路径（`hard_core_paths` 非空）的改动不沿用，一律出新卡。这一条留给你定（§3 F2）。

### 2.3 额度按仓库
- landing:dev 的 `repos[].limits` 可以写 `max_landings_per_day`，没写时用全局的值。
- 要签 landing:dev v6 才生效（你签）。

## 6. 风险与未核实

- 沿用放行的前提，是「改动内容相同」就等于「你批的东西没变」。但 main 上的新提交可能和这个改动在语义上冲突。这一点由新操作的落地 CI 兜底：条件 6 要求 CI 在新的 R 上重跑并且绿。
- 正则判定仍然可以被绕开，例如用字符串拼出 import 路径。现在的 S5 内容检查器（R5:5.4）是更完整的方案；本步只修已知的误判，不扩大放行面。
- 工作量：platform 约 1 人日，不含复核和等卡。
- 未核实：放行事件的词表和投影能不能直接加「沿用」一种，还是要新的事件类型（`store/vocab.go`）。实施时确认。
