## 1. 要做成什么

1. 一步如果分几片，就在它的完成规则里列出片号。每片的证据是一件挂在这一片上、已验收、已落地、并且 STG 已稳定的任务。全部片都成立，这一条才成立。
2. 任务在提出时写明它属于哪一步的哪一片。平台检查这一片在这一步的规则里有没有，没有就拒。
3. 只用通用原子（`step_tasks`、`step_landed`、`step_stg_settled`）的规则，只能用在单一交付的步骤上：这种步骤上第二件实现任务会被拒绝，并提示把规则改成按片。
4. 计划外已经落地的任务（P-a 到 P-c2），由 Owner 在卡上批一份「任务 → 步骤 / 片」的清单，挂到对应的片上。
5. 5.5-11 在此基础上，把「main 上显式认领的提交」作为片的第二种证据。

## 3. 契约

### 3.1 规则
- 新原子 `step_delivered {parts: [<片号>, …]}`。片号是 1–32 个字符（字母、数字、`.`、`-`、`_`），同一条规则里不能重复，最多 20 片。
- 一片的取值：
  - 本片有一件任务已验收、已落地、STG 已稳定（infra 这类没有 STG 发布的仓库，按落地即稳定，和 `step_stg_settled` 一样，`store/stepevidence.go:88-104`），这一片取 True；
  - 本片有任务在路上，或者落地状态读不到，取 Unknown；
  - 否则取 False。
- 整条是各片的三值 AND。它是历史原子，和三个通用原子一样（§0 #3）。
- 签收照旧放在最后：`all: [step_delivered {...}, owner_signoff "<ref>"]`。设含 `step_delivered` 的规则时，没有签收就拒（5.5-11 附录 C 的 S4）。
- 常备授权：含 `step_delivered` 的规则不在常备授权内，一律走卡（5.5-11 D6）。

### 3.2 片的绑定
- propose 接受 `plan_part`。条件：
  - 必须同时写 `plan_node_id`；
  - 这一步的现行规则里有 `step_delivered`，并且列出了这一片。
- 规则里没有 `step_delivered` 的步骤，写了 `plan_part` 就拒。
- 同一片可以有多件任务（返工、重交）。一片里有任何一件任务成立，这一片就成立。
- 新的计划改动 `bind_part {task, node, part}`：给已有任务挂到某一步的某一片。只能挂已验收的任务；一律走卡，不进常备授权。
- `handin.sh propose` 加 `--part`（infra）。

### 3.3 单一交付的约束（Q3 A）
- 步骤的规则只用通用原子、且没有 `step_delivered` 时，本步上第二件实现任务（`subject_task_id` 为空、`effect_class` 为 branch）的 propose 被拒。
- 拒绝信息写明：把规则改成 `step_delivered` 加签收。
- 验证和复核任务（有 `subject_task_id`）不计。返工照旧走同一件任务的新尝试，不是新任务。

### 3.4 Console
- 规则的文字说明：`step_delivered` 写成「Each of n parts (a, b, …) has an accepted task landed and settled on STG」。
- 步骤卡显示「Parts k / n」，每片一行：片号、任务、状态。数据来自 GET /plan?node= 的事实快照，不改 plan-view，所以闭合校验不受影响（§0 #6）。
- 旧 Console 遇到不认识的原子，会显示「Rule not recognised」（`planModuleModel.tsx:207`），不会出错。

## 7. 风险与未核实

- 新原子、新列、新的计划改动、propose 的新参数，都是架构级改动，要等 Q1–Q5 定下来才能动。
- 工作量估计：platform 一次落地约 1.5 人日，infra 约 0.3 人日；不含复核轮次和等卡。复核最多 3 轮。
- §3.3 的约束会拒掉现在「一步挂多件实现任务」的做法。现有步骤上没有挂任务（§0 #5），所以上线时不会误伤，但以后要先改规则、再挂第二件。
- 未核实：propose 的事务里能不能拿到步骤规则的行锁，并且锁顺序和 `lockChanges`（`store/planchange.go:215`）一致。这一点在实施时用并发测试确认。
