# 协作在哪里运行：页面在集群，Agent 分散在多台主机上，靠平台协作

状态：方向记录，2026-10-11。不是设计，设计是 W-67 的第一片。本文把 Owner 当天的两段话、已经签过的架构里和它有关的条文、现状和要定的事放在一处，供设计引用。

## 1. Owner 说的（2026-10-11 14:45、14:55）

- 进展页是今后多 Agent 协作的一部分：他靠它知道项目走到哪，也靠它及时给反馈。
- 它不能长期跑在本机：本机是他的 Mac Pro，不能 7×24 开着；他要用手机交互。
- 应该放到 Mac mini 上。两台 mini 都是 7×24 的，**任何一台都可以**，两台之间也可以协作。
- 多 Agent 的协作**不局限于单台主机**：可以分散在不同的服务器上，通过网络通讯协作；他提到两台 Windows 机器（跑 TWS 的）也可以考虑。

## 2. 已经签过的架构里，这件事是怎么定的

方向不是新的，`ADR-ops-architecture.md` 里已有，Owner 2026-10-07、10-08 定的：

| 条文 | 内容 |
|---|---|
| §1 | 平台不启动 Agent，也不替 Agent 做判断：**Agent 主机上的守护进程主动来领任务** |
| §3 位置表 · Mac mini `.50` / `.52` | 带外层 + Agent 层。宿主跑带外操作面和告警中转；**虚拟机里跑 Claude Code 线程、Agent SDK harness、沙箱**。不放集群管理员凭证、节点 root、子系统管理员密码；带外与 Agent 不共用账户和配置 |
| §3 位置表 · Mac Pro | 开发 + Owner 驾驶舱。不承担任何维护，不跑任何被 PROD 依赖的服务 |
| §3 位置表 · Win11 ×2 | 交易设备，**只有 TWS**；其他软件不放（以后可加维保进程，单独决定） |
| §3 位置表 · k8s 节点 | 不跑 LLM Agent 的执行面 |
| §5 分区 | 交易区（Win11 ×2）只出到 IB，到不了内网；Agent 区（mini 上的沙箱虚拟机）只能到平台 API、GitHub 和外网白名单，到不了数据库、Redis、TWS、NAS、K8s API、节点 SSH |
| §12.2 第 2 条 | **靠共享状态协调，不靠互相发消息**。事实只存一处，在 PROD platform |
| §12.2 第 10 条 | 不做 Agent 之间的聊天总线 |
| §12 执行 | `agentd` 跑在 Agent 主机上：先是 MacBook，之后迁到 mini 的虚拟机 |

所以「分散在多台主机、通过网络协作」在这套架构里的形态是：**每台主机只和平台说话，主机之间不直接说话**。两台 mini 互不知道对方的存在也能协作，因为任务、租约、状态、规则都在平台上。这也让增加一台主机不需要改别的主机。

## 4. 目标

**主机是一种角色，不是某一台机器。** 一台机器装上同一套东西（记录器的发事件一侧、命令的包装器、主机心跳、各家命令行、隔离的工作目录），向平台登记自己能做什么（哪几家已登录、什么系统、在哪个网络分区），就是一台 Agent 主机。平台按能力把任务租给它。

- **页面和交互**：集群上的 Console，7×24，手机可用。批准、回答、反馈、回执都在这里。本机看板只留作改样子的试验台。
- **状态**：平台是唯一来源。主机只推事件（W-66）；Console 只读平台。
- **执行**：任意多台主机。起步是两台 mini。
- **两台 mini 怎么协作**：从同一个队列领任务，各自带租约。三样好处：① 一台实现、另一台验收和复核，「作者不能验收自己的产出」（§12.2 第 3 条）落到了不同的机器上；② 一台失联，租约到期，另一台接手（阶段 1 的「卡住自动重派」）；③ 各家额度按主机上登录的账号分开用。
- **统筹**：现在是 Mac Pro 上桌面应用里的一个线程。目标是它也常驻在一台主机上；形态（无界面的命令行会话，或桌面应用加远程控制）在设计里比较后请 Owner 定，两种都还没有在 mini 上验证过。

## 5. 每类机器能不能当 Agent 主机

| 机器 | 能不能 | 依据和说明 |
|---|---|---|
| Mac mini `.50`、`.52` | 能，起步就用这两台 | §3：虚拟机里跑线程、harness、沙箱。两台对等，任何一台都可以先上 |
| Mac Pro | 过渡期在用，目标是不再依赖它 | §3：不跑任何被 PROD 依赖的服务。它合盖之后协作应当照常 |
| 以后新增的机器（另一台 mini、一台专门的 Windows 或 Linux 主机、云上的机器） | 能，装同一套东西并登记即可 | 设计按「与机器无关」来做。云上的 Agent 只碰公开仓库、只经 GitHub 的分支接入（§12 主仓库） |
| **跑 TWS 的两台 Win11** | **现在不能；将来会，放在最后**（Owner 2026-10-11 15:00 定） | §3 写的是「只有 TWS」；§5 把它们放在交易区，到不了平台。Owner 的话：现在没有计划，多 Agent 协作架构真正做完之前不敢在这两台上跑；但将来一定会在上面跑——它上去的那一天，就是整个系统真正用实盘数据的那一天；那里是真实账户，非常危险，要非常谨慎。所以它不是「多一台主机」，是整件事的最后一步，条件见第 9 节 |
| k8s 节点 | 不能 | §3：不跑 LLM Agent 的执行面 |
| 4090 | 不当主机，当算力 | §3：本地推理和重型计算，按需唤醒 |

## 6. 怎么走过去

1. **设计**（W-67 第一片）：主机装哪一套、怎么登记能力、凭证怎么放、统筹的形态、手机从外面怎么进。
2. **一台 mini 试点**：跑通一条「验收 + 独立复核」，统筹仍在 Mac Pro；Console 上显示的和实际发生的逐项对一遍。
3. **第二台 mini 加入**：证明跨主机——一台实现，另一台验收；拔掉一台，另一台接手。
4. **记录器和观测搬到主机上**（排在 W-66 第 2–4 片之后），Console 的数据不再来自 Mac Pro。
5. **统筹搬过去**。
6. 每一步之后 Mac Pro 合盖 30 分钟，看哪些还在走；最后合盖一整夜。

相关的已有条目：W-57 主机心跳、W-50 带外执行器、W-66 状态由事件生成、W-52 网页推送、W-62 Console 的进展页；运行时的阶段 0（任务、租约）和阶段 1（交互总线、叫停、自动重派）。

## 7. 要 Owner 定和做的

| 事 | 统筹方的建议 |
|---|---|
| TWS 的两台 Win11 上不上 Agent | **已定（Owner 2026-10-11 15:00）**：现在不上；将来上，放在最后，条件见第 9 节 |

| 各家命令行的登录 | 只能 Owner 做，每台主机一次 |
| 手机不在家里的网络时怎么进 Console | 没有实测过，现有文档里也没有远程接入的记录。要不要加一层远程接入是网络和安全的决定 |

## 8. 不做的

- 主机之间直接通讯或聊天（§12.2 第 2、10 条）。
- 在 k8s 节点上跑 Agent 的执行面。
- 在 Agent 主机上放集群管理员凭证或子系统管理员密码。
- 让 Console 的页面依赖任何一台个人电脑开着。

## 9. 最后一步：跑 TWS 的两台 Windows（Owner 2026-10-11 15:00）

Owner 定的次序：协作架构先在不碰交易的主机上做完、跑稳，TWS 的两台最后才上。那一步的含义不是扩容，是系统第一次站到真实账户旁边。

在那之前，本文和 W-67 的任何一片都不在这两台机器上装任何东西，不改交易区的网络规则，不为它做准备性的接线。

到那一步之前必须已经成立的（缺一条就不开始）：

1. 协作架构在两台 mini 上完整跑过：跨主机、失联接手、Mac Pro 合盖一整夜，都验收过。
2. 交易执行冻结（D10）由 Owner 明文解除，并且 spine 里的状态已改。本文不构成解除，也不为解除做铺垫。
3. 一份单独的隔离设计，Owner 签过：Agent 在这两台上以什么身份跑、够得着什么、够不着 TWS 的登录和下单入口、出了事怎么一键停。
4. §3 的位置表和 §5 的网络分区按那份设计改过，改动本身是 Owner 批的。
5. 先只读：第一阶段只观测（行情、持仓、连接状态），不带任何能下单的入口；观察期由 Owner 定。

这五条是统筹方按现有规则整理的下限，到时由 Owner 增删。
