### 2.4 引用检查（回应 677 R-04；机械判据）

目的：允许清单里的文件**不得**被任何会执行、解析或判定权限的代码读取。只看本次变更的路径集合 C（两端），扫描候选树 R 上的「消费者文件」：

- 消费者文件：`*.py`、`*.sh`、`*.go`、`*.js`、`*.ts`、`*.yaml`、`*.yml`、`*.json`、`*.toml`、`Makefile`、`Dockerfile*`，不含 `agent-config/work/**` 与 `docs/**` 自身。
- 只看**字符串字面量**（Python/Go/JS 引号内、YAML 值、shell 的单双引号与裸词参数），注释行与行尾注释不算（`#`、`//`、`/* */`、YAML `#`）。由 `scripts/landing/doc_refs.py`（新）做简单词法切分；切不出的文件按「有引用」处理（宁拒）。
- 命中规则：字面量 L 是 C 中某路径 p 的①完全相等；②目录前缀（`L` 以 `/` 结尾或是 p 的父目录）；③glob 且 `fnmatch(p, L)` 为真；④基名相等且 L 里含 `/` 以外的通配。任一命中即拒，报告消费者 `文件:行`。
- 既有依赖不会永久报红：检查只针对本次变更的 C；清单本身（§2.2）已排除有消费者的目录。新加一个消费者（例如脚本开始 glob `reviews/*.md`）发生在 `scripts/**`（硬底线），那次提交只能由 Owner 推或走 D 级单；之后任何落地变更碰到被消费的文件即被拒。
- 引用检查在两处跑同一份代码：ci-infra（§3）与第二道闸的资格判定（经 CI 结果读回，不在 workers 里扫 Git）。

## 4. 额度与上限（回应 677 R-05、S6 D3）

### 4.1 规则 schema

```yaml
limits:                      # 全租户
  max_landings_per_day: 8    # 总额：所有仓库合计，串行预留
repos:
  - repo: bifrost-platform
    limits: {max_files: 10, max_changed_lines: 400, max_in_flight: 1}   # 可选；缺省继承旧全局字段
  - repo: bifrost-trade-infra
    limits: {max_files: 5, max_changed_lines: 1500, max_in_flight: 1}
```

- 兼容：旧规则（v1）的全局 `max_files` / `max_changed_lines` / `max_in_flight_per_repo` 继续可解析，语义为「所有仓库的缺省」；新规则里每仓 `limits` 缺省时继承它们。
- 规范序列化：签名覆盖原文字节，不变；解析后的有效值（每仓展开）用于比较。
- 收紧判定 `landingTightens`：逐仓比较**有效值**（展开后），总额只降、每仓单件与在途只降、仓库只减、allow 只减；新增仓库或任一值升高即为放宽，需要签名。
- 每仓**日**额度本版不加；以后若加，只作附加上限，总额照旧在额度流里串行预留。

### 4.2 计数维度与锁序

- 总额：`ReservedToday` 读当天额度流 `landing-quota:<tenant>:<UTC 日>`（跨仓库）——维持现状。
- 在途：`OtherInFlight` 读 `landing:`+`f.Repo`（`store/landingfacts.go:104` 已经按仓库），v2 要核的是**所有调用者**都传对 repo：`landingFactsDB`、第二道闸 `AuthorizeLandingPush`、领取 `ClaimLanding`、到限结算与对账的读法。逐个列进 §5.2。
- 锁序（不变，两仓一致）：能力 → 规则（`landing:<tenant>`）→ 绑定（任务 / mission / 计划节点）→ 当天额度流 → 本仓落地流。两仓都先拿同一个额度流，再拿各自的仓库流，不会死锁；第二个到的看到总额已满按 `limit` 拒。

### 4.3 两仓抢最后一份额度（两连接，PostgreSQL）

- 成功对照：总额剩 1，只有 platform 一件 `branch_pushed` → 它写 `main_intent`、预留 1、push 调用 1 次。
- 被测：总额剩 1，platform、infra 各一件 `branch_pushed` 且两件单独都能通过；连接 A 在拿到额度流后由钩子挂住，连接 B 等锁；放开后恰好一件写意图，另一件 `limit`、无预留、push 调用 0 次；两个远端（§5.4 的本地双远端）只有赢的那个 main 前进。
- 错误实现检出：把额度流改成按仓库（`landing-quota:<tenant>:<repo>:<日>`）的变体必须让本测试失败（两件都推）——用测试钩子注入该变体跑一次，确认红。

## 11. 仍需 Owner 决定的点

677 已给出推荐、且与已定原则一致的不再问（D1 收窄、D2 已定、D3 修订后的 A、D4 先 STG、D5 核心后 S6 先于 S5）。剩下两个：

- **F1 第一批是否包含 `CUT-*.md`**（设计决定记录，近 30 天 34 次改动；内容里记着 Owner 的决定，但系统授权不读它）：
  - A 包含（推荐）：CUT 是统筹改得最频繁的文档之一，排除它手推减少有限；改动照样过验收与异家评审，「Owner 已定」的文字不产生任何授权。
  - B 排除：CUT 的修改仍由你推，其余五类走落地。
  - C 包含，但要求每次 CUT 变更的 diff 不得删改已有的「Owner 决定」小节（引用检查之外再加一条「只增不改」判定，约多 3–4 h）。
- **F2 infra 单件上限**：
  - A 5 个文件、1500 行（推荐）：设计稿与复核报告单次常在 300–1200 行。
  - B 5 个文件、600 行：更紧，大设计稿需拆分或走 D 级单。
