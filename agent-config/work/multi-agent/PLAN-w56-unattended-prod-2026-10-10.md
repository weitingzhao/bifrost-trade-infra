## 1. 这些步骤要挡住什么

每条后面是出处：14、15、18 = review 14、15、18，30 = check 30，编号见第 5 节。

1. 请求里的参数变成 shell，或者换掉闸门的代码、仓库地址、观察时间（14-P1a、14-P1b）。
2. 旧的成功 CI 盖住后来的失败或还在跑的重跑；标签冒充流水线身份（14-P1d、14-P2c、15-1f）。
3. 发布记录能被伪造、覆盖或删了重建；构建用的镜像、Dockerfile、来源能被换掉；「构建成功」被当成「STG 验过」（15-1a、15-1b、14-P2b、18-P1e、18-P2b）。
4. 过闸之后、写入之前情况变了：STG 换版、CI 重跑变红、证据过期、PROD 被别的入口改了、规则过期（14-P1c、15-1f、18-P2a）。
5. 并发：两次发布交错、发布与恢复交错、失去租约的旧执行者醒来继续写（包括 Git 认领之后才暂停的）、平台和监督器同时恢复（14-P1f、15-1c、18-P1c、30-P1c）。
6. 不经闸门就能改 PROD：推 main 后 Argo 自动同步、旧流水线、内联的 run、别的流水线指向 PROD、直接 patch Deployment 或 Application、手工同步、applier、删 Pod 和缩放（15-1d、18-P1a、30-R3、30-R4）。
7. 冻结拦不住：有的入口不查；平台账号和 `tekton-deliver` 能直接改冻结；读冻结和发同步之间插进冻结；旧流水线在查冻结之前就推了镜像（TD-293、TD-294、15-2g、18-P1b、30-R1、30-N1）。
8. 提交成套，部署不成套：`Recreate` 必有中断，三个 Deployment 可能只换了一部分；执行的进程中途死了没人接（14-P1e、15-1e）。
9. 仓库的写凭证限制不到两个键，谁拿到谁就能改任何文件（15-2j、18-P2k）。
10. 借「回滚」发任意旧版；恢复要用的镜像被 registry 回收或保留标签被覆盖（15-2c、15-2g、18-P2g）。
11. 新版平台起不来，而回滚要靠平台自己（15-3a、15-3b）。
12. 核对不完整：漏 Pod、不看副本数和 generation、不看 Argo 实际同步到哪个提交（14-P2d、15-1g）。
13. 退不回去的发布：新旧版本对持久状态不兼容，Git 回退撤不掉状态迁移（15-1e、15-5d、18-P2c）。
14. 守门的部件自己被改：闸门、动作、写入器、监督器和它们的部署定义（15-5c）。
15. 监督器误判：发布已经成功，却因为超时、确认丢失或它自己重启而被撤回（18-P1d）。

## 2. 建成之后，一次发布怎么走

1. STG 发布（`bifrost-deliver-platform`）构建两个镜像，摘要作为任务结果输出；PROD 平台生成一条改不了、删不掉的发布记录，构建输入要和受批准的清单一致。
2. 申请方调用平台动作 `promote_platform_prod`，只带三样：发布记录 ID、幂等请求 ID、它认为的当前 PROD 发布 ID。PROD 这一段没有流水线，也没有构建。
3. 平台在代次对象上取得新的代次，把意图落盘并交给带外程序保存、等它确认，再跑闸门（第 3 步的六项）。
4. 授权：命中签名规则就自动放行；否则建 C 级单等 Owner（单里写明失败时回到哪一组合），到期作废。
5. 带外程序（写入器）自己重验授权、证据、代次、冻结和 PROD 现状，认领后向 GitHub 提交一次：只改两项 `digest`。
6. 它在同步之前再认领一次，然后让 Argo 同步到这一个提交。平台的发布操作和监督器各自核对：同步的提交、三个工作负载、每个 Pod 的摘要、功能探针。
7. 通过：成功终态写进代次对象。不通过或超时：由持有当前代次的一方（先是平台的操作，过了期限由监督器接管）把两项摘要写回发布前的组合，再核对；恢复也不过就停下、冻结、带外通知 Owner。

通用约定：

- 第 1–6 步期间，PROD 发布一直由 Owner 逐次批准（C 级）。每一步单独上线、单独验收、能单独回退；回退的是这一步新加的能力，已经封住的旁路不重新打开，迁移之后也不回到可变标签。实现交 Cursor，决策线程重跑验收，Codex 独立复核。apply 通道允许的对象（含 Tekton 的 Pipeline / Task）走 `plan_manifest` / `apply_manifest`；RBAC、准入策略、Application 和凭证它应用不了，由 Owner 亲手做（D 级）。
- 判定全在带单测的程序里（ADR §12.2 第 13 条）。每次拒绝的第一行是「拒绝：<差在哪>；<下一步怎么办>」，同时写审计。请求不带代码、地址、阈值、摘要。验收只认程序或演练能检查的结果。
- 闸门、新动作、写入器、监督器、构建用的 Pipeline / Task / Dockerfile、构建输入清单，以及它们的部署清单，都算信任根：加进 `agent-config/release-policy/paths.json` 的 `no_trust_anchor_change`；触及它们的发布永远走人工批准。

- **冻结的串行边界**：规则只有一条——认领是切点。发出会改 PROD 的副作用之前，执行方对一个对象做一次比较交换，写下认领（请求号、提交、期限）；设冻结也是对同一个对象的一次比较交换。apiserver 把两者排出先后：冻结先落，认领失败，什么都不发；认领先落，这一个请求**继续**，在期限内发出并走到核对通过或恢复为止，冻结的回执写明它，之后的晋升认领都被拒；过了期限还没发出的认领作废，执行方自己不再发——什么都没发到 PROD，操作以「已停止」结束，没有要恢复的东西。这里说的都是晋升认领；已经发出的操作在冻结之下怎么恢复，用的是另一类「恢复认领」，见第 4 步「代次」和第 5 步「恢复」。选「继续」而不选「拒绝」：要拒绝就得在发出前再读一次冻结，读和发之间又是一个窗口，只有同一个对象上的先后是确定的。第 1–3 步里这个对象是 `bifrost-release-freeze`，同步由平台发（E 片建；E 片之前自动同步还开着，冻结管不到它，这是 E 片要关掉的现状）；第 4 步起是代次对象，由带外程序认领。旧流水线写不了 ConfigMap，它的切点是**第一次推镜像之前**那次冻结检查：过了它的 run 照常构建并滚动完，不在推完镜像之后再拦——那样会留下「`:prod` 已换、滚动被拒」，Pod 一重建就拉到没发布的镜像。检查到滚动完成之间（构建要几分钟）是接受的窗口，冻结的回执列出在途的 run。可变标签本身的残留——绕过流水线直接推 registry、run 在推完一个镜像后失败或被取消——在第 4 步摘要钉住之前关不掉，写进例外文件，期限是第 4 步迁移日。
- **解冻的独立授权**：设冻结谁都可以（经平台）；解冻靠 Owner 的签名。一次冻结的标识是对象里的两样：冻结序号（每设一次冻结加一）和 `frozen_at`；签名的原文同时写着这两样，所以给早先那次冻结的签名，对后来的冻结验不过。选序号而不选「时间加随机数」：「只升不降、不复用」这件事，准入比较新旧对象就能执行，不用记住历史上用过哪些值。两处把关。准入管这一个 ConfigMap 的结构，对所有身份生效：create 和 delete 只有 Owner；update / patch 只有 PROD 平台账号；设冻结（`false → true`）时序号必须正好是旧值加一，并清掉上一次留下的解冻字段；冻结期间（`true → true`）序号和 `frozen_at` 不能改；解冻（`true → false`）时这两样也不能改，解冻字段里写的序号必须等于它；未冻结时这些字段都不能动。签名本身由每个读它的一方按钉死的 Owner 公钥验——冻结任务、平台，第 4 步起还有写入器和监督器：`frozen=false` 而序号不是 0，就必须有一份对「当前序号 + 当前 `frozen_at`」验得过的签名，否则读作冻结；平台、写入器、监督器还记着自己见过的最大序号，序号变小也读作冻结。所以同一个账号绕过接口直接写 `frozen=false`、换掉标识、重放旧签名，都没有用。冻结任务没有记忆：有人绕过准入把序号也一起改回去，它分不出来；那要 Owner 一级的权限，在矩阵里归管理员身份那一行。
- **审批的一次性消费**：批准时平台已经先把单子认领成 `running` 再执行（`approvals/service.go`），首个 task 看不到「已批准、没用过」，两个 run 也可能同时读到同一张单。绑定改成四样：run 的名字由审批单号确定地得出，同名的第二次创建被 apiserver 拒绝；run 带着单号和参数哈希，准入要求 PROD 部署流水线的 run 必须是这个名字、由 PROD 平台账号创建；审批记录在认领时原子地写下这个 run 名；首个 task 核对「单子处于 `running`、登记的 run 就是自己、自己的实际参数的哈希等于单上的哈希」，不符就失败。创建成功而响应丢失：平台按那个确定的名字去查，查到就认，不再建第二个。run 被清理之后单子已是终态，同名重建过不了首个 task。这防的是平台里绕过审批的代码路径；平台整体失陷要到第 4 步由带外程序独立重验。
- **字段级例外（只有一条）**：除 Argo 控制器外，谁都不能改 PROD 的三个 Deployment。例外：身份 `cicd/tekton-deliver`；对象是这三个 Deployment；字段只有 Pod 模板上的 `kubectl.kubernetes.io/restartedAt` 和记 run 名的一个注解，其余与旧对象逐字相等；验证点是准入策略，run 名必须等于当前被认领的那张审批单登记的 run；期限到第 4 步迁移日（之前旧流水线靠重启换上新构建的镜像）。每条例外都要这样写全，「它是一张 C 级单」本身不算控制。
- **拒绝**：「拒绝：发布已冻结（<原因>，<时间>）；解冻要 Owner 签名」；「拒绝：读不到冻结状态（404 / 超时 / 字段缺失），按冻结处理」；「拒绝：解冻签名不是给第 <n> 次冻结（<frozen_at>）的，仍按冻结处理」；「拒绝：冻结期间不能改冻结的序号和 `frozen_at`」；「拒绝：新冻结的序号必须是上一次加一，且不带旧的解冻字段」；「拒绝：PROD 部署流水线的 run 只能由平台按审批单的名字创建」；「拒绝：审批单 <#n> 不在执行中、登记的 run 不是本 run，或参数哈希不符」；「拒绝：`bifrost-platform-prod` 的 `spec` 不能改」；「拒绝：只能同步到完整的提交号」；「拒绝：认领已过期，不发送」；「冻结回执：已认领的同步 <请求号>、在途的 run <名字> 会走完」。
- **退出**：以**测量**的输出为准，认证的是一次快照：由读得全的身份跑完，每条命令自己成功与否都有记录，没有 `unknown-surface`，没有截断，零个未分类；每条例外都绑定了身份、目标、字段、授权验证点和期限，没有过期的，其中可变标签那一条由 Owner 点名接受到第 4 步。零个未分类的意思是面已经完整清点、剩下的每一项风险都有人点名接受，不是「没有绕过闸门的路」；「其余没试过的请求」那些行说的是不知道能不能写，不是已知能写。汇总把信任根例外和普通字段例外分开，各列数量和风险范围；读取失败、清单缺失、预算截断不能用例外盖住。此外，仓库棘轮是绿的；六片各自的演练和两轮复核通过。快照记下时间和输入指纹；证据作废或满 14 天，那些行重新是未分类，退出条件不再成立，直到补测。演练全过而测量没清零，不算退出。测量在第 4、7 步退出时重跑，新动作和同步入口各占一行。

### 第 2 步　可信的发布记录（原 G1 的证据部分）

- **建什么、在哪**：① 受批准的构建输入清单（`agent-config/release-policy/build-inputs.json`，随策略由 Owner 签，改它要重签）：每个 Task 实际执行的镜像摘要、两个 Dockerfile 的内容哈希、来源仓库地址、两个目标镜像仓库、Pipeline / Task 规格的哈希。② 构建侧（`k8s/cicd/tekton/`）：Task 的镜像从标签改成摘要；`bifrost-deliver-platform` 去掉 `giteaBase` 和两个镜像目标参数，请求只能给 `revision`、`uiRevision`；放 Dockerfile 的 ConfigMap 只有刷新任务能写；两个构建任务把推送后的摘要写成任务结果，并多推一个保留标签——按 run UID 和摘要命名，推之前先查，同名标签已指向别的摘要就失败。部署只认摘要。③ 记录器是 PROD platform-api（`api/internal/releases`）。记录增加：platform 和 ui 的完整 SHA、实际的构建输入、两个镜像的仓库名与摘要、构建和部署 run 的 UID、STG 三个工作负载全部收敛的时间。④ 记录的保护靠准入，不靠 `immutable`：`cicd` 里名字以 `release-` 开头或带 `bifrost.io/release-record` 标签的 ConfigMap，只有 PROD 平台账号能创建，更新（含去掉标签）和删除一律拒绝，不带标签的不能占用这个前缀；名字由 run UID 得出，所以也无法同名替换。清理只由 Owner 做。⑤ 任务结果只能由 Tekton 控制器写：RBAC 断言没有别的身份能改 PipelineRun / TaskRun 的 `status`。⑥ 用记录的一方不只信记录：按 run UID 回查本体（`pipelineRef` 是 `bifrost-deliver-platform`，不是内联规格，终态成功，结果里的 SHA 和摘要与记录一致），把记录里的构建输入和**受批准的清单**逐项比（不是和集群当下的定义比），再向 registry 确认两个摘要存在、仓库名在清单里、架构与节点相符。⑦ 保留：registry 关掉删除接口；回收作业开跑前先核对「保留期内每条记录的两个摘要都有保留标签指着，标签名和指向一致」，不满足就不跑。当前和上一份 PROD 成功组合永远在保留期内。
- **拒绝**：「拒绝：记录 <id> 不完整（缺 console 摘要）」；「拒绝：记录与 run <uid> 的结果不一致（api 摘要）」；「拒绝：构建输入不在受批准的清单里（<哪一项>）」；「拒绝：run <uid> 已被清理，无法复核；重新发一次 STG」；「拒绝：不接受参数 `platformApiImage`」；「拒绝：发布记录不能改、不能删」；「拒绝：保留标签 <名字> 已存在且指向别的摘要」；「回收未执行：记录 <id> 的摘要没有保留标签」。
- **验收**：正例：连续三次真实的 STG 发布都生成完整记录，摘要等于 STG 三个工作负载 Pod 的 `imageID`。反例：手工建假记录；删掉一条记录再建同名的；去掉记录的标签；占用 `release-` 前缀；记录里的 SHA 与 run 不符；缺一个摘要；把某个 Task 的镜像换成另一个摘要后发 STG（晋升时因构建输入不符被拒）；请求里带镜像目标参数；以平台账号改 TaskRun 的 `status`；重推一个已存在的保留标签。回收演练：跑一次回收之后，api 和 console 两个仓库里，当前和上一份 PROD 组合都能按摘要拉取；摘要是 index 的，连它引用的各架构 manifest 一起核对。
- **谁批**：全部 PROD 发布仍由 Owner 批；这一步不改 PROD 的发布方式。Owner 签一次带构建输入清单的策略，它只增加约束，不放行任何 PROD 动作。
- **退出**：正例、反例、回收演练全过，并且「受批准的清单 ↔ 记录 ↔ run 本体 ↔ registry」四方比对由程序完成。只凭记录完整和回收的正反例不算来源可信。记录格式的变更写明新旧版本能否并存（LESSONS 第 21 行）。

### 第 3 步　发布闸门：先影子运行，再强制（原 G1）

- **建什么、在哪**：判定放在 PROD platform-api 的发版策略引擎里（`api/internal/releasepolicy`，它已经是唯一的裁判），由持久的发布操作驱动，不从请求指定的仓库版本里取代码，也不经 Tekton 脚本；第 4 步的写入器独立重验，带外恢复不依赖这个引擎活着。输入只有记录 ID；SHA 和摘要先按格式校验。六项：① CI：按 run 里克隆任务的实际提交认，不按参数字面；`pipelineRef` 必须是 `bifrost-ci-platform`，和标签矛盾即拒；提交在 main 的历史里；覆盖（platform SHA，ui SHA）这一对的**最新一次尝试**终态成功。最新一次还在跑就有限等待 15 分钟，不回退到更早的成功。② STG 身份：先看 `bifrost-deliver-platform` 的**最新一次部署尝试**（按 `pipelineRef` 认、按创建时间排，不论成败）——它的 UID 必须是这条记录的部署 run，且终态成功；有更新的尝试在跑或已失败就拒绝，时间缺失或解析不了的也拒绝。再看实况：api、workers、console 三个 Deployment 的 `observedGeneration` 等于 `generation`、副本齐、所有非终止 Pod Ready 且摘要等于记录（workers 等于 api）。③ 观察时间：从三个工作负载全部收敛起算，最低 10 分钟；期间换版、Pod 重启或健康探针失败就清零重算。④ 差异：当前 PROD 成功组合 → 候选，platform、ui 逐仓，加构建输入；触及信任根、D10 路径、DDL 路径的不走自动；能不能自动恢复按未决 4 的判据算，结论写进证据。⑤ 未冻结；读不到按冻结算。⑥ 走自动放行时，规则签名有效、未过期。结论带证据 ID，10 分钟内有效；人工单等批准超过有效期的，批准时重跑闸门，不用旧证据。
- **影子与强制**：影子期每次 PROD 发布申请都算一遍，结论写审计并显示在审批单上，不拦。强制之后，闸门不过就不建普通审批单。人工例外是另一种有界的单：点名豁免「CI 结果」或「观察时间」中的哪一项、针对哪条记录、一次有效、会过期。产物身份、冻结、信任根不能豁免，也没有请求参数式的旁路。迁移之前 PROD 仍是重新构建的，这一步保证的是「记录完整、STG 跑的就是记录里的摘要」；PROD 用同一份摘要要到第 4 步。
- **拒绝**：「拒绝：CI 最新一次是红的（<run>）」；「拒绝：CI 还在跑，已等 15 分钟」；「拒绝：没有同时覆盖 platform <sha> 和 ui <sha> 的 CI」；「拒绝：STG 有更新的一次部署尝试 <uid>（运行中 / 失败）」；「拒绝：STG 上是 <sha>，不是要发的 <sha>」；「拒绝：platform-workers 还没收敛」；「拒绝：STG 才观察 3 分钟（14:32 重启过，已重新计时），规则要求 10 分钟」；「拒绝：闸门证据已过期，批准时重算未通过（<哪一项>）」。
- **验收**：反例矩阵，在真实 STG 上逐格注入，预期都是拒绝且原因正确：最新 CI 红、CI 运行中、STG 错版、有更新的部署尝试在跑、更新的尝试失败、workers 未收敛、观察期内重启、观察期内换版、等批准期间证据过期。影子期的每次真实发布，另由一份不调用闸门代码的核对脚本（直接读 PipelineRun、Deployment、registry）给出独立的预期结论，和闸门的结论逐次比对。review 14 复现过的三个反例做成单测（旧成功盖住新失败、观察时间为 0、标签冒充流水线）；参数里放 `$(id)` 被格式校验拒绝。
- **谁批**：全部 PROD 发布仍由 Owner 批。强制之后，他批到的每张单都已经过了这些检查。
- **退出**：反例矩阵每一格都被拒；影子期每次真实发布的闸门结论都与独立预期一致，不一致的逐条定位是闸门错还是预期错并修掉；满五次且最近三次没有不一致，再切强制（收紧，不需要签名）。次数本身不算证明。

### 第 4 步　窄动作和写入器，先人工授权（决定 A；原 G2）

- **动作与状态**（`bifrost-platform/api/internal/actions`，C 级）：`promote_platform_prod` 的参数只有 `record_id`、`request_id`、`expected_current_release`，调用方是有自己身份的授权申请者。发布操作的状态放 statefile（ADR §12.3）：已授权 → 已提交 → 同步中 → 验证中 → 成功，或 恢复中 → 已恢复 / 已停止。写入之前先落意图：请求身份、规则 ID 或审批单号、证据 ID、前后摘要、Git 基准与提交、代次；之后每一步的结果接着写。同一个 `request_id` 重试得到同一个操作。调用方的发布窗口在操作建立时移交给操作本身：调用方退出不影响它，它也不去等调用方那把锁。
- **代次（谁有资格写）**：权威是 `cicd` 里一个点名的 ConfigMap（下称代次对象），记代次、持有者（平台的操作 / 监督器 / Owner 应急）、操作 ID、登记的恢复目标和恢复期限、阶段和它的期限、Git 认领与提交、同步认领、冻结（序号和时间，规则同第 1 步「解冻的独立授权」）、终态。所有更新都是带 `resourceVersion` 的比较交换，apiserver 是裁判。代次只在三种情况加一：平台开始一次操作（没有未过期的持有者时）、监督器接管（阶段期限已过或续租已断）、Owner 应急。设冻结不加代次、不换持有者，只写冻结的序号和时间。带外程序在两处认领（切点规则见第 1 步「冻结的串行边界」）：推送之前和发同步之前；认领带期限，过期作废。认领分两类。**晋升认领**把 PROD 推向候选，条件是代次和持有者没变、未冻结、证据未过期；冻结一落下就不再接受。**恢复认领**属于一个在冻结之前就已授权的操作，写明四样：当前代次、操作 ID、目标、期限。准入（比较代次对象的新旧内容）和写入器都只在这四样与代次对象里登记的那个操作逐项相同时才接受，冻结之下也一样；认领上标着「恢复」不算数，目标对不上登记的就拒绝。所以恢复不需要解冻，也只能把 PROD 带回那个操作登记的目标。准入里没有当前时间可用，它只核对认领写的期限就是登记的期限；期限过没过，由写入器和监督器按自己的时钟判断。操作 ID、恢复目标、恢复期限在操作开始时写进代次对象，之后不能改；接管只换代次和持有者；新的操作只有在未冻结、上一个操作已到终态时才能开始。冻结落下时分三种情况：晋升的认领过期而没发出——什么都没发，操作以「已停止」结束，没有要恢复的；提交已推而同步没认领上——PROD 没变，用恢复认领撤回那次提交（只动 Git，不发同步），操作以「已停止（冻结）」结束；同步已发出——走到核对，通过就写成功，不过就用恢复认领回到登记的目标，不会被冻结晾在半路。同步请求里带种类、代次、操作 ID 和提交，准入策略以代次对象为参数：必须对得上对象里一条现存的认领，旧代次的、没有认领的同步都被 apiserver 拒绝。**Git 这一侧**：非强制推送只比较分支头，证明不了代次——旧执行者在 Git 认领之后暂停，新持有者接管而还没推送时，旧的推送仍会成功。所以接管的第一件事是换基准：上一个持有者留下「已认领、没记下提交」的 Git 认领时，新持有者先推一个带新代次的接管提交（没有东西要回退时是空提交），推上去才做别的。之后旧的推送不是快进，被 GitHub 拒绝；它想重来就得重新认领，而代次已变。旧的推送如果抢先落了地，接管提交会因为不是快进而失败——新持有者取回分支，认出那次带旧操作 ID 的提交并回退它，这次回退就是换基准；那次提交没有同步过，PROD 没变。选换基准而不是只靠认领期限：期限要暂停的进程自己守，卡在推送调用里的进程守不住；分支头的比较由 GitHub 执行，不依赖任何一方的时钟。从这一步起只有带外程序能对该 Application 发同步，平台账号的这项权限收回。
- **写入器**（放哪、拿什么凭证见未决 2）：独立进程，仓库的写凭证只在它手里，平台只能向它提交意图。写入边界的最后检查，缺一项就拒：授权（规则由它自己验 Owner 的签名；试运行期认平台的审批记录）；证据按第 2、3 步用 run UID、registry、STG 实况重算，且没过有效期；代次和冻结（冻结显示已解除却没有 Owner 对那次冻结的签名，按冻结算）；PROD 实际运行的组合仍等于 `expected_current_release`——看 Argo 已同步的提交和三个工作负载的实际摘要，Git 基准没变不算数；最终改动。改动的范围是一个文件里的两项摘要：`k8s/overlays/platform-prod/kustomization.yaml` 的 `images:` 里按固定镜像名匹配的两项（专用小仓库可行时是它里面的那个文件，见未决 2），只换 `digest` 的值，api 和 workers 用同一个 api 摘要；其他键、其他文件有任何变化都拒绝。它只推 GitHub（权威源，Gitea 继续单向镜像），非强制，带基准 SHA；基准变了就放弃，由平台重新过闸，不强推。提交信息带操作 ID、记录 ID、发布前的组合。
- **一次性迁移和旧流水线退役**（单独一张人工批准的单）：`images:` 两项从 `newTag: prod` 改成 `digest:`，值是当时 PROD 实际在跑的摘要。三个前提，缺一个不迁移：① 迁移前的成功组合已存成记录，两个仓库的摘要都有保留标签、能拉取。② Owner 有一条不经过 platform-api 的应急通道：先把代次拿到自己名下，用自己的 Git 回退那次提交，点名同步到回退后的提交，再跑一份独立的核对脚本（Argo 的提交、三个工作负载、每个 Pod 的摘要、探针）。③ 这条通道演练过三种情况：平台持续起不来、推送成功但响应丢失、只有一部分工作负载换了版。迁移同步之日，旧流水线 `bifrost-deliver-platform-prod` 和 `platform-prod-pinned-from-stg.sh` 退役，收回 `tekton-deliver` 在 PROD 的重启权限。之后每次晋升：提交，同步到这一个提交，等三个 Deployment 滚动完成；没有 `rollout restart`。
- **拒绝**：「拒绝：不接受参数 <名字>」；「拒绝：已有发布在进行（操作 <id>，代次 <n>）」；「拒绝：代次 <n> 已过期（当前 <m>，持有者 <谁>）」；「拒绝：认领已过期，不推送、不同步」；「拒绝：冻结之后不接受晋升认领」；「拒绝：恢复认领与登记的不符（代次 / 操作 / 目标 / 期限中的 <哪一项>）」；「拒绝：同步请求没有对应的认领」；「拒绝：上一个持有者的 Git 认领还没了结，先换基准」；「拒绝：闸门证据已过期；重新申请」；「拒绝：PROD 实际运行的不是 <id>（<工作负载> 是 <摘要>）」；「拒绝：改动超出两项摘要（<路径>）」；「拒绝：main 已前进，基准不符；请重新申请」；「拒绝：main 上有未同步的 PROD 清单改动（<提交>）；先由人工同步或回退」；「拒绝：发布已冻结，未同步的提交已回退」。
- **验收**：反例都不产生提交：改第三个键；给一个不在记录里的摘要；带 Git 地址或路径参数；两个请求同时到；同一个 `request_id` 发两次；基准之后有人推了 main；批准之后 platform 的 main 前进或 `:stg` 标签被改；等批准期间证据过期；等批准期间 PROD 被一张同步单改了；用 deploy key 强推 main 或推非快进（GitHub 的分支保护拒绝）。冻结与认领的并发演练：在同步认领之前、认领之后发出之前、发出之后三个点注入暂停并同时设冻结，各跑多轮；每一轮的结果只能是「冻结在先，没有同步，提交被回退，PROD 不变」或「认领在先，恰好一次同步，冻结的回执写明它，之后的晋升认领被拒」，不能出现回执里没有而事后发生的同步。旧执行者，暂停点在 **Git 认领之后、推送之前**：其间租约到期，Owner 应急接管并推了接管提交，另有一次新发布；再唤醒它——推送因为不是快进被 GitHub 拒绝，同步被准入按代次拒绝。反过来先唤醒它，让旧的推送先落地：接管提交失败，新持有者回退那次提交，PROD 不变。崩溃点矩阵，对 platform-api 和带外程序各做一遍：意图落盘后、Git 认领后、推送发出而响应丢失、提交已记下、同步认领后、Argo 同步中、核对中、看到成功而终态未写。每一格的预期终态写在测试里，只能是「候选且核对通过」或「发布前的组合」；不能有第二个提交、半套部署或没人持有的代次。
- **谁批**：每次 `promote_platform_prod` 是一张 C 级单；迁移是一张单；写入器的部署和凭证是 D 级。这一步到第 5 步之间发布失败，由 Owner 走上面的应急通道。
- **退出**：反例全拒；冻结与认领的并发演练、旧执行者的两种顺序、崩溃点矩阵每一格都符合预期；第 1 步的矩阵重跑通过；然后才做第一次真实晋升，结果是一个成套提交、PROD 三个工作负载的摘要等于记录。一次成功的晋升和「杀一次进程能接上」不算退出。

### 第 5 步　人工批准的摘要晋升和受限的恢复（原 G2、G3）

- **授权**（未决 3，按 B 写）：每张人工批准的晋升单自带失败时的恢复条款，缺一项就不建单：恢复目标（发布前的成功组合，写明记录 ID 和两项摘要）；期限（核对各段超时之和，过了期限不再自动恢复，停下并通知）；触发条件（核对不过，或阶段超时）；谁接管（先是平台的操作；第 6 步之后，阶段期限过了由监督器接管）；以及「不兼容的变更不自动恢复」。一次批准覆盖一次有界的发布操作：发布，加上它自己在期限内的撤回。这已经是放权——Owner 批的那一下之后，撤回不再问他——所以未决 3、未决 4 定了，这一步才开始试发。
- **核对**（平台的发布操作）：绑定这次的提交和摘要。Argo 报告的已同步提交就是它；三个 Deployment 的 `observedGeneration` 等于 `generation`、更新后的副本数等于期望值、全部 Ready；每个非终止 Pod 的镜像摘要等于记录（按 manifest / index 与节点架构的对应关系比）；功能探针通过（API `/health`、Console 首页、一个只读接口）。每一段都有超时，超时按失败算。
- **恢复**：不是另一个可以随便调用的动作，而是发布操作自己的一个分支，只有操作处在「已提交」「同步中」「验证中」才能进入，由持有当前代次的一方执行，同一时刻只有一方。它把两项摘要写回单里写明的恢复目标，走同一个写入器、同样的改动约束，用的是恢复认领（第 4 步「代次」）：绑定当前代次、这个操作、登记的目标和恢复期限。冻结期间不允许新的晋升；这种恢复照常进行，不需要解冻，也到不了登记目标之外的任何组合。之后做同样的核对。恢复后仍不过：状态「已停止」，设冻结，带外通知，不再自动尝试。发布成功之后才发现问题：人工批准下把 PROD 设回上一份成功组合，只能是上一份，不走自动。
- **排除与用时**：能不能自动恢复按未决 4 的判据由程序判断；判不出来的转人工批准，单子上写明「不能自动恢复」。Git 回退撤不掉状态迁移，这里不建通用的迁移回滚。用时不预设「一分钟」：检测、Git 恢复、Argo 收敛、健康恢复四段各自量，`Recreate` 造成的 API 中断单独量；演练后把实测值写成规则里的超时和中断上限。
- **拒绝**：「拒绝：晋升单缺恢复条款（<哪一项>）」；「拒绝：恢复目标只能是操作 <id> 开始前的组合 <release>」；「拒绝：操作 <id> 已结束，不能恢复」；「拒绝：冻结之下只接受操作 <id> 自己的恢复认领，目标、期限要和登记的一致」；「拒绝：这次发布判不出能否自动恢复；转人工，不自动恢复」；「停止：恢复期限已过，或恢复后仍未通过核对；已冻结并通知」。
- **验收**：让第二个工作负载在 PROD 起不来（最终回到发布前的组合）；同步中杀掉 platform-api 和 workers（重启后接续，不重复提交）；Argo 迟迟不同步（按超时处理，不算成功）；让恢复指向一个更早的版本（被拒）；让恢复拖过期限（不再自动恢复，停下并通知）；发一个触及状态格式路径的版本（不进自动范围）。冻结之下的恢复：同步发出之后设冻结，再让核对不过——恢复在冻结之下照常进行并到达登记的目标，冻结还在，没有发生解冻；把恢复认领的目标换成别的组合、把操作 ID 换成另一个操作、把认领里的期限改得和登记的不一样，三种都被准入拒绝（它逐项比对登记值），写入器也拒绝；期限与登记值相符但已经过了的认领，准入放得过去（准入里没有当前时间），由写入器和监督器按自己的时钟拒绝，不产生任何副作用（复核 34）；晋升的同步认领过期没发出时落下冻结——操作停止，已推的提交被撤回，PROD 不变。未决 4 的契约测试在这一步接进平台的 CI：新 API 对上一版 Console；新版读旧状态、旧版读新状态不丢字段。全程没有构建，没有覆盖后来的发布。
- **谁批**：每次晋升一张 C 级单，恢复条款是单的一部分。
- **退出**：新路径上至少五次真实发布成功；上面的演练全过；四段用时和 API 中断有实测值；契约测试在 CI 里是必过项。

### 第 6 步　带外的监督器（原 G4、G6）

- **建什么、在哪**：独立于 platform-api 和 workers 的常驻进程（位置见未决 2），用自己的身份直接看 Argo 和三个工作负载，不经平台的 API。每次发布独立出一份核对结果；平时巡检 PROD 的实际摘要是否等于最近的成功组合。
- **契约**：① 保存与确认：发布开始之前它收到意图（含发布前的组合和恢复授权；授权在这时取得，这次发布结束前不因规则到期而失效），落到本地磁盘后，把意图的哈希写进代次对象作为确认；写入器推送之前要看到这个确认。确认丢了就按哈希重投，重投是幂等的；等不到确认，操作在任何写入之前结束。② 终态：成功由持有者写进代次对象（阶段、提交、两项摘要），监督器自己核对通过后在同一处记一笔。终态在集群的对象里，不只在平台的 statefile 或监督器的内存里。③ 判断：超时本身不触发撤回。监督器（包括它自己重启之后）先读代次对象：已是成功终态，什么都不做；阶段期限未到，等；期限已过或续租已断，用比较交换接管，然后自己看 PROD——等于候选且核对通过就补写成功，否则用恢复认领回到登记的目标；提交已推而同步未认领的，用恢复认领撤回那次提交。接管不改登记的操作、目标和期限；期限已过就不再恢复，停下并通知。读不到代次对象（集群不可用）不动，到超时告警。「发布已成功」和「平台失联」靠终态记录和对 PROD 的直接观察区分，不靠平台答不答应。④ 不并行：恢复的每个副作用都要当前代次；平台在恢复而期限未到时，监督器只看不动；Owner 应急拿走代次后两者都停。⑤ 结论冲突：平台记了成功而监督器核对不过，或者反过来——不自动撤回，设冻结并通知，由人判断。⑥ 独立冻结：它在代次对象上写冻结的序号和时间（比较交换；不加代次、不换持有者），不经平台。冻结和在途操作走同一套协议：冻结之后不再接受晋升认领；已经发出同步的操作仍由原持有者走完核对，要恢复就用恢复认领，原持有者失联就按 ③ 接管，不会留下一个没人能完成的操作。它的 kube 身份因此要能更新这一个点名的 ConfigMap（见未决 2）。通知走 .50 的告警中转。⑦ 范围只到应用升级失败：GitHub、Argo 或整个集群不可用时，到超时就告警、转人工，不自己修。W-50 的带外执行器靠向平台领已批准的单子，平台坏了就领不到，所以不算这一步；监督器可以和它同机，但恢复这条路不经过领单。
- **拒绝**：「拒绝：监督器未确认已保存意图，不写入」；「拒绝：没有这次发布的意图记录，不恢复」；「拒绝：恢复目标和保存的发布前组合不一致」；「拒绝：监督器未就绪，不发布」；「告警：GitHub 不可达，已超时，没有做任何改动，请人工处理」。
- **验收**：发起一次发布后关掉 PROD 的 platform-api 和 workers，或者发一个持续起不来的版本：监督器不联系平台就完成恢复并通知，四段用时记录在案。确认丢失：丢掉确认那一次写，操作在写入前结束；重投之后只有一份意图。监督器在三个点重启（提交前、提交后同步前、同步后核对中）：结果只能是候选核对通过或发布前的组合，已经成功的发布没有被撤回。平台和监督器结论冲突（给监督器的探针注入失败而平台记成功）：冻结并通知，没有撤回。完整的旧执行者演练，暂停点同样在 Git 认领之后：跨过租约到期，其间监督器接管（先推接管提交）并完成恢复，另有一次新发布；唤醒后它的推送和同步都被拒，旧推送先落地的顺序也跑一遍。平台死在「已提交、还没记成同步中」：监督器接管后回退那次提交，PROD 没变。独立冻结：平台关着，监督器设冻结，随后新的同步认领被拒；一个已经同步、正在核对的操作在冻结之下照样走到成功或恢复。反例：断开它到 GitHub 的网络（只告警、不动）；给它一条没有意图的恢复请求；停掉监督器再申请发布。
- **谁批**：每次晋升仍是 C 级单。监督器自己的部署、升级和凭证由 Owner 批或亲手做。
- **退出**：上面的演练全过；监督器登记为维护者，有存活信号，失联会呼到 Owner（ADR §2 第 4 条），失联期间自动发布不放行。

### 第 7 步　Owner 签自动发布的规则（最后）

- **前提**：第 1–6 步都按各自的退出条件退出，含补充的矩阵和演练；未决 4 已定，它的判据是可执行的（契约测试是平台 CI 的必过项，并对最近五次发布回放过）；Codex 对实现的独立复核通过。
- **规则写什么**（模板 `agent-config/release-policy/template.json`，Owner 用签名密钥签，W-42 的引擎）：规则授权的是**动作** `promote_platform_prod`，不是「启动某条流水线」。绑定环境 `platform-prod`、来源（`bifrost-deliver-platform` 的记录）、构建输入清单、最低观察时间、核对要求和各段超时、API 中断上限、恢复条款（失败回到发布前的组合，期限和接管者同第 5 步）、可自动恢复的判据、有效期 90 天。条件沿用现有的（未冻结、不触 D10 路径、不触信任根、不含 DDL），差异按当前 PROD → 候选算，含 ui 和构建输入。
- **拒绝**：签名无效、规则过期、证据缺失或过期、差异触及信任根 / D10 / DDL、判不出能否自动恢复：自动入口一律拒绝并写明是哪一条，转人工单；人工单到期作废，不执行。
- **验收**：签之前把第 1–6 步的通过与拒绝矩阵完整重跑一遍，另加四项：规则过期、冻结中、改了信任根的发布、证据重放（把用过的闸门证据或旧记录再交一次）。签之后，第一次符合条件的发布无人点击到达 PROD，审计记下命中的条款，Owner 收到事后通知。
- **之后**：清掉旧路径的残留（`paths.json` 里 `pinned` 的 `bifrost-deliver-platform-prod`、registry 里不再被引用的旧标签、RELEASE.md 的旧说明），再跑一次第 1 步的矩阵。规则到期就回到逐次人工批准，到期前 14、3、1 天提醒。
- **退出**：W-56 进「待你签收」。计数口径：签规则后的 30 天里，按审计分两类数——符合规则的平台 PROD 发布，和转人工的例外单（每张带着被哪一条拒绝）。目标是第一类里需要 Owner 点击的为零；第二类单独列出，不混进这个数。

## 4. 和原来六个门槛的对应，以及什么时候能签规则

原 G1 = 第 2、3 步；G2 = 第 2、4、5 步；G3 = 第 5 步；G4 = 第 5、6 步；G5 = 第 1 步；G6 = 第 6 步。第 1–4 步做完，新路径只能在 Owner 逐次批准之下试运行；原 G1–G4 的内容全部验收，也只到这个程度。第 5 步起每张批准的单带着有界的自动撤回，这已经是一处放权（未决 3），不能算作「还没放权」；普通的自动晋升仍然没有开放。自动规则必须等原 G5、G6 的等价物（第 1 步的矩阵与冻结、第 6 步的带外监督器）和未决 4 的判据都验收过才能签，也就是第 7 步。第一版里「Owner 批两次之后就签第一份规则」的说法作废。
