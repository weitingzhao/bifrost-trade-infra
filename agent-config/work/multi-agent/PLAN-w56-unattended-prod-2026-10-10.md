# W-56 — 平台的 PROD 发布由事先签名的规则放行：一条七步的上线路线

状态：方案，2026-10-11 重写。本文把第一版（六个门槛 G1–G6）、Codex review 14 之后的修订、review 15（结论：方向成立，要改）合成一份；原来的补丁段落已删，历史在 git 里。等 Owner 过目并定第 6 节的三项，还没有派实现。改写稿由一个 Claude 子任务起草，统筹线程通读后加了「写凭证的范围」一条。本文先交 Codex 复核，通过后才派实现；每一步实现完再复核一次（LESSONS 第 53 行）。

## 0. 目标、已定的事、现状

**目标**：`bifrost-platform` 发 PROD 不再由 Owner 逐次点批准：符合他事先签过名的规则的发布立刻自动放行，发布后由独立的程序核对，不过就回到发布前的那一套。不符合的由程序拒绝并写明原因，转人工；任何形式的「超时或沉默即同意」都不做。

**Owner 已定，不再讨论**：

- 2026-10-08（ADR §5）：放宽规则要他签名，收紧谁都可以做；规则过期回到更严的默认值；发版后健康检查不过，自动回到上一版，事后通知。
- 2026-10-10：PROD 的发布流水线在 W-56 验收之前不进发版策略，仍由他逐次批。
- 2026-10-10 晚：放行只来自签过名的规则。没人处理的单到期作废、不执行。衡量标准是他逐次批准发布的次数降到零。
- 2026-10-10 23:54，**决定 A**：两个镜像摘要由平台自己经一个新增的窄动作写进 PROD overlay；流水线不拿仓库的写权限。
- D10 不在范围内：本文只管 `bifrost-platform` 的发布，不涉及 Trade、daemon、下单；D10 也不在可配置的规则集里。

**现状**（前四条 2026-10-10 实测；其余 2026-10-11 读仓库文件确认）：

- `bifrost-deliver-platform-prod` 的第一步 `preflight-stg` 只看 STG 的 API 和 Console 回 200；然后按 `revision`（默认 main）重新克隆、重新构建 `:prod` 镜像，`rollout restart` 三个 Deployment，最后让 Argo 同步 HEAD。
- 它不查该提交的 CI，不查 STG 上跑的是不是同一个提交，部署的也不是 STG 验过的那份产物（当天 api 镜像的摘要 STG 与 PROD 不同；Console 的构建恰好是确定的）。
- `e5a0703` 在 CI 红的情况下发了 PROD，唯一的检查是 Owner 那一下批准（LESSONS 第 38 行）。
- 平台仓库没有合并前的 CI，CI 只由 main 的推送触发（第 40 行）。STG 没有审批数据和通知配置，演练不了审批链路（第 36 行）。
- 2026-10-11 起，线程建 PROD 发布单之前要自己核对三条：CI 成功、STG 是同一个提交、同仓库没有另一张未结的单（工作区 `CLAUDE.md`）。这是模型记着的规则，第 3 步把它变成程序。
- 冻结没有覆盖全部入口（TD-294）；两个环境的平台账号都能直接改冻结和发布窗口的 ConfigMap（TD-293）。两项都未开始。
- Argo 应用 `bifrost-platform-prod` 跟踪 GitHub `main` 的 `k8s/overlays/platform-prod`，自动同步（prune + selfHeal）；overlay 引用 `k8s/base-platform`。推 main 就改 PROD，不经审批（ADR §5 列为已接受的风险，归 W-31）。
- PROD overlay 的 `images:` 两项是 `newTag: prod`，三个 Deployment `imagePullPolicy: Always`；`platform-api` 和 `platform-workers` 是 `Recreate`，api 1 副本、console 2 副本；`cicd/tekton-deliver` 对 PROD 的 Deployment 有 `patch`。
- 构建任务不输出镜像摘要。发布记录（`bifrost-platform/api/internal/releases`，`release-*` ConfigMap）只有逐仓 SHA，同名记录会被重写。终态的 PipelineRun 7 天后被清理（`pipelinerun-ttl.yaml`）。发版策略模板的 `allow` 只列流水线，不含两条 PROD 流水线，也没有「动作」这一类条目。`gitops_sync_app` 只能同步到 HEAD。

## 1. 这些步骤要挡住什么

每条后面是出处：14 = review 14，15 = review 15，编号见第 5 节。

1. 请求里的参数变成 shell，或者换掉闸门的代码、仓库地址、观察时间（14-P1a、14-P1b）。
2. 旧的成功 CI 盖住后来的失败或还在跑的重跑；标签冒充流水线身份（14-P1d、14-P2c、15-1f）。
3. 发布记录能被伪造或覆盖；「构建成功」被当成「STG 验过」（15-1a、15-1b、14-P2b）。
4. 过闸之后、写入之前情况变了：STG 换版、CI 重跑变红、设了冻结、规则过期（14-P1c、15-1f）。
5. 并发：两次发布交错、发布与恢复交错、失去租约的旧执行者醒来继续写（14-P1f、15-1c）。
6. 不经闸门就能改 PROD：推 main 后 Argo 自动同步（overlay、base、patch、配置）、旧流水线、直接建 run、直接 patch 镜像、手工同步（15-1d）。
7. 冻结拦不住：有的入口不查；平台账号能直接改冻结；冻结前已推送的提交照样被同步（TD-293、TD-294、15-2g）。
8. 提交成套，部署不成套：`Recreate` 必有中断，三个 Deployment 可能只换了一部分；执行的进程中途死了没人接（14-P1e、15-1e）。
9. 仓库的写凭证限制不到两个键，谁拿到谁就能改任何文件（15-2j）。
10. 借「回滚」发任意旧版；恢复要用的镜像被 registry 回收（15-2c、15-2g）。
11. 新版平台起不来，而回滚要靠平台自己（15-3a、15-3b）。
12. 核对不完整：漏 Pod、不看副本数和 generation、不看 Argo 实际同步到哪个提交（14-P2d、15-1g）。
13. 退不回去的发布：新旧版本对持久状态不兼容，Git 回退撤不掉状态迁移（15-1e、15-5d）。
14. 守门的部件自己被改：闸门、动作、写入器、监督器和它们的部署定义（15-5c）。

## 2. 建成之后，一次发布怎么走

1. STG 发布（`bifrost-deliver-platform`）构建两个镜像，摘要作为任务结果输出；PROD 平台生成一条不可改的发布记录。
2. 申请方调用平台动作 `promote_platform_prod`，只带三样：发布记录 ID、幂等请求 ID、它认为的当前 PROD 发布 ID。PROD 这一段没有流水线，也没有构建。
3. 平台取发布租约（带代次），先把意图落盘，再跑闸门（第 3 步的六项）。
4. 授权：命中签名规则就自动放行；否则建 C 级单等 Owner，到期作废。
5. 写入器领走意图，自己重验授权和证据，在写入边界再查一次冻结、CI、STG 身份，然后向 GitHub `main` 提交一次：只改 `images:` 两项的 `digest`。
6. Argo 同步到这一个提交。平台的发布操作和带外的监督器各自核对：同步的提交、三个工作负载、每个 Pod 的摘要、功能探针。
7. 通过：记为新的成功组合，释放租约。不通过或超时：把两项摘要写回发布前的组合，再核对；恢复也不过就停下、冻结、带外通知 Owner。

通用约定：

- 第 1–6 步期间，PROD 发布一直由 Owner 逐次批准（C 级）。每一步单独上线、单独验收、能单独回退。实现交 Cursor，决策线程重跑验收，Codex 独立复核；集群变更走 `plan_manifest` / `apply_manifest`，RBAC 和凭证是 D 级，由 Owner 批或亲手做。
- 判定全在带单测的程序里（ADR §12.2 第 13 条）。每次拒绝的第一行是「拒绝：<差在哪>；<下一步怎么办>」，同时写审计。请求不带代码、地址、阈值、摘要。
- 闸门、新动作、写入器、监督器、构建用的 Pipeline / Task / Dockerfile，以及它们的部署清单，都算信任根：加进 `agent-config/release-policy/paths.json` 的 `no_trust_anchor_change`；触及它们的发布永远走人工批准。

## 3. 七步上线

顺序取自 review 15 第 4 节：先降低今天就存在的风险，再建新路径，最后才放权。数字（观察 10 分钟、等待 15 分钟、五次发布）都是起点，按实测改；最低观察时间最终写进签名规则。

### 第 1 步　先堵旁路和冻结的缺口（原 G5）

- **建什么、在哪**：① TD-294：给不查冻结的七条流水线加一个只读冻结的首个 task（`k8s/cicd/tekton/`）。② TD-293：两个平台账号在 `cicd` 只能写点名的 ConfigMap，STG 账号一律不能写（`k8s/platform-rbac/` 加准入策略）。③ 引用 PROD 部署流水线的 PipelineRun 只允许 PROD 平台账号创建（准入策略，TD-271 已在用同类）；Owner 的管理员身份是唯一例外，进审计。④ `bifrost-platform-prod` 不再自动跟随 main，只同步到点名的提交（`k8s/cicd/applications/bifrost-platform-prod.yaml`；做法见未决 1，下文按推荐项写）。overlay、base、patch、配置的其他改动走 C 级同步单，单里附「上次同步的提交 → 这次」在 `k8s/overlays/platform-prod/` 和 `k8s/base-platform/` 下的差异。冻结期间不为新的发布或配置改动做同步（第 5 步的恢复除外），所以冻结前已推送的提交不会生效。
- **拒绝**：「拒绝：发布已冻结（<原因>，<时间>）；解冻要 Owner 签名」；「拒绝：PROD 部署流水线只能由平台在批准后创建」；「拒绝：`bifrost-release-freeze` 只能经平台的冻结接口改」。
- **验收**：冻结后从每个入口发起都被拒并给出原因（平台的 `start_pipeline_run`、直接创建 `platform-prod-pinned-from-stg.sh` 生成的 run、触发器）；不冻结、不带批准直接建 run，被准入拒绝；向 main 推一个只改 PROD overlay 注释的提交，PROD 不变，Argo 显示未同步；`make check-platform-rbac` 新增的「不该能」各行全过（两个平台账号直接 patch 冻结 ConfigMap 都被拒）。
- **谁批**：一切照旧。旧流水线 `bifrost-deliver-platform-prod` 保留为人工批准的通道，到第 4 步迁移时退役。
- **退出**：上面的演练全过；`check-release-chain.py` 断言每条发布和构建流水线的首个 task 查冻结。

### 第 2 步　可信的发布记录（原 G1 的证据部分）

- **建什么、在哪**：① 两个构建任务（`task-kaniko-platform-{api,console}-stg.yaml`）把推送后的镜像摘要写成任务结果，并在构建时多推一个按提交命名、以后不再移动的标签，只为不被 registry 回收；部署只认摘要。② 记录器是 PROD platform-api（`api/internal/releases`，已在信任根路径内）。记录增加：platform 和 ui 的完整 SHA、构建输入（两个 Dockerfile 的内容哈希，run 实际解析出的 Pipeline / Task 规格的哈希）、两个镜像的仓库名与摘要、构建和部署 run 的 UID、STG 三个工作负载全部收敛的时间。记录写成一次就不可改（`immutable` ConfigMap，名字由 run UID 得出）。③ 只有 PROD 平台账号能创建带 `bifrost.io/release-record` 标签的 ConfigMap，谁都不能改；当前和上一份 PROD 成功组合的记录与标签不清理。④ 用记录的一方不只信记录：按 run UID 回查 PipelineRun / TaskRun 本体（`pipelineRef` 是 `bifrost-deliver-platform`，不是内联规格，终态成功，结果里的 SHA 和摘要与记录一致，规格哈希等于集群里受保护的定义），再向 registry 确认两个摘要存在、仓库名在固定清单里、架构与节点相符。
- **拒绝**：「拒绝：记录 <id> 不完整（缺 console 摘要）」；「拒绝：记录与 run <uid> 的结果不一致（api 摘要）」；「拒绝：run <uid> 已被清理，无法复核；重新发一次 STG」；「拒绝：摘要 <sha256> 不在 registry，或仓库名不在清单里」；「拒绝：记录已存在，不能覆盖」。
- **验收**：正例：连续三次真实的 STG 发布都生成完整记录，摘要等于 STG 三个工作负载 Pod 的 `imageID`。反例：手工建一条带标签的假记录（准入拒绝）；记录里的 SHA 与 run 不符；缺一个摘要；覆盖已有记录；跑一次 registry 回收之后，当前和上一份组合仍能拉取。
- **谁批**：全部 PROD 发布仍由 Owner 批；这一步不改 PROD 的发布方式。
- **退出**：正例和五个反例全过；记录格式的变更写明新旧版本能否并存（LESSONS 第 21 行）。

### 第 3 步　发布闸门：先影子运行，再强制（原 G1）

- **建什么、在哪**：判定放在 PROD platform-api 的发版策略引擎里（`api/internal/releasepolicy`，它已经是唯一的裁判），不从请求指定的仓库版本里取代码，也不经 Tekton 脚本。输入只有记录 ID；SHA 和摘要先按格式校验。六项：① CI：按 run 里克隆任务的实际提交认，不按参数字面；`pipelineRef` 必须是 `bifrost-ci-platform`，和标签矛盾即拒；提交在 main 的历史里；覆盖（platform SHA，ui SHA）这一对的**最新一次尝试**终态成功。最新一次还在跑就有限等待 15 分钟，不回退到更早的成功。② STG 身份：按创建时间最新的一条 platform STG 记录就是这一条，时间缺失或解析不了的记录拒绝；api、workers、console 三个 Deployment 的 `observedGeneration` 等于 `generation`、副本齐、所有非终止 Pod Ready 且摘要等于记录（workers 等于 api）。③ 观察时间：从三个工作负载全部收敛起算，最低 10 分钟；期间换版、Pod 重启或健康探针失败就清零重算。④ 差异：当前 PROD 成功组合 → 候选，platform、ui 逐仓，加构建输入；触及信任根、D10 路径、DDL 路径、持久状态格式路径的不走自动。⑤ 未冻结；读不到按冻结算。⑥ 走自动放行时，规则签名有效、未过期（人工批准的单不看这一项）。结论带证据 ID，10 分钟内有效。
- **影子与强制**：影子期每次 PROD 发布申请都算一遍，结论写审计并显示在审批单上，不拦。强制之后，闸门不过就不建普通审批单。人工例外是另一种有界的单：点名豁免「CI 结果」或「观察时间」中的哪一项、针对哪条记录、一次有效、会过期。产物身份、冻结、信任根不能豁免，也没有请求参数式的旁路。迁移之前 PROD 仍是重新构建的，这一步保证的是「记录完整、STG 跑的就是记录里的摘要」；PROD 用同一份摘要要到第 4 步。
- **拒绝**：「拒绝：CI 最新一次是红的（<run>）」；「拒绝：CI 还在跑，已等 15 分钟」；「拒绝：没有同时覆盖 platform <sha> 和 ui <sha> 的 CI」；「拒绝：STG 上是 <sha>，不是要发的 <sha>」；「拒绝：platform-workers 还没收敛」；「拒绝：STG 才观察 3 分钟（14:32 重启过，已重新计时），规则要求 10 分钟」。
- **验收**：演练最新 CI 红、CI 运行中、STG 错版、workers 未收敛、观察期内重启、观察期内换版，各自被拒且原因正确。review 14 复现过的三个反例做成单测（旧成功盖住新失败、观察时间为 0、标签冒充流水线）。参数里放 `$(id)` 被格式校验拒绝。
- **谁批**：全部 PROD 发布仍由 Owner 批。强制之后，他批到的每张单都已经过了这些检查。
- **退出**：影子期覆盖至少五次真实发布，没有一次误放行，误拒逐条有解释；然后切强制（收紧，不需要签名）。

### 第 4 步　窄动作和写入器，先人工授权（决定 A；原 G2）

- **动作、状态、租约**（`bifrost-platform/api/internal/actions`，C 级）：`promote_platform_prod` 的参数只有 `record_id`、`request_id`、`expected_current_release`，调用方是有自己身份的授权申请者。发布操作的状态放 statefile（ADR §12.3）：已授权 → 已提交 → 同步中 → 验证中 → 成功，或 恢复中 → 已恢复 / 已停止。写入之前先落意图：请求身份、规则 ID 或审批单号、证据 ID、前后摘要、Git 基准与提交、租约代次；之后每一步的结果接着写。同一个 `request_id` 重试得到同一个操作。租约是现有发布窗口加代次（ADR §12.7）：平台核对持有者、范围和代次，并续租；操作一建立，调用方的窗口就移交给操作本身，调用方退出不影响它，它也不去等调用方那把锁；租约持到核对或恢复结束。
- **写入器**（放哪、拿什么凭证见未决 2）：独立进程，仓库的写凭证只在它手里，平台只能向它提交意图。它自己核验四样：授权（规则由它自己验 Owner 的签名；试运行期认平台的审批记录）；证据（按第 2、3 步用 run UID、registry、STG 实况重算，写入边界再查冻结、CI、STG 身份；冻结记录显示已解除却没有 Owner 对那次冻结的签名，按冻结算）；租约代次是它见过的最大值；最终改动。改动的范围：`k8s/overlays/platform-prod/kustomization.yaml` 的 `images:` 里按固定镜像名匹配的两项，只换 `digest` 的值，api 和 workers 用同一个 api 摘要；仓库名、其他键、其他文件有任何变化都拒绝。它只推 GitHub（权威源，Gitea 继续单向镜像），非强制，带基准 SHA；基准变了就放弃，由平台重新过闸，不强推。提交信息带操作 ID、记录 ID、发布前的组合。
- **一次性迁移**（单独一张人工批准的单）：`images:` 两项从 `newTag: prod` 改成 `digest:`，值是当时 PROD 实际在跑的摘要。迁移同步之日，旧流水线 `bifrost-deliver-platform-prod` 和 `platform-prod-pinned-from-stg.sh` 退役，收回 `tekton-deliver` 对 PROD Deployment 的 `patch`。之后每次晋升：提交，再让 Argo 同步到这一个提交，等三个 Deployment 滚动完成；没有 `rollout restart`。
- **拒绝**：「拒绝：不接受参数 <名字>」；「拒绝：当前 PROD 是 <id>，不是请求里的 <id>」；「拒绝：已有发布在进行（操作 <id>，代次 <n>）」；「拒绝：代次 <n> 已过期」；「拒绝：改动超出两项摘要（<路径>）」；「拒绝：main 已前进，基准不符；请重新申请」；「拒绝：main 上有未同步的 PROD 清单改动（<提交>）；先由人工同步或回退」；「拒绝：发布已冻结」。
- **验收**：反例都不产生提交：改第三个键；给一个不在记录里的摘要；带 Git 地址或路径参数；两个请求同时到（只有一个拿到租约）；同一个 `request_id` 发两次（只有一次提交）；基准之后有人推了 main（放弃并重评）；批准之后 platform 的 main 前进或 `:stg` 标签被改（发出去的仍是记录里的摘要）。正例：推送成功但响应丢失，进程重启后认出远端那个提交是自己的，状态接到「已提交」，不推第二次。
- **谁批**：每次 `promote_platform_prod` 是一张 C 级单；迁移是一张单；写入器的部署和凭证是 D 级。这一步到第 5 步之间发布失败，由 Owner 应急：回退那次提交并手动同步；命令写进 runbook，迁移前演练一次。
- **退出**：反例全拒；一次人工批准的真实晋升只产生一个成套提交，PROD 三个工作负载的摘要等于记录；在任何一步杀掉进程都能从状态接续。

### 第 5 步　人工批准的摘要晋升和受限的恢复（原 G2、G3）

- **核对**（平台的发布操作）：绑定这次的提交和摘要。Argo 报告的已同步提交就是它；三个 Deployment 的 `observedGeneration` 等于 `generation`、更新后的副本数等于期望值、全部 Ready；每个非终止 Pod 的镜像摘要等于记录（按 manifest / index 与节点架构的对应关系比）；功能探针通过（API `/health`、Console 首页、一个只读接口）。每一段都有超时，超时按失败算。
- **恢复**：不是一个可以随便调用的新动作，而是发布操作自己的一个分支，只有操作处在「同步中」或「验证中」才能进入。它把两项摘要写回**该操作开始前记录的成功组合**，走同一个写入器、同样的改动约束，之后做同样的核对。冻结期间不允许新发布，允许这种恢复。恢复后仍不过：状态「已停止」，设冻结，带外通知，不再自动尝试。发布成功之后才发现问题：人工批准下把 PROD 设回上一份成功组合，只能是上一份，不走自动。
- **排除与用时**：差异触及持久状态格式路径的发布不进自动范围，单子上写明「不能自动恢复」；Git 回退撤不掉状态迁移，这里不建通用的迁移回滚。新版本必须能和过渡期里的旧 Console、旧状态并存。用时不预设「一分钟」：检测、Git 恢复、Argo 收敛、健康恢复四段各自量，演练后把实测值写成规则里的超时。
- **拒绝**：「拒绝：恢复目标只能是操作 <id> 开始前的组合 <release>」；「拒绝：操作 <id> 已结束，不能恢复」；「拒绝：这次发布改了状态格式，不能自动恢复；转人工」；「停止：恢复后仍未通过核对，已冻结并通知」。
- **验收**：让第二个工作负载在 PROD 起不来（最终回到发布前的组合）；同步中杀掉 platform-api 和 workers（重启后接续，不重复提交）；Argo 迟迟不同步（按超时处理，不算成功）；暂停的旧执行者醒来再写（代次过期被拒）；让恢复指向一个更早的版本（被拒）。全程没有构建，没有覆盖后来的发布。
- **谁批**：每次晋升一张 C 级单。失败时自动恢复的授权从哪来，见未决 3。
- **退出**：新路径上至少五次真实发布成功，五个演练全过，四段用时有实测值。

### 第 6 步　带外的监督器（原 G4、G6）

- **建什么、在哪**：独立于 platform-api 和 workers 的常驻进程（位置见未决 2）。① 发布开始之前它就拿到并自己保存三样：发布意图、发布前的成功组合、恢复授权。授权在发布开始时取得，这次发布结束前不因规则到期而失效。它没确认收到，写入器不写。② 它用自己的只读身份直接看 Argo 和三个工作负载，不经平台的 API，每次发布独立出一份核对结果；和平台的结论对不上就冻结并通知。平时巡检 PROD 的实际摘要是否等于最近的成功组合。③ 到超时仍未通过核对，它不向平台领单、不等重新批准、不依赖原来的操作继续，自己把两项摘要写回发布前的组合，让 Argo 同步，核对，经 .50 的告警中转通知 Owner。④ 范围只到应用升级失败。GitHub、Argo 或整个集群不可用时，它到超时就告警、转人工，不自己修。⑤ 和 W-50 的关系：W-50 的带外执行器靠向平台领已批准的单子，平台坏了就领不到，所以不算这一步；监督器可以和它同机、用同一种部署方式，但恢复这条路不经过领单。
- **拒绝**：「拒绝：没有这次发布的意图记录，不恢复」；「拒绝：恢复目标和保存的发布前组合不一致」；「拒绝：监督器未就绪，不发布」；「告警：GitHub 不可达，已超时，没有做任何改动，请人工处理」。
- **验收**：发起一次发布后关掉 PROD 的 platform-api 和 workers，或者发一个持续起不来的版本：监督器不联系平台就完成恢复并通知，四段用时记录在案。反例：断开它到 GitHub 的网络（只告警、不动）；给它一条没有意图的恢复请求（拒）；停掉监督器再申请发布（平台拒绝）。
- **谁批**：每次晋升仍是 C 级单。监督器自己的部署、升级和凭证由 Owner 批或亲手做。
- **退出**：上面的演练全过；监督器登记为维护者，有存活信号，失联会呼到 Owner（ADR §2 第 4 条）。

### 第 7 步　Owner 签自动发布的规则（最后）

- **前提**：第 1–6 步全部退出；Codex 对实现的独立复核通过。
- **规则写什么**（模板 `agent-config/release-policy/template.json`，Owner 用签名密钥签，W-42 的引擎）：规则授权的是**动作** `promote_platform_prod`，不是「启动某条流水线」。绑定环境 `platform-prod`、来源（`bifrost-deliver-platform` 的记录）、最低观察时间、核对要求和各段超时、恢复条款（失败回到发布前的组合）、有效期 90 天。条件沿用现有的（未冻结、不触 D10 路径、不触信任根、不含 DDL），加上「不触持久状态格式路径」和「差异按当前 PROD → 候选算，含 ui 和构建输入」。
- **拒绝**：签名无效、规则过期、证据缺失或过期、差异触及信任根 / D10 / DDL / 状态格式：自动入口一律拒绝并写明是哪一条，转人工单；人工单到期作废，不执行。
- **验收**：签之前把第 1–6 步的通过与拒绝矩阵完整重跑一遍，另加四项：规则过期、冻结中、改了信任根的发布、证据重放（把用过的闸门证据或旧记录再交一次）。签之后，第一次符合条件的发布无人点击到达 PROD，审计记下命中的条款，Owner 收到事后通知。
- **之后**：清掉旧路径的残留（`paths.json` 里 `pinned` 的 `bifrost-deliver-platform-prod`、registry 里不再被引用的旧标签、RELEASE.md 的旧说明），再跑一次第 1 步的旁路演练。规则到期就回到逐次人工批准，到期前 14、3、1 天提醒。
- **退出**：W-56 进「待你签收」；衡量的数字是 Owner 逐次批准平台发布的次数。

## 4. 和原来六个门槛的对应，以及什么时候能签规则

原 G1 = 第 2、3 步；G2 = 第 2、4、5 步；G3 = 第 5 步；G4 = 第 5、6 步；G5 = 第 1 步；G6 = 第 6 步。第 1–4 步做完，新路径只能在 Owner 逐次批准之下试运行；原 G1–G4 的内容全部验收，也只到这个程度。自动规则必须等原 G5、G6 的等价物（第 1 步的旁路与冻结、第 6 步的带外监督器）都上线并演练过才能签，也就是第 7 步。第一版里「Owner 批两次之后就签第一份规则」的说法作废。

## 6. 未决（等 Owner 定；正文按推荐项写）

1. **怎么让「推 main」不再直接改 PROD**（15-1d、15-2g）
   - A（推荐）：`bifrost-platform-prod` 关掉自动同步，只同步到点名的提交；`gitops_sync_app` 要加一个「提交」参数。纯收紧，和 Trade 的 `bifrost-prod` 现在的做法一致。代价：PROD overlay 的配置改动每次要一张同步单（以后可以另签一条只管配置的规则）；失去 selfHeal，漂移改由监督器发现。
   - B：保留自动同步，让应用跟踪一个只有写入器能推进的引用。保住 selfHeal；多一个引用要维护，写入器的职责变宽。（不封、只在事后发现并冻结，是检测不是阻止，不列为选项。）
2. **写入器和监督器放哪、拿什么凭证**（15-2j、15-3a）
   - A（推荐）：一个带外程序兼做两件事，放 .50 的独立账户，与 W-50 的执行器同机。凭证两样：只对 `bifrost-trade-infra` 可写的 GitHub deploy key；一个只读、外加只能 patch `cicd/bifrost-platform-prod` 这一个 Application 的 kube 身份。要在 ADR §3 给 .50 加这一类凭证。
   - B：集群里单独命名空间的 Deployment。部署快；和集群同命运，集群里权限最强的账号读得到它的 Secret。
   - C：平台自己持有写凭证，不设写入器。最省；平台失陷等于整仓可写，窄动作只约束正常调用，监督器仍要另建。
   - 不管放哪，还要定**写凭证的范围**（第 1 节第 9 条只靠「凭证只在写入器手里」回答，没有把凭证本身变窄）。GitHub 的 deploy key 只能按整个仓库授权，而 `bifrost-trade-infra` 里还有治理层（`agent-config/`、`preflight.js`）、Trade 的 overlay 和 D10 的两个补丁：写入器只改两项，但 key 被拿走就是整仓可写。(i) 接受整仓的 key，靠 .50 的独立账户隔离，监督器另外巡检 main 上不是写入器该有的提交。(ii)（推荐，可行性待验证，见第 7 节第 12 条）把这两项摘要搬到一个只放它们的小仓库，Argo 应用多一个源，key 只对这个小仓库可写：凭证的范围和动作的范围一样窄，治理层和 D10 补丁不在它够得着的地方。
3. **第 7 步之前，失败时自动恢复的授权从哪来**（15-2g、15-3c）
   - A（推荐）：Owner 在第 5 步先签一条只含恢复的窄规则：只允许回到这次发布开始前的成功组合。这是第一处放宽，范围最小；ADR §5（2026-10-08）已定「不过就自动回到上一版」。
   - B：每张晋升单写明「失败时回到 <组合>」，一次批准覆盖发布和它自己的撤回。不用多签一次；要改 ADR §5 的「一次批准执行一次」。
