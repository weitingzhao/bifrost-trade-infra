# Bifrost Ops Console 的 Owner 业务价值与 UI 方案

2026-10-10，按 Owner 补充要求修订。本文是 UI 审查主线；此前 REPORT.md 的响应式测量作为工程证据。目标是把多 Agent 协作思想体现为 Owner 可理解、可判断、可追溯的体验。布局为这一目标服务。

## Console 应当替 Owner 减少什么工作

依据 ADR §1、§6、§12，系统承担协调、执行、验收与维护，Owner 负责定目标、定规则、处理不可逆事项。Console 的价值是让 Owner 在有限注意力下掌握自主权：知道哪些目标在推进、为什么某件事需要自己、授权边界是什么、自己的决定有没有落实。

跨厂商 Agent 之间的状态和交接留在平台，参谋长整理成简报和决策卡。Owner 不必翻多个聊天、转交消息、追问谁在负责，或从 Pod、分支和流水线名称推测发生了什么。开发阶段临时需要 Owner 接手的工作也必须解释原因，不能把过渡负担伪装成长期职责。

设计 v4 §19 已明确手机的五件事：被叫到、处理需要你、问现在怎样、给目标、紧急叫停。它还明确“手机上不做监控”。因此手机适配的主要验收对象应是这五个场景。健康、数据、IB和集群详情保留在既有页面，作为需要时的证据；不占用首页形成另一套监控驾驶舱。

## 架构思想如何变成 UI

| 架构原则 | Owner 应当感受到的价值 | 具体呈现 |
|---|---|---|
| Owner 只做三件事 | 找我的理由是清楚的，日常可自动工作不用我逐步放行 | 每条事项说明属于目标、规则或不可逆决定；过渡期人工步骤说明未满足哪条自动化门槛 |
| 共享状态协调 | 我不用在会话之间传话，换设备也能接着处理 | 同一事项有稳定编号，关联目标、工作项、请求与后续结果；通知是同一事项的提醒 |
| 岗位稳定，人员可换 | Claude/Cursor/Codex更换不会让我丢掉进度与决定 | 以mission和岗位为主，厂商/模型为明细；固定参谋长入口，显示在岗和最近有效简报 |
| 权威在代码，作者不能验收自己 | 我能区分“Agent说完成”和“已经验证可签收” | 显示产物、独立验收、提交与环境证据；submitted、accepted、deployed、signed-off不混为一谈 |
| 规则内自动，越界等Owner | 我知道系统凭什么继续、为什么此处停止 | 显示命中的有效规则或越界项；待签提议比较现有边界与新边界，不只给参数JSON |
| 未回复安全等待 | 我晚点处理的影响可预期，其他工作仍然能推进 | 显示不回复会怎样、受影响目标、截止/过期时间，区分只阻塞此项与更广影响 |
| 可替换性与额度账本 | 我知道这支团队能持续干活，而不是依赖某个会话 | 团队与规则页说明合格候选、单厂商依赖、预算/额度观测时间；未知不能画成正常 |
| 可追溯 | 我做过的判断留下记录，系统处理结果回到同一条事上 | 从请求追到批准、排队、执行、验收和签收；历史可按编号找回，不让Owner拼多张表 |

“Decide / Approve / Sign off”是处理方式；“Goal / Rule / Irreversible”是为什么必须由Owner参与。这两组含义不能合并。例如批准一次PROD发布目前是过渡期要求，不能因此把所有PROD发布描述为不可逆。

## 一条需要 Owner 的事项必须回答什么

首先读到业务问题和影响，再看到证据与动作。列表应让Owner理解为什么值得点开；详情应足以作出决定。

1. **需要我做什么**：一句可理解的问题，说明是选择、批准、签规则，还是签收成果。
2. **为什么需要我**：对应Owner职责；如果是过渡期人工门槛，说明限制及关联工作项。
3. **影响什么目标**：关联mission/W-n，说明结果与受影响范围，避免只写内部动作名。
4. **推荐怎么做**：推荐与理由、实际选项；来自参谋长的推荐标明为建议，不当作授权或事实。
5. **晚点或不回复会怎样**：安全默认、等待影响、到期后是否失效；不制造虚假的紧急感。
6. **依据是什么**：最新状态、参数/命令全文、风险与回滚、验收证据；重要细节不能用truncate替代。
7. **处理后发生什么**：批准、执行、验收等各阶段分别显示，失败/回执未知要有明确解释。

这些是展示要求，不是新增API草案。缺少相应字段时，必须标清未提供，由既定业务lane补数据；UI不能自行推断权限、完成状态、阻塞原因或执行结果。

## 手机主入口的具体草案

保留Owner已经确定的首页约束：只列待定、待批、待签，加一句与Status同源的系统结论；首页不放批准按钮。参谋长简报/对话归团队与规则页，首页提供进入该既有目的地的入口，暂未实现时不展示假在线或假简报。跨类优先级尚未由业务层给出时，沿用W-44三组，不能凭颜色或时间猜一个业务排序。

```text
Needs you                                 PROD
System status: …               Updated …
3 waiting for you               [Read status]

APPROVE · 1
┌ Apply the new node reboot alert rule ───┐
│ Why you: production approval required  │
│ Purpose: detect unexpected restarts    │
│ W-38 · Request #… · waited …           │
│ Recommended: approve this scoped plan  │
│ If unanswered: current monitoring stays│
│ Review request                     →   │
└────────────────────────────────────────┘
DECIDE · …
SIGN OFF · …

Team & rules →                  Records →
```

这是目标版信息草案，数字与编号是占位，不是实际待办计数。W-38例子来自现有计划里的观测变更，其生产审批是当前规则；这里的英文文案需要对应真实plan证据后才能使用。受保护数据读不到时显示Unknown，不能显示“3”或“Nothing needs you”。未接入的决定和签收也不能算0。

空状态只表示“当前已覆盖的事项中没有待你处理”，不代表系统健康、全部工作已完成或运行时已接通。系统异常可以存在但正在自动处理；需要Owner的事项也可以存在于健康系统里。这两种状态必须分别表达。

## 重点场景及成功标准

| 场景 | Owner 的体验 | 需要平台提供的事实 |
|---|---|---|
| 收到需要自己判断的通知 | 点开同一事项，知道问题、推荐、影响和等待后果，无需找原会话 | 稳定编号、事项类型、摘要、关联工作与真实截止时间；沿用W-49/W-52入口 |
| 决定目标或取舍 | 看选项与成功标准，回答后知道哪项工作继续 | 决策卡、回答记录、mission关联；W-40过渡层及后续agentrt |
| 批准动作 | 在详情看完整对象与参数；批准后明确看到等待/执行结果 | W-48状态机与W-50执行回执；批准不等于执行成功，网络错误不等于没执行 |
| 签规则 | 看新旧授权差异、范围、预算和有效期，理解过期后收紧什么 | 已签版本与修改提议；当前ssh签名仍按既有流程，不假设手机按钮能签 |
| 签收成果 | 看达成的目标、独立验收、防线与后续，能签收或打回 | W-n/TD-n、证据绑定提交与环境；不把分支合并当作成果验收 |
| 问现在怎样 | 一份有时间与证据的简报说明推进、阻塞、风险和下一步 | 参谋长席位、运行时快照与简报产物；席位离线时仍可读有时间的上一份 |
| 给新目标 | 描述想实现的结果，得到整理后的目标、范围、成功标准与授权差异 | 参谋长将输入整理成mission提议；输入文字不直接扩大授权 |
| 紧急叫停 | 清楚停止范围；反馈已请求、哪些执行者确认、是否仍有未确认工作 | 运行时阶段1真实叫停协议；未接通前不做虚假的全局Stop按钮 |
| Owner离线一夜 | 回来后先知道已完成什么、哪些在规则内继续、哪些安全地等自己 | 最新简报与积压事项；不能宣称当前运行时已经24小时自动工作 |

建议的可用性门槛：手机列表10秒内能说出最需要处理的事项及原因；详情30秒内能找到推荐、不回复后果、受影响目标与执行内容。长命令或复杂方案需要更久阅读，这两个时间只衡量信息能否找到，不能催促盲批。

## 八个问题分别创造什么价值

- **Needs you**：集中Owner的判断与签收，减少遗漏与催问。计数代表具体待处理事项；不同页面引用同一项时不重复当作多件事。
- **Status**：判断当前可靠性与风险范围；说明异常在自动处理、等待证据还是需要进一步核实。warning本身不自动变成Owner待办。
- **Data**：确认研究与业务所需数据是否按期到齐，缺口、影响和修复路径可查；具体数据业务仍在对应域。
- **IB**：明确连接与数据链路是否可用、哪些受影响；保留D10边界，不把“连接健康”解释成交易可以启用。
- **Releases**：知道成果到哪个环境、什么在排队、是否失败与恢复；版本和流水线是证据。自动回滚未验收前不能显示“系统会自动恢复”的承诺。
- **Infrastructure**：需要深入或应急时找到真实部件、范围与有权限的动作。
- **Progress**：按目标与W-n看成果、阻塞和验收；分支、提交、测试作为下钻证据。进度比例没有可靠分母时不画伪精确百分比。
- **Team & rules**：理解谁在承担职责、规则是否有效、团队能否替换和持续运行，找到固定参谋长入口。

Records提供追溯，不是另一份待办队列。手机优先处理与简报，平板支持阅读方案、验收证据与目标进度，桌面适合完整比较和下钻；三者共享同一事实与事项状态。

## 当前能力和未来能力要分别设计

当前代码基线仍沿用REPORT.md：main `7cda6cb`，STG集成版`11ebb8c`，PROD版本在STG版本页显示`efeaf69`；这些是上轮只读核对的快照，并非实时发布承诺。

W-44已提供首页三组与同源结论；W-45有发布分段；W-48/49/54仍属待集成批次；W-40、运行时mission/决策/独立验收、团队规则与参谋长尚待相应阶段。ADR最新门槛规定W-56验收前PROD仍逐次批准，增量DDL自动执行目前关闭。UI须说清“当前待你批准”和“未来满足门槛后自动”，不能靠视觉提前放权。

静默线程尤其需要区分：检测到没有心跳，是观测事实；任务失败、可以接管、需要Owner介入，是额外判断。W-54决定将静默计入Needs you，W-57会补“等你授权/未接入监测”等区分；UI沿用其真实类型与计数，不自行删除这项，也不让Owner面对一条不知道该做什么的红色主机名。需要由该lane给清楚的处置说明。

## 修订后的实施优先级

1. **先定义并检查事项内容**：用真实待批、待定、待签实例逐项核对问题/原因/影响/推荐/不回复后果/证据/结果。将缺口分为现有数据未呈现与后端尚未提供，归属对应lane。
2. **完成Owner处理链路的呈现**：首页可理解、详情可判断、处理后可追踪、记录可找回。响应式页头、44px触控、可读参数和断线提示服务于这条链路。
3. **随运行时能力接入目标与简报**：Progress以mission/W-n为主；Team & rules承载席位、简报、规则与可替换性。先有真实能力与证据，再启用交互。
4. **最后逐页适配监控证据**：Status/Data/IB/Infrastructure的卡片、表格和图表处理按实际下钻需要推进。

继续遵守W31文件归属与阶段边界。本文没有另定多Agent架构、API或审批语义，也没有要求其他线程停工；独立worktree中的UI实现仍待本阶段报告后的实施指令。产品代码、现有计划与Design ASK未修改。
