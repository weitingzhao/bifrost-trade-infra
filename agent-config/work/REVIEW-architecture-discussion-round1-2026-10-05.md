## 0. 先给体量一个数（实测）

| 指标 | 数值 |
|------|------|
| 代码量（py/go/ts/tsx/sql/yaml，11 个活跃 repo） | 约 86 万行：frontend 30 万、platform 28 万（含 console）、research 10 万、market-data 5.8 万、core 3.8 万、infra 2.9 万、api 2.3 万 |
| 最近 30 天提交 | 约 2,100 次（frontend 932、research 381、market-data 267、infra 207、platform 110） |
| 前端页面 | 232 个 `.tsx` 页面，其中 `/research` 下 73 条路由 |
| 定时作业 | 约 40 个（Dagster 驱动） |
| spine 决策 | 55 条 |
| 记忆里的「坑」条目 | 约 140 条 |

**结论**：这已经是一个中型团队量级的系统，但只有一个人在用，开发几乎全靠 AI。AI 让「写」几乎不花钱，所以瓶颈不再是写代码，而是：

- 理解现状的成本：每个新会话都要重新读懂；
- 不变量被悄悄打破（键名漂移、改名失配、测试抄旧名单）；
- 发布协调。

冰山下的问题之所以重要，是因为它们直接决定新业务（回测）能不能落地。

## 1. 「先建议、有正反馈，再谈执行」——我同意，而且建议把「正反馈」量化

你的直觉是对的，系统现状也支持它：

- **没有「建议 → 结果」的闭环数据**：每日持仓快照未建；plan 与真实持仓没有关联（`reviewContracts.ts:129`）；Review 里「vs backtest」那一列恒为空。
- **回测本身还不可信**：B1–B7 七个正确性问题未修；没有 bid/ask，滑点恒为 0；Canonical PnL 100% 是插值模型价；铁鹰实际是 ATM 铁蝶。
- **执行链不是一个开关的距离**：协议里没有下单和撤单，没有适配器，flatten 未实现。

我会把「正反馈」变成一个可以测的门槛，到点再讨论执行，而不是凭感觉：

1. **每条建议落库，并且是时点数据**：给出时的数据快照、理由、建议结构、预期，事后不能改。
2. **自动结算**：到期或 T+N 时用真实价格（含价差估计）算结果，并和一个机械基线比较，例如每周卖 SPY 30Δ put。
3. **门槛（示例，由你定）**：至少 6 个月、跨两种以上市场状态（升波、降波）、至少 50–100 条建议，扣成本后的期望值为正且跑赢基线；你实际采纳的那部分也要单独统计。
4. **执行之前还有一个中间档**：系统生成订单草稿，你在 TWS 里手工确认下单。这一档拿到了大部分效率，D10 可以继续冻结。

## 2. DEV/STG/PROD + Golden Source：快和稳怎么平衡

### 现在的设计哪里合理，哪里是在白付成本

- **合理**：Golden Source 只放一份。供应商数据是「事实」，不因环境而异；复制 33 GB 到三份既贵又没有收益。行业里的做法也是行情数据只有一份，环境隔离的是**写**和**策略状态**。
- **白付的成本**：Trade 有三套完整环境、三条发布链、DEV 镜像还要单独同步。但数据链路（插件、Research、redis-ib、GS）只有一套，所以 STG 验证的是 Trade 代码，验证不了数据。三套环境的仪式感很强，隔离效果却很薄。

### 平衡的关键：按变更的风险分道，而不是按环境个数

| 道 | 适用 | 流程 |
|----|------|------|
| **快道** | 只读 UI、只读 API、Research 新指标（加字段、加表） | main 合入 → 自动到 STG → 冒烟绿 → 一键或自动到 PROD。目标是一天内多次 |
| **慢道** | GS 上的 DDL 或删数据、写 raw_broker 的代码、跨载荷的契约破坏、任何 D10 相关 | 计划 → Owner 确认 → STG 用真实数据演练 → PROD → 验证 |

AI 开发模式下，保证「稳」的不是环境数量，而是**机械护栏**：

- 契约测试（插件键名、API schema）；
- 一个时刻只发一个版本（已有发布窗口）；
- preflight 守卫；
- 「删数据前先备份」写进工具，而不是写进规则文档；
- 回滚要便宜（Argo、镜像钉版本）。

Golden Source 真正要保护的不是隔离，而是**区分可再生和不可再生的数据**：

| 类别 | 例子 | 丢了怎么办 |
|------|------|------------|
| 可再生 | `features.*`、`dw_stock.*`（重算）；大部分 `raw_market` 历史（重新下载）；`raw_broker`（IB Flex 可重拉） | 能补 |
| **不可再生** | `option_snapshot`（vendor 当时的 IV/Greeks）、`option_open_interest`、你手工录入的 strategy / review / journal | **补不回来** |

而不可再生的那部分，现在正被**滚动物理删除**：snapshot 只保留 90 个交易日，期权日线保留 2 年。从回测的角度看，这是最该先停下来的事：改为归档到 NAS 或 MinIO（parquet），而不是删除。

## 3. 「平台不碰业务」：保留原则，但换一种实现；算技术债，但不急于偿还

**建议**：原则保留，因为你明确要做多应用云平台，这是对的方向。但「平台完全不知道业务」做不到也没必要。正确的形态是：**平台只认识一份「应用清单」，不认识业务概念。**

- 每个应用（Trade、家庭日程、自动化……）用一份 manifest 声明自己有什么：命名空间、健康端点、作业、数据库、发布链、要观察的 Redis 键或指标、哪些动作是 L1/L2/禁止。
- 平台按清单去探测、发布、备份、告警，不再为某个应用写专门的 Go 包。

**现状的越界算技术债吗？** 算，但要分轻重：

| 优先级 | 项目 | 理由 |
|--------|------|------|
| **高（与纯洁性无关，是耐久性）** | platform 状态在 emptyDir 上、审计只在内存里存 500 条、几个有副作用的 POST 没有鉴权、Trade 的 token 是 operator 角色 | 现在就会丢东西或越权 |
| 中 | `ibgateway` Go 包读写 IB 键、切 mock/live；硬编码分析作业名；platform 中转 watchlist | 等第二个应用上线时一起处理最省：那是这条原则第一次被真实检验，比抽象重构便宜，也不会设计过度 |
| 低 | 文档与代码不符、`scopeToDomain` 子串匹配 | 顺手修 |

**接第二个应用（女儿的日程小程序）时，有几件事 Trade 自己也需要**：

- 每个应用独立 namespace 与资源配额，防止小程序拖垮交易时段；
- CNPG 里每个应用一个库、一个角色；
- 独立域名入口；
- NetworkPolicy 默认拒绝跨应用访问。

## 4. 三个插件：按美股期权交易的业务分类来归位

三个插件其实属于三个不同的业务类别，而不是同一种「分包商」：

| 插件 | 业务类别 | 性质 | 建议归属 |
|------|----------|------|----------|
| IB Gateway | **券商连接**（实时报价、账户、未来的下单） | 实时、有状态、最敏感；将来执行就从这里出去 | **Trade 应用**的执行与连接层 |
| Flex Query | **券商记录 / 账本**（成交、现金流、对账的权威源） | 批量、事后、审计级 | **Trade 应用**的会计层（现在它已经 import `bifrost_core`） |
| Market Data（Polygon/Massive） | **市场数据供应**（股票、期权链、OI、基本面、公司行为、SEC） | 批量、体量最大（26 GB）、与账户无关 | 独立的**市场数据应用**，与 Research 同属「数据与研究」，Dagster 也归它 |

于是平台之上是：

- **两个业务应用**：交易（Trade：连接 + 账本 + 持仓 + 前端）、数据与研究（Market Data + Research + Dagster）；
- **将来的家庭应用**；
- 三个插件都变成**应用自带的适配器**，通过 manifest 登记到平台；
- 「Ops 插件」这个概念留给真正通用的东西，例如备份、证书、通知、UniFi。

这样也解释了今天的别扭之处：插件组织上属于 Ops、语义上属于业务、调度又在 Research。

## 5. 能否零停机：不能。先定目标，再补单点

当前单点（实测）：

- **k3s 只有一个 server 节点（.73）**：它挂了，调度和 API 都停，但已经在跑的 pod 继续跑。
- **PROD Trade 全部 pod 和 PG 主库同在 .70**。
- 单实例：redis-ib、ib-gateway、redis-live-prod、research-api、platform-api。
- PG 备份落在 NAS 上，经 NFS 跑 MinIO（不受官方支持，10-03 出过 InvalidPart）。
- gpu-server 现在 NotReady。
- TWS 在两台 Win11 上，各自是单点。

**建议的目标**（不追零停机，追「交易时段可恢复、关键数据不丢」）：

| 层 | RTO（恢复时间） | RPO（可丢数据） | 理由 |
|----|-----|-----|------|
| 交易时段看盘（报价、持仓） | 分钟级 | — | 你会盯着它 |
| 手工录入（strategy / review / journal） | 小时级 | **≈0** | 补不回来；体积只有几十 MB，异地多份很便宜 |
| 不可再生行情（snapshot、OI） | 小时级 | ≤1 天 | 当天能补拉，过后就没有了 |
| 可再生（features、raw_market 历史、raw_broker） | 天级 | 可重建 | 你说的「恢复后补全」正好适用 |

**性价比最高的补法**：

1. k3s 改成 3 个 server（嵌入式 etcd HA，现有节点就够）；
2. PROD 应用与 PG 主库用反亲和分开；
3. 关键单实例加 PDB 或第二副本；
4. 不可再生数据与手工数据另做一份到 NAS 原生共享（不经 MinIO-on-NFS）和异地；
5. 定期做恢复演练。

UniFi 我目前没有接入（`mcp/unifi` 未注册，spine D9）。网络改动属于你点名才动的事，等讨论到这一步再说。

## 6. 回测 + PineTS：可行，但要先做三件地基

### PineTS 是什么

LuxAlgo 的开源 TypeScript 运行时：把 Pine Script v5/v6 转译到 Node 或浏览器里执行，能喂自定义 OHLCV 数组，有 `strategy` 命名空间和 broker emulator；**不支持期权**；许可证是 AGPL-3.0 与商业双许可（你的 repo 本来就是公开的，个人使用没有障碍）。

### 它在闭环里的正确位置

PineTS 负责**标的的择时信号层**（趋势、动量、波动过滤），不负责期权定价和盈亏。闭环是：

> Pine 指标在 `stock_daily` 上出信号 → 写 `features.pine_signal_daily` → 期权结构模板（按 delta、DTE 选合约）→ 在真实 `option_daily` 价格上回测 → 与你的真实交易（journal、每日快照）对照 → 回到第 1 节的「建议 → 结算」门槛

### 实现方式

Research 是 Python，PineTS 是 Node，所以要引入一个新运行时。建议做成 Research 里的一个批处理 sidecar 或作业：只读 `stock_daily`，只写 `features.*`。浏览器里也能交互跑同一份脚本，用来调参。这是**新增外部依赖、新增表**，属于架构级决定，需要你确认。

### 先做的地基（否则回测结论不可信，或者样本在不断缩短）

1. **修 B1–B7，把五套回测收敛成一套引擎**：铁鹰按 delta 选腿、交易日偏移、财报日按真实发布日、幸存者偏差。
2. **停止物理删除，改为归档**：样本只会往前平移、不会变长的问题，对回测是致命的。
3. **价差模型**：没有 bid/ask，至少按 OI、成交量、价位分档估一个滑点，否则卖方策略的回测会系统性偏乐观。

与之配套的是**每日持仓快照**（你 09-30 已批准，但还没建）：没有它，「回测对照实盘」这一环接不上。

### 建议顺序

| 阶段 | 内容 | 粗估 |
|------|------|------|
| 0 · 地基 | 停删改归档、每日快照、手工数据异地备份、回测 bug 与引擎收敛 | 2–4 周 |
| 1 · PineTS 信号层 | 加上真实期权价格回测 | — |
| 2 · 建议落库与自动结算 | 第 1 节的门槛开始计时 | — |
| 并行（只做阻塞项） | 平台状态耐久化、k3s 3 server、PROD 与主库分开 | — |

平台的「纯洁性」重构等第二个应用上线时再做。
