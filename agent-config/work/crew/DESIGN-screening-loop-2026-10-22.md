## 零、一页看完

- **走什么**：一条真实问题。太太的反馈（Owner 转述）或业务参谋的提议 → 评估 → 接单 → 分支 → STG → 太太试用 → 记结果 → 结束或回到评估。
- **不加表、不加路由**（推荐 B，第三节）。问题记录 = 运行时产物（正文，每次修订一份）+ 档案第九节一行索引（git）。
  工作照旧用 mission / task / 验收；只有 Owner 能定的写成决策卡；进展给 Owner 看 Console。
- **一个问题一个编号 `BI-n`**，独立于 mission。接单时才建 mission，`work_id = BI-n`。
  mission 只管到「代码验收通过」；STG、试用、结论都记在问题记录里。
- **谁做**：过渡期统筹线程执笔，每条记录署名以哪个职责（业务参谋 / 建设负责人）。
  两处业务判断交参谋长席位（只读的另一会话）：评估分类、能不能结束。太太没有运行时身份，记录写「来源：太太（Owner 转述）」。
- **代码完成 ≠ 业务完成**：运行时在任务全部验收后就把 mission 记成 done（平台 `store/close.go:41-45,86-87`）。
  所以问题状态不读 mission；「已解决」必须有太太明确的确认（原话、时间、入口），沉默不算；检查脚本拦没有这三样的结束。
- **不重复派工**：只有建设负责人建工作 mission；建之前查索引和在途任务；索引一行只挂一个在途接单。
  跨会话同时建没有程序锁，这是本切片接受的缺口，C 补。
- **要 Owner 做的**：转述第一条反馈；方法变化时答卡；有前端改动时批 PROD 单；请太太试用并转述结果；签收计划步。

## 二、路径

**问题的状态**（不是 mission 的）：待评估 → 推进中 → 待试用 → 已结束；非结束态可转暂缓；待试用可回推进中；已结束有新证据可重开回待评估。
**结束结论**：已解决 / 部分解决 / 现有能力满足 / 不采纳。**三个结论分开记**：工程（验收）、交付（环境与提交）、业务（太太）。

### 第 0 步　选题（业务参谋）

- 从档案第七节和太太的反馈里挑。本设计不预选。
- 建议的挑选条件：她在意的；只改前端或不用改代码；不碰档案第五节「改选股方法」清单；一个 mission 一天内做得完；
  在 STG 用她自己的 Research 令牌就能试（不用 Plan this，它要共用的 operator 令牌）。
- 第七节的限制大多是读代码所得；写进给她的话之前先实测（业务优先）。

### 第 1 步　收到（反馈或提议）

- **谁**：太太的反馈由 Owner 转述（S4 A，现在生效）。首选入口是统筹线程（Owner 只在统筹线程里交互）；在 Console Chief 页说也行。
  业务参谋自己的提议标「业务参谋提议」，不写成太太的要求。
- **写什么**：
  - 产物：`put_artifact` kind `other`，修订 1。来源、入口与时间、原话（Owner 转述的原文）、服务对象、摘要（模板见第三节）。
  - 索引：档案第九节加一行 `BI-n`，状态「待评估」，写下一步。提交 infra，只暂存这一个文件。
- **运行时对象**：只有产物（`artifact_put` 事件，平台 `store/write.go:72-110`）。还没有 mission。
- **Owner 看到**：Console 上统筹线程给他的最新 note：「已记 BI-n，下一步评估，预计 …」（Console `src/api/agentRuntimeBus.ts:67-89` 读线程发给他的 note）。
- **为什么首选统筹线程**：Chief 页的话会变成 `owner → seat:chief_of_staff` 的 ask，并起一个 brief mission

- **S4 的事实**（她平时在哪反馈）还欠着；本路径不依赖它。

### 第 2 步　评估

- **谁**：建设负责人补技术证据；业务参谋（席位）判断分类。
- **怎么做**：
  1. 建设负责人实测：现象能否复现、数据有没有、代码在哪、碰不碰方法（对照档案第二节钉的两个提交）。
  2. 线程给席位发 ask（`send_message`，正文不超过 8 KiB，平台 `store/messages.go:15`），附问题原文、实测证据、档案第五节 S1 那条线和第七节相关条。
     席位答：问题是什么；属于哪类（指导即可 / 普通改善 / 方法变化 / 已有数据未呈现 / 运行故障）；有没有已有能力。
  3. 结论写进修订 2：接下 / 先调查 / 补信息 / 暂不接 / 指导即可，附理由。索引同步。
- **分支**：
  - 指导即可：业务参谋写一段用法说明，交 Owner 转给太太，跳到第 6 步（试用的是用法）。
  - 方法变化，或拿不准是不是：出决策卡（`ask_owner`，owner_duty `rule`，work_id `W-31`，标题带 `BI-n`；
    问题的 work_id 只收 W- / TD- / LANE-，平台 `../questions/canonical.go:41`）。他的回答定的是方法，不是任何发布的批准（平台 `../questions/doc.go:3`）。
  - 新数据、采购、读账户内容：同上，Owner 定。
- **运行时对象**：席位的 brief mission（max_action none、没有 work_id，平台 `store/brief.go:149-150`）；可能一张卡。
- **等待**：线程等席位答复，上限 30 分钟（RULE-waits 第 1 类的下限）；超了再问一次，仍没有就由线程写评估并标「席位未答」。
  卡属第 5 类：不设默认动作，期间做不依赖它的部分。
