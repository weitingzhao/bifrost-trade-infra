# W-33 第 3 步讨论材料：Mac 上的 Agent 不再持有管理员凭证

2026-10-09，全部只读实测。凭证只看文件名、键名和指纹，没有读值。**Owner 定之前不写道、不落地。**

前提已经满足：第 2 步完成。

- Agent 的写操作都能经平台的动作完成：五个通用动作、发版链、插件部署，都已在 PROD 真跑过；
- PROD 的 DB 步骤和其余兜底操作走 `owner_run_command`；

## 〇、要 Owner 定的事（待定）

### 1. 节点 root 怎么收（新发现）

**实测**：

- 5 个 k3s 节点的 `vision` 账号，`authorized_keys` 里只有一把 `ssh-rsa`，注释是 `gh:weitingzhao`。指纹就是本机的 `~/.ssh/id_rsa`，也是推 GitHub 用的那把；
- `id_rsa` 有口令，但已经在 ssh-agent 里解锁，`ssh -F /dev/null vision@192.168.10.73 true` 只靠 ssh-agent 就能登录；
- 节点上 `sudo -n true` 成功，免密 sudo，也就是节点 root；
- `~/.ssh/bifrost_deploy` **没有授权到任何节点上**，而且没有口令。之前「它能登录」是 `~/.ssh/config` 里 `Host *` 的 `IdentityFile ~/.ssh/id_rsa` 在起作用。

结论：同一个 macOS 用户下的任何进程（包括 Agent 会话）都能借 ssh-agent 拿到节点 root。只搬 `bifrost_deploy` 没有用。

**选项**：

- **A（推荐）Owner 专用节点密钥**：
  - 新建一把节点密钥，带口令，**不加入 ssh-agent**，放在 Owner 目录；
  - 授权到 5 个节点，确认能登录后，从节点上删掉 `id_rsa` 那一行。GitHub 推送不受影响；
  - `bifrost_deploy` 删掉；
  - `rolling-reboot.sh` 用 `BIFROST_SSH_KEY` 指向新密钥，由 Owner 执行（10-08 的决定第 8 条：第 3 步之后只有 Owner 执行）。
- B 只把 `bifrost_deploy` 搬进 Owner 目录：节点仍然能经 ssh-agent 的 `id_rsa` 登录，等于没收。
- C 节点去掉 `vision` 的免密 sudo：运维方式整体改变，滚动重启每台都要输密码，暂不推荐。

### 2. 只读 kubeconfig 放在哪

- **A（推荐）放在原路径 `~/.kube/bifrost-k3s.yaml`，管理员那份搬到 `~/.bifrost-owner/kube/admin.yaml`**：
  - 所有现有的命令、文档、记忆、bdev 脚本都不用改，自动变成只读；
  - Cursor 用的是同一个路径，同样变成只读；
  - 本机 bdev 的 platform-api（`PLATFORM_KUBECONFIG` 指向这个路径）跟着变成只读，相当于 STG 的观测角色。
- B 新路径，同时改掉所有引用：要改的地方很多，容易漏。

### 3. 只读角色给哪些权限

推荐下面这一组：

- `view`（不含 Secret），加上 Pod 日志、metrics；
- **exec 和 cp**：只在 research、plugin-market-data、plugin-flex-query 三个命名空间（10-09 已定）；
- **port-forward**：只对 `monitoring/prometheus-kube-prometheus-stack-prometheus-0` 这一个 Pod，用 resourceNames 限定。bdev 的 `prometheus-pf` 要用它，Prometheus 的接口是只读的；
- 其他 port-forward（比如 Redis Insight 连 redis）只有 Owner 能用。D10 的 operator 流就在 redis 上。

### 4. 其余管理员级凭证（.env 和 Secret 文件）

**实测**：Agent 能读到的明文里，除了 kubeconfig，还有下面这些。只看了键名，没有读值。

| 位置 | 内容 | 本机谁在用 |

**选项**：

- **A（推荐）搬一部分**：

  - **DB 日常密码（最后一行）不在本步**：拿掉会断 Agent 在 DEV 上的开发和测试。正确的修法是 TD-85（每个环境的密码分开，P1，要你批），这里作为接受的残余风险写进 ADR；

- B 只做第 1–3 条，`.env` 和 Secret 文件都不动，作为残余风险写进 ADR。

## 已定、照做的（不再讨论）

## 一、目标状态

- `~/.kube/bifrost-k3s.yaml` 是 ServiceAccount `bifrost-agent` 的只读 kubeconfig，`kubectl auth whoami` 显示这个账号；
- `~/.bifrost-owner/`（700）放管理员 kubeconfig、节点密钥（带口令）、`owner.env`、Trade Secret 文件。preflight 拦住所有引用这个路径的工具调用；
- 本机任何密钥都登不上 k3s 节点，只有 Owner 输入口令后的那把节点密钥可以；
- Agent 的写只有四条路：
  - 平台动作（B 级直接调；C / D 级走审批）；
  - `owner_run_command`；
  - research 和两个插件命名空间里的 exec；
  - `agent_reader` 只读查库。

## 二、步骤

**Cursor 一条道（LANE-W33D）**，只推分支、写报告：

1. infra `k8s/agent-access/`：
   - 命名空间 `bifrost-access`、ServiceAccount `bifrost-agent`、长期令牌 Secret；
   - ClusterRoleBinding 绑 `view`，另加 metrics 读权限；
   - 三个命名空间的 exec RoleBinding；
   - Prometheus Pod 的 port-forward（用 resourceNames 限定）。

   不归 Argo 管，手工 apply。
2. `scripts/owner/make-agent-kubeconfig.sh`：Owner 用管理员身份执行，写出只读 kubeconfig，令牌不打印。
3. `scripts/owner/move-owner-secrets.sh`：按第 4 条 A 的清单，把指定的键从 `.env` 挪进 `owner.env`，把 Secret 文件挪进 `~/.bifrost-owner/secrets/`，全程不打印值；可重复执行；支持 `--undo`。
4. 改 Owner 脚本：Secret 物化、密码轮换、UniFi、redis-ib、`rolling-reboot.sh`、`owner-run.sh`，从 Owner 目录读凭证。
5. `scripts/check_agent_access.py --live`，查四件事：
   - 当前 kubeconfig 的身份；
   - 权限矩阵：Secret、cicd 写、data 的 exec 都不行，research 的 exec 可以，Prometheus 的 port-forward 可以，其他 port-forward 不行；
   - 本机经 ssh-agent 登不上节点；
   - Agent 能读到的 `.env` 里没有第 4 条 A 清单上的键，`k8s/base/secrets/` 下只剩 `.example`。
6. 准备 preflight 补丁（`agent-config/work/ops-arch/preflight-w33d.patch`），由 Owner 应用：
   - 拦截引用 `.bifrost-owner` 和 `owner.env` 的 Bash / Read / Grep 调用；
   - 拦截把 `KUBECONFIG` 或 `--kubeconfig` 指向别处的命令；
   - Claude 和 Cursor 两侧共用这一份。
7. 文档：
   - AGENT_FACTS §8c：kubeconfig 是只读的；写操作和动作的对照表；
   - CLAUDE.md 和 workspace.mdc 同步，bump parity-id；
   - 涉及 kubectl 写操作的 skill 跟着改；
   - ADR §5「已知的接受风险」加三条：同一 macOS 用户下靠文本拦截、DB 属主密码（等 TD-85）、推 GitHub main 会触发 Argo 自动同步（交 W-31）。

**Owner 依次执行**（每一步我都先给出原样命令，并说明怎么回滚）：

1. `kubectl apply -k k8s/agent-access`；
2. 运行 `make-agent-kubeconfig.sh`。我用 `KUBECONFIG=<新文件>` 先试一遍：常用的读能用，写被拒；
3. 交换 kubeconfig：管理员那份搬进 Owner 目录，只读那份放到原路径；
4. 节点密钥：
   - 新建并授权到 5 个节点；
   - 确认新密钥能登录后，删掉各节点上 `id_rsa` 那一行；
   - 删掉 `bifrost_deploy`；
5. 运行 `move-owner-secrets.sh`；
6. 应用 preflight 补丁；
7. （可选）auto mode 里那组发布放行规则可以收一收：它们对应的 kubectl 写操作已经没有权限了。

**Claude 验收**：

**回滚**：Owner 把两份 kubeconfig 换回来；节点上用 Owner 的密钥加回 `id_rsa`；`move-owner-secrets.sh --undo`；撤回 preflight 补丁。
