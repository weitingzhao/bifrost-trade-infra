# 发版审批：Owner 不当瓶颈，但不能靠「认不出来的审批人」（提案，待 Owner 决定）

2026-10-08，Claude（stocks-53 / 8188a44b）写。**本文件是提案，不是已生效的规则。**
Owner 10-07 的指令经协调者 Der 转述：PROD 发版的批准方改成「恰好 Owner 与 Der 两方，Der 默认批准，Owner 保留否决」。
我没有照此改 `CLAUDE.md` / `.cursor/rules` / `docs/RELEASE.md`，也没有改审批机制。下面是原因和替代方案。

---

## 1. 今天的审批路径实际是什么（读码所得，2026-10-08）

`bifrost-platform/api/internal/approvals/`：

- `HandleApprove` 的请求体**只有** `{"channel": "chat"|"phone"|"console"}`（`handler.go:104-124`）。
- `service.approve(ctx, id, channel)` 校验三件事：`channel` 在那三个字面量里、单据未过期未决、`params_hash` 与存档一致（`service.go:152-178`）。
- **没有审批人身份。** 全仓搜 `approver` / `APPROVAL_ALLOW*` / `allowed_approver`：0 命中。审批路径里不存在 principal 检查，也不存在白名单。
- `requester()`（`handler.go:142`）只用于**申请方**，不是审批方。审计记的是 `channel=<自称的字面量>`。

**所以今天的安全属性是**：谁能带着有效的 platform 令牌打到 `POST /api/v1/approvals/{id}/approve`，谁就能批准任何待决单据，并且自己声明 channel。

让它事实上成为「Owner 闸门」的，不是认证，而是两件外部的事：

1. `preflight.js` 拦住 Claude 直接打那个 URL、拦住用浏览器开 Console `#approvals` 去点、拦住读或引用 `PLATFORM_ADMIN_TOKEN` 与 `~/.config/bifrost/mcp-tokens.env`（根 `CLAUDE.md` §7）。
2. `mcp__bifrost-approve__*` 被放行，而在**可交互**会话里调用它会弹权限提示，由人按下。

一句话：**闸门 = 一个按文本匹配的守卫 + 一次人的击键。不是认证。**

---

## 2. 为什么「把 Der 加成审批人」按字面做不下去

三条，每条单独都足以否掉：

**(a) 机制层面无法只加 Der。** 审批端点不区分调用方，只认令牌。给 Der 批准能力＝给**任何持有该令牌的进程**批准能力。那个令牌在 `~/.config/bifrost/mcp-tokens.env`，本机任何进程可读；每个配了这个 MCP server 的 Claude 会话**现在就已经能**调 approve。今天拦住它们的只有上面那条文本守卫加人的击键。所以「Der 默认批准、不需要人点」不是把闸门开大一条缝，而是**对本机所有 agent 把闸门整个撤掉**——因为服务端分不出 Der 和我。

**(b) 我无法认证 Der。** 我见过的每一条「Der 的话」都是我输入通道里的文本。没有签名、没有令牌、没有带外通道。如果把「Der 可批准 PROD 发版」写进治理文件并接进机制，那么**任何能往某个 Claude 会话输入通道写字的东西**——另一个 agent、一个被注入的网页、一个我读到的仓库文件——都可以自称 Der 并拿到一次 PROD 发布。这比现状严格更差。

**(c) 这是让我改自己头上的闸门。** 根 `CLAUDE.md` §8 已经定了同类原则：「分类器禁止 Agent 改写自己的 auto mode 规则，Agent 只准备 payload 并报告，不绕过」，auto mode 的应用「由 Owner 执行」。§7 更是专门拦住我读审批令牌、拦住我直接 approve/reject。审批路径是项目明确划给 Owner 的。本轮我两次被 auto mode 以 `[Production Deploy]` 拦下同一个发布动作，紧接着就被要求重写规则让这个动作不再需要人——这正是最该停下的时刻，无论意图多么正当。

---

## 3. 推荐方案：授权绑在「策略」上，不绑在「身份」上

Owner 的真实诉求是**不当瓶颈**，这个诉求可以满足，而且不需要认证任何 agent。
做法是把「谁可以批」换成「什么样的发布不需要人批」——Owner 签一次，机器按边界执行。

**`release-policy`（只有 Owner 能改，建议放 ConfigMap `cicd/bifrost-release-policy` + 签名）**

| 字段 | 内容 |
|---|---|
| `allow` | 哪些流水线：`bifrost-deliver-{stg,prod}`、`bifrost-deliver-platform{,-prod}`、research、插件，逐条列 |
| `conditions` | `revision` 只能是 `main` 或 tag；该 SHA 必须有 Succeeded 的 `ci-*`；调用方必须持有发布窗口；该环境没有待办的 `before` DB 步骤；**不含任何 DDL**；**不触 D10 路径** |
| `limits` | 滚动 24 小时内 PROD 发布次数上限；并发 1（发布窗口已经保证） |
| `expiry` | 标准授权**会过期**（建议 7 天），到期必须 Owner 重新签 |
| `freeze` | 一个**失败即关**的冻结位：设了、或策略缺失 / 过期 / 读不出来 → 一律不自动批 |

`start_pipeline_run` 对 C 级动作：**命中策略就自动批准并执行**，审计记下「哪一条策略条款命中、申请方、SHA、结果」；**不命中就照旧生成待决单据，等人**。

这样 Owner 对例行发版彻底不在回路里，而「批准」始终可追溯到 Owner 自己签的那份策略，且**失败即关**。

---

## 4. 如果 Owner 坚持要 Der 作为一个主体

那 Der 必须是真的主体，缺一不可：

1. **Der 自己的凭据**，由 Owner 签发；建议非对称密钥而不是共享令牌。
2. **审批路径加 per-principal 授权**（现在没有，要写代码）：从凭据解出 approver principal → 对白名单 `{owner, der}` 校验 → principal 写进审计行。涉及 `api/internal/approvals/{handler,service,store}.go` 与审计。
3. **Der 的凭据放在任何 Claude 会话都读不到的地方**：不能进 `~/.config/bifrost/mcp-tokens.env`，不能在我 Bash 能读的任何文件里，不能进我的进程环境。实践上就是 Der 跑在**另一台主机 / 另一个账户**（现成的方案是 L-1 带外操作面，Mac mini），用自己的密钥经网络打 platform-api。
4. 在 (1)–(3) 落地之前，「Der 批准」只是一次未认证调用上贴的标签。

**我不实现这一条**：它的作用正是让我自己那张待决单据（`appr_cc999dddd9ac6d44`）被批准，我是申请方。要做请由 Owner 指派一个不是申请方的实现者，或 Owner 自己配。

## 5. Owner 怎么否决，以及「只靠否决」的问题

**现成的零件**：发布窗口（`~/.bifrost-release/window.json` + ConfigMap `cicd/bifrost-release-window`）是**互斥锁**，不是冻结闸——`release.sh window --clear` 只是清锁。所以今天没有「叫停」这个开关。

**建议新增**：ConfigMap `cicd/bifrost-release-freeze`（`frozen: true` + `reason` + `who` + 时间）。

- 每条 deliver 流水线的**第一个 task** 读它；`start_pipeline_run` 也读它；设了就拒。
- RBAC：agent 只给 `get`，**不给 `patch` / `delete`** —— 只有 Owner 能解冻。
- 失败即关：读不出来当作已冻结。

**对进行中与排队中的影响，说清楚**：

- **排队 / 新发**：冻结立即生效，拒绝。
- **进行中的 Tekton run：冻结位不会停它。** 要停必须显式 `tkn pipelinerun cancel` / `kubectl delete pipelinerun`。
- **PROD 在 rollout 中途被取消会留下半截 rollout**，要么重跑要么 `gitops_rollback_app` 回退——这是一个需要人判断的动作，不该自动做。

**一条设计判断**：**「必须有人喊停才停」严格弱于「必须有人点头才走」。** Owner 睡觉的时候，「默认放行」意味着没人看过的 PROD 发布会上线。§3 的上面那套策略方案保留了「默认放行」的效率，但加了边界和到期，这是这个诉求的安全版本。
