# ADR — Ops 维护与 Ops Platform 的目标架构

- **状态**：已采纳（Owner 2026-10-07）。**落地顺序还没定**，由后续计划另写；本文只定「应该是什么样」。
- **适用**：新增、搬动或删除任何维护者（会自动运行、会改东西的程序）、Ops Platform 的功能与界面、Agent 的凭证与审批、备份、网络分区。冲突时以本文为准，并修正冲突的一方。
- **不在本文**：TWS 与两台 Win11 的维护（放在所有优化最后单独处理）；D10 交易冻结不变。

## 1. 定位

业务终极目标不变：Ops 让 Trade 跑得更快更稳，AI 承担大部分工作。变的是实现方式（Owner 2026-10-08 改写本节）：

**AI Agent（Claude Code、Cursor、Codex 等，不绑定一家）是执行者。Ops Platform 是它们共用的仪器、护栏和调度底座。**
它提供三样东西：

- **事实**：探测、版本、血缘、维护者存活；
- **护栏**：动作目录、审批、发布队列、D10；
- **调度**：任务与租约、交互总线、推理网关、额度账本，对开发和业务两个租户通用。

平台不启动 Agent，也不替 Agent 做判断：Agent 主机上的守护进程主动来领任务，规划者席位提出计划，控制器只在 Owner 批准的范围内校验、记账、放行。UI 只给 Owner 用于看状态、审批和追溯。设计见 §12 与 `work/multi-agent/DESIGN-agent-runtime-2026-10-08.md`（v4）。

**Owner 只做 Agent 做不了的三件事**（Owner 2026-10-08）：

1. **定目标**：做什么、什么算好、能承受多少风险。
2. **定规则**：哪些事可以自动做、边界在哪、预算多少——常备授权的边界、发版策略。Agent 不能给自己授权，规则只能从 Owner 这里来。这里的「责任」指的是这一条，不是出了事由 Owner 担着。
3. **处理不可逆的事**：钱与交易（D10）、删数据或备份、密钥、对外发布。可撤回、可自动验证的事，一律自动做、事后可查，出了问题自动回滚，不进入这三类。

Owner 不在环里，而是在环上：不逐步批准，只写规则、看例外、做不可逆的决定。需要 Owner 的事在他不在线时安全地等（默认是「不做」），不卡住其他工作。每一件送到 Owner 面前的事都要标明属于上面哪一类；标不出来的，就是系统的缺陷，要改成自动。

Ops Platform 收成四层，全部只在 PROD 一份：

| 层 | 内容 |
|---|---|
| 事实层 | 带时间与来源的探测信号、维护者清单与存活、各环境运行的版本、工作项与提交血缘 |
| 动作层 | 具名、确定性、有审计的写操作（API / MCP 调用），外加护栏：发布窗口与发布队列、D10、审批 |
| 调度层 | 多 Agent 运行时：mission、任务与租约、交互总线、产物与验收、推理网关、额度账本（§12） |
| 呈现层 | Console：回答 Owner 的 7 个问题（§6） |

保留还是删除平台上的一项功能，按三个问题判断：Agent 经 API / MCP 用它吗？Owner 用它来批、签、看吗？有维护循环依赖它吗？三个都答「否」，就删。删除不再由 Owner 逐项过目（Owner 2026-10-10）：Ops Console 上删什么、留什么是底层细节，由统筹的线程把关，标准只有一条——Console 只让 Owner 看到需要他定目标、定规则、处理不可逆的事的内容；被删的东西列成清单留在仓库里，能从 git 恢复。

## 2. 四条判据

1. **按「什么坏了它还得活着」放置。** 维护集群和数据的在集群里；看守集群的在集群外（Mac mini）；看守 mini 的是集群与两台 mini 互看。
2. **动手权按信任分级，级别决定位置与凭证**（§5）。确定性修复只在 PROD 集群里；Agent 不常驻写凭证、只提议或申请。
3. **每件维护事只有一个修复者**，其他人只看。
4. **每个维护者都登记、有存活信号、坏了能呼到 Owner**（§7）。

## 5. 动作分级与审批

| 级 | 例子 | 谁能直接做 | 批准 |
|---|---|---|---|
| A 只读 | 状态、日志、指标、只读 SQL | 所有 Agent | 不需要 |
| B 可逆、低风险 | 重启无状态服务、IB 重连、补采某日数据、重跑失败 CI、发 STG、克隆数据到 DEV | Agent；autopilot 试运行期后 | 不需要，事后可查 |
| C 生产变更 | 发 PROD、Argo 同步 PROD、STG / DEV DDL | Agent 发起 | Owner 逐次批 |
| D 不可逆或对外 | PROD DDL、删数据、删备份、节点关机 / drain / 重启、UniFi 改动、Secret 变更、对外发消息 | Agent 只能申请 | Owner 逐次批，必要时亲手做 |
| X 禁止 | 下单、daemon 扩容、写 `ib:operator:cmd` | 无人 | 只有 D10 解锁 |

- 写操作都是 PROD 平台上的具名动作，由平台用自己的受限身份执行；目录外的写操作走兜底动作「Owner 批准执行这条命令」，命令全文进审计。
- **凭证**：Agent（Mac Pro、mini、Cursor）只拿只读令牌、申请令牌与只读 kubeconfig；集群管理员身份只在 Owner 手里应急用。分阶段收：先把写操作收进动作目录，最后换只读。
- **审批交互（形式从简，不用 Face ID）**：PROD 平台一张申请单列表（谁申请、动作、参数、理由、回滚、谁在哪批的）。三个入口看同一张表：
  - 聊天：Claude 应用弹出的「允许」点击即批准，**只限 C 级**；签收同样在聊天里点一下。D 级只能在 Console 批（Owner 2026-10-10）：会话入口显示不了命令全文，带外执行器上线后批准就是唯一一道，看不到全文就批等于盲批；
  - 手机：ntfy 推送，点开进 Console 审批页（在外用 UniFi VPN）；
  - Console：「待你批 / 待你签」页。
- 审批规则：批的是什么就只执行什么（参数签进审批）；一次批准执行一次；过期作废。聊天文字「批了」与其他线程转述都不构成审批，以审批记录为准。
- Agent 不得用浏览器工具访问审批页（preflight 拦截）。
- **发版策略（Owner 2026-10-08 选择，实现中：`cursor-tasks/LANE-RP-release-policy.md`）**：C 级的**发版**动作若命中 Owner 签过的发版策略（ConfigMap `cicd/bifrost-release-policy`：允许的流水线、条件——main 或 tag、该 SHA 的 CI 通过、持有发布窗口、无待办 DB 步骤、不含 DDL、不触 D10——与有效期），平台自动批准并执行，审计记下命中的策略条款；不命中照旧等人批。**失败即关**：策略缺失、过期、读不出来或设了冻结位，一律不自动批。D 级永远不自动。策略不设次数上限；到期前 48 / 24 / 2 小时手机推送 + Console 横幅提醒 Owner 重签。依据：`agent-config/work/release-approval/PROPOSAL-2026-10-08.md` §3、§7。
  - **修订（Owner 2026-10-08，多 Agent 线程）**：
    - **发 PROD 全自动**，每次发版都不等 Owner；
    - 有效期从 7 天改为 **90 天**，提醒相应提前到期前 14 天、3 天、1 天；
    - DDL 分两类：**只增不删的**（加表、加列、并发建索引）可以随策略自动执行，**删除或改动的**（删表、删列、改类型、清空）仍是 D 级，逐次找 Owner；
    - 发版后健康检查不过，**自动回滚**到上一版，事后通知 Owner。
- **规则集（Owner 2026-10-08）**：Owner 只管规则，Agent 在规则之下自动运行。
  - 所有可配置的边界合成一份规则集，每条规则都有版本、签名和有效期。包括：常备授权的边界（mission 不用逐个批）、发版策略、租户与路由的硬规则、预算和额度上限、DDL 分类、自动回滚阈值、可见性阈值。
  - **放宽规则**（新增或扩大授权、延长有效期）必须由 Owner 单独确认并签名。
  - **收紧规则**（冻结、缩小范围、降低额度）谁都可以做，立即生效、事后通知。
  - **过期即回到更严的默认值**，不自动续期。到期前提醒 Owner；同一批到期的规则可以一次续签。
  - Agent 可以**提议**修改规则（附证据，比如「这一类审批 98% 原样通过」），但只有 Owner 能签。
  - **D10 不在可配置的规则集里**：解锁仍要 Owner 的书面指令，并把 spine 改为 UNLOCKED。
- **2026-10-10 的三条（Owner）**：
  - PROD 的两条发布流水线在 W-56 的门槛验收之前不进发版策略，PROD 发布仍由 Owner 批；策略先覆盖 research 和插件构建。
  - 增量 DDL 自动执行先关闭（`additive_ddl: false`），W-55 把分类器重做成允许清单并经独立复核后再打开。
  - 观测类清单变更（`monitoring` 里的告警规则、抓取配置、看板；只新建或更新；不含 critical 级告警；CI 通过）随策略按 B 级自动执行。判断只用 plan 的结构化结果。实现归 W-59，签进策略后生效；细则见 `work/multi-agent/RULE-PROPOSAL-observability-apply-2026-10-10.md`。
- **已知的接受风险（Owner 2026-10-07 选择）**：聊天里批准靠 MCP 工具 `bifrost-approve` + Claude 的「允许」弹窗，工具需要的 admin 令牌在本机进程可读。同一台机器上的 Agent 理论上能读到它、绕过弹窗直接调审批接口；目前只靠 preflight 的文本拦截挡一挡。Owner 的取舍是先简单快，「今后感觉不行，再收权」——收权的做法是把 admin 令牌只留在手机与 Console 浏览器里，聊天只展示申请与链接。
- **已知的接受风险（Owner 2026-10-09，LANE-W33D）**：同一个 macOS 用户下，Owner 目录 `~/.bifrost-owner/` 只靠 preflight 的文本拦截。闸门防的是善意误读，不是有决心的绕过。
- **已知的接受风险（Owner 2026-10-09，LANE-W33D）**：DB 属主密码 `POSTGRES_PASSWORD` / `PGPASSWORD` 四个库共用，仍留在 Agent 能读的 infra `.env`。分开是 TD-85，不在这一步。

## 6. Console：8 个问题（Owner 2026-10-10 修订；原为 7 个）

Ops Platform 的重心已经从后台 CI/CD 转到监控、审批和 Owner 的三件事（§1）。所以 Console 首先要回答的是「现在要我做什么」。

| 问题 | 动作 |
|---|---|
| ④ **需要你**：现在要我做什么？（待你定、待你批、待你签；**首页，导航排第一**） | 回答决策卡、批准、驳回、签收、打回 |
| ① 现在一切正常吗？（一句结论 + 红项） | 只看 |
| ② 今天的数据到齐了吗？（行情、Flex、Research、备份） | 补采、Doctor 修复 |
| ③ 和 IB 的连接正常吗？ | 重连 |
| ⑤ 发布到哪了？（各环境版本、窗口与队列、策略状态、在途、失败、血缘） | 至多一个回滚应急 |
| ⑥ 集群与机器（节点、网络、mini、NAS、4090、TWS 主机、Agent 主机、待重启节点） | 只留应急与经审批的动作 |
| ⑦ 项目进度（mission、W-n、已定的事、基准结果；分支血缘是下钻；§8、§12） | 签收 |
| ⑧ **团队与规则**：谁在替我干活、在什么规则之下？（岗位与候选、参谋长入口、规则集及到期、额度与可替换性；§5、§12） | 签规则、看提议 |

- 编号是页面的名字，不代表顺序。其他文档里引用的 ④、⑤、⑦ 含义不变。
- **版式原则：每一页分三段，默认只展开前两段。**
  1. **需要你**：要 Owner 现在决定、批准、签收的事，标明等了多久。没有的时候明确写「现在没有需要你做的事」。
  2. **进行中**：系统自己在做的事。
  3. **历史**：已经结束的。默认收起，或者放进「记录」；能查，但不占首屏，也不计入任何计数。
- **计数只算「需要你」**：外壳上的数字和手机推送的条数，都只统计第 1 段。等待超过 7 天变黄，超过 14 天变红（§12.2）。
- **页头的结论和 ① 同源**：不允许页头写「一切正常」，而页面里是红的。
- **「记录」**是一个入口，不是一个问题。它收纳历史：审计、已关闭的单子、巡检运行、已完成的发布。
- 健康类页面只看 PROD；STG / DEV 只在 ⑤ 里作为一列出现。
- 退场的：
  - Console 内的 Agent 派发：runner 派发、Operate Queue、决策简报、Hermes 工作台、各页的「AI Fix」和「Copy for Agent」；
  - Vision 关卡与 Tier-B 签字；
  - 发布驾驶舱，改为 ⑤ 的只读视图；
  - Guides 静态页，回到仓库文档。
  
  删除由统筹的线程按 §1 的标准把关，清单留档，不再等 Owner 过目（Owner 2026-10-10）。
- CI/CD 的流水线与 API / MCP 能力保留；发版只走 Claude / MCP / `release.sh`。
- 现状评估与落地安排见 `work/multi-agent/UI-ASSESSMENT-2026-10-10.md` 和 `STEP0-PLAN` 的第 0.2 节。

## 7. 维护者清单与存活

- `agent-config/MAINTAINERS.yaml`：每个维护者一行——维护什么、在哪跑、何时跑、最高动作级（A–D）、靠哪条告警发现它坏了。
- 每晚在集群里对账：清单 vs 实际（CronJob、Dagster schedule、platform 后台循环、mini 的 launchd），多出或缺少都告警。**新增维护者必须先进清单。**
- 存活信号用现有 Prometheus / Alertmanager；清单每行必须对应一条存在的告警；platform 后台循环导出「上次成功时间」。
- 告警只分两档：**呼 Owner**（critical → ntfy）与**记账**（warning → PROD Console ①；Owner 2026-10-10 由 ④ 改为 ①，④ 只放待定、待批、待签）。STG 不在告警链路里。
- Tekton 运行记录的保留（Owner 2026-10-10，起点值，运行中不合适再调）：成功的留 24 小时，失败的留 7 天，每条流水线至少留最近 5 次；发布类的运行必须先有发布记录才删。运行记录是执行现场，不是档案：发布证据在平台写的发布记录里，步骤日志在 Loki。清理由平台写发布记录的同一个循环做，登记为维护项。首次清理的清单由 Owner 批一次，之后按规则自动（W-60，TD-299）。
- 节点补丁：Console ⑥ 显示待重启节点；重启是 D 级「滚动重启」，Owner 周末批，一次一台（不用 kured）。

## 8. 工作项与进度

- 进度是算出来的，不人工维护。
- 一个工作项登记（infra `agent-config/`，沿用 TECH_DEBT 的五种状态、验收命令、待你签收），覆盖全部工作线：债、计划、Cursor LANE。
- 计划、评审、申请、LANE 任务与报告都放进 infra `agent-config/`（版本控制），不放在工作区根目录。
- 每个提交带 `Work: <编号>` 尾注（git hook 补，防线保证不漏）；线程标题带编号。
- 进度视图按工作项拼出：状态与验收 → 线程 → 提交 → 到达的环境 → 是否待签；顶部为待你签收、在途、本周上线、卡住。PROD Console ⑦ 为主，claude.ai 页面为导出版。

副本原则：线上（Linux 节点盘）+ NAS；不用云。NAS hot / cold 同在一台 NAS，防误删、不防 NAS 本身损坏（Owner 接受，以后可能再加一台 NAS）。

| 级 | 包含 | 能丢多少 | 恢复用时 | 副本与留存 |
|---|---|---|---|---|

### 12.1 问题与目标

- **问题**：额度分在几家厂商手里，Owner 不想被一家绑死。可是 IDE 自带的协调手段跨不了厂商：会话之间的消息、子 Agent、规则、记忆、钩子都是各家各管各的。于是 Owner 成了消息总线和瓶颈。2026-10-08 一天之内就出了这些事：
  - 一张批准单因为窗口冲突作废（TD-267）；
  - 同一个 bug 被修了两遍（TD-261）；
  - 发出去的消息丢了；
  - Owner 只能用 curl 批准；
  - 两个协调者撞了编号；
  - 工作区根目录堆满了没纳入 git 的记录。
- **目标**：建一个厂商中立的协作运行时，同时服务**开发**和**业务**两个租户；Owner 只做 §1 列出的三件事。

### 12.2 原则

1. **岗位稳定，人员可换。** 我们定义岗位、规则和账本，Agent 来应聘。Agent 会不断有新的出现，岗位和规则留在我们手里。
2. **靠共享状态协调，不靠互相发消息。** 事实只存一处，在 PROD platform。
3. **权威在代码，不在 LLM。** 任务状态只有控制器能改，作者不能验收自己的产出。Agent 之间的消息只是数据，不能用来授权。
4. **平台不启动 Agent**（§1）。Agent 主机上的守护进程主动来领任务。
5. **可见性。** 凡是需要 Owner 决定、批准、签收的事，以及正在积压的事，都必须出现在 PROD Console 上，并标出已经等了多久：超过 7 天变黄，超过 14 天变红。
6. **做粘合剂，不重复造轮子**（Owner 2026-10-08）。巨头的产品和主流开源项目迭代得比我们快，自己造的通用能力很快就会落后。所以优先把它们聚合起来，自己只造三类东西：
   - 没有人提供的：签名规则集、岗位与考试、参谋长、跨订阅的额度账本；
   - 决定我们自主权的：状态和规则；
   - 把别人的东西粘在一起的那一层薄胶水。
   每个自建的部件，随规则集每 90 天续签时复核一次：如果市面上已经有合格的现成方案，就换掉自己的。
7. **能力用他们的，状态放我们的**（Owner 2026-10-08）。模型、推理，以及单个任务内部的工具（子 Agent、团队模式、钩子），都可以随意用厂商的。跨任务、跨 Agent 的状态和流程必须留在我们自己的系统里：任务、决定、规则、岗位、验收记录、代码历史、审批、记忆。真正造成锁定的，是状态住进了厂商的产品里。
8. **可替换性要看得见。** Console ⑧「团队与规则」显示每个岗位有几位合格的候选（只有一家能胜任的岗位标红），以及每家上一次完整跑完一个 mission 的时间。每 90 天做一次可替换性演练，让非主力的厂商跑一遍基准集和一个真实 mission。
9. **采用外部组件的门槛**：优先选开放标准（有基金会治理的，优于单一厂商）；看许可证（source-available、AGPL 要单独评估）；看维护是否健康；看会不会往外发遥测；装之前先读源码；最后，同样要用平台功能那「三个问题」判断留不留（§1）。
10. **不做**：平台里的「AI 修复」按钮；汇总各主机的对话记录；Agent 之间的聊天总线；允许 Agent 自己建频道。

| 部件 | 决定 |
|---|---|

### 12.4 规则集（§5）

Owner 只管规则，Agent 在规则之下自动运行。规则包括：

- 常备授权的边界；
- 发版策略；
- 租户与路由的硬规则；
- 预算；
- DDL 分类；
- 回滚阈值与可见性阈值；
- **岗位定义和候选名单**。

**放宽要 Owner 签名，收紧谁都可以做；过期就回到更严的默认值。** D10 不在规则集里。

### 12.5 岗位与参谋长

- **岗位说明书**：每个岗位都写清楚职责、权限、能力要求、资格考试、在岗考核和适配器清单。能力要求分两类：
  - 能力类，可以用工具补上，比如 MCP 或命令行工具、常驻在线、对话入口、记忆；
  - 边界类，不能豁免：要有自己的身份，要有宿主强制的护栏，不冒充他人，不越权。Agent 自己做不到的，由环境来保证；环境也保证不了的，就不能上岗。
- **候选**：通过资格考试才能进候选名单；在岗考核不达标就自动降级。
- **开发租户的岗位**：参谋长、规划、实现、验收、策展、人工运输（Design）。
- **参谋长**：一个全局席位，是 Owner 与整个 Agent 团队之间唯一的对接人。
  - 对 Owner：写简报、整理决策卡、随时回答问题；把目标写成 mission，把规则意图写成修改提议。
  - 对 Agent：任命或兼任各 mission 的规划，处理跨 mission 的事。
  - 不能批准，不能改规则，不能执行副作用，**不能冒充 Owner**。
  - 24 小时在线，跑在 mini 上。
  - 席位上的人可以轮换；对话入口固定，记忆存在运行时里，不靠某个模型的上下文。
- **运行时建成之前的安排（Owner 2026-10-10）**：参谋长席位由 Claude 的 W-31 决策线程担任；它用命令行直接驱动 Cursor 做实现并验收，用命令行请 Codex 做独立复核。线程之间不经 Owner 传话：动作写进仓库里的计划文件，发布靠发布窗口互斥。Cursor 应用里的参谋长线程收尾后停用。验收独立性按模型提供方算：Claude 验收时，Cursor 的实现任务指定非 Claude 模型。
- **Grok Bot**：它作为「总调度」的旧角色退场（2026-10-08 调查：Grok Bot 跑在云上，只支持远程 MCP，没查到钩子）。保留它的模型（cursor-agent 里的 Grok 4.7）。以后它可以配上适配器，按岗位重新应聘。

### 12.6 租户与算力

| 租户 | 算力 | 硬规则 |
|---|---|---|
| 开发 | 订阅制 Agent，按各家剩余额度分流；本地 GPU 只做杂活 | 不用 API；Agent 环境里没有业务键 |
| 业务 | Owner 发起的任务优先用订阅；**低频定时任务可以用订阅**；高扇出、重复性的批量任务先用本地 GPU，API 兜底 | **高扇出的批量任务不走订阅额度**；低频的界限写在规则集里（Owner 2026-10-08 读完条款后定：可以用订阅，前提是只调用官方的命令行程序、符合「普通个人使用」） |

- 业务 API 键**只放在推理网关里**。网关负责计量、GPU 信号量，并拒绝开发租户的调用。
- 本地 4090 只做批量、简单、可校验的杂活，账户内容也优先放在本地处理。

### 12.7 mission 与发布

- **mission**：落在常备授权边界内的自动成立，只通知 Owner；超出边界的要 Owner 签名。每个 mission 都有截止日期（默认 7 天）。中途想扩大范围，要发修订单。常用的做成模板，批准时只看差异。
- **发布队列**：
  - 窗口的权威迁进平台，并改成队列，并发为 1；
  - 由主机执行的发布领租约，由平台执行的发布进执行器；
  - 每次发版钉住提交号；
  - 暂时性的拒绝不消耗批准（TD-267）；
  - 排队超过 24 小时自动过期。
- **发 PROD 全自动**（§5 修订）：策略有效 90 天；只增不删的 DDL 可以自动执行；健康检查不过就自动回滚，事后通知 Owner。不可逆的动作仍然逐次找 Owner，Owner 不在时安全地等待。
