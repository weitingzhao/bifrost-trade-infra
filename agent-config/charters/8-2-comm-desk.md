标记：【量】= 读 `bifrost-platform` main 8f40e001 或实测得到，带文件名或行数；【推】= 推断。

## 4. 权限
- **自己定自己做**：
  - 第 1 项里代码的改动和合入（走 `ready/<名字>`）。
  - 不碰信任锚的 platform 发布：`check_release_policy` 试判，覆盖了就直接发。
  - 通讯录格式。
  - 替别的线做非作者复核（`record_release_review`）。
- **机器拦着的**：
  - auto mode 分类器：等信命令靠那条放行规则才能跑；推 infra 治理文件时被拦过一次，后来是 Owner 推的。
  - `preflight.js`：直推 main、整树暂存等。
  - 平台回 422「not a registered actor」：没登记的线程收不到信。
  - 碰信任锚的发布，要有非作者的复核记录。
- **硬边界不碰**：
  - 交易和钱（D10），以及 Trade 五个仓库。
  - 令牌、口令、Secret 数据、Owner 的凭证目录。
  - 用 kubectl 写集群。
  - 改规则本身和 auto mode。
  - 不放松 `seat:` 身份防线：席位地址走文件通讯录，不走平台。

## 5. 目标和读数
目标：任意两个席位之间，**发出的信不丢、闲着的能被叫醒、每次收信花的 token 少**。排窗口的人不用一直盯着，轮到了会被叫醒。

- **收信大小**【量】：只给摘要时，一封信从 2881 字符降到 646（11-14 实测）。没有持续的读数。
- **叫醒延迟**【量】：桌面会话从发信到被叫醒约 7 秒，只量过一次。
- **能被叫醒的表**【量，部分】：
  - `directory.md` 的「登记」一栏：12 行里 6 个 ✓、6 个 ?（? 多数是占位席位）。
  - 台账 Artifact 里另有一张能不能叫醒的表，手工维护。
下面三个读数是我负责的，进每日读数（主统筹 11-15 裁）。现在都还没有数，先写清怎么量：
- **丢信数**：统计发出超过 30 分钟还没被 ack 的信，按收件人分；平台出读数，放到 Ops 上。
- **your_turn 延迟**：从上一位放窗口到下一位收到 `window.your_turn` 的时间；通知里带上放窗口的时间，由平台算差值。改成只有 workers 推进之后，还没人真排过。
- **叫醒成功率**：等信命令每次退出都记一条（收到 / 到点 / 出错），平台按席位统计。各席位能不能被叫醒的表也从这里算出来，不再手抄。
- 每日读数做出来之前，我手工量一次填进席位台账，不编数。

## 6. 现状和缺口
- **现状**【量】：下面这些 10b70655 起都在 PROD：
  - 信封和只给摘要。
  - MCP 启动时自动登记。
  - 等信命令，遇平台断线会重试。
  - 窗口排队和通知：在 PROD 端到端走通过一次。
- **缺口**：
  - 等信命令不重试 429 和 505–599【量，领域 5 复核时提出】。
  - 放窗口时，服务端对 `who` 的权限判断还没人复核【量】。
  - 平台自己发起的发布还不排队。这是第 2 期，要和领域 5 的退避（≤60 秒）一起做【量】。
  - 全平台只有一个窗口，不分环境、不分应用（留到 v2）【量】。
  - 没有系统事实推送（进了 main、发完了、卡关了），各席位还得自己去查【推】。
  - Codex 没有常驻地址，也没有等信守护，叫不醒【量】。算力线在接。
  - 旧会话的 MCP 看不到新工具，要靠 `call-tool.mjs` 或 Owner 点 Reconnect；共享检出要人工快进【量】。
  - 通讯录是手抄的，「登记」一栏会过时【推】。应改成由平台按线程最近活动算出来。
  - Ops 上看不到席位之间的往来（Owner 说这件「重要不紧急」）【量】。
