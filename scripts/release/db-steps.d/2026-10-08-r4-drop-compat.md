# Naming R4: drop R3's one-version objects and the frozen split table (core 0.47.0 / api 0.9.0)

Owner-approved 2026-10-03 (`REQUEST-naming-program-decision-pack-2026-10-03.md` §4 "R4 收口" and §5.5; D4-A, D7-A).
**Release gate first** (D4-A): R1–R3 on PROD for one release cycle (R3 live 2026-10-04 04:31 UTC) **and** zero hits for
the old names for ≥ 4 days — `python3 scripts/release/naming_r4_gate.py` must exit 0 (earliest 2026-10-08 04:31 UTC).
One transaction per env, generated by core 0.47.0's `scripts/db/drop_trade_compat.py --env <env> [--commit]`
(`bifrost_core.persistence.postgres.drop_trade_compat`), committed here per env:

| # | statement | object | owner (all envs, read 2026-10-04) | reversible? | rollback |
|---|-----------|--------|-----------------------------------|-------------|----------|
| 0 | guards (RAISE, nothing kept): database; `trade_execution` + FDW tables exist; the two public objects are views; the 9 objects below owned by `bifrost`; no other view depends on them; frozen table = 2 rows, each in `trade_execution` | — | — | — | — |
| 1 | `DROP VIEW IF EXISTS public.strategy_instance_execution` | R3 compatibility view | bifrost | yes | reverse SQL recreates it (R3 definition) |
| 2 | `DROP VIEW IF EXISTS public.strategy_instance` | R3 compatibility view | bifrost | yes | reverse SQL (R3 definition) |
| 3 | `DROP VIEW IF EXISTS brokerage.instance_allocations` | R3 env compatibility view | bifrost | yes | reverse SQL (core 0.45.0 definition, over `trade_fill_splits`) |
| 4 | `DROP VIEW IF EXISTS brokerage.{executions_tws, trade_fill_splits, executions_fly, executions_final, executions} CASCADE` + `CREATE OR REPLACE VIEW` the five, exactly as core 0.47.0's `_create_brokerage_views(env=True)` | env views: same rows, column `strategy_instance_id` (= `trade_id`) removed | bifrost (recreated by bifrost; `trade_app_<env>` SELECT comes from bifrost's default privileges, TD-85) | yes | not needed: no pod on core ≥ 0.45.0 reads the column (rehearsed: core 0.45.0 14/14 calls OK on the rebuilt views). R3's `--reverse`-era definitions are in `sql/2026-10-04-r3-rename-trade-entity-<env>.sql` if ever wanted |
| 5 | `DROP TABLE IF EXISTS public.account_execution_instance_allocation` (+ its sequence, 3 indexes, UNIQUE, FK → `trade`) | frozen pre-TD-09 splits, 2 rows per env, each also in `trade_execution` | bifrost | **only from the CSV** | reverse SQL recreates it empty (core 0.46.x DDL), then the CSV restore (below) |
| 6 | report: trade / trade_execution / splits / attributed fills / split rows before = after, the 4 objects gone, no rebuilt view with `strategy_instance_id` — RAISE otherwise | — | — | — | — |

**Why the step rebuilds the env views**: db-init never does in dev / stg / prod. Its FDW step stops at
`must be owner of foreign server golden_source_server` and the Job only logs `FDW setup skipped` (Loki: every db-init
of 2026-10-01..03 in all three envs), so `setup_fdw_foreign_tables` — the one caller of `_create_brokerage_views` —
never reaches them. R3's step rebuilt them itself; this one does the same. (That db-init skip is older than R4 and is
reported separately.)

**Why after the env's release (`when: after`)**: no running pod needs any of these objects since core 0.45.0 (every
SQL statement names `trade` / `trade_execution` / `trade_fill_splits`), so the views could go any time; but core
≤ 0.46.x db-init runs `CREATE TABLE IF NOT EXISTS account_execution_instance_allocation` on every release, so dropped
before 0.47.0 the table would come back empty. Rehearsed: core 0.45.0 db-init after the drop recreates it.
**Run it only once the env's `/health` says `core_version` 0.47.0** (the `precheck` line below prints it).

**Window**: none. The transaction takes ACCESS EXCLUSIVE on the 9 objects for well under a second (`lock_timeout` 5s;
rerun if it times out). Reads of `brokerage.executions*` wait that long at most. Old and new pods work on both sides
of it (rehearsed).

**Selective data clone** (platform, reads `/api/ops/data-probe` `clone_groups`): the `trades` group is the FK closure of
`trade`, so it lists `account_execution_instance_allocation` until this step and not after. Run the three envs in one
sitting, or do not clone `trades` across envs while they differ.

## Rehearsal (2026-10-04, throwaway Docker Postgres 17 — PROD runs 17.9)

PROD's `pg_dump --schema-only` (read-only; user mappings stripped before it reached disk) + Golden Source `raw_broker`
schema, invented rows (2 trades, a whole fill, a fill split 1 + 2, the 2 frozen rows, a review), smoke as
`trade_app_prod` with core 0.45.0 and 0.47.0 (14 calls each: trades, executions, splits, performance, attribution,
win rate, data probe, plans, reviews, review patch, three attribution writes):

- today: core 0.45.0 14/14; the dry run before 0.47.0 changes nothing (schema identical).
- core 0.47.0 db-init: `FDW setup skipped` as in the envs; the precheck still shows 5 views with the column; 0.45.0 and
  0.47.0 both 14/14.
- dry run: ROLLBACK, schema identical; CSV export 2 rows.
- commit: the 4 objects gone, `strategy_instance_id` left only on the 3 foreign tables (Golden Source's frozen column),
  counts equal; 0.47.0 and 0.45.0 both 14/14; 0.47.0 db-init afterwards changes nothing; the commit a second time
  passes (idempotent).
- rollback drill: core 0.45.0 db-init on the dropped database recreates the frozen table empty (why `when: after`);
  the reverse + CSV restore brings back the same 2 rows (byte-identical export) and the 4 objects as before; 0.45.0 14/14.

Core's own tests (`tests/test_drop_trade_compat*.py`, Postgres 16 and 17) cover the guards (a third or unmatched
frozen row, a table where a view should be, a dependent view) and the rebuild of R3-shaped views.

## The sitting, per env (STG → DEV → PROD, each after that env's release of core 0.47.0 / api 0.9.0)

1. `precheck` (read-only): core version over HTTP, then the SQL.
2. `export`: the frozen table to `~/bifrost-backups/trade-db/`, with its SHA256 appended to `SHA256SUMS` there. Read-only
   (`PGOPTIONS` sets the session read-only; COPY TO STDOUT writes only to the local file). Check the file has 3 lines
   (header + 2).
3. `dry-run` → `commit` → `verify`.
4. `scripts/release/release.sh db-done <env> 2026-10-08-r4-drop-compat`, and add the env to `done:` above in the next
   infra commit.

Commands run from the `bifrost-trade-infra` checkout with `KUBECONFIG=~/.kube/bifrost-k3s.yaml`. Regenerate and compare
from the core 0.47.0 checkout: `python scripts/db/drop_trade_compat.py --env prod --commit | diff - ../bifrost-trade-infra/scripts/release/db-steps.d/sql/2026-10-08-r4-drop-compat-prod.sql`
(no output = identical; no `--commit` for the dry runs, `--reverse --commit` for the rollbacks).
