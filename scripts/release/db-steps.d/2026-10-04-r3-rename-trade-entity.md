# Naming R3: rename the Trade entity's tables (core 0.45.0 / api 0.7.3)

Owner-approved 2026-10-03 (`REQUEST-naming-program-decision-pack-2026-10-03.md`, D1-A / D2-A / D7-A; pack §5.1–5.4).
One transaction per env, generated by core 0.45.0's `scripts/db/rename_trade_entity.py --env <env> [--commit]`
(`bifrost_core.persistence.postgres.rename_trade_entity`), committed here as files because the SQL differs per env:

- `strategy_instance` → `trade` (`strategy_instance_id` → `trade_id`), `strategy_instance_execution` → `trade_execution`
  (`trade_execution_id`, `trade_id`, `allocated_quantity` → `split_quantity`), `strategy_plan.strategy_instance_id` →
  `trade_id`, `trade_review.strategy_instance_id` → `trade_id`, `tags_added` / `tags_dropped` → `tags_added_json` /
  `tags_dropped_json`, with the 2 sequences, 9 constraints and 5 indexes (27 `ALTER … RENAME`; no data is rewritten).
- The five env views are dropped and rebuilt exactly as core 0.45.0 builds them: `brokerage.executions` / `_final` /
  `_fly` / `_tws` output `trade_id` (the Trade), `ib_trade_id` / `ib_related_trade_id` (IB) and, one version,
  `strategy_instance_id` (= `trade_id`); new `brokerage.trade_fill_splits`.
- One-version compatibility views (R4 drops them): `public.strategy_instance` (no `notes`: dropped 10-03),
  `public.strategy_instance_execution`, `brokerage.instance_allocations`.
- Guards (RAISE, nothing kept): wrong database; brokerage views not owned by whom the file expects (DEV `postgres`,
  STG / PROD `bifrost`); `public.trade` already there; `strategy_instance` not a table. `lock_timeout` 5s (rerun if it
  times out). The last step compares each count before / after and RAISEs if one changed.
- **DEV is different**: its brokerage views belong to `postgres` (TD-09). The DEV files `RESET ROLE` for the view drops
  and the rebuild, then `GRANT SELECT … TO bifrost` and switch back. STG / PROD run everything as `bifrost`.
- Golden Source is not touched. `account_execution_instance_allocation` (frozen) keeps its column; its FK follows
  `trade`. It goes in R4 (D7-A).

Files (`sql/`): `2026-10-04-r3-precheck.sql` (read-only, all envs), `…-<env>-dryrun.sql` (the whole transaction,
ending ROLLBACK: it takes the locks for well under a second and keeps nothing), `…-<env>.sql` (COMMIT),
`2026-10-04-r3-verify.sql` (read-only, all envs), `…-<env>-rollback.sql` (the reverse, COMMIT). Regenerate and compare
from a core 0.45.0 checkout (bifrost-trade-core): `python scripts/db/rename_trade_entity.py --env prod --commit | diff - ../bifrost-trade-infra/scripts/release/db-steps.d/sql/2026-10-04-r3-rename-trade-entity-prod.sql`
(no output = identical; `--reverse --commit` for the rollback files, no `--commit` for the dry runs).

## Order, and what release.sh does

`release.sh stg` and `release.sh prod` **stop before the deliver run** while this step is pending for that env (it is
`when: before`): core 0.45.0's db-init refuses a database that is not renamed (`_ensure_tables` raises before its first
change), so the rename must be committed first. `release.sh dev` stops the same way — DEV has no deliver of its own;
it copies STG's images (`make dev-sync-backend-images RESTART=1`), so **DEV is migrated, then `release.sh dev`**, after
the STG release has built 0.45.0. Suggested sitting:

1. All three: precheck, then dry run (harmless; checks the guards and the counts on real data).
2. STG: commit → verify → `scripts/release/release.sh db-done stg 2026-10-04-r3-rename-trade-entity` → `release.sh stg`.
3. DEV: commit → verify → `release.sh db-done dev 2026-10-04-r3-rename-trade-entity` → `release.sh dev`.
4. PROD: commit → verify → `release.sh db-done prod 2026-10-04-r3-rename-trade-entity` → `release.sh prod --from-stg <run>`.

After each env, the HTTP checks of pack §5.3: `/api/strategy/trades` and `/api/strategy/strategies/instances` give the same
count; three trades' `/api/trading/executions?trade_id=` are the fills they had; `/api/trading/performance` unchanged.

## Window (from COMMIT until the env's new pods are Ready)

It lasts from the commit until the deliver run has rolled out core 0.45.0 / api 0.7.3: the time to record db-done and
start the release, plus the run (recent runs: STG 3.5–11 min, PROD 5–7 min; DEV until `release.sh dev` restarts it).
Old pods (core 0.44.0 / api 0.7.2) work through the compatibility objects — rehearsed on DEV's schema, Postgres 16 and 17,
both view owners (22 of 30 smoke calls). **What fails in the window (500 / 503), exactly:**

| Route (api 0.7.2, gateway `/api/strategy`) | core call | error |
|---|---|---|
| `GET /strategies/plans`, `GET /strategies/plans/{id}` | `list_plans`, `get_plan` | `column p.strategy_instance_id does not exist` |
| `PATCH /strategies/plans/{id}` | `patch_plan` (reads the row back) | same; the change itself is rolled back |
| `POST /strategies/plans/{id}/link-fill` | `link_fill` | `column "strategy_instance_id" of relation "strategy_plan" does not exist` |
| `GET /trade-reviews`, `GET /strategies/reviews` | `list_reviews` | `column "strategy_instance_id" does not exist` |
| `PATCH /trade-reviews/{id}`, `PATCH /strategies/reviews/{id}` | `patch_review` | same (WriteFailed) |
| `DELETE /trades/{id}`, `DELETE /strategies/instances/{id}` | `delete_instance_strict` (counts plans / reviews) | same (WriteFailed); nothing is deleted |

Everything else works in the window: trades list / get / create / patch, win rate, every executions and attribution write
(whole fill — the `INSERT … ON CONFLICT (account_id, exec_id) WHERE allocated_quantity IS NULL` upsert works through the
compatibility view, insert and conflict arms — splits, clear), performance, position attribution, plans create / intend /
cancel / delete. One more: an old pod's `GET /api/ops/data-probe` answers `clone_groups[trades] = ["strategy_instance"]`
(the view): do not start a selective data clone in the window. Rows on DEV / STG / PROD: 0 reviews, 0 linked plans.

## Rollback

Run the reverse **before** putting core 0.44.0 back: core 0.44.0's db-init fails on the renamed database
(`cannot create index on relation "strategy_instance"`; rehearsed: it changes nothing, but the Job fails), and core
0.45.0's db-init refuses the reversed one, so the images go back in the same sitting. The reverse drops the R3 views and
the compatibility views, undoes the 27 renames backwards and rebuilds core 0.44.0's env views (embedded); it also checks
and compares the counts. Rehearsed: the schema after the reverse is identical (`pg_dump --schema-only`) to before the
rename, and core 0.44.0's db-init and smoke pass on it.

Commands run from the `bifrost-trade-infra` checkout with `KUBECONFIG=~/.kube/bifrost-k3s.yaml`.
